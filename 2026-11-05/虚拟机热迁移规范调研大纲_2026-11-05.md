## 0. 前置说明

### 0.1 本调研不存在的那个"依据"

本项目**没有、也不假设存在**一部名为《虚拟机热迁移安全规范》的标准。标准体系按系统/服务/密码应用的粒度制定，热迁移在其中通常是**某一层的若干控制项**，不单独成篇。

因此调研方法是**自上而下抽取**，而非"查找热迁移标准"：

```
上位标准（等保 / 密评 / 云服务安全要求 / 密码模块要求）
      │  抽取与"虚拟化资源迁移""数据迁移""可用性""审计"相关的控制项
      ▼
要求条目清单（RQ-1xx … RQ-6xx）
      │  逐条映射到本系统
      ▼
差距分析（符合 / 部分符合 / 不符合 / 不适用 + 证据）
      │
      ▼
整改建议 → 落到界面检查项 / 接口约束 / 实验验证
```

**铁律**：任何标注为【标准条款】的条目，必须写出标准编号 + 条款号，且编号已在标准平台核实为**现行有效**。核实不到就降级为【官方文档】或标注"待核实"，**不得凭记忆填写编号**——错误引用比不引用伤害更大。

### 0.2 六分法的前提

六部分划分已确认可用（能自然容纳导师给出的四个问题），但六类**不是同一平面上的概念**：

- 基本技术 / 安全 / 性能 —— 属性切面
- 操作流程 / 异常处理 —— 生命周期切面
- 企业级产品功能 —— 完备性切面

因此需要一条分类规则，否则同一条要求会同时落进两三个格子。

### 0.3 分类规则（一条要求只归一个主类）

| 这条要求约束的是…… | 主类 | 其余类中的写法 |
|---|---|---|
| 协议 / 进程的行为与状态 | §3.1 基本技术规范 | 只写一行"交叉引用 RQ-1xx" |
| 人或流程的动作顺序 | §3.2 操作流程规范 | 同上 |
| 通道、数据、身份、凭据 | §3.3 安全规范 | 同上 |
| 一个可测的数值指标 | §3.4 性能基线 | 同上 |
| 失败路径与恢复语义 | §3.5 异常处理规范 | 同上 |
| 功能的完备程度 | §3.6 产品功能对标 | 同上 |

### 0.4 依据强度四档（每一条目必须标注）

| 标注 | 含义 | 可写入报告的前提 |
|---|---|---|
| 【标准】 | 强制性/推荐性标准的具体条款 | 编号 + 条款号齐全，且已核实现行有效 |
| 【文档】 | QEMU / libvirt / 内核官方文档或源码 | 能给出文档页或源码文件:行号 |
| 【实测】 | 本项目实验环境测得的数据 | 附实验条件与采集命令 |
| 【对标】 | 同类产品（PVE / OpenStack / vMotion / FusionCompute）的实现约定 | 附产品版本与文档出处 |

**这条标注是本文档最重要的设计**：性能基线和对标结论本质不是"规范"，若不加区分地写进报告，评审只需一句"这条出自哪份标准"就会问穿。诚实标注反而让整份材料可信。

## 1. 条目模板

每一条要求条目固定六列，缺列即视为未完成：

| 字段 | 填写要求 |
|---|---|
| **条目号** | RQ-章号-序号，如 RQ-1-03 |
| **要求** | 一句话，可判定（能回答"是/否满足"） |
| **依据** | 依据强度标注 + 具体出处（标准编号+条款 / 文档URL或源码行 / 实验编号 / 产品名+版本） |
| **对本系统的约束** | 落到哪个模块、哪个界面对话框、哪个接口参数；不落地的条目说明它是"不适用"或"远期" |
| **判定方式** | 怎么证明满足：代码核查 / 实测 / 抓包 / 界面截图 / 配置比对 |
| **现状** | 符合 / 部分符合 / 不符合 / 不适用 / 未测 |

条目清单完成后，"现状"列的统计分布就是差距分析章的结论，不需要另写一段。
