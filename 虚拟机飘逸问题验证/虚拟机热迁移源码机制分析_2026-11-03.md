# 虚拟机热迁移源码机制分析

> 本文档基于对 libvirt 与 QEMU master 分支源码的系统阅读整理，完整覆盖一次热迁移从 virsh 命令入口到源端收尾的实现主线，并延伸到迁移过程中的通信协议、兼容性检查、传输安全与异常恢复机制。关键函数均附官方源码仓库（GitHub）链接，行号以阅读时点的 master 分支为准，后续阅读优先按函数名定位。
>
> 分析主线限定为：virsh 客户端协调的 managed direct 迁移、普通预拷贝（pre-copy）热迁移；内存状态走共享存储示例路径，非共享存储的磁盘复制（mirror 与 NBD 机制）在第五部分专项分析。特殊模式（P2P、tunnelled、post-copy）仅在帮助理解主线时提及，其中 post-copy 的故障恢复特性在第五部分第 4 节单独说明。

# 第一部分 控制连接与迁移五阶段

## 1. 代码运行在哪个进程里

阅读源码前须先明确各段代码的宿主进程，否则会产生"调用即跨进程"的误解。一次热迁移涉及两个宿主机上的四类进程：

| 进程 | 职责 |
|---|---|
| virsh 客户端进程 | 解析命令、建立连接、协调五阶段调用 |
| libvirt 服务进程（libvirtd 或模块化的 virtqemud） | 接收 RPC、执行迁移协调逻辑、经 QMP 指挥 QEMU |
| 源端 QEMU 进程 | 发送内存与设备状态 |
| 目标端 QEMU 进程 | 接收状态并恢复运行 |

三条关键边界：其一，libvirt 客户端库的代码运行在 virsh 进程内，调用库函数不产生进程切换，跨进程只发生在 RPC 通信处。其二，QEMU 驱动是 libvirt 服务进程内的代码，不是独立的 QEMU 进程。其三，"客户端/服务端"描述请求关系，"源端/目标端"描述迁移方向——Begin 与 Confirm 的服务端是源端 libvirt 服务，Prepare 与 Finish 的服务端是目标端 libvirt 服务。

## 2. virsh 如何建立目标控制连接

以示例命令贯穿全文：`virsh -c qemu:///system migrate --live vm1 qemu+ssh://hostB/system`，在源主机 A 上执行，目标为 B。其中 qemu:///system 是 virsh 到源主机的本机管理连接；qemu+ssh://hostB/system 是经 SSH 到目标主机的管理连接。

### 2.1 工具层的连接与线程安排

cmdMigrate（[virsh-domain.c:11854](https://github.com/libvirt/libvirt/blob/master/tools/virsh-domain.c#L11854)）先经已有源连接取得源虚拟机句柄，随后建立目标连接（virshConnect），存入控制结构。普通迁移路径中，当前线程先完成目标连接，再创建工作线程执行 doMigrate（[virsh-domain.c:11444](https://github.com/libvirt/libvirt/blob/master/tools/virsh-domain.c#L11444)），当前线程则进入任务监控并等待其退出。

两点须分清：其一，目标连接对象的指针在 cmdMigrate、doMigrate、virDomainMigrate3 各函数间层层传递，但指向同一个客户端连接对象，并非每进入一个函数就重新连接。其二，线程创建成功不等于迁移成功；迁移 API 返回非空目标句柄后才将结果标志置为成功。

### 2.2 SSH 通道的建立过程

目标连接经调用链 virshConnect、virConnectOpenAuth、virConnectOpenInternal、remoteConnectOpen、doRemoteOpen、virNetClientNewSSH、virNetSocketNewConnectSSH 完成（[SSH 分支](https://github.com/libvirt/libvirt/blob/master/src/remote/remote_driver.c#L1203)）。`+ssh` 方式下客户端启动外部 SSH 子进程，整条通道的形态为：源端 remote 驱动与 SSH 子进程之间经本地 socketpair 相连，SSH 经加密连接抵达目标端 sshd，目标端由 virt-ssh-helper（或兼容路径下的 nc）经本地 UNIX socket 接入 libvirt 服务。通道建立后还需完成服务端认证协商与连接打开 RPC，客户端才拿到可用的目标管理连接。（[辅助命令构造](https://github.com/libvirt/libvirt/blob/master/src/rpc/virnetclient.c#L416)、[remoteCallOpen](https://github.com/libvirt/libvirt/blob/master/src/remote/remote_driver.c#L771)）

### 2.3 socket 与文件描述符

三个概念必须区分：socket 是内核管理的通信端点；文件描述符（fd）是进程描述符表里访问该端点的编号，不是进程号，也不跨进程通用；UNIX socket 用于本机进程通信。

源端创建 socketpair 时，内核一次性返回两个已互相连通的端点，客户端保留一端，另一端接到 SSH 子进程的标准输入与输出。当 libvirt 把已建立的连接交给 QEMU 使用时，须经专门的描述符传递机制（而非把 fd 整数值发过去），使 QEMU 获得对同一内核 socket 对象的引用——两个进程中的 fd 编号可以不同。（[socketpair 与子进程连接](https://github.com/libvirt/libvirt/blob/master/src/rpc/virnetsocket.c#L775)、[保存 fd](https://github.com/libvirt/libvirt/blob/master/src/rpc/virnetsocket.c#L270)）

## 3. Begin：源端检查、保护与信息生成

### 3.1 调用链与迁移作业

virsh 工作线程经源端连接发出 Begin 的 RPC；源端 libvirt 服务经分发函数进入 QEMU 驱动，逐层调用 qemuMigrationSrcBegin（[qemu_migration.c:3063](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L3063)）、SrcBeginPhase（:2793）、SrcBeginXML（:2712）。本阶段走源端本地连接，不涉及目标端。

驱动入口检查参数与权限后，启用变更保护时调用 qemuMigrationJobStart 建立迁出作业。作业是 libvirt 内部的操作管理状态，不是新线程也不是新进程，其职责是协调冲突的管理操作：Begin 返回与后续 Perform 到来之间存在时间间隔，作业跨 API 保留，防止间隔期间发生不允许的冲突操作。本层还记录迁移前状态——记录的是管理状态，不是内存数据的备份。

### 3.2 检查与产出

BeginPhase 将迁出作业推进到 BEGIN3 阶段后执行两类检查：qemuMigrationSrcIsAllowed 检查迁移阻塞条件（含直通设备限制、进行中的块任务等）；常规安全路径调用 qemuMigrationSrcIsSafe 检查存储条件（可写共享盘、镜像状态等）。随后检查特殊选项组合的合法性，并按迁移条件决定 cookie 需携带的元数据类别。

本阶段产出两样东西，随 RPC 回复一起返回客户端：迁移 XML（目标端准备环境所需的虚拟机配置描述，是容量与布局等定义信息，不是内存内容）与 cookie（按条件生成的锁管理状态、CPU 信息、迁移能力等附加协调信息）。用户通过 `--xml` 提供替代配置时，此处解析并做 ABI 稳定性检查——允许宿主机侧路径不同，不允许对客户机可见的硬件接口变化。cookieFlags 控制元数据类别，flags 控制迁移行为，二者不可混淆。

## 4. 客户端衔接与目标端 Prepare

### 4.1 Begin 结果交给 Prepare

Begin 的结果先返回 virsh 协调代码，而非源端服务直接调用目标端。客户端整理目标端标志，将 cookie 的指针归属从"输出"转移为"下一步的输入"——这是本地指针归属转移，本身不产生网络发送；网络发送发生在随后经目标连接发出的 Prepare RPC 中。同时将迁移 XML 写入参数数组，随 Prepare 请求发往目标端。

### 4.2 Prepare：四个层次须分开

目标端经 qemuDomainMigratePrepare3Params 进入 qemuMigrationDstPrepareDirect、DstPrepareAny（[qemu_migration.c:3773](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L3773)）、DstPrepareFresh、DstPrepareActive（:3313）层层准备。四个概念必须区分：def 是解析后的虚拟机配置对象；vm 是 libvirt 内部的虚拟机管理对象；job 是迁入作业（操作状态与并发协调机制）；QEMU 进程是承载客户机状态的独立进程。建立作业不等于启动 QEMU；启动 QEMU 不等于让客户机执行业务。

准备流程依次为：取出迁移 XML 并解析为配置对象；确定迁移数据通道地址（用户未指定时从端口池分配并生成 URI）；解析 cookie 得到协调元数据；经对象列表处理配置归属与冲突检查，取得内部虚拟机对象；建立迁入作业并标记 Prepare 阶段；准备存储与宿主机资源；经 qemuProcessLaunch 启动用于迁入的目标 QEMU 进程。

### 4.3 通知 QEMU 进入接收状态

目标 QEMU 启动后，DstRun（qemu_migration.c:2478）经监控层向其下发 QMP 命令 migrate-incoming，命令携带监听地址，目标 QEMU 由此进入等待迁入状态。该命令处理成功后 Prepare 即返回——目标端不在 Prepare 中等待全部数据到达，否则"客户端等 Prepare、目标端等数据、源端等客户端发 Perform"三者互相等待，流程无法推进。

Prepare 完成时的全局状态：源端客户机仍在运行；目标端 QEMU 已启动并等待接收，客户机尚未执行业务；客户端收到成功结果、新 cookie 与数据通道地址。失败时按实际进度清理，客户端会按需通知源端取消已建立的受保护作业。

## 5. Perform：数据通道的建立

客户端将 Prepare 返回的数据通道地址写入参数数组，将 Prepare 的输出 cookie 转为 Perform 的输入，经源端连接调用 Perform。注意请求发往源端，而数据通道地址在参数数组中——迁移数据地址与目标管理地址是两个不同的地址。

源端经 qemuDomainMigratePerform3Params 进入 qemuMigrationSrcPerform、SrcPerformPhase（[qemu_migration.c:6448](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L6448)）、SrcPerformNative（:5391），汇入执行体 SrcRun（:4965）。驱动层检查 Begin 留下的迁出作业仍有效（变更保护），将阶段推进到 PERFORM3。

普通 TCP 路径下，连接的建立者与数据的发送者是分开的：源端 libvirt 解析目标 URI 得到连接描述，经 SrcConnect（:4569）主动向目标端迁移接收地址发起 TCP 连接，取得连接的文件描述符；随后经描述符传递机制将该连接交给源 QEMU，并向 QEMU 下发 QMP migrate 命令（uri 引用刚交付的连接）。交付完成后 libvirt 关闭自己对该连接的引用，数据传输完全由源 QEMU 向目标 QEMU 进行，不经 virsh 或 libvirt 中转。"谁建连接"与"谁发数据"必须分别判断——这一事实也是"控制面加密不等于数据面加密"结论的源码依据。（[SrcStart](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L4814)、[fd 交付](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_monitor.c#L2255)）

## 6. 等待模型与协调点

QMP migrate 命令的回复只表示命令处理成功，运行状态传输仍在继续。libvirt 的等待模型为"检查—等待—被唤醒—再检查"：等待循环反复调用状态判断函数 qemuMigrationAnyCompleted（:2150），未完成则让当前处理线程在虚拟机对象上等待（SrcWaitForCompletion，:2252）；QMP 事件处理逻辑更新迁移状态后唤醒等待者；被唤醒不代表完成，必须重新检查。

**pre-switchover 协调点**：首次等待带有"允许在切换前协调点返回"的标志。pre-switchover 是设备状态序列化前的暂停点，源客户机 CPU 已停止，libvirt 可在此处理收尾工作（例如非共享存储的块任务 pivot）。因此第一次等待成功返回有两种可能——停在协调点，或已到达完成状态；不能仅凭第一次返回成功就宣布整次迁移完成。

**等待 STOP 事件**：源 QEMU 停止客户机 CPU 后发出 STOP 事件，libvirt 收到并处理后才更新内部状态为暂停，二者存在短暂间隔；等待循环只确保管理状态与实际状态同步，期间不向 QEMU 发送任何停机命令。事件处理同时请求锁管理器处理暂停时的资源锁——迁移作业与资源锁不是同一件事，锁行为取决于具体插件。

**继续与收尾**：若迁移停在协调点，源端经 qemuMigrationSrcContinue（:4629）下发 QMP migrate-continue 命令放行——继续的是迁移状态机，不是恢复客户机运行。随后清除协调点标志再次等待，直至 QEMU 迁移完成或出错。正常成功后更新迁移统计、整理后续阶段所需的新 cookie，作业阶段标记为 PERFORM3_DONE 并保留迁出作业，RPC 结果返回 virsh 协调代码。

Perform 返回时的全局状态：源 QEMU 进程仍在、客户机 CPU 暂停；源端迁出作业保留；目标端待后续阶段确认；virsh 准备推进 Finish。三种"成功"必须区分：migrate 命令成功、Perform 成功、整次迁移成功，任何一种都不蕴含下一种。

## 7. Finish：目标端确认接收并恢复运行

### 7.1 请求与目标端入口

Perform 返回后，客户端根据其结果计算取消标志（成功为零，失败为一），将源端输出的 cookie 转为 Finish 的输入，经目标连接发出 Finish 请求。目标端经分发进入 qemuMigrationDstFinish（[qemu_migration.c:7087](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L7087)）。

驱动入口提取目标名称并查找虚拟机对象——找到的是 Prepare 创建并加入目标端列表的管理对象，不是 Perform 新建的。Finish 先检查迁入作业仍有效（此前错误清理可能已结束作业），然后解析 cookie、检查取消标志、确认目标实例未意外退出，进入 DstFinishFresh（:6849）。

### 7.2 等待接收完成与恢复执行

需要澄清一个常见误解：数据接收在 Perform 阶段就已经开始，不是进入 Finish 才开始。Finish 的等待函数（DstWaitForCompletion，:2297）确认的是目标 QEMU 已处理完全部迁移数据——若目标早已完成，等待立即通过。完成后经 qemuProcessRefreshState 刷新 libvirt 对设备实际状态的记录。

未要求保持暂停时，Finish 经 qemuProcessStartCPUs 恢复客户机执行，顺序是：先启用网络设备并恢复资源锁使用（virDomainLockProcessResume 恢复的是资源锁，不是 CPU），再经 QMP 发送 cont 命令。cont 恢复客户机 CPU 执行；目标 QEMU 随后发出 RESUME 事件，libvirt 据此更新管理状态。命令回复与异步事件是不同消息，可以交错到达。（[StartCPUs](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_process.c#L3447)、[资源锁获取](https://github.com/libvirt/libvirt/blob/master/src/locking/domain_lock.c#L212)）

### 7.3 收尾与句柄返回

恢复成功后，Finish 整理统计、保存状态、移除迁入期间的连接关闭自动销毁回调（意味着不再因控制连接关闭而销毁已成功迁入的虚拟机，但不等于保存为持久定义），结束迁入作业。目标端以现有虚拟机的名称、UUID、ID 生成 API 层句柄，随 RPC 回复返回虚拟机标识（不是指针）与统计 cookie；客户端据此获得自己的目标句柄 ddomain。（[目标成功收尾](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L6747)）

## 8. 结果不确定性：回复丢失的处理边界

一个必须正视的协议边界：Finish 成功执行后，成功回复可能在传输中丢失。此时客户端得到空句柄，但目标虚拟机可能已经在运行。

| 故障位置 | 可能结果 |
|---|---|
| 请求未送达 | 目标未执行这次 Finish |
| Finish 执行中失败 | 未成功完成，状态取决于失败位置 |
| Finish 成功但回复丢失 | 目标可能已运行，客户端却未获得成功句柄 |

因此不能只凭客户端收到空句柄就断言可以无条件恢复源端，否则可能出现两端同时运行、访问共享磁盘的双活事故。libvirt 源码注释（[libvirt-domain.c:3520](https://github.com/libvirt/libvirt/blob/master/src/libvirt-domain.c#L3520)）指出该问题应由锁管理插件处理；五阶段协议本身不是一个消除所有通信不确定性的分布式事务协议。这一边界是产品化设计中"失败自动归因"与"安全恢复条件判断"的直接依据。

## 9. Confirm：源端的最终裁决

### 9.1 请求与入口

客户端根据 Finish 是否返回目标句柄重新计算取消标志，将 Finish 输出的 cookie 转为 Confirm 输入，经源端连接发出 Confirm 请求。普通成功路径必须执行 Confirm；若 Perform 已失败，源端已知失败并已处理，协调代码不再重复通知。Confirm 返回整数处理结果，不再返回句柄——API 返回目标句柄与源端清理是否成功，也应分别关注。

源端经 qemuMigrationSrcConfirmPhase（[qemu_migration.c:4169](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L4169)）解析 cookie、补充统计后按取消标志分支。

### 9.2 成功：结束源 QEMU 进程

成功路径调用 qemuMigrationSrcComplete（:4122），经 qemuProcessStop 停止源端这台虚拟机对应的 QEMU 进程并清理源端运行资源——不是只暂停 CPU，不是关闭 libvirt 服务，也不是删除虚拟机磁盘。随后产生因迁移而停止的生命周期事件。

| 时点 | 源 QEMU | 源客户机 CPU |
|---|---|---|
| Perform 成功返回 | 进程保留 | 暂停 |
| Finish 成功返回 | 仍保留，等待确认 | 仍暂停 |
| Confirm 成功收尾 | 进程结束 | 源端不再执行 |

### 9.3 取消：尝试恢复迁移前状态

取消路径先取消可能存在的 NBD 复制作业，再调用 qemuMigrationSrcRestoreDomainState（:253）检查迁移前状态与当前状态：仅当迁移前原本运行、当前暂停时才考虑恢复——原本就暂停的不应擅自变成运行，I/O 错误暂停等情况也不直接恢复。符合条件时经资源锁与 QMP cont 尝试恢复源端运行。这是"尝试恢复"，可能失败，不能把取消处理返回与业务已恢复划等号。post-copy 有单独的失败分支，不能套用"失败就恢复源端 CPU"。

### 9.4 结束迁出作业与源配置处理

迁出作业到 Confirm 收尾结束。源实例已不活动时，仅在没有取消、处理成功且设置了相应标志（--undefinesource）的条件下删除源持久配置。停止进程、删除持久配置、删除磁盘是三个不同层次的操作，不能混为一谈。

## 10. 五阶段正常主线总结

| 阶段 | 主要执行端 | 主要工作 | 正常交接结果 |
|---|---|---|---|
| Begin | 源 libvirt | 检查源虚拟机，建立变更保护，生成配置与协商信息 | XML、cookie |
| Prepare | 目标 libvirt | 建立管理对象与迁入作业，启动等待接收的 QEMU，分配数据地址 | 地址信息、cookie |
| Perform | 源 libvirt 协调，两端 QEMU 传输 | 建连接、传 fd、下发迁移命令，跟踪传输与切换 | 源暂停保留，返回结果与 cookie |
| Finish | 目标 libvirt | 确认接收完成、刷新设备、恢复 CPU，结束迁入作业 | 目标句柄、cookie |
| Confirm | 源 libvirt | 成功则结束源 QEMU；取消则按原状态尝试恢复 | 源端处理结果 |

成功主线为：源 CPU 暂停且源 QEMU 保留，目标完成接收并恢复执行，目标成功回复到达客户端，客户端通知源端 Confirm，源 QEMU 结束而目标继续运行。共享存储场景下磁盘内容不在内存迁移流中复制（非共享存储的磁盘复制机制见第五部分第 5 节）。

# 第二部分 迁移过程中的通信协议

## 1. 协议分层总览

整条迁移链路涉及五类通信关系，各层职责不同：

| 层次 | 含义 | 本场景载体 |
|---|---|---|
| 操作协调 | 哪一方按什么次序执行什么操作 | libvirt 五阶段 |
| 消息协议 | 请求、回复、事件、状态记录怎样组织 | libvirt RPC、QMP、QEMU 迁移格式 |
| 编码 | 字段怎样变成可传输字节 | RPC 的 XDR、QMP 的 JSON、QEMU 状态的二进制编码 |
| 传输通道 | 怎样把字节交给另一端 | TCP、UNIX socket、fd |
| 安全保护 | 认证、加密、防篡改 | SSH、TLS，分别作用于实际经过它们的通道 |

## 2. libvirt RPC 与 XDR

以 Begin 请求为例：客户端 remote 驱动提取虚拟机标识、参数数组与标志填入请求结构（进程内对象，不是网络包），经通信层编码发送。RPC 消息由长度字段、消息头与编码后的参数组成；消息头包含程序号/版本号（识别 RPC 接口）、操作号（识别调用哪个远程操作）、消息类别、序列号（关联本次请求及其回复，不是 TCP 分片编号）与状态。

libvirt RPC 使用 XDR 编码（不是 gRPC）：按字段类型和声明顺序编码，32 位整数使用 4 字节大端表示，字符串包含长度、内容与对齐填充——不是直接复制 C 结构体的整块内存。接收端面对的是无边界的字节流：先解析长度，再累计所需字节，按消息头定位操作，用对应解码函数还原参数。返回的虚拟机标识在客户端形成客户端自己的句柄，远端指针地址不会变成有效对象。（[remote_protocol.x](https://github.com/libvirt/libvirt/blob/master/src/remote/remote_protocol.x)、[virnetprotocol.x](https://github.com/libvirt/libvirt/blob/master/src/rpc/virnetprotocol.x)）

## 3. QMP：命令、回复与事件

QMP 有三类消息：命令（带 id）、回复（按 id 对应请求，失败时含 error）、事件（描述状态变化，不按命令 id 配对，可能与回复交错到达）。连接建立后须经 greeting 与 qmp_capabilities 能力协商才能进入正常命令模式——协商的是 QMP 功能，不是迁移兼容性，也不是 SSH 认证。

须注意的边界：migrate 或 migrate-incoming 命令成功不等于迁移任务完成，后续状态须通过事件与 query-migrate 跟踪；客户机 STOP 事件也不等于迁移完成。（[QMP 规范](https://www.qemu.org/docs/master/interop/qmp-spec.html)）

## 4. QEMU 迁移流格式

QEMU 的迁移数据流是自身定义的二进制格式（不使用 XDR），核心结构分四层：

**流头**：魔数标记与迁移流格式版本（当前为 3）。目标端加载时检查格式标记与版本——这验证的是"外层结构是否为认识的格式"，不回答"每个设备的状态是否都能恢复"。

**section 段头**：分 START/PART/END/FULL 四类。目标端首次按名称与实例编号查找本地已登记的状态条目（find_se），找不到即报错——这是"找接收者"，不是"按名字自动创建缺少的设备"。之后按段编号定位相同加载逻辑。

**设备状态**：双方代码中已有字段顺序与类型约定（VMStateDescription，即设备状态的"读写说明书"），网络中主要传值。段头中的版本号告诉目标端"这段状态采用哪套格式规则"；目标端按版本范围检查（收到版本太新或太旧均拒绝），版本检查通过仍可能在字段与加载回调中失败。

**RAM 记录**：内存按页组织传输。RAMBlock 是 QEMU 管理的大片内存，记录以"块身份 + 块内偏移 + 编码标志 + 页内容"描述——不传源端指针，目标端定位自己的对应块再加偏移写入。编码标志包括：PAGE（后接普通页内容）、ZERO（全零页的简写记录，目标端须恢复对应页为零——依据的是页当前内容，与使用历史无关）、CONTINUE（沿用前一记录的块）、EOS（本段 RAM 记录结束，不是某个 RAMBlock 的结束）。偏移按页对齐后低位用于存标志，接收端用掩码拆开。段尾 footer 检查固定标记与段编号，帮助发现错位，但不是整段哈希或密码学完整性证明。EOF 表示主要迁移状态流结束，之后还可能有分析用的附加数据。

（源码：[savevm.c](https://github.com/qemu/qemu/blob/master/migration/savevm.c)、[ram.c](https://github.com/qemu/qemu/blob/master/migration/ram.c)）

## 5. "迁移完成"不是一个单独的标志

| 观察到的信息 | 能说明什么 | 不能仅凭它说明什么 |
|---|---|---|
| 源端写入 EOF | 已写到主要状态段结尾 | 目标已读完、加载成功 |
| 目标读到 EOF | 主状态段解析到结尾 | 加载线程与后续检查全部成功 |
| 目标 QMP 迁入 completed | 目标 QEMU 的迁入状态完成 | 客户机 CPU 必然已运行 |
| QMP RESUME | 客户机恢复执行 | 客户机内业务健康、源端已清理 |
| Finish 成功回复到达客户端 | 客户端取得目标处理结果 | 源端清理必然成功 |

状态传递链为：目标 QEMU 完成迁入，经 QMP MIGRATION 事件通知目标 libvirt，后者更新迁移作业记录并唤醒内部等待者（进程内条件变量通知，不是网络广播），等待函数重新检查后决定继续或完成。在 libvirt 管理的普通预拷贝路径中，目标 QEMU 以暂停模式启动，CPU 恢复时机由 libvirt 控制：Finish 确认并准备好后才发送 cont；要求迁移后保持暂停时，暂停也是合法成功结果。

# 第三部分 兼容性检查

## 1. 检查的目标与四个"版本"

热迁移不是在目标端重新安装系统：客户机要从暂停处继续执行，因此目标端须看得懂状态数据、找得到对应设备实例、提供兼容的虚拟硬件与 CPU 能力、能恢复具体运行状态。TCP 能连接只说明有通信路径；接收到字节不说明有能力正确恢复。检查分散在配置校验、能力探测、创建目标实例与实际加载等多个位置，不是一次握手保证全部兼容。

四个容易混淆的"版本/型号"必须分开：QEMU 软件版本（程序实现能力）、迁移流格式版本（外层组织规则）、设备状态格式版本（各设备分别定义）、带版本的机器类型（虚拟平台及兼容行为）。另外 libvirt RPC 头中的接口版本又是远程接口层的版本，不能混入以上几项。

## 2. 机器类型与 CPU 兼容性

**机器类型**：可理解为"虚拟主板/平台类型及兼容版本"（如 pc-q35-8.2 中 q35 是平台、8.2 是该版的兼容规则），影响芯片组、总线结构与设备默认属性。客户机已按源端虚拟硬件完成初始化，迁入后若平台行为突变，即使内存正确也无法继续运行。典型做法是目标端新版 QEMU 继续使用源端的旧机器类型（经兼容属性保留旧行为）。两个误解须同时避免：软件版本不同不一定不能迁（版本化机器类型正是跨版本兼容机制）；机器类型名称相同也不保证能迁（CPU、设备实例、状态加载仍须兼容）。

**CPU 配置与 CPU 运行状态是两件事**：配置指模型、指令集特性与拓扑（决定目标能否提供客户机原先看到的 CPU）；运行状态指寄存器、程序计数器等（决定怎样从暂停处继续）。若客户机已探测并依赖某特性（如 AVX2），目标无法提供时，即使寄存器与内存原样恢复，后续指令也可能无法执行——不能为迁移成功临时删掉客户机已依赖的特性，应在启动前为迁移集群规划兼容配置。

三种 CPU 模式的迁移要点：

| 模式 | 含义 | 热迁移重点 |
|---|---|---|
| host-passthrough | 尽量呈现宿主 CPU 特征 | 依赖两端硬件、微码、QEMU 与配置一致性；两端物理 CPU 型号相同不是充分条件 |
| host-model | 按宿主能力形成明确虚拟 CPU 定义 | 迁移传递该运行实例已确定的定义，目标必须能提供；不是到目标端按其 CPU 重新挑选 |
| custom | 明确指定模型与特性 | 可为多主机规划共同配置，但须验证能力可提供，不能凭空创造能力 |

目标端从迁移 XML 中获得 CPU 要求，与本机支持能力比较（[qemuProcessUpdateGuestCPU](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_process.c#L6628)）；比较的是"虚拟机要求与目标可提供的能力"，不是要求两台物理 CPU 特性完全相等。检查在时间上分层发生：准备目标环境前后（模式/模型/机器类型检查）、创建目标 QEMU 时（CPU 核对）、接收迁移流时（流版本/设备身份/状态版本检查）、恢复执行前（接收结果与资源检查）——某项早期检查通过，不能消除后续加载失败的可能。这正是此前实验中 host-passthrough 首次迁移失败的机制解释：状态数据全部到达，但目标端加载 CPU 状态时校验失败。

# 第四部分 传输安全：TLS 机制与配置分工

## 1. 通道安全边界

**TCP 可靠性不等于加密。** TCP 经序号、确认、重传提供可靠有序的字节流，但其校验和不是抵抗恶意篡改的密码学认证；QEMU 的魔数、版本与 footer 检查也不是传输内容的密码学保护。

**SSH 控制连接不自动保护数据通道。** 控制连接（virsh 经 SSH 到目标 libvirt，承载 RPC）与数据连接（源 QEMU 到目标 QEMU，承载迁移流）是两条不同通道。控制连接用了 SSH，不代表 QEMU 原生迁移流自动加密；为原生数据通道启用 TLS 须经专门配置（VIR_MIGRATE_TLS 机制）。（[libvirt 迁移与安全](https://libvirt.org/migration.html)）

## 2. TLS 的位置与三个作用

TLS 位于 QEMU 迁移代码与 TCP 之间：先建立 TCP 连接，再在同一条连接上完成 TLS 握手，随后传输受保护的迁移数据。QEMU 迁移代码仍按自身格式生成字节，TLS 层负责认证加密。TLS 提供三个作用——身份认证（验证对方证书与私钥持有证明）、加密（网络旁观者不能读取内容）、完整性保护（发现篡改即拒绝并断连）——不判断设备兼容性，不证明业务正常，不保护已被控制的端点。

## 3. 证书体系与私钥持有证明

证书体系的工作顺序：目标端管理员先为该端生成密钥对，将身份与公钥经证书签名请求交给 CA，CA 核实后签发证书（私钥不交给 CA）；证书是"经签发者签名的身份与公钥绑定"，签发后不能任意修改。发起连接的一端预先配置可信 CA 材料，收到对方证书后用 CA 公钥验证签发关系、检查有效期与目标名称，确认适用于预期目标后才信任其中的公钥。实验环境可自建 CA，但须明确配置为可信。

**拿到可信证书还不够**：证书是公开信息，冒充者可以复制，因此还须证明当前对方持有对应私钥。以 TLS 1.3 为例，对方对本次握手相关内容生成 CertificateVerify 签名，本端用对方证书中的公钥验证。三个常见误解须纠正：其一，签的是本次握手相关内容，不是重新为证书签名；其二，验签用的是对方的公钥，与本端公私钥无关；其三，验签结果是有效或无效，不是"用公钥解出证书"。

**证书密钥与流量密钥不是同一套**：CA 签名密钥用于签发证书；端点证书公私钥用于身份认证；握手中协商的共享秘密派生出流量密钥，用于对每条 TLS 记录做认证加密。两个传输方向使用不同的流量密钥；内存数据不是由证书私钥逐页加密。

## 4. TLS 记录保护与层次边界

TLS 将迁移字节流组织成记录（record）逐条保护，无需等待全部内存生成完毕。TLS 1.3 使用 AEAD 认证加密：结合流量密钥、每条记录的 nonce 与头部信息生成密文与认证标签。接收端累计完整记录后由 TLS 层验证并解密——验证失败则不交付明文、报错终止连接；不是 TLS 只验标签再让迁移代码解密密文。认证标签是密码学完整性凭据，检测到异常不自动修复数据。

各层边界互不重合：RAM 页记录、section、TLS record、TCP 分段分属四个层次，一页可跨多条记录，一条记录也可包含多个迁移记录的片段。TLS 不知道 RAMBlock 与偏移的业务含义，只还原受保护的原始字节；TLS 验证通过不替代设备版本与加载检查。

## 5. libvirt 与 QEMU 的配置分工

管理员提前在各主机准备证书、私钥与信任材料；libvirt 通过本地 QMP 控制各自 QEMU，创建 TLS 凭据对象并将对象名称填入 tls-creds 迁移参数、按需设置验证的目标主机名（[qemuMigrationParamsEnableTLS](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration_params.c#L1169)）。QMP 负责配置和控制；TLS 握手消息走两端 QEMU 之间的迁移连接。启用 TLS 不表示把数据交回 libvirt 转发。

这一分工结构对国密改造的意义：迁移数据路径上的加密组件（TLS 库）与迁移逻辑（QEMU 序列化代码）相互独立，认证加密能力可在通道层透明替换——这正是本调研国密路线（exec 传输方式接入国密代理）的源码依据。

# 第五部分 异常恢复与非共享存储磁盘复制

## 1. 先区分哪条连接断开

异常分析的第一步是区分故障通道：控制连接（virsh 与对应 libvirt，承载 RPC）、数据连接（源 QEMU 与目标 QEMU，承载迁移流）、以及 libvirt 与本机 QEMU 的 QMP 连接是三条独立连接。控制连接断开不直接证明数据连接也已断开；控制请求未得到回复不证明远端没有执行。

## 2. 预拷贝中途数据连接失败

场景特征：源虚拟机仍保留运行状态（可能仍在运行，也可能已到暂停阶段）；目标实例只接收了部分状态，尚未开始客户机执行。处理方向：识别迁移失败，取消迁移并清理未完成的目标接收实例；源端原来仍在运行时尽量保持运行，已暂停时在安全条件允许下尝试恢复。

四条边界须明确：其一，不是让只收到半份数据的目标虚拟机恢复运行；其二，不是把目标收到的半份数据迁回源端——普通预拷贝中源端始终保留自己的状态，无需回传；其三，清理目标运行实例不等于无条件删除目标磁盘镜像；其四，不是所有阶段失败都能恢复，源状态是否可用、目标是否接管、资源与锁条件均需判断。

## 3. Finish 已执行但回复丢失

从客户端的观察看，失联可能发生在请求发送前、执行中、执行后或回包途中——客户端不能仅凭"没收到回复"确定目标已运行，也不能确定没有运行，这就是执行结果不确定。若目标已运行而源端贸然恢复，会产生两个活跃实例：共享存储可能双写，非共享存储也会重复对外服务导致数据分叉。

| 已知情况 | 应理解的处理方向 |
|---|---|
| 目标尚未接管，源状态与资源条件允许 | 可按取消/恢复路径让源端继续服务 |
| 已确认目标接管并正常运行 | 让目标继续运行，源端停止执行并完成清理 |
| 目标执行结果不能确认 | 不能贸然恢复源端；需进一步核实并满足安全恢复条件 |

libvirt 文档说明客户端协调模式中失联会尝试中止迁移并恢复源端，不能安全完成时可能保留一端或两端暂停——这是可能的结果，不是对所有失联情况的通用算法。该场景直接支撑产品化设计中的两个功能：失败自动归因（区分故障位置与恢复前提）与安全恢复条件检查（目标接管状态核实）。

## 4. 结果核实的边界：重试、锁与隔离

**重发命令不等于查询状态。** 假设第一次 Finish 已成功执行、目标已运行、迁入作业已结束，但成功回复丢失：再发 Finish 会因已无迁入作业而报错，第二次报错不证明第一次失败——Finish 入口先检查迁入作业是否有效（qemu_migration.c:7087），正常收尾即结束作业，这类阶段接口不能默认"重复调用总能返回原结果"。重发是要求对方再次执行操作；查询状态是了解现状；查询失败仍不能据此断定对方已停止。须结合两端运行状态、作业状态、日志与资源所有权核实结果，某一次查询只是观察，不保证后续状态不变。

**运行状态与资源锁是不同问题。** 暂停状态表示客户机执行状态，不证明它有权写共享磁盘；恢复 CPU 的代码顺序（[qemu_process.c:3447](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_process.c#L3447)）是先恢复资源锁、失败即返回，之后才发 cont——锁取得失败可能是锁服务或存储异常，不能直接证明目标在运行。锁管理器有 lockd、sanlock 等插件，也有不执行锁操作的 nop：不能看到调用锁接口就认定已配置保护；非共享存储中两端各锁自己的磁盘副本，也不能防止重复服务与数据分叉。

| 机制 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 运行状态查询 | 查询时实例的执行状态 | 不能单独证明有权恢复或数据一致 |
| 资源锁 | 对受保护资源的互斥使用约束 | 不证明迁移已完成或客户机应用健康 |
| 取得锁失败 | 本次未能取得锁 | 不能直接证明目标在运行 |

**隔离（fencing）与恢复不是同一步。** 管理连接不可达时目标 QEMU 仍可能访问磁盘并服务用户；fencing 通过可靠手段阻止一端继续操作资源（独立电源管理关闭主机、存储侧撤销访问权等），断开 SSH 不能代替这些措施。且隔离不自动使旧源端状态可恢复：目标接管后已修改内存与磁盘到更晚时刻，即使此后目标被隔离，源端内存仍停留在迁移暂停时刻，共享存储可能已有更新的磁盘内容——仍须选择一致、可用的状态恢复，不能直接恢复旧源端执行。概括：查询用于了解状态，隔离用于阻止竞争，恢复还要选择正确的数据与运行状态。（[ClusterLabs fencing](https://clusterlabs.org/projects/pacemaker/doc/3.0/Pacemaker_Explained/html/fencing.html)）

**post-copy 的恢复逻辑不能照搬预拷贝。** post-copy 已切换且尚未传完时，客户机在目标端执行，缺页时向源端请求：已到达并被目标修改过的页，最新内容在目标；尚未到达的页，仍需源端提供——两端可能各持有一部分完整状态。因此不能套用预拷贝切换前"回退源端"的思路。若只是连接故障、两端 QEMU 及所需状态仍保留，且满足版本与配置条件，可修复或重建通道、执行恢复握手、同步页接收情况后继续原有 post-copy——这是继续迁移，不是回退。任一端所需状态丢失则运行中的虚拟机可能无法恢复，此时不能机械关闭源 QEMU（它可能仍保留必需页）。（[QEMU post-copy recovery](https://www.qemu.org/docs/master/devel/migration/postcopy.html#postcopy-recovery)）

## 5. 非共享存储与 NBD：磁盘复制机制

实验目标是非共享存储热迁移：磁盘内容须同步到目标端，不能只恢复磁盘控制器的运行状态。现代 libvirt/QEMU 路径由镜像作业（mirror）与 NBD 协议配合完成。

### 5.1 分工与两条数据通道

整条磁盘复制链有明确分工：libvirt 经 QMP 配置、启动和检查两端 QEMU 的迁移及磁盘作业；源 QEMU 的 mirror 负责组织磁盘内容复制、跟踪变化、维护作业状态；源 QEMU 的 NBD 客户端向目标导出发送磁盘操作请求；目标 QEMU 内置的 NBD 服务端提供磁盘导出并经目标块后端执行操作；TCP socket（可加 TLS）承载字节流。目标端提供可写磁盘入口、源端向它写入，不要求另起独立的 NBD 服务进程，也不依赖系统的 /dev/nbdX 设备。（[QEMU mirror + NBD](https://www.qemu.org/docs/master/interop/live-block-operations.html#qmp-invocation-for-live-storage-migration-with-drive-mirror-nbd)）

磁盘内容与内存状态走两条独立通道：内存、CPU、设备状态按 QEMU 迁移格式走迁移连接；磁盘内容按 NBD 块操作走 NBD 连接——磁盘数据不放进 RAM 页记录中传输。NBD 只提供块访问协议，本身不会自动发现源盘变化并完成镜像同步，同步由 mirror 组织。

### 5.2 端口、连接与导出

NBD 标准端口是 10809，但迁移不必使用它：libvirt 的 DstStartNBDServer（qemu_migration.c:635）可使用指定端口或从迁移端口池申请，再经 QMP 启动目标 NBD 服务。`--disks-port` 指定监听端口，`--disks-uri` 指定地址/端口或 UNIX socket，二者互斥。SSH 控制端口、内存迁移端口、NBD 磁盘端口是三个不同的端口。三层定位信息各司其职：IP 与端口定位 NBD 服务，导出名称定位服务提供的某个逻辑磁盘入口，offset 与 length 定位该磁盘中的数据区域。一个监听端口可接受多条 TCP 连接，常见多盘路径中每块盘分别连接并选择自己的导出；进入传输阶段后一条连接关联到选定导出，不能在后续写入中随意换盘，但不必为每次写入重连。（[目标 NBD 服务启动](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L635)）

### 5.3 握手、写入与持久化语义

连接建立后按 fixed newstyle 协商：交换协议标识与握手标志、按配置进行 TLS 升级、客户端以 NBD_OPT_GO 指定导出名称、服务端返回容量与能力后进入传输阶段。写入请求携带操作类型、请求标识（cookie）、逻辑偏移与数据；回复携带同一 cookie，按 cookie 匹配而非按到达顺序——一条连接可有多个在途请求，回复不必按请求顺序返回。此 NBD cookie 只是请求标识，与五阶段之间交换的 libvirt 迁移 cookie 是完全不同的东西。NBD 消息使用自己的二进制格式，不使用 XDR。（[NBD 协议](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md)）

写入成功不等于数据已到非易失存储：普通 WRITE 允许持久化前回复；NBD_CMD_FLUSH 要求此前写入完成持久化后才成功回复；带 FUA 标志的写入要求本次写入持久化后才回复。正确顺序是先等待一批写入成功回复，再发 FLUSH——FLUSH 不重新传输原数据，持久化完成也不等于镜像同步结束（客户机可能继续产生新写入）。

### 5.4 mirror 的变化跟踪与就绪收尾

复制期间客户机仍在写盘，mirror 用脏位图记录需要同步的区域——位图是"待办状态"，不保存数据副本。某区域复制到目标后若又被客户机修改，会再次被标记并后台同步。两种复制模式：background 模式跟踪变化、后台继续同步；write-blocking 模式写源端时同步执行目标写入（不表示两盘同一瞬间落盘，也不自动等于 FUA）。达到 READY 后作业仍然存在、继续处理变化。（[mirror 写入路径](https://github.com/qemu/qemu/blob/master/block/mirror.c)）

磁盘复制与内存迁移的配合顺序：启动各盘 mirror，等待本次需复制的磁盘全部 READY，之后才启动内存状态迁移；mirror 继续同步客户机的新写入；最终切换时源客户机 CPU 暂停，处理剩余磁盘同步与在途 I/O，完成剩余状态传输与目标接管。libvirt 侧对应 SrcNBDStorageCopy（:1289）等待就绪、SrcStart（:4814）启动内存迁移、最终调用 SrcNBDCopyCancel（:992）收尾磁盘作业。此处 Cancel 不等于失败或删除副本——对已 READY 的 mirror，它是正常结束持续同步、保留目标结果的语义。若 QEMU 停在 pre-switchover 协调点，libvirt 在块作业收尾后经 SrcContinue 放行。（[多盘就绪检查](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L806)、[取消语义](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L941)）

### 5.5 复制对象：逻辑内容而非文件布局

NBD 不按数据内容分类磁盘；磁盘先由虚拟机配置确定，复制任务再绑定对应源盘与目标导出。复制的是逻辑磁盘内容，不是照搬 qcow2 文件布局：qcow2 除客户机数据外还有格式头、映射表、引用计数等元数据，逻辑偏移与镜像文件偏移不是同一概念——目标端自行维护格式映射，只要求客户机从相同逻辑位置读到一致内容，包括客户机的分区表、文件系统元数据与文件数据；QEMU 按块处理，无需识别客户机文件名。一段磁盘数据的路径为：mirror 选出逻辑偏移与长度的待同步区域，源块层按 qcow2 映射读入本进程内存缓冲区（这只是暂存磁盘数据，不是 RAM 页迁移），经 NBD 客户端编码、TLS（若启用）与 TCP 发送，目标解析后经自己的块层完成相同逻辑位置的写入。（[qcow2 cluster mapping](https://www.qemu.org/docs/master/interop/qcow2.html#cluster-mapping)）

### 5.6 镜像链与全量/增量复制

镜像可为基础层加变化层的链式结构。全量同步（--copy-storage-all）让目标获得组合后的完整内容；浅复制（--copy-storage-inc）主要复制当前变化层，前提是目标必须已具有正确的基础内容——若目标基础层内容错误，即使变化层写入全部成功，最终得到的也是错误结果。两个时间范围须分开：初始复制覆盖迁移前相对基础层积累的全部当前层内容；迁移期间的新变化由 mirror 的脏位图持续同步。--copy-storage-inc 不是自动比较任意两份镜像找差异，也不同于增量备份的脏位图机制。

### 5.7 磁盘通道的 TLS

NBD 的 TLS 经 NBD_OPT_STARTTLS 升级：在已有 TCP 连接上完成初始握手后请求升级，服务端同意（回复 ACK）后，在同一条连接上完成 TLS 握手（身份验证、协商密钥），此后导出选择与全部磁盘操作都在 TLS 内进行。STARTTLS 是请求升级的协商选项，不是加密函数，也不要求建立第二条连接；实际加密由 QEMU 进程内的 TLS 库完成——源端 mirror 产出的 NBD 请求字节经 TLS 库加密后写 socket，目标端经验证解密后交给 NBD 解析。升级同意后握手失败应终止会话，不能退回明文继续。（[QEMU NBD TLS 升级](https://github.com/qemu/qemu/blob/master/nbd/client.c#L617)）

内存通道与磁盘通道是独立通道：即使复用同一套证书材料，也须各自建立 TLS 会话——看到内存通道已加密，不能推断 NBD 通道已加密。这一点与调研主线直接相关：通道加密状态须逐通道验证。

### 5.8 磁盘复制失败与空白区域处理

源端仍运行、目标尚未接管时的故障边界：目标返回写错误表示本次未成功完成，但不保证已修改部分自动回滚；连接中断时写入可能未执行、部分执行或已完成但回包丢失，不能当作成功确认。错误沿"源 NBD 客户端、mirror 作业状态、libvirt 经 QMP 得知"的链路传播；libvirt 检查到镜像作业失败即报告错误，即使内存通道正常，也不能让磁盘未确认同步完成的目标接管。连接恢复不等于镜像已一致，不能按"已复制百分比"直接续传。

空白区域处理须区分四种情况：独立 qcow2 中未分配且无 backing 数据的区域读取为零，目标也必须为零；当前层未分配但 backing 有数据的区域按 backing 读取，不能当作零；已分配且内容全零的区域可在确认后优化传输；客户机文件系统认为空闲的区域可能残留旧字节，不能据此视为零。对确认全零的范围，支持 NBD WRITE_ZEROES 时可只发偏移和长度而不携带零字节；但源区域为零而目标原有旧数据时，什么也不做会留下不一致内容，必须让目标变为零或有可靠依据证明目标已为零。TRIM/discard 不等于 WRITE_ZEROES：单独 TRIM 不保证此后读取为零。

### 5.9 实验准备要点

容量与空间：virtual size 是客户机看到的磁盘容量，disk size 是镜像在宿主机上的实际占用——实际占用 8 GiB 不代表数据都在逻辑前 8 GiB，目标须按对应逻辑容量准备，也不能因源占用小就准备同等大小的目标盘；目标容量足够还须检查宿主机实际剩余空间。

路径与标识：源镜像与目标镜像路径可不同（如 /data 与 /ssd），经 `--xml` 提供完整目标端 XML 调整 source 路径，但不能改变设备地址等客户机可见配置；XML 的 target dev 是虚拟设备逻辑标识而非目标文件名；NBD 导出名称由服务端关联到块后端，不必等于文件路径或设备名。--copy-storage-inc 要求预先创建目标镜像。（[virsh migrate 参数](https://libvirt.org/manpages/virsh.html#migrate)、[非共享磁盘迁移](https://libvirt.org/migration.html#migration-of-vms-using-non-shared-images-for-disks)）

# 第六部分 关键辨析汇总

以下为本次源码阅读中确认的、最易混淆的概念边界：

| 易混说法 | 确认的理解 |
|---|---|
| 调用 libvirt 库即进入服务进程 | 客户端库先在 virsh 内执行，跨进程发生在 RPC 处 |
| Begin/Perform 的服务端是目标端 | 二者的服务端均为源端 libvirt 服务 |
| 句柄跨进程通用 | 句柄仅在所属进程内有意义，跨进程靠虚拟机标识对应 |
| 建立作业就是创建 QEMU | 作业是管理状态，QEMU 是独立进程 |
| fd 是全局编号 | fd 是本进程访问端点的编号，跨进程须专门传递 |
| cookie 指针转移就是网络发送 | 指针归属转移在本地完成，RPC 才编码传输 |
| SSH 管理连接承载全部数据 | 数据通道独立建立，不能据 SSH 推断数据面已加密 |
| QMP 命令成功即迁移完成 | 仍需跟踪迁移状态与事件 |
| migrate-continue 恢复客户机运行 | 它继续迁移状态机，客户机 CPU 保持暂停 |
| Finish 才开始接收数据 | Perform 时已接收；Finish 确认处理完成 |
| 服务端指针原样返回 virsh | RPC 返回标识，客户端取得自己的句柄 |
| 客户端句柄为空证明目标没运行 | 回复可能丢失，远端执行结果可能不确定 |
| Confirm 成功只暂停源 CPU | 停止并结束源 QEMU 进程，清理运行资源 |
| 停止源 QEMU 就删除磁盘与定义 | 运行实例、持久定义、磁盘是不同层次 |
| Confirm 取消总能恢复源虚拟机 | 取决于原状态、故障原因、资源锁与恢复结果 |
| 五阶段确保所有故障原子回滚 | 回复丢失的不确定性、锁与 post-copy 等需单独分析 |
| XDR 即 gRPC | XDR 是 libvirt RPC 的编码方式 |
| QEMU 迁移数据经 XDR 编码 | QEMU 迁移流使用自身二进制格式 |
| 迁移按整个 RAMBlock 一次传完 | 按页组织；块身份用于定位 |
| ZERO 页表示未使用的内存 | 表示页内容全零，与使用历史无关 |
| EOS 表示一个 RAMBlock 结束 | 表示本段 RAM 记录结束 |
| completed 必然表示客户机运行 | 迁入可 completed 而客户机保持暂停 |
| 机器类型版本即 QEMU 软件版本 | 新 QEMU 可支持旧机器类型，两者不能混同 |
| CPU 配置迁移即寄存器复制 | 配置决定能力，寄存器属于运行状态 |
| 型号相同的物理 CPU 即兼容 | host-passthrough 还受微码、软件、配置影响 |
| 证书私钥直接加密每页内存 | 证书密钥用于身份认证，流量密钥用于数据保护 |
| TLS 验标签后由迁移代码解密 | TLS 完成验证解密后才交出明文 |
| TLS record 等于一页或一个 TCP 包 | 三者分属不同层次，边界不必一致 |
| QMP 承载两端 QEMU 的 TLS 握手 | QMP 配置本机 QEMU；握手走两端迁移连接 |
| 预拷贝半途失败就恢复目标端 | 目标尚未接管时清理未完成实例 |
| 控制失联必须让两端都暂停 | 取决于实际状态与可控性 |
| 重发 Finish 报错即证明首次失败 | 阶段接口不能默认幂等；重发是再次执行，不等于查询 |
| 拿到锁失败即证明目标在运行 | 也可能是锁服务或存储异常 |
| 隔离目标后源端即可恢复运行 | 源端状态停留在暂停时刻，仍须选择一致状态恢复 |
| post-copy 失败即回退源端 | 两端可能各持部分最新状态；连接故障可修复后继续迁移 |
| NBD 自动同步两端磁盘变化 | mirror 组织同步，NBD 只执行远端块操作 |
| NBD cookie 即迁移 cookie | 前者关联请求与回复，后者交换迁移协商信息 |
| 磁盘读取进内存即 RAM 页迁移 | 只是源 QEMU 缓冲区暂存磁盘数据 |
| READY 后磁盘就不再同步 | 后续写入仍持续同步，最终切换时统一收尾 |
| 磁盘作业 Cancel 即迁移失败 | 已 READY 作业的正常收尾也用 cancel 语义 |
| WRITE 成功即已持久化 | 须区分 FLUSH 与 FUA 的持久化语义 |
| 源盘复制走 NBD 即已加密 | 内存与磁盘是独立通道，TLS 须逐通道建立 |
| 客户机空闲块即零数据 | 空闲空间可能残留旧字节 |
| 源镜像实占 8 GiB 目标即 8 GiB | 目标须按虚拟容量准备，另查宿主机剩余空间 |
