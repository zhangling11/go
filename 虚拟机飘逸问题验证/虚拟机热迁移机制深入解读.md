## 1. 本次贯穿的示例与边界

```bash
virsh -c qemu:///system migrate --live vm1 qemu+ssh://hostB/system
```

假设命令在源主机 A 上执行，目标为 B。使用客户端协调的 v3 可扩展参数接口、普通预拷贝热迁移和共享存储。

未指定 P2P、tunnelled、post-copy、并行迁移或磁盘复制；两端支持本次阅读的接口能力，源端支持并使用迁移变更保护。特殊分支只在帮助理解主线时提及。

两个管理地址：

| 地址 | 作用 |
|---|---|
| `qemu:///system` | virsh 到源主机 A 的本机系统级管理连接 |
| `qemu+ssh://hostB/system` | virsh 经 SSH 到目标主机 B 的系统级管理连接 |

`/system` 选择系统级管理实例，不是磁盘目录，也不是某台 VM。

## 2. 先确定代码在哪个进程里执行

```text
源主机 A                                  目标主机 B

virsh 进程
  ├─ 当前线程：执行 cmdMigrate，监控任务
  └─ 工作线程：执行 doMigrate 和客户端协调逻辑
       │                         │
       │ 源管理连接              │ 目标管理连接（SSH）
       ▼                         └───────────────► libvirt 服务进程
libvirt 服务进程                                   │ QMP
  │ QMP                                           ▼
  ▼                                            目标 QEMU 进程
源 QEMU 进程 ═════════ 迁移数据通道 ═══════════════►│
```

- libvirt 服务通常是 `libvirtd` 或模块化的 `virtqemud`；部署中也可能有 `virtproxyd` 转发。
- 服务通常已在运行，也可按需启动。每次 RPC 不会新建一个服务进程。
- “客户端/服务端”描述请求关系，“源端/目标端”描述迁移方向。Begin 的服务端就是源主机 A 的 libvirt 服务。
- libvirt 客户端库的代码运行在 virsh 进程内。调用库函数不自动创建线程或切换进程。
- QEMU 驱动是 libvirt 服务内的代码，不等于独立的 QEMU 进程。

## 3. 从 cmdMigrate 建立目标控制连接

源码：[cmdMigrate](https://github.com/libvirt/libvirt/blob/master/tools/virsh-domain.c#L11854)。

源端管理连接已经可用，保存在 virsh 控制结构的 `priv->conn` 中。命令通过它查找源 VM，取得句柄。

目标连接最初为空：

```c
virshCtrlData data = {
    .dconn = NULL,
    .ctl = ctl,
    .cmd = cmd,
    .eventLoop = eventLoop,
    .ret = -1,
};
```

普通迁移路径中，当前线程先连接目标，再创建工作线程：

```c
dconn = virshConnect(ctl, desturi, false);
if (!dconn)
    goto cleanup;

data.dconn = dconn;

if (virThreadCreate(&workerThread, true, doMigrate, &data) < 0)
    goto cleanup;

virshWatchJob(...);
virThreadJoin(&workerThread);
```

执行顺序：

```text
取得源 VM 句柄 → 建立目标 dconn → 创建工作线程
                                    ├─ 工作线程执行迁移
                                    └─ 当前线程监控并等待退出
```

### 3.1 dconn 如何层层传递

```text
virshConnect() 返回目标连接对象的指针
    → cmdMigrate 中的 data.dconn
    → doMigrate 中的局部 dconn
    → virDomainMigrate3 的形参 dconn
```

这些局部指针变量所在位置不同，但指向同一个客户端连接对象。不是每进入一个函数就重新连接。

### 3.2 线程与结果

- `&data` 可以交给工作线程，因为线程共享进程地址空间；还必须保证对象生命周期及并发访问正确。
- `virThreadJoin()` 等工作线程退出，避免当前函数返回后工作线程还使用其局部上下文。
- 线程创建成功不等于迁移成功；线程正常退出也不等于迁移成功。
- `data.ret` 初始为 `-1`，普通路径中迁移 API 返回非空目标句柄后才设为 `0`。
- `return !data.ret` 将 `0` 转为命令成功，将 `-1` 转为失败。

## 4. SSH 控制连接如何建立

调用链：

```text
virshConnect()
  → virConnectOpenAuth()
    → virConnectOpenInternal()
      → remoteConnectOpen()
        → doRemoteOpen()
          → virNetClientNewSSH()
            → virNetSocketNewConnectSSH()
              → virNetSocketNewConnectCommand()
```

源码：[virshConnect](https://github.com/libvirt/libvirt/blob/master/tools/virsh.c#L102)、[连接 API](https://github.com/libvirt/libvirt/blob/master/src/libvirt.c#L1308)、[SSH 分支](https://github.com/libvirt/libvirt/blob/master/src/remote/remote_driver.c#L1203)。

`virshConnect()` 调用库函数完成连接，并处理认证相关逻辑及 keepalive。`+ssh` 路径启动外部 SSH 子进程。SSH 子进程与迁移工作线程是不同概念。

```text
A：virsh / remote 驱动
       ⇅ 本地 socketpair
A：SSH 子进程
       ⇅ SSH 加密连接
B：sshd 管理的会话
       ⇅
B：virt-ssh-helper 或 nc
       ⇅ 本地 UNIX socket
B：libvirt 服务
```

自动代理模式优先使用目标端 `virt-ssh-helper`，不可用时有 `nc` 兼容路径；实际行为受配置影响。[辅助命令构造](https://github.com/libvirt/libvirt/blob/master/src/rpc/virnetclient.c#L416)

通道建立后，还要完成 libvirt 服务端认证协商，并发送 `REMOTE_PROC_CONNECT_OPEN` 打开服务端管理连接。全部初始化成功后，客户端才返回可用的 `dconn`。

源码：[remoteCallOpen](https://github.com/libvirt/libvirt/blob/master/src/remote/remote_driver.c#L771)、[服务端 ConnectOpen](https://github.com/libvirt/libvirt/blob/master/src/remote/remote_daemon_dispatch.c#L2165)。

## 5. socket、socketpair 与 fd

### 5.1 三者关系

- socket 是内核管理的通信端点。
- fd 是进程文件描述符表里的编号，用于操作该进程持有的端点。
- fd 不是进程编号、网络地址，也不是连接本身。
- 创建 socket 时，内核为进程分配对应的 fd；不是先随意创建一个整数，再把它绑定成连接。
- UNIX socket 用于本机进程通信。这里 `socketpair()` 创建的也是 UNIX socket。

### 5.2 源端：创建两个已连通端点

```c
int sv[2] = { -1, -1 };
socketpair(PF_UNIX, SOCK_STREAM, 0, sv);
```

数组声明本身不创建 socket。`socketpair()` 成功后，两个端点已经连通，fd 写入 `sv[0]`、`sv[1]`：

```text
向 sv[0] 写入 → 从 sv[1] 读取
向 sv[1] 写入 → 从 sv[0] 读取
```

libvirt 将一端接到 SSH 子进程的标准输入和输出：

```c
virCommandSetInputFD(cmd, sv[1]);
virCommandSetOutputFD(cmd, &sv[1]);
virCommandRunAsync(cmd, &pid);
```

virsh 保留 `sv[0]`，关闭自己不再需要的 `sv[1]` 副本。SSH 仍持有另一端的引用。

```text
virsh 的 fd → 端点 X ⇄ 端点 Y ← SSH 标准输入/输出
```

标准输入、输出不一定连接键盘、屏幕，也可以重定向到 socket。

### 5.3 目标端：客户端连接已有监听地址

以 `/run/libvirt/libvirt-sock` 为示意，实际路径取决于部署：

```text
服务：socket → bind 路径 → listen → accept 得到通信 fd
辅助程序：socket 得到自己的 fd → connect 服务路径
```

服务的监听 fd 负责接待新连接，`accept()` 返回的新 fd 负责与某个客户端收发数据。使用 socket 激活时，监听端点也可由 systemd 创建并交给服务。

路径用于找到服务，不是请求内容的磁盘中转文件。辅助程序不会取得服务端的 fd 数字来直接使用，而是持有自己的通信端点。

### 5.4 实际发送字节的源码

```text
socketpair(..., sv)
    → virNetSocketNew(..., sv[0], ...)
    → sock->fd = fd
    → write(sock->fd, buf, len)
```

`virNetSocketNew()` 包装已有 fd，不是再创建一对内核 socket。`write()` 返回本次实际写入字节数，可能小于请求长度；写入成功不代表远端业务操作成功。流式 socket 不保留每次写入的消息边界，RPC 层负责组装完整消息。

源码：[socketpair 与子进程连接](https://github.com/libvirt/libvirt/blob/master/src/rpc/virnetsocket.c#L775)、[保存 fd](https://github.com/libvirt/libvirt/blob/master/src/rpc/virnetsocket.c#L270)、[write](https://github.com/libvirt/libvirt/blob/master/src/rpc/virnetsocket.c#L1812)。

参考：[socketpair 手册](https://man7.org/linux/man-pages/man2/socketpair.2.html)、[UNIX socket 手册](https://man7.org/linux/man-pages/man7/unix.7.html)。

## 6. doMigrate：把命令转成 API 输入

源码：[doMigrate](https://github.com/libvirt/libvirt/blob/master/tools/virsh-domain.c#L11444)。

工作线程从上下文取出已有连接和命令：

```c
virshCtrlData *data = opaque;
const vshCmd *cmd = data->cmd;
virConnectPtr dconn = data->dconn;
```

### 6.1 flags 与 params 是独立信息

```c
unsigned int flags = 0;
virTypedParameterPtr params = NULL;
int nparams = 0;
int maxparams = 0;
```

| 变量 | 含义 |
|---|---|
| `flags` | 迁移行为开关的位集合 |
| `params` | 参数数组，每项有名称、类型和值 |
| `nparams` | 数组中有效项数，不统计 flags 中的位 |
| `maxparams` | 构建数组时分配的容量 |

`--live` 通过映射表变成：

```c
flags |= VIR_MIGRATE_LIVE;
```

带宽等带值参数通过 `virTypedParamsAddULLong()` 等函数加入数组。

只有 `--live` 的示例，在调用 API 前可以是：

```text
flags = VIR_MIGRATE_LIVE
params = NULL
nparams = 0
```

数组为空不意味着 flags 全部为零。

### 6.2 调用迁移 API

```c
if ((ddom = virDomainMigrate3(dom, dconn, params, nparams, flags)))
    data->ret = 0;
```

这是工作线程里的普通函数调用，不会因调用这个 API 再自动创建一个工作线程。

## 7. virDomainMigrate3：校验与接口选择

源码：[virDomainMigrate3](https://github.com/libvirt/libvirt/blob/master/src/libvirt-domain.c#L4263)。

主要步骤：

1. 清除旧错误，检查源 VM 句柄。
2. 检查源、目标管理连接不能只读。
3. 检查迁移选项冲突及该 API 不支持的模式。
4. 读取可选参数。
5. 查询双方驱动支持的迁移接口能力。
6. 选择对应协调函数，返回目标 VM 句柄或 `NULL`。

注意 `domain->conn->flags`、`dconn->flags` 是连接属性；形参 `flags` 是迁移选项，不能混淆。

```c
rc_src = VIR_DRV_SUPPORTS_FEATURE(...源连接..., VIR_DRV_FEATURE_MIGRATION_PARAMS);
rc_dst = VIR_DRV_SUPPORTS_FEATURE(...目标连接..., VIR_DRV_FEATURE_MIGRATION_PARAMS);
```

负数表示查询错误，零表示不支持，正数表示支持。“双方支持”是接口能力判断，不代表 CPU、设备、资源等所有迁移条件已验证通过。

双方支持后：

```c
ddomain = virDomainMigrateVersion3Params(domain, dconn, params, nparams, flags);
```

即使 `nparams == 0`，也可以选择这个接口。

### 7.1 domain、dconn、ddomain

| 变量 | 含义 |
|---|---|
| `domain` | 已有的源 VM 句柄 |
| `dconn` | 已建立的目标管理连接 |
| `ddomain` | 用来保存迁移后返回的目标 VM 句柄 |

`virDomainPtr ddomain = NULL` 只是声明并初始化一个局部指针，不创建目标虚拟机。API 返回 `NULL` 也不能单独证明目标端从未创建过 VM，仍需看失败阶段和清理结果。

## 8. 进入五阶段协调函数

```text
virDomainMigrate3()
  → virDomainMigrateVersion3Params()
    → virDomainMigrateVersion3Full()
```

包装函数调用：

```c
return virDomainMigrateVersion3Full(domain, dconn,
                                    NULL, NULL, NULL, 0,
                                    params, nparams, true, flags);
```

`true` 对应 `useParams`：使用参数数组接口。三个 `NULL` 和 `0` 对应旧式独立参数 XML、名称、URI、带宽，不会覆盖参数数组里的用户设置。

`Full()` 首先检查五阶段函数入口是否存在，然后复制参数数组。后续会向这个副本中添加或替换 XML、迁移 URI 等参数。

源码：[Params 包装](https://github.com/libvirt/libvirt/blob/master/src/libvirt-domain.c#L3589)、[Full 协调函数](https://github.com/libvirt/libvirt/blob/master/src/libvirt-domain.c#L3277)。

## 9. RPC、指针与驱动分发

### 9.1 为什么不能跨进程直接传 domain 指针

普通进程各自拥有独立虚拟地址空间。virsh 中某个地址对应句柄，在服务进程里同一数值可能没有映射或对应其他数据。

所以客户端提取 VM 的 ID、名称、UUID 等标识，而不是发送指针让服务端解引用：

```text
virsh 的 domain 对象
  → 提取身份信息，编码 RPC
  → 服务端取得自己的 dom 句柄
  → QEMU 驱动找到内部 vm 对象
```

两边句柄代表同一台 VM，但不是同一个跨进程 C 对象，也不代表创建了两台 VM。

### 9.2 函数指针决定具体执行谁

```c
conn->driver->domainMigrateBegin3Params(...);
```

先从连接里取驱动，再从驱动里取函数指针并调用：

```c
/* 客户端 remote 驱动 */
.domainMigrateBegin3Params = remoteDomainMigrateBegin3Params,

/* 服务端 QEMU 驱动 */
.domainMigrateBegin3Params = qemuDomainMigrateBegin3Params,
```

同名成员可以保存不同的函数地址。不是依靠名字相似自动关联，也不是调用一次函数指针就跨进程；跨进程发生在 remote 驱动发送 RPC 的过程中。

## 10. Begin：源端检查、保护和生成信息

### 10.1 调用链

```text
virsh 工作线程：virDomainMigrateVersion3Full()
  → remoteDomainMigrateBegin3Params()
  → 源端管理连接上的 RPC
源端 libvirt 服务：
  remoteDispatchDomainMigrateBegin3Params()
    → virDomainMigrateBegin3Params()
      → qemuDomainMigrateBegin3Params()
        → qemuMigrationSrcBegin()
          → qemuMigrationSrcBeginPhase()
            → qemuMigrationSrcBeginXML()
```

本例 Begin 走 A 上的本地管理连接，不走到 B 的 SSH 连接。

客户端序列化参数；服务端反序列化，取得自己的句柄，调用驱动。返回时把 XML、cookie 放入 RPC 回复，客户端再解码。

源码：[客户端 Begin](https://github.com/libvirt/libvirt/blob/master/src/remote/remote_driver.c#L6471)、[服务端分发](https://github.com/libvirt/libvirt/blob/master/src/remote/remote_daemon_dispatch.c#L5668)、[QEMU 驱动 Begin](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_driver.c#L11424)。

### 10.2 源端迁移作业与变更保护

`qemuDomainMigrateBegin3Params()` 检查 flags、参数、权限，并通过 `qemuDomainObjFromDomain()` 找到内部 VM 对象。

启用 `VIR_MIGRATE_CHANGE_PROTECTION` 时：

```c
qemuMigrationJobStart(vm, VIR_ASYNC_JOB_MIGRATION_OUT, flags);
```

job 是操作管理状态，不是新线程或新进程。它按规则协调冲突管理操作，并非禁止所有查询，也不是覆盖两端的分布式锁。

Begin 返回与后续 Perform 到来之间有间隔。作业跨 API 保留，防止这段期间发生不允许的冲突操作；正常到 Confirm 收尾，失败时可提前清理。

本层还记录迁移前状态、检查活动状态，再进入 BeginPhase。记录状态不是备份 VM 内存。

源码：[qemuMigrationSrcBegin](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L3063)。

### 10.3 BeginPhase 检查与输出

- 将迁出作业阶段推进为 `BEGIN3`。
- `qemuMigrationSrcIsAllowed()` 检查迁移阻塞条件，包括按能力向 QEMU 查询 blocker、检查活动 block job 和某些设备限制。
- 普通安全路径调用 `qemuMigrationSrcIsSafe()` 检查相关磁盘条件。
- 检查特殊选项组合，决定 cookie 需要携带的信息类别。
- 调用 BeginXML 生成输出。

`cookieFlags` 控制元数据类别，`flags` 控制迁移行为；设置锁状态类别不等于获得锁。

| 输出 | 用途 |
|---|---|
| `dom_xml` | 描述目标需要准备的 VM 配置 |
| `cookieout`、长度 | 携带按条件生成的锁管理状态、CPU、迁移能力等附加信息 |

XML 的内存配置是容量和布局等，不是 RAM 内容。cookie 也不是 RAM 数据或认证令牌。

提供自定义 XML 时会解析并检查 ABI 兼容；未提供时依据当前 VM 配置生成迁移 XML。

源码：[BeginPhase](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L2793)、[BeginXML](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L2712)。

## 11. 客户端将 Begin 结果交给 Prepare

Begin 结果先返回 virsh 协调代码，不是源端服务直接调用目标 Prepare。

客户端查询源 VM 状态；若本来暂停且不是 post-copy 恢复，则加上保持暂停的标志。查询状态不会暂停 CPU。

```c
destflags = flags & ~(VIR_MIGRATE_ABORT_ON_ERROR |
                      VIR_MIGRATE_AUTO_CONVERGE);
```

整理目标端标志，随后转移 cookie：

```c
cookiein = g_steal_pointer(&cookieout);
cookieinlen = cookieoutlen;
cookieoutlen = 0;
```

概念上等同于把指针交给 `cookiein`，并将 `cookieout` 设为 `NULL`。没有复制 cookie 内容，也没有因这句赋值发送网络数据。

然后将 XML 加入参数副本：

```c
virTypedParamsReplaceString(&params, &nparams,
                            VIR_MIGRATE_PARAM_DEST_XML, dom_xml);
```

因此原先为空的参数数组此时会有 XML 项。最后通过 `dconn` 调用目标 Prepare。

源码：[客户端 Prepare 调用](https://github.com/libvirt/libvirt/blob/master/src/libvirt-domain.c#L3353)。

## 12. Prepare：目标接收环境准备

### 12.1 调用链

```text
客户端经 dconn 发送 Prepare RPC
  → 目标服务端分发
    → qemuDomainMigratePrepare3Params()
      ├─ qemuMigrationAnyPrepareDef()
      └─ qemuMigrationDstPrepareDirect()
          → qemuMigrationDstPrepareAny()
            → qemuMigrationDstPrepareFresh()
              → qemuMigrationDstPrepareActive()
```

### 12.2 配置、对象、作业和进程是四件事

1. 从 `params` 取出 XML，检查权限并解析为 `virDomainDef *def`。
2. 确定迁移数据地址；用户未提供时从端口池分配端口并生成 URI。
3. 解析 cookie，获得迁移元数据对象 `mig`。
4. `virDomainObjListAdd()` 处理配置归属、冲突检查，取得内部 VM 对象 `vm`；可能利用已有非活动对象，不是无条件新增。
5. 建立 `VIR_ASYNC_JOB_MIGRATION_IN` 作业，标记 Prepare 阶段。
6. 准备存储、VM 和宿主机资源。
7. `qemuProcessLaunch()` 启动用于迁入的目标 QEMU 进程。

| 名称 | 含义 |
|---|---|
| `def` | 解析后的配置对象 |
| `vm` | libvirt 内部的 VM 管理对象 |
| `job` | 操作状态与并发协调机制 |
| QEMU 进程 | 承载客户机状态的独立进程 |

建立 job 不等于启动 QEMU；启动 QEMU 不等于让客户机 CPU 执行业务。

`PrepareDirect` 的名称也不意味着用户指定了 virsh `--direct`；当前普通原生迁移同样进入此函数。

源码：[驱动入口](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_driver.c#L11524)、[解析配置](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L4067)、[地址准备](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L3913)、[PrepareFresh](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L3500)、[PrepareActive](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L3313)。

### 12.3 通知 QEMU 接收：migrate-incoming

```text
qemuMigrationDstRun()
  → qemuMonitorMigrateIncoming()
    → qemuMonitorJSONMigrateIncoming()
      → QMP migrate-incoming
```

示意：

```json
{
  "execute": "migrate-incoming",
  "arguments": {
    "uri": "tcp:0.0.0.0:49152",
    "exit-on-error": false
  }
}
```

地址仅为示意；`exit-on-error` 依能力设置，目的是使 libvirt 可以在错误后查询、报告情况。目标监听地址可与返回源端的可达地址不同。

对于迁入 job，`qemuMigrationDstRun()` 在命令处理成功后返回，不在 Prepare 中等待全部数据。否则客户端等 Prepare、目标等数据、源端又等客户端发 Perform，会无法推进。

源码：[DstRun](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L2478)、[QMP 命令构造](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_monitor_json.c#L7589)。

### 12.4 Prepare 完成后的状态

```text
源端：客户机仍运行。
目标：QEMU 已启动，准备接收，客户机尚未执行业务。
客户端：收到成功结果、新 cookie，以及按需生成的数据 URI。
```

目标迁入 job 正常保留到 Finish。Prepare 不返回迁移完成后的目标 VM 句柄。失败时按实际进度清理；客户端会按需通知源端取消已经建立的受保护作业。

## 13. 客户端将 Prepare 结果交给 Perform

客户端把返回的数据 URI 放入 `VIR_MIGRATE_PARAM_URI`，释放已用完的旧 cookie，将 Prepare 输出 cookie 转为 Perform 输入。

```c
ret = domain->conn->driver->domainMigratePerform3Params(
    domain, NULL, params, nparams,
    cookiein, cookieinlen,
    &cookieout, &cookieoutlen,
    flags | protection);
```

- 使用 `domain->conn`，所以请求发给源端。
- 第二个参数 `NULL` 是 `dconnuri`：普通客户端协调模式无需让源端接管目标管理连接。
- 源端需要的数据地址在 `params` 中，与目标管理地址不同。

源码：[客户端 Perform 调用](https://github.com/libvirt/libvirt/blob/master/src/libvirt-domain.c#L3398)。

## 14. Perform：源端执行与传输

### 14.1 主调用链

```text
qemuDomainMigratePerform3Params()
  → qemuMigrationSrcPerform()
    → qemuMigrationSrcPerformPhase()
      → qemuMigrationSrcPerformNative()
        → qemuMigrationSrcRun()
          ├─ qemuMigrationSrcStart()
          ├─ 等待和切换协调
          └─ 统计、cookie 和收尾
```

驱动检查参数、权限，取得内部 `vm`。启用变更保护时，Perform 检查 Begin 留下的迁出 job 仍有效；否则此时再申请迁出 job。然后阶段变为 `PERFORM3`。

源码：[驱动入口](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_driver.c#L11762)、[PerformPhase](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L6448)。

### 14.2 当前 TCP 路径：libvirt 建连接，QEMU 发数据

`qemuMigrationSrcPerformNative()` 解析目标 URI，将协议、主机名和端口放入 `spec`。`spec` 是连接方式的描述，不是连接本身。

未开启 RDMA、并行或 post-copy 的普通 TCP 路径选择 `MIGRATION_DEST_CONNECT_HOST`：

```text
qemuMigrationSrcStart()
  → qemuMigrationSrcConnect()
    → virNetSocketNewConnectTCP()
    → 取得用于交给 QEMU 的 fd
    → spec 改为 MIGRATION_DEST_FD
```

连接的是目标迁移数据接收端，不是 SSH 管理端口。

随后：

```c
qemuMonitorSendFileHandle(mon, "migrate", fd);
qemuMonitorJSONMigrate(mon, flags, "fd:migrate");
```

通过本地 fd 传递机制，QEMU 获得对同一个 socket 的引用；不是把 libvirt 的 fd 数字直接当作 QEMU 的 fd。两进程里的编号可以不同。

示意 QMP 命令：

```json
{
  "execute": "migrate",
  "arguments": {
    "resume": false,
    "uri": "fd:migrate"
  }
}
```

`fd:migrate` 引用已交给 QEMU 的连接。交付后关闭 libvirt 自己的相应 fd 引用，不会关闭 QEMU 仍持有的引用。

```text
libvirt 建连接、发 QMP 命令
    ↓
源 QEMU ═══════ 迁移运行状态 ═══════► 目标 QEMU
```

其他模式可以由 QEMU 自己建立连接，因此“谁建连接”和“谁发数据”必须分别判断。当前原生路径下数据不经 virsh 中转。

源码：[PerformNative](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L5391)、[SrcConnect](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L4569)、[SrcStart](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L4814)、[交付 fd](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_monitor.c#L2255)、[migrate 命令](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_monitor_json.c#L3464)。

## 15. Perform 如何等待 QEMU

### 15.1 命令成功不等于迁移完成

QMP 命令回复表示该命令的处理结果。VM 运行状态传输还会继续，libvirt 需要跟踪后续迁移状态。

```text
源端 libvirt 的 Perform 处理线程        源 QEMU
       发 migrate 命令 ───────────────►│
       收到命令回复 ◄──────────────────│
       等待状态通知                   持续传数据
       被通知后重新判断 ◄──────── 状态变化事件
```

### 15.2 检查、等待、被唤醒、再检查

核心循环：

```c
while ((rv = qemuMigrationAnyCompleted(vm, asyncJob, dconn, flags)) != 1) {
    if (rv < 0)
        return rv;
    if (qemuDomainObjWait(vm) < 0)
        ...;
}
```

- `qemuMigrationAnyCompleted()` 判断是否满足本次等待条件。
- `qemuDomainObjWait()` 让当前处理线程等待，不是暂停客户机，也不是停住整个 libvirt 服务。
- QMP 事件处理逻辑更新 `privJob->stats.mig.status`，再 `virDomainObjBroadcast(vm)` 唤醒等待者。
- 被唤醒不代表完成，必须再次检查。
- 此辅助判断返回 `1` 表示满足等待条件，等待包装函数成功最终返回 `0`；不要混用两个函数的返回值语义。

源码：[等待函数](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L2252)、[状态判断](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L2150)、[事件处理](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_process.c#L1670)。

### 15.3 第一次等待可能只到 pre-switchover

```c
waitFlags = QEMU_MIGRATION_COMPLETED_PRE_SWITCHOVER;
```

它允许此次等待在切换前的迁移暂停点返回。设置等待标志本身不会命令 QEMU 暂停。

`pre-switchover` 是设备状态序列化前的协调点，源客户机 CPU 已停止；libvirt 可在此处理必要工作，例如非共享存储块作业收尾。

```text
第一次等待成功返回
    ├─ 可能到达 pre-switchover
    └─ 也可能已经到达 QEMU 迁移完成状态
```

因此不能仅凭第一次 `rc == 0` 就宣布整次迁移成功。这里的作业 `PAUSED` 也不等于“用户任意暂停 VM 就算完成”。

源码：[第一次等待](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L5187)。

## 16. 等待 STOP 事件：实际暂停与管理记录同步

QEMU 暂停源客户机 CPU 后发出 STOP 事件。libvirt 收到并处理事件，才更新内部 VM 状态，两者可能有短暂间隔。

```c
while (virDomainObjGetState(vm, NULL) == VIR_DOMAIN_RUNNING) {
    priv->signalStop = true;
    rc = qemuDomainObjWait(vm);
    priv->signalStop = false;
    if (rc < 0)
        goto error;
}
```

这段没有发送停 CPU 命令，只是等待管理状态更新。如果 STOP 已处理，则直接跳过循环。

事件处理中的关键动作包括：

```c
virDomainObjSetState(vm, VIR_DOMAIN_PAUSED, reason);
virDomainLockProcessPause(driver->lockManager, vm, &priv->lockState);
```

它更新暂停状态、通知等待者，并请求锁管理器处理暂停时的资源锁和状态保存。具体锁行为取决于插件；失败可能记录警告，因此不能仅凭走过这段代码证明所有锁都已成功转移。

迁移 job 与资源锁不是同一件事。等待 STOP 不等于销毁源 QEMU，也不证明目标端已经取得资源锁。

源码：[STOP 等待](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L5206)、[STOP 事件处理](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_process.c#L824)。

## 17. Perform 的继续与收尾

如果迁移仍停在协调点：

```c
qemuMigrationSrcContinue(vm,
                         QEMU_MONITOR_MIGRATION_STATUS_PRE_SWITCHOVER,
                         VIR_ASYNC_JOB_MIGRATION_OUT);
```

对应 QMP：

```json
{
  "execute": "migrate-continue",
  "arguments": { "state": "pre-switchover" }
}
```

继续的是迁移流程，不是恢复源客户机 CPU 执行业务。

随后：

```c
waitFlags ^= QEMU_MIGRATION_COMPLETED_PRE_SWITCHOVER;
```

这个位此前已设置，此处异或将它清除，再调用等待函数。在当前普通预拷贝路径中，这次等待后续 QEMU 迁移完成或错误。若首次已经完成，就不会走此分支。

正常成功后：

1. 更新迁移时间、停顿时间等统计。
2. 整理后续阶段需要的新 cookie，数据内容不是 VM 内存。
3. 下层成功返回到 `qemuMigrationSrcPerformPhase()`。
4. 标记 `PERFORM3_DONE`，继续保留迁出 job。
5. RPC 结果回到 virsh 协调代码。

当前源码中，部分收尾 cookie 编码失败会记录警告，不应把所有元数据编码都理解成必然导致整次迁移失败的硬条件。

源码：[继续与收尾](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L5223)、[PerformPhase 成功路径](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L6497)。

## 18. Perform 返回时的阶段状态

在当前普通预拷贝成功路径中：

| 位置 | Perform 返回时的状态 |
|---|---|
| 源 QEMU | 进程仍在，客户机 CPU 暂停 |
| 源端迁出 job | 保留，等待后续确认收尾 |
| 目标端 | 还需后续检查接收、恢复结果并完成运行切换 |
| virsh | 收到 Perform 结果，准备推进后续协调 |

三种成功应分开：

- **migrate 命令成功**：QMP 启动命令没有报告失败。
- **Perform 成功**：源端本阶段的传输与协调流程成功结束。
- **整次迁移及业务可用**：还涉及后续阶段、实际资源状态和业务验证。

首次阅读停在这里。2026-11-01 补充的 Finish、Confirm 见第 20 节起。本文仍未展开 Perform 的全部失败、取消及 post-copy 恢复分支，不能把正常成功路径直接当作所有故障情况下的恢复保证。

## 19. 复习时最容易混淆的概念

| 容易混淆的说法 | 本次确认的理解 |
|---|---|
| 工作线程建立目标 dconn | 普通路径中，当前线程先建立 dconn，再创建工作线程 |
| 调用 libvirt 库就是进入服务进程 | 客户端库先在 virsh 内执行，跨进程发生在 RPC 通信处 |
| 服务端就是目标端 | Begin、Perform 的服务端是源端 libvirt 服务 |
| 同名指针跨进程指向同一对象 | 句柄在各进程内独立，通过 VM 标识对应同一 VM |
| 建立 job 就是创建 QEMU | job 是管理状态；QEMU 是独立进程 |
| 建立 vm 对象就是运行客户机 | 管理对象、QEMU 进程、客户机 CPU 运行是不同层次 |
| fd 是 socket 本身或全局编号 | fd 是本进程访问端点的编号 |
| 传 fd 就是把整数发过去 | 需要描述符传递机制，使接收进程获得内核对象引用 |
| params 为空，flags 必然为零 | 参数数组与开关位集合彼此独立 |
| cookie 指针转换就是网络发送 | g_steal_pointer 是本地归属转移；RPC 才编码传输 |
| SSH 管理连接承载全部 VM 数据 | 本例 QEMU 数据通道独立，不能据 SSH 推断数据通道已加密 |
| QMP 命令成功就是迁移完成 | 还要跟踪迁移状态和事件 |
| WaitForCompletion 返回就是全程结束 | 返回条件由等待标志决定，可能先到协调点 |
| migrate-continue 是恢复客户机 CPU | 它继续迁移状态机，当前源客户机 CPU 仍暂停 |
| Perform 结束立即删除源 VM | 源 QEMU 和迁出 job 正常保留，等待后续确认 |

## 20. Finish 请求：virsh 把源端结果交给目标端

执行位置仍是 virsh 工作线程中的 `virDomainMigrateVersion3Full()`。Perform 返回后，客户端并未退出迁移 API，而是继续协调后续阶段。

```c
cancelled = ret < 0 ? 1 : 0;
```

这里 `ret` 是 Perform 的结果。`cancelled == 0` 表示源端报告成功，目标端应继续完成；`cancelled == 1` 表示前一阶段失败，要求目标端处理取消和清理。它不只表示用户主动取消。

### 20.1 输出 cookie 转为下一阶段输入

```c
VIR_FREE(cookiein);
cookiein = g_steal_pointer(&cookieout);
cookieinlen = cookieoutlen;
cookieoutlen = 0;
```

这次的 `cookieout` 来自源端 Perform；转为 `cookiein` 后交给目标端 Finish。它仍通过独立的 cookie 参数传递，不是放入 `params` 数组。上述操作只改变 virsh 内部指针所有权，之后的 RPC 才负责发送内容。

### 20.2 指定目标名称并通过 dconn 发出请求

若 `params` 中没有 `VIR_MIGRATE_PARAM_DEST_NAME`，协调代码补入 `domain->name`。若用户指定了目标名称，则沿用指定值。

```c
ddomain = dconn->driver->domainMigrateFinish3Params(
    dconn, params, nparams, cookiein, cookieinlen,
    &cookieout, &cookieoutlen, destflags, cancelled);
```

| 变量 | Finish 调用中的意义 |
|---|---|
| `dconn` | virsh 已建立的目标端控制连接 |
| `params` / `nparams` | 迁移参数及数量，包含目标名称 |
| `cookiein` / `cookieinlen` | Perform 返回的协商、统计等信息 |
| `cookieout` / `cookieoutlen` | 接收 Finish 新产生的 cookie |
| `destflags` | 适用于目标端的迁移标志 |
| `cancelled` | 根据 Perform 结果得出的取消标志 |
| `ddomain` | 成功回复后，virsh 获得的目标虚拟机句柄 |

源码：[客户端 Finish 调用](https://github.com/libvirt/libvirt/blob/master/src/libvirt-domain.c#L3461)。

## 21. 目标端如何进入 Finish 并找到已有 vm

```text
virsh：remoteDomainMigrateFinish3Params()
    │ RPC，使用已有 dconn
    ▼
目标端 libvirt：remoteDispatchDomainMigrateFinish3Params()
    → virDomainMigrateFinish3Params()
    → qemuDomainMigrateFinish3Params()
    → qemuMigrationDstFinish()
```

服务端反序列化参数，再调用内部接口及 QEMU 驱动。服务端连接对象不是 virsh 指针跨主机复制过去的。

驱动入口先检查 flags 和 typed parameters，再提取目标名称：

```c
virTypedParamsGetString(params, nparams,
                        VIR_MIGRATE_PARAM_DEST_NAME, &dname);
vm = virDomainObjListFindByName(driver->domains, dname);
```

名称是查找依据。找到的 `vm` 是 **Prepare 创建并加入目标端列表的管理对象**，不是 Perform 新建的。找不到时报告错误，并尝试报告已记录的目标端迁移错误。通过 ACL 检查后进入：

```c
return qemuMigrationDstFinish(driver, dconn, vm,
                              cookiein, cookieinlen,
                              cookieout, cookieoutlen,
                              flags, cancelled, true);
```

最后两个实参在被调用函数中叫 `retcode` 和 `v3proto`：`retcode` 接收取消标志，不是未经转换的 Perform 返回值；`true` 表示 v3 协议。

源码：[RPC 分发](https://github.com/libvirt/libvirt/blob/master/src/remote/remote_daemon_dispatch.c#L5902)、[内部接口](https://github.com/libvirt/libvirt/blob/master/src/libvirt-domain.c#L5519)、[QEMU 驱动入口](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_driver.c#L11921)。

## 22. Finish 检查迁入作业和前一阶段结果

`qemuMigrationDstFinish()` 先检查：

```c
if (!qemuMigrationJobIsActive(vm, VIR_ASYNC_JOB_MIGRATION_IN))
    goto cleanup;
```

找到 `vm` 不等于其迁入作业仍有效。此前错误清理可能已经结束 job。普通 v3 路径把阶段推进到 `QEMU_MIGRATION_PHASE_FINISH3`，移除 Prepare 的临时清理回调，由 Finish 接管收尾。

在线迁移进入 `qemuMigrationDstFinishActive()`，主要检查：

1. 解析输入 cookie，取得 `qemuMigrationCookie *mig`。
2. 若 `retcode != 0`，检查目标迁移错误并进入失败处理。
3. 检查 `virDomainObjIsActive(vm)`，确认目标实例没有意外退出。
4. 普通新迁移进入 `qemuMigrationDstFinishFresh()`。

这里 **active 不等于客户机 CPU 正在执行**。目标 QEMU 进程已在 Prepare 启动，迁入时可以 active 且暂停。它不能被描述为“虚拟机已经关机”。

源码：[DstFinish](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L7087)、[DstFinishActive](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L6978)。

## 23. 等待目标接收完成，再刷新设备状态

`qemuMigrationDstFinishFresh()` 先处理相关网络端口配置、NBD 接收服务、virtio 通道和 Guest Agent 连接。具体动作取决于设备和迁移配置；共享存储示例不涉及 NBD 磁盘复制，有 Guest Agent 配置才有相应连接需求。

只有指定 `VIR_MIGRATE_PERSIST_DEST` 时才走目标持久配置保存分支。`--live` 本身不表示必须保存目标持久定义。

核心等待是：

```c
qemuMigrationDstWaitForCompletion(vm,
                                  VIR_ASYNC_JOB_MIGRATION_IN,
                                  !!(flags & VIR_MIGRATE_POSTCOPY));
```

本例未开启 post-copy，最后一个参数为 `false`。

```text
Prepare：目标准备接收
Perform：源端发送，目标端接收和恢复状态
Finish：确认目标 QEMU 已处理完迁移数据
```

不是进入 Finish 才开始接收数据。源端报告发送完成不能替代目标端对自己处理结果的确认；若目标早已完成，等待立即通过。

等待函数的核心：

```c
while ((rv = qemuMigrationAnyCompleted(vm, asyncJob, NULL, flags)) != 1) {
    if (rv < 0 || qemuDomainObjWait(vm) < 0)
        return -1;
}
```

处理请求的 libvirt 线程等待状态变化，目标 QEMU 可以继续工作；唤醒后重新检查。完成后执行：

```c
qemuProcessRefreshState(vm, VIR_ASYNC_JOB_MIGRATION_IN);
```

这是刷新 libvirt 对设备实际状态的记录，不是再创建一遍设备。v3 路径中这些关键检查失败会返回错误，不会继续正常恢复 CPU。

源码：[DstFinishFresh](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L6849)、[目标等待函数](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L2297)。

## 24. 恢复客户机 CPU：资源锁、cont 和 RESUME

没有 `VIR_MIGRATE_PAUSED` 时，Finish 调用：

```c
qemuProcessStartCPUs(driver, vm,
                     VIR_DOMAIN_RUNNING_MIGRATED,
                     VIR_ASYNC_JOB_MIGRATION_IN);
```

有该标志时，成功迁移也可以让目标保持暂停。这里恢复的是客户机 CPU 执行，不是创建新的 QEMU 或“CPU 进程”。

### 24.1 先处理网络设备和资源锁

`qemuProcessStartCPUs()` 的关键顺序：

```c
virDomainInterfaceStartDevices(vm->def);
virDomainLockProcessResume(driver->lockManager, cfg->uri,
                           vm, priv->lockState);
```

实际源码检查每一步错误；网络设备启用或获取资源锁失败，就返回，不发送后面的 `cont`。

`virDomainLockProcessResume()` 内部调用 `virLockManagerAcquire()`。这个 Resume 恢复的是资源锁使用，不是 CPU。具体保护取决于所配置的锁管理插件及存储环境，不能仅凭存在调用就宣称获得跨主机互斥保证。

| 机制 | 用途 |
|---|---|
| migration job | libvirt 内部迁移状态及冲突操作管理 |
| 资源锁/租约 | 由锁管理器协调磁盘等资源的使用 |

锁获取失败保留 `priv->lockState` 供重试；成功后释放这份保存的数据，不代表此时把刚获取的锁释放掉。

### 24.2 通过已有 QMP 通道发 cont

```c
priv->runningReason = reason;
qemuDomainObjEnterMonitorAsync(vm, asyncJob);
ret = qemuMonitorStartCPUs(priv->mon);
qemuDomainObjExitMonitor(vm);
```

这是简化顺序，实际源码包含错误分支。`EnterMonitorAsync` 负责在作业约束下进入 monitor 访问和同步，不是新建进程。

```text
qemuMonitorStartCPUs()
    → qemuMonitorJSONStartCPUs()
    → qemuMonitorJSONMakeCommand("cont", NULL)
```

核心 QMP 请求：

```json
{"execute": "cont"}
```

| 命令 | 含义 |
|---|---|
| `migrate-continue` | 继续暂停在特定协调点的迁移流程 |
| `cont` | 恢复客户机 CPU 执行 |

### 24.3 根据 RESUME 事件更新管理状态

`priv->runningReason` 先记录“因迁移而运行”的原因；实际状态更新由 `qemuProcessHandleResume()` 处理：

```c
virDomainObjSetState(vm, VIR_DOMAIN_RUNNING, reason);
```

它还保存状态、产生生命周期事件。命令回复和异步事件是不同消息：

```text
目标 libvirt ── cont ──→ 目标 QEMU
目标 libvirt ←─ RESUME ─ 目标 QEMU
```

若进入 monitor 或恢复命令失败，`release:` 分支尝试释放已获取的资源锁、保存锁状态，并返回失败。

源码：[StartCPUs](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_process.c#L3447)、[资源锁获取](https://github.com/libvirt/libvirt/blob/master/src/locking/domain_lock.c#L212)、[QMP cont](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_monitor_json.c#L1551)、[RESUME 处理](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_process.c#L881)。

## 25. Finish 收尾、结束迁入 job 并返回句柄

### 25.1 服务端句柄不是新的 VM

`qemuMigrationDstFinishFresh()` 整理统计并成功返回后，`qemuMigrationDstFinishActive()` 取得服务端句柄：

```c
dom = virGetDomain(dconn, vm->def->name, vm->def->uuid, vm->def->id);
```

这不是创建虚拟机，而是以现有 VM 的名称、UUID、ID 取得 API 层句柄。`vm` 是内部管理对象，`dom` 是服务端 API 句柄，二者也不等于客户端的 `ddomain`。

然后编码输出 cookie，包含迁移统计信息。这一处编码失败记录警告，不直接跳到失败分支。

### 25.2 成功收尾

`qemuMigrationDstComplete()` 负责保存状态、移除迁入期间的连接关闭自动销毁回调、重置迁移参数，并处理端口分配记录、内存锁定限制等临时状态。

移除自动销毁回调，意味着不再因为此前关联的控制连接关闭而自动销毁已成功迁入的 VM；这不等于把 VM 保存成持久定义。

返回外层 `qemuMigrationDstFinish()` 后，普通成功路径执行：

```c
qemuMigrationJobFinish(vm);
```

目标迁入 job 到此结束，QEMU 继续保留。外层还释放之前保留的迁移端口分配、清理临时字段，并 `virDomainObjEndAPI(&vm)` 释放本次 API 的对象锁/引用；不是销毁正在运行的 VM。

### 25.3 RPC 返回的是标识，不是指针

服务端 RPC 分发函数：

```c
make_nonnull_domain(&ret->dom, dom);
ret->cookie_out.cookie_out_len = cookieoutlen;
ret->cookie_out.cookie_out_val = cookieout;
```

客户端 remote 驱动收到成功回复后：

```c
rv = get_nonnull_domain(dconn, ret.dom);
```

```text
目标内部 vm
    → 服务端 API 句柄 dom
    → RPC 中的名称、UUID、ID 等标识
    → virsh 本地目标句柄 ddomain
```

源码：[目标成功收尾](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L6747)、[客户端 Finish 返回](https://github.com/libvirt/libvirt/blob/master/src/remote/remote_driver.c#L6713)。

## 26. 为什么 ddomain 为 NULL 不证明目标未运行

RPC 报错有可能只表示没有确认到结果，而不是远端没有执行成功。

```text
virsh 发 Finish 请求 → 目标执行成功，恢复客户机运行
                            ↓
                       成功回复传输失败
                            ↓
virsh 得到 NULL，但目标 VM 可能已经运行
```

| 故障位置 | 可能结果 |
|---|---|
| 请求未送达 | 目标未执行这次 Finish |
| Finish 执行中失败 | 未成功完成，状态取决于失败位置和清理结果 |
| Finish 成功，但回复丢失 | 目标可能已运行，客户端却未获得成功句柄 |

因此不能只凭 `ddomain == NULL` 就断言可以无条件恢复源端，否则可能出现两端同时运行、访问共享磁盘。源码注释指出锁管理插件应处理这种安全问题；实际保障依赖插件、配置和环境，五阶段本身不是一个消除所有通信不确定性的分布式事务协议。

源码：[客户端结果不确定性注释](https://github.com/libvirt/libvirt/blob/master/src/libvirt-domain.c#L3520)。

## 27. Confirm 请求：virsh 把 Finish 结果通知源端

### 27.1 cancelled 再次赋值

```c
cancelled = ddomain == NULL ? 1 : 0;
```

| 传给哪个阶段 | 根据什么设置 cancelled |
|---|---|
| Finish | Perform 的返回值 |
| Confirm | Finish 是否返回目标句柄 ddomain |

非空句柄意味着收到目标成功结果；空句柄进入取消处理，但仍有上一节的 RPC 不确定性。

### 27.2 notify_source 决定是否还需要通知

```c
if (notify_source) {
    ...
}
```

普通成功路径需要 Confirm。若 Perform 自己已经失败，协调代码会将 `notify_source` 设为 `false`，因为源端已知失败并走了相应处理，不再从这里重复通知。五阶段不是所有失败路径都逐一执行的固定五次调用。

### 27.3 通过源端连接调用

Finish 输出 cookie 转为输入后：

```c
ret = domain->conn->driver->domainMigrateConfirm3Params(
    domain, params, nparams, cookiein, cookieinlen,
    flags | protection, cancelled);
```

使用的是原来的源句柄 `domain` 及 `domain->conn`，不是目标句柄 `ddomain`。目标端 cookie 经 virsh 转发给源端。

Confirm 返回整数处理结果，不再返回新的目标句柄。若 `ret < 0`，协调代码记录源端可能仍暂停的警告；这里没有把 `ddomain` 清空，最后仍返回 `ddomain`。因此 API 返回目标句柄与源端清理是否全部成功，也应分别关注。

源码：[Confirm 协调代码](https://github.com/libvirt/libvirt/blob/master/src/libvirt-domain.c#L3536)。

## 28. 源端 Confirm：检查作业、解析结果

```text
virsh 经源端连接发送 RPC
    ↓
源端服务还原句柄及参数，进入驱动
    qemuDomainMigrateConfirm3Params()
        → qemuMigrationSrcConfirm()
        → qemuMigrationSrcConfirmPhase()
```

驱动检查参数，用 `qemuDomainObjFromDomain(domain)` 找到原来的源 `vm`，通过 ACL 检查后继续。

`qemuMigrationSrcConfirm()` 确认 `VIR_ASYNC_JOB_MIGRATION_OUT` 有效。普通路径按结果选择 `CONFIRM3` 或 `CONFIRM3_CANCELLED`，移除相关临时清理回调，然后进入处理函数。

`qemuMigrationSrcConfirmPhase()` 的 `retcode` 接收的仍是 `cancelled`。它解析目标 cookie，补充耗时、停机时间统计，再分支：

```c
if (retcode == 0) {
    qemuMigrationSrcComplete(driver, vm, VIR_ASYNC_JOB_MIGRATION_OUT);
} else {
    /* 取消相关作业，尝试恢复原状态，恢复迁移参数等 */
    ...
}
```

源码：[驱动入口](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_driver.c#L11993)、[SrcConfirm](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L4273)、[SrcConfirmPhase](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L4169)。

## 29. Confirm 成功与取消，两种处理方式

### 29.1 成功：结束源 QEMU 进程

`qemuMigrationSrcComplete()` 整理统计，必要时等待 SPICE 迁移相关收尾，然后调用：

```c
qemuProcessStop(vm, VIR_DOMAIN_SHUTOFF_MIGRATED, asyncJob,
                VIR_QEMU_PROCESS_STOP_MIGRATED);
```

这会停止源端这台 VM 对应的 QEMU 进程，清理源端运行资源。它不是只暂停 CPU，不是关闭 libvirt 服务，也不是删除虚拟机磁盘。代码随后产生因迁移而停止的生命周期事件及作业完成事件。

| 时点 | 源 QEMU | 源客户机 CPU |
|---|---|---|
| Perform 成功返回 | 进程保留 | 暂停 |
| Finish 成功返回 | 仍保留，等待确认 | 仍暂停 |
| Confirm 成功收尾 | 进程结束 | 源端不再执行 |

目标 QEMU 则继续承载迁入的虚拟机。客户机不是在这里正常关机、重新开机，而是已经在目标端接续运行。

### 29.2 取消：尝试恢复迁移前状态

普通预拷贝取消路径先取消可能存在的 NBD 复制作业，再调用：

```c
qemuMigrationSrcRestoreDomainState(driver, vm);
```

它检查迁移前状态和当前状态：

```c
if (preMigrationState != VIR_DOMAIN_RUNNING ||
    state != VIR_DOMAIN_PAUSED)
    return;
```

迁移前原本运行、当前暂停，才考虑恢复。原本就暂停不应擅自变成运行；I/O 错误暂停等情况也不会直接恢复。符合条件时调用：

```c
qemuProcessStartCPUs(driver, vm,
                     VIR_DOMAIN_RUNNING_MIGRATION_CANCELED,
                     VIR_ASYNC_JOB_MIGRATION_OUT);
```

这次发生在源端，也要经过资源锁和 QMP `cont`。它是尝试恢复，可能失败，不能把 Confirm 取消处理返回与业务已恢复划等号。随后还会恢复迁移参数、内存锁定限制并保存状态。

post-copy 有单独的失败和恢复分支，不能套用“失败就恢复源端 CPU”。

### 29.3 结束迁出 job，按标志处理源配置

普通路径返回外层后执行 `qemuMigrationJobFinish(vm)`。源端 Begin 以来保留的迁出保护到此结束。

源实例已不活动时，仅在没有取消、处理成功且设置 `VIR_MIGRATE_UNDEFINE_SOURCE` 的条件下删除源持久配置：

```c
if (!cancelled && ret == 0 && flags & VIR_MIGRATE_UNDEFINE_SOURCE) {
    virDomainDeleteConfig(...);
    vm->persistent = 0;
    ...
}
```

当前只有 `--live` 的示例没有该标志。因此，若源 VM 原本是持久定义，迁移后其定义可保留，显示关闭状态；临时实例的管理对象则会按不活动实例清理规则处理。不能把停止进程、删除持久配置、删除磁盘三者混在一起。

源码：[SrcComplete](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L4122)、[恢复原状态](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L253)、[源端最后收尾](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L4273)。

## 30. 五阶段正常主线与最终状态

| 阶段 | 主要执行端 | 主要工作 | 正常交接结果 |
|---|---|---|---|
| Begin | 源 libvirt | 检查源 VM，建立变更保护，生成配置和协商信息 | XML、cookie |
| Prepare | 目标 libvirt | 建立 vm 和迁入 job，启动等待接收的 QEMU，准备接收地址 | 地址信息、cookie |
| Perform | 源 libvirt 协调，两端 QEMU 传输 | 建连接、传 fd、下发迁移命令，跟踪传输和切换 | 源暂停保留，返回结果和 cookie |
| Finish | 目标 libvirt | 确认接收完成、刷新设备、按要求恢复 CPU，结束迁入 job | 目标句柄信息、cookie |
| Confirm | 源 libvirt | 成功则结束源 QEMU；取消则按原状态尝试恢复；结束迁出 job | 源端处理结果 |

```text
virsh 工作线程协调
    Begin(源) → Prepare(目标) → Perform(源) → Finish(目标) → Confirm(源)

迁移数据路径
    源 QEMU ═════ 内存、CPU/设备等运行状态 ═════→ 目标 QEMU
```

本例共享存储的磁盘内容不是在上述内存迁移流中完整复制一遍。

在普通、源 VM 原本运行且未要求目标暂停的成功路径中：

```text
源 CPU 暂停，源 QEMU 保留
    ↓
目标完成接收并恢复执行
    ↓
目标 Finish 成功回复到达 virsh
    ↓
virsh 通知源端 Confirm
    ↓
源 QEMU 结束，目标继续运行
```

迁移 API 返回后，工作线程按结果结束，当前线程 join 并清理本次目标连接等资源。交互式 virsh 的源端管理连接可以继续供其他命令使用，不应说“一条迁移命令结束就断开所有连接”。

## 31. 后半程复习纠错表

| 容易混淆的说法 | 准确理解 |
|---|---|
| 目标 vm 是 Perform 创建的 | Prepare 创建管理对象并启动目标 QEMU |
| 目标 QEMU 存在，但 VM 已关机 | 在迁入期间可以是进程存在、客户机 CPU 暂停 |
| Finish 才开始接收内存 | Perform 时已接收；Finish 确认处理完成 |
| 恢复 CPU 是创建 CPU 进程 | 向已有 QEMU 发 cont，恢复客户机执行 |
| LockProcessResume 直接恢复 CPU | 它处理资源锁；之后才发送 cont |
| 目标一定恢复运行才算迁移成功 | 要求保持暂停时，暂停也可为成功结果 |
| 服务端 dom 指针原样返回 virsh | RPC 返回标识，客户端取得自己的 ddomain |
| ddomain 为 NULL 证明目标没运行 | 回复可能丢失，远端执行结果可能不确定 |
| Finish cancelled 和 Confirm cancelled 不变 | 前者根据 Perform，后者根据 Finish 结果重新计算 |
| Confirm 成功只暂停源 CPU | 停止并结束源 QEMU 进程，清理运行资源 |
| 停止源 QEMU 就删除磁盘和定义 | 运行实例、持久定义、磁盘是不同层次 |
| Confirm 取消总能恢复源 VM | 取决于原状态、故障原因、资源锁和恢复结果 |
| job 结束就是虚拟机结束 | job 是迁移操作状态；目标 job 结束后 VM 可继续运行 |
| 五阶段确保所有故障都原子回滚 | RPC 不确定性、资源锁和 post-copy 等都需单独分析 |

## 33. 先分清协议、编码和传输通道

### 33.1 通信关系

当前讨论的是 virsh 客户端协调两端的 managed direct migration，而不是 peer-to-peer：

```text
virsh 进程中的 libvirt 库
    ├─ 源端控制连接：libvirt RPC → 源端 libvirt
    └─ 目标控制连接：libvirt RPC → SSH → 目标端 libvirt

源端 libvirt ── QMP / 本地 UNIX socket ── 源 QEMU
目标 libvirt ── QMP / 本地 UNIX socket ── 目标 QEMU

源 QEMU ── QEMU 二进制迁移流 / 原生 TCP 通道 ── 目标 QEMU
```

图中“RPC → SSH”表示 RPC 字节由 SSH 通道承载。不是两个 libvirt 必然直接通过 SSH 交流，也不是所有迁移数据都经 virsh 转发。

| 层次 | 含义 | 本次例子 |
| --- | --- | --- |
| 操作协调 | 哪一方按什么次序执行什么操作 | libvirt 五阶段 |
| 消息协议 | 请求、回复、事件、状态记录怎样组织 | libvirt RPC、QMP、QEMU 迁移格式 |
| 编码 | 字段怎样变成可传输字节 | RPC 的 XDR、QMP 的 JSON、QEMU 状态的二进制编码 |
| 传输及访问接口 | 怎样把字节交给另一端 | TCP、UNIX socket、fd |
| 安全保护 | 如何认证、加密并防止篡改 | SSH、TLS，分别作用于实际经过它们的通道 |

### 33.2 TCP socket 与 UNIX socket

- TCP socket 使用 IP 地址和端口，可用于同机或跨主机通信。
- UNIX domain socket 用于同机进程通信，常见地址是本地路径，如 `/run/libvirt/libvirt-sock`。这个路径不是保存消息内容的普通文件。
- 两者都可以提供流式通信，进程都通过自己的 fd 访问。
- `AF_INET` 与 `AF_UNIX` 是地址族；`SOCK_STREAM` 是套接字类型。不能把 UNIX socket 理解成 TCP 的另一种加密方式。
- 两端 fd 是各自进程的资源编号；网络传的是字节，不是 fd 整数或 C 指针的可用性。

示意：

```c
socket(AF_INET, SOCK_STREAM, 0); /* IPv4 TCP */
socket(AF_UNIX, SOCK_STREAM, 0); /* 本地流式 UNIX socket */
```

## 34. libvirt RPC：请求、编码、接收和回复

### 34.1 Begin 请求作为例子

virsh 工作线程在本进程内调用 libvirt 库。remote 驱动提取虚拟机标识，将 typed params 和迁移 flags 填入 `args`，再调用通信层。

Begin3Params 请求中包含的是虚拟机标识、参数数组和 flags；**这个 Begin 请求没有输入 cookie**。XML 和输出 cookie 是执行 Begin 后的返回数据。

`args` 是进程内的请求参数结构，不是已经发到网络上的包，也不是完整 RPC 消息头。操作编号由调用过程另外指定。

重要源码：

- [remote_driver.c：remoteDomainMigrateBegin3Params](https://github.com/libvirt/libvirt/blob/master/src/remote/remote_driver.c#L6471)
- [remote_protocol.x：远程接口结构及操作编号](https://github.com/libvirt/libvirt/blob/master/src/remote/remote_protocol.x)
- [virnetprotocol.x：RPC 消息头定义](https://github.com/libvirt/libvirt/blob/master/src/rpc/virnetprotocol.x)

### 34.2 消息头与 XDR

普通、不携带 fd 的 RPC 消息可以概念化为：

```text
消息总长度字段 → RPC 消息头 → 编码后的参数或返回值
```

消息头包含 `prog`、`vers`、`proc`、`type`、`serial`、`status`：

| 字段 | 作用 |
| --- | --- |
| prog / vers | 识别 RPC 接口及其版本；不是 QEMU 迁移流版本 |
| proc | 识别调用哪个远程操作，例如 Begin3Params |
| type | 区分调用、回复等消息类别 |
| serial | 关联本次请求及其回复，不是 TCP 分片编号 |
| status | 消息的协议状态；请求里的 OK 不代表操作已经成功 |

消息头和消息体都需要按规则编码。libvirt 在这里使用自己的 RPC 协议和 **XDR**，不是 gRPC。

XDR 按字段类型和声明顺序编码。例如 32 位整数使用 4 字节大端表示；字符串包含长度、内容及对齐填充；变长数组包含元素数量。它不是直接复制 C 结构体的整块内存：指针、平台字节序和结构体填充不能直接跨进程使用。

### 34.3 接收端如何识别完整消息

流式 socket 没有应用消息边界，一次读可能不足一条消息，也可能读到连续消息的一部分。接收端先解析长度，再累计所需字节；它不靠 RPC serial 拼接网络包。

随后解析消息头、定位接口及操作，用对应 XDR 解码函数还原参数，交给服务端处理函数。服务端按虚拟机标识取得本地句柄，执行操作后，把返回值编码成 RPC 回复。

返回的虚拟机标识在客户端形成客户端自己的句柄；目标进程的指针地址不会变成 virsh 里的有效对象。

## 35. QMP：命令、回复、事件及连接初始化

### 35.1 三类消息

```json
{"execute":"cont","id":"resume-1"}
```

这是命令。以下是成功回复：

```json
{"return":{},"id":"resume-1"}
```

以下是事件，示例省略时间戳：

```json
{"event":"RESUME"}
```

- 回复通过 `id` 对应请求；失败回复包含 `error`。
- 事件描述状态变化，不是原命令的第二次回复，不按命令 id 配对。
- 事件可能穿插在回复之间，不能假定“发送命令后下一条一定是它的回复”。
- `migrate` 或 `migrate-incoming` 命令成功，不等于整个迁移任务完成。后续通过事件和 `query-migrate` 等查询了解任务状态。
- pre-copy、stop-and-copy 是迁移机制中的概念，不是每个术语都有同名 QMP 状态值；客户机 STOP 事件也不等于迁移完成。

### 35.2 greeting 与能力协商

```text
建立 QMP socket 连接
    ↓
QEMU → libvirt：greeting，包含版本与支持的能力
    ↓
libvirt → QEMU：qmp_capabilities 命令
    ↓
QEMU → libvirt：成功回复
    ↓
进入正常命令模式
```

`qmp_capabilities` 是命令，不是客户端返回自己的完整能力列表。可按需要选择 QEMU 提供的扩展；即使不启用扩展，也要完成这个步骤。它协商的是 QMP 功能，不是迁移的 CPU/设备兼容性，也不是 SSH 登录认证。

参考：[QMP 规范](https://www.qemu.org/docs/master/interop/qmp-spec.html)、[QMP 命令与事件手册](https://www.qemu.org/docs/master/interop/qemu-qmp-ref.html)。

## 36. QEMU 迁移流：从 QEMUFile 到 RAM 记录

### 36.1 `QEMUFile *f` 不等于磁盘文件或 socket fd

`f` 是指向 QEMU 数据流读写对象的指针。它封装读写、缓冲和错误管理等，通常连接到底层 `QIOChannel`。在普通 TCP 场景中，下层通道最终通过 socket 传输。

```text
qemu_put_be32(f, value)
    ↓ 编码并写入
QEMUFile → I/O 通道 → socket fd → TCP
    ↓ 对端
对端 I/O 通道 → 对端 QEMUFile → qemu_get_be32(f)
```

源端与目标端各有自己的 `f`。一次 `put` 不等于一次网络包发送，一页也不等于一个 TCP 包。

### 36.2 流头

`qemu_savevm_send_header()` 写入：

```c
qemu_put_be32(f, QEMU_VM_FILE_MAGIC);
qemu_put_be32(f, QEMU_VM_FILE_VERSION);
```

本次核对的值为：

```text
51 45 56 4D │ 00 00 00 03
识别标记     迁移流格式版本 3
```

`be32` 表示 32 位大端整数。Magic 不是密码或哈希；版本 3 不是 libvirt 五阶段 v3，也不是 QEMU 软件版本。

目标端 `qemu_loadvm_state_header()` 读入并检查。它是在验证收到的格式，不是在此处来回协商版本。按配置还会读写 configuration section。

### 36.3 section 段头

`save_section_header()` 写入类型、section ID；`START` 和 `FULL` 还携带名称、实例编号和状态格式版本。

```text
START / FULL 段头：
类型(1字节) │ section ID(4) │ 名称长度(1) │ 名称(N) │ instance ID(4) │ version ID(4)

PART / END 段头：
类型(1字节) │ section ID(4)
```

- START：一个迭代状态对象的开始段。
- PART：后续数据段。
- END：该对象的结束段，里面仍可能携带最后的数据。
- FULL：一次保存完整状态的段。

目标端首次通过名称和 instance ID 找到本地登记的状态条目，记住源端 section ID。后续根据这个编号找到相同加载逻辑。编号不是网络包序号，也不是内存块号。

### 36.4 普通设备的数据：双方已经有读写规则

`VMStateDescription` 可以理解为设备状态的“读写说明书”：规定哪些字段、什么类型、什么顺序以及版本/条件规则。

教学示例：双方约定 `status`、`mode` 各 1 字节，源端值为 2、3，则字段数据是 `02 03`。目标端按相同规则恢复，不必在每个数值前再发送字段名称。

`VMSTATE_END_OF_LIST()` 是源码里的字段描述结束，不是网络上的结束标记。真实设备可能有数组、条件字段、子段，不能认为所有状态都是固定长度。

### 36.5 RAMBlock、页与偏移

RAMBlock 是 QEMU 管理的一大片内存，里面包含很多页。在当前普通页传输路径中，按页组织记录，不是把整个 RAMBlock 当成一条记录发送。

```text
RAMBlock A
    页 1：偏移 0
    页 2：偏移 4096
    页 3：偏移 8192
```

这里假设页大小 4096 字节，实际由所讨论路径的页大小定义决定。

记录需要说明“哪个 RAMBlock + 块内偏移 + 怎样解释后面的数据”。目标端找到自己的对应块，再加偏移定位写入位置。两端宿主进程中的实际指针地址可以不同。

假设源端块起点为 100000、目标端块起点为 500000，页偏移都是 8192：源端读 `100000 + 8192`，目标端写 `500000 + 8192`。这些是教学数字，不是真实机器地址。

### 36.6 页记录中的偏移与标志

`save_normal_page()` 的普通迁移流分支先写页头，再发送 `TARGET_PAGE_SIZE` 大小的内容：

```c
save_page_header(pss, pss->pss_channel, block,
                 offset | RAM_SAVE_FLAG_PAGE);
/* 随后通过同步或异步写接口写出页内容 */
```

页偏移按页对齐，低位为零，可用来存标志。假设 4 KiB 页：偏移 `0x2000` 与 PAGE 标志 `0x008` 组合为 `0x2008`。它是编码后的“位置 + 标志”，不是把数据写到偏移 8200。接收端用掩码拆开。

| 标志 | 含义 |
| --- | --- |
| PAGE | 后面是普通页的原始内容 |
| ZERO | 用简短记录表示全零页，目标端恢复对应页为零 |
| CONTINUE | 沿用前一页记录的 RAMBlock，省去重复块名；不是偏移自动加一 |
| EOS | 本段 RAM 记录结束，本身不是内存页 |

这些是记录的编码/解析标志，不按“操作系统重要数据、普通应用数据”分类。全零也不等于“从未使用”：依据的是页当前内容。目标端不能简单跳过 ZERO 页，必须确保对应内容恢复为零。

### 36.7 EOS、footer、EOF 是三个层次

```text
RAM section 段头
    PAGE / ZERO 等记录（可来自不同 RAMBlock）
    EOS
section footer（若启用）：固定标记 + section ID
下一个 section
……
EOF：主要迁移状态段结束
```

**EOS 不是某个 RAMBlock 的结束，也不一定代表一整轮脏页扫描完成。** 同一 RAMBlock 的页可在后续 section 继续发送。

RAM 加载函数读到 EOS 后返回，外层再检查 footer。`check_section_footer()` 检查固定段尾标记和匹配的 section ID：

- 不要求段头类型（如 PART）等于段尾标记。
- footer 不携带整段长度供比较。
- 不扫描数据寻找 footer；按规则读完数据后，在当前位置检查。
- 它能帮助发现读多、读少等错位，但不是整段哈希或密码学完整性证明。

EOF 表示主要状态流结束，不是一个内存页结束，不是 TCP 断开；后面还可能有供分析使用的 VM description。

源码入口：[savevm.c](https://github.com/qemu/qemu/blob/master/migration/savevm.c)、[ram.c](https://github.com/qemu/qemu/blob/master/migration/ram.c)、[ram.h](https://github.com/qemu/qemu/blob/master/migration/ram.h)。

## 37. 第一项：怎样判断迁移完成

### 37.1 “完成”不是一个单独的标志

| 观察到的信息 | 能说明什么 | 不能仅凭它说明什么 |
| --- | --- | --- |
| 源端写入 EOF | 已写到主要状态段的结尾 | 目标已读完、加载成功、客户机正在运行 |
| 目标读到 EOF | 主状态段解析到结尾 | 加载线程与后续检查全部成功 |
| 目标 QMP MIGRATION/completed | 目标 QEMU 的迁入状态已完成 | 客户机 CPU 必然已运行、应用必然正常 |
| QMP RESUME | 客户机恢复执行 | 客户机内业务服务健康、源端已清理 |
| Finish 成功回复到客户端 | 客户端取得目标端处理结果 | 所有后续源端清理必然成功 |

`qemu_loadvm_state_main()` 遇 EOF 退出解析，`qemu_loadvm_state()` 后面仍会检查迁移错误、加载线程池和数据流错误等。

### 37.2 QMP 事件到 libvirt 本地状态

```text
目标 QEMU：迁入状态 completed
    ↓ 已有 QMP 连接上的 MIGRATION 事件
qemuMonitorJSONHandleMigrationStatus：取出 status
    ↓
qemuProcessHandleMigrationStatus：更新迁移作业记录
    ↓
virDomainObjBroadcast：唤醒目标 libvirt 内部等待者
    ↓
qemuMigrationDstWaitForCompletion：重新检查，再决定继续/失败/等待
```

关键代码：

```c
privJob->stats.mig.status = status;
virDomainObjBroadcast(vm);
```

Broadcast 是进程内部条件变量通知，不是网络广播，也不是创建一个新进程。被唤醒只表示该重新检查，不能直接等同于成功。

### 37.3 谁决定恢复 CPU

当前 libvirt 管理的普通 pre-copy 路径中，目标 QEMU 以 `-S` 启动，CPU 恢复时机由 libvirt 管理。QEMU 完成迁入后可保持暂停，Finish 确认并准备好后发送 QMP `cont`。要求迁移后保持暂停时，不执行正常的自动恢复路径。

QEMU 自身也有允许自动运行的分支；因此不能把“必须等 libvirt cont”泛化到所有独立 QEMU 使用方式。

```text
迁入完成 → MIGRATION/completed
    ↓
目标 libvirt 检查及准备
    ↓ cont 命令
QEMU 恢复虚拟 CPU 执行 → RESUME 事件
```

`cont` 的回复与 RESUME 是不同消息，可以交错到达。RESUME 不是“新建 CPU 进程”。

### 37.4 回到客户端与源端

目标端 Finish 的 RPC 回复携带虚拟机标识和 cookie；virsh 进程里的 libvirt 库取得自己的 `ddomain`，再调用源端 Confirm。它不是 QEMU 把 QMP 事件直接发给源端 virsh。

正常成功时，源端 Confirm 停止源 QEMU，清理运行资源。若 Finish 回复丢失，`ddomain == NULL` 不证明目标没有运行；故障恢复留到第四项专题处理。Confirm 失败的表现也不能简单等同于“目标迁入失败”，前文已说明其返回值边界。

## 38. 第二项：兼容性检查（详细版）

### 38.1 兼容性的目标：继续运行同一台虚拟机

热迁移不是在目标端重新安装系统，也不是重新启动应用。客户机要从暂停处继续执行。因此目标端至少要做到：

1. 看得懂收到的状态数据。
2. 找得到对应的状态对象/设备实例。
3. 提供与源端兼容的虚拟硬件及行为。
4. 提供客户机已经看到、可能正在使用的 CPU 能力。
5. 能恢复该设备和 CPU 的具体运行状态。

**TCP 能连接，只说明有通信路径；接收到了字节，不说明有能力正确恢复。**

这些检查分散在 libvirt 配置校验、QEMU 能力探测、创建目标实例及实际加载等多个位置。不是一次握手就保证了全部兼容，也不是所有问题都等到流加载时才发现。

### 38.2 四个容易混淆的“版本/型号”

| 名称 | 管什么 | 是否等于其他版本 |
| --- | --- | --- |
| QEMU 软件版本 | 运行的程序实现及支持能力 | 不等于迁移流版本 |
| 迁移流格式版本 | 外层头部、section 等组织规则 | 不等于 libvirt 的迁移 v3 |
| 设备状态格式版本 | 某个设备的数据按什么规则读取 | 各设备分别定义，不要求全部相同 |
| 带版本的机器类型 | 虚拟平台及相关兼容行为 | 不要求和正在运行的 QEMU 软件版本相同 |

另外，libvirt RPC 头里的 `vers` 又是远程接口层的版本，不能混在以上几项中。

### 38.3 第一层：能否识别外层迁移流

源端写 Magic 和 `QEMU_VM_FILE_VERSION`。目标端 `qemu_loadvm_state_header()` 检查格式标记与版本。本次源码中流版本为 3，旧版 2 被明确拒绝。

这只能帮助判断：

> “后面的外层结构是否是我认识的迁移格式？”

它不回答：

> “里面每个设备的状态，我是不是都能恢复？”

类比：认识一本书的封面和目录结构，不代表读得懂每一章的内容。

### 38.4 第二层：能否找到对应的状态对象

首次读取 START/FULL 段，目标端调用：

```c
se = find_se(idstr, instance_id);
```

它按名称和实例编号查找本地已登记的状态条目。找不到会报错，例如两端设备配置不匹配、对应实例不存在。

这是“找接收者”，不是“按名字自动创建缺少的设备”。目标环境应已准备好相应设备，之后才能向其中恢复状态。

地址/身份配置也重要：有多个同类设备时，不能只说“两端都有网卡”就算匹配，还要让状态落到正确实例。

源码：[qemu_loadvm_section_start_full](https://github.com/qemu/qemu/blob/master/migration/savevm.c#L2698)。

### 38.5 第三层：设备状态格式是否支持

回忆 VMState：双方代码中已有字段顺序和类型，网络中主要传值，不会为每个值重新发送字段说明书。

教学示例，不代表某个真实设备的版本演变：

```text
设备格式版本 1：status(1字节) → mode(1字节)
设备格式版本 2：status(1字节) → mode(1字节) → counter(1字节)
```

源端按版本 2 发送 `02 03 05`，如果目标只认识版本 1，就不知道第三个字节应如何处理。不能因为前两个字节看起来正常就强行继续。

所以段头中的 `version_id` 是告诉目标：**“这段设备状态采用哪套格式规则。”**

对于 VMStateDescription，目标端支持范围由以下字段表达：

```c
.version_id = 3,
.minimum_version_id = 2,
```

这个假设例子表示可以读取版本 2 到 3：

| 收到的版本 | 版本范围检查 |
| --- | --- |
| 1 | 太旧，拒绝 |
| 2 | 在范围内，继续按对应规则加载 |
| 3 | 在范围内，继续加载 |
| 4 | 太新，拒绝 |

`migration/vmstate.c` 的关键判断：

```c
if (version_id > vmsd->version_id) {
    /* 收到的版本太新，失败 */
}
if (version_id < vmsd->minimum_version_id) {
    /* 收到的版本太旧，失败 */
}
```

注意变量归属：`version_id` 是收到的值；`vmsd` 是目标端的本地描述。这里是在接收后验证，不是双方来回协商一个共同版本。

版本检查通过仍可能在字段、子段、加载回调中失败。QEMU 也使用条件字段、子段和兼容属性演进格式，不是每增加一个字段都提升整个设备版本。遇到不认识的子段，也可能拒绝加载。使用自定义加载函数的状态对象不能机械套用所有 VMState 宏路径。

源码：[vmstate.c 版本范围检查](https://github.com/qemu/qemu/blob/master/migration/vmstate.c#L358)。背景：[VMState 版本](https://www.qemu.org/docs/master/devel/migration/main.html#versions)、[子段](https://www.qemu.org/docs/master/devel/migration/main.html#subsections)。

### 38.6 第四层：机器类型为什么影响迁移

machine type 可以先理解为“虚拟主板/平台类型及兼容版本”。它影响芯片组、总线结构和相关设备默认属性等，但不单独决定虚拟机所有设备与 CPU 配置。

例子：

```text
-machine pc-q35-8.2
```

- `q35`：平台类型。
- `8.2`：这一版机器类型的兼容规则。
- 这是教学配置，不代表实验两端一定安装了支持它的 QEMU。

客户机已经根据源端虚拟硬件初始化、使用驱动、操作设备。迁入后如果突然变更平台或设备行为，即使内存复制正确，客户机也可能无法继续运行。

典型兼容思路：

```text
源 QEMU 8.2：使用 pc-q35-8.2
           ↓
目标较新 QEMU：仍使用 pc-q35-8.2（前提：它支持该机器类型）
```

新版 QEMU 可以通过旧机器类型的兼容属性保留相关旧行为；不应因为软件更新，就在迁移中把机器类型切到最新。可用 `-machine help` 检查本机支持列表，但名称存在仍不能证明所有迁移条件都满足。

必须同时避免两个误解：

- “QEMU 软件版本不同，一定不能迁”——不一定，版本化机器类型等就是跨版本兼容机制。
- “机器类型名称相同，一定能迁”——也不成立，CPU、设备实例、特性、后端资源和状态加载仍需兼容。

参考：[QEMU -machine 说明](https://www.qemu.org/docs/master/system/invocation.html#standard-options)。

### 38.7 第五层：CPU 配置和 CPU 运行状态不是同一件事

| 内容 | 例子 | 迁移中解决的问题 |
| --- | --- | --- |
| CPU 配置/能力 | 模型、指令集特性、拓扑及相关属性 | 目标能否提供客户机原先看到的 CPU |
| CPU 运行状态 | 寄存器、程序计数器和相关执行状态 | 怎样从暂停处继续执行 |

假设客户机已经探测到 AVX2，并选择使用它的代码路径。若目标无法提供这个能力，即使把寄存器和内存原样恢复，后续指令也可能无法执行。

因此不能为迁移成功，临时从运行中客户机的 CPU 配置里删掉它已经依赖的特性。应该在启动前为迁移集群规划兼容的 CPU 配置。

简化例子：

```text
主机 A 能提供 a,b,c,d
主机 B 能提供 a,b,c
预先给虚拟机提供 a,b,c
```

这只是理解需求与能力关系，不是完整 CPU 比较算法。真实判断还涉及模型、架构、属性、KVM/QEMU、微码等；客户机可用能力也不等于裸物理 CPU 的所有特性。

### 38.8 三种 CPU 模式详细对比

本节以 x86 QEMU/KVM 为背景；其他架构或纯软件模拟可能有差异。

| 模式 | 含义 | 热迁移时重点 |
| --- | --- | --- |
| host-passthrough | 尽量呈现宿主 CPU 的特征，包括 libvirt 未完整建模的部分 | 依赖两端硬件、微码、QEMU 和配置的一致性；不能只看 CPU 商品型号 |
| host-model | libvirt 根据宿主能力形成明确的虚拟 CPU 定义 | 迁移传递该运行实例已经确定的 CPU 定义；目标必须能提供 |
| custom | 管理者明确指定模型与特性 | 可为多个主机规划共同配置，但必须验证，不能凭空创造能力 |

最简单的 XML 示例：

```xml
<cpu mode='host-passthrough'/>
```

```xml
<cpu mode='host-model'/>
```

对于 custom，应结合实际支持的 CPU 模型填写，不能随意复制一个示例模型到实验环境。

**host-model 重点：**

```text
源端启动前，确定具体 CPU 配置
           ↓
迁移时把完整配置交给目标
           ↓
目标保持该运行实例的 CPU 定义
```

不是到目标端重新按其更强 CPU 自动挑选另一套能力。客户机关机后，在新主机重新启动，host-model 可能根据新主机重新生成定义；这与保持运行实例的热迁移不同。

**host-passthrough 重点：**两端物理 CPU 型号相同不是充分条件。`migratable='on'` 可以移除某些妨碍迁移的特性，但不能把不同主机自动变成兼容主机。

**custom 重点：**它让 CPU 配置可明确控制；“指定了一个名称”仍不等于两端都能实现它。能力是否能提供，应结合宿主和虚拟化软件检查。

参考：[libvirt CPU 模型与拓扑](https://libvirt.org/formatdomain.html#cpu-model-and-topology)、[QEMU/KVM CPU 模型](https://www.qemu.org/docs/master/system/qemu-cpu-models.html)。

### 38.9 目标端从哪里得到 CPU 要求

在前文客户端协调路径中，源端生成迁移用的虚拟机 XML，经客户端交给目标端。CPU 定义是其中的配置输入之一；相关 cookie 可按实现分支携带额外协商信息，不能把 cookie 当作唯一 CPU 配置来源。

```text
运行中虚拟机的配置要求
    ↓ 迁移 XML 等输入
目标端解析后的 def->cpu
    ↓ 与本机支持能力比较
能否准备符合要求的虚拟 CPU？
```

例如这条 XML 特性要求：

```xml
<feature policy='require' name='avx2'/>
```

表示要求该特性，不是对宿主机 CPU 新增这项能力的命令。实际 CPU 需求还包含模型本身带来的特性等，不能只看显式列出的 feature 行。

目标端比较的是虚拟机要求与目标可提供的能力，不是要求两台物理 CPU 的所有特性列表完全相等。目标可能有额外特性，但不应因此改变迁入客户机的 CPU 约定。

### 38.10 源码入口与检查模式

在 [qemuProcessUpdateGuestCPU](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_process.c#L6628) 中，本次读到以下 partial 分支：

```c
if (def->cpu->check == VIR_CPU_CHECK_PARTIAL &&
    qemuDomainCheckCPU(hostarch, def->virtType, qemuCaps, def->cpu,
                       VIR_QEMU_CAPS_HOST_CPU_FULL, true) < 0)
    return -1;
```

| 变量 | 归属及含义 |
| --- | --- |
| def->cpu | 虚拟机的 CPU 配置需求 |
| def->virtType | 虚拟化类型，例如 KVM |
| qemuCaps | 本机 QEMU 能力信息 |
| hostarch | 宿主架构 |
| return -1 | 该步骤失败，不沿成功路径继续 |

不能把这一行当成所有模式统一的最终检查。函数还检查 CPU 模式支持、禁止特性、模型转换等；实际检查随架构、配置、版本而变。

`check` 属性与 `mode` 属性不同：

| check 模式 | 主要含义 |
| --- | --- |
| none | 不执行相应 libvirt CPU 核对；不代表已经兼容，也不适合作为掩盖问题的办法 |
| partial | libvirt 在启动前检查 CPU 定义，后续仍依赖 hypervisor 行为 |
| full | 检查 hypervisor 实际创建的虚拟 CPU 是否符合指定配置 |

不要把 `check='full'` 理解成“已经验证整个迁移操作”，它的范围是虚拟 CPU 配置核对。也不要把 `match='exact'` 理解成两台物理 CPU 必须完全相同；它约束的是提供给客户机的 CPU 与所指定配置的匹配。

另一个入口 [qemuProcessStartValidate](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_process.c#L5893) 涉及启动前配置检查，并调用 TSC 等检查。这说明 CPU 兼容性不只是比一组指令集名称。本次尚未逐行深入各架构 CPU 比较算法及 QMP 能力探测实现。

### 38.11 检查发生在不同时间

```text
准备目标环境前后
    CPU 模式/模型、机器类型、设备配置、目标能力等检查
             ↓
创建目标 QEMU 和虚拟 CPU
    按配置核对可提供或实际创建的 CPU
             ↓
接收迁移流
    流头版本、设备身份、设备状态版本、字段/子段及加载检查
             ↓
恢复执行前
    接收结果和后续资源准备检查
```

这是帮助理解的分层图，不是每个版本都严格一致的完整调用顺序。某项早期检查通过，不能消除后续加载失败的可能。

### 38.12 不兼容实例与应有判断

| 情况 | 问题所在 | 不能采用的理解 |
| --- | --- | --- |
| 流头版本支持，某设备状态版本太新 | 外层能读，设备内容格式不支持 | “流头通过就全部兼容” |
| 两端同机型，目标缺少一个设备实例 | 状态找不到正确接收对象 | “让 QEMU 根据数据临时补一个就行” |
| 两端 QEMU 软件不同，但支持相同旧机器类型 | 可能具备跨版本迁移基础，仍需核对其他条件 | “软件不同就必然失败” |
| 目标缺少客户机需要的 CPU 特性 | 执行能力无法保持 | “传完后把这个特性删掉” |
| host-model 在源端选了更多特性 | 目标仍要满足该运行实例的具体定义 | “两边都写 host-model 就自动匹配” |
| host-passthrough 两边 CPU 型号相同 | 还存在微码、软件、配置等差异 | “型号一样就是充分条件” |
| 数据格式能读，但设备后端资源不可用 | 环境准备或运行资源问题 | “数据能解析就肯定能运行” |

**复述模板：**迁移需要目标读懂源端状态，同时准备兼容的虚拟硬件和 CPU 能力。格式版本、机器类型和 CPU 配置分别约束不同层次；检查分散在准备、创建、加载等环节，任何一个“通过”都不能代表全局成功。

## 39. 第三项：安全与完整性（已学到的部分）

### 39.1 TCP 可靠性不等于加密

TCP 通过序号、确认、重传等机制提供可靠、有序的字节流；连接也可能失败，不保证迁移最终成功。TCP 确认不等于目标 QEMU 成功加载，更不等于客户机应用正常。

TCP 本身不加密迁移内容；其校验和不是抵抗恶意篡改的密码学认证。QEMU 的 Magic、版本和 footer 检查也不是传输内容的密码学保护。

| 需求 | 已讨论的对应层次 |
| --- | --- |
| 处理丢包、乱序 | TCP |
| 知道字段与段怎样解析 | QEMU 迁移格式及加载逻辑 |
| 判断目标能否恢复 | 兼容性与加载结果检查 |
| 身份验证、加密、防篡改 | TLS 身份认证、流量密钥和记录保护，详见下文 |

### 39.2 SSH 控制连接不自动保护原生数据通道

```text
控制：virsh ── SSH ── 目标 libvirt（RPC）
数据：源 QEMU ── 原生 TCP ── 目标 QEMU（迁移状态流）
```

当前模式下是两条不同通道。控制连接用了 SSH，不代表 QEMU 原生迁移流自动加密。libvirt 支持通过 `VIR_MIGRATE_TLS` 等机制为原生迁移启用 TLS，下面继续记录证书验证、密钥和配置分工；具体实验部署尚未执行。

参考：[libvirt 原生迁移与安全](https://libvirt.org/migration.html)、[TCP 标准 RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)。

### 39.3 TLS 在 QEMU 与 TCP 之间的位置

在当前 TCP 迁移路径中，先建立 TCP 连接，再在同一条连接上完成 TLS 握手，随后传输受保护的迁移数据。TLS 不是必须单独启动的另一个服务进程；QEMU 调用 TLS 库，由本进程内的 TLS 层处理握手和数据保护。

```text
源 QEMU 迁移代码：生成迁移字节
    ↓
QEMUFile / TLS I/O 通道：加密、生成认证标签
    ↓
底层 socket → TCP 网络传输
    ↓
目标端 TLS 通道：验证、解密
    ↓
目标 QEMU 迁移代码：解析并恢复状态
```

`qemu_put_be32()`、`qemu_put_buffer()` 等仍按 QEMU 迁移格式输出数据，底层通道负责 TLS 保护。**QEMU 与 QEMU 的迁移流不使用 XDR；XDR 属于前文 virsh 与 libvirt 的 RPC 编码。**

### 39.4 TLS 的三个作用及边界

| 作用 | 含义 | 不应混淆为 |
| --- | --- | --- |
| 身份认证 | 验证对方证书、预期身份及相应私钥持有证明 | 仅因 TCP 连上就信任对方 |
| 加密 | 使网络旁观者不能直接读取迁移内容 | 改变虚拟机内存的逻辑内容或格式 |
| 完整性保护 | 发现受保护记录被非法修改或损坏，拒绝接受 | 自动修复数据、保证迁移一定成功 |

TLS 不判断设备状态版本兼容，不证明客户机应用正常，也不能保护已经被控制的通信端点。这里讨论正常配置与密钥未泄露的保护机制。

### 39.5 公钥、私钥、证书与 CA：先准备，再连接

通常由 B 的管理员先为 B 生成密钥对：

```text
B 的私钥：保密保存，B 用它生成身份认证所需的签名
B 的公钥：可以公开，用来验证对应私钥生成的签名
```

管理员将 B 的身份和公钥通过证书签名请求（CSR）等方式交给 CA。CA 按其签发规则核实后，签发包含 B 身份、公钥、有效期等信息的证书。**通常不需要把 B 的私钥交给 CA。**

证书可以理解为“经过签发者签名的身份与公钥绑定”。证书并不是在每次连接时由 B 临时塞入一个公钥；签发后的内容不能任意修改，否则证书签名验证会失败。

CA 可以是商业机构，也可以是实验环境自建并明确配置为可信的 CA。不是名字叫 CA 就自动可信；A 的信任依据来自事先配置的信任材料。

### 39.6 A 怎样拿到并信任 B 的公钥

建立 TLS 连接时，B 将自己的证书发给 A。A 收到后就能读取其中的公钥；**能读取与能信任是两个步骤**。

在 CA 直接签发 B 证书的简化情形中：

```text
A 已配置可信 CA 证书
    ↓ 使用 CA 公钥检查签发关系
收到 B 的证书
    ↓ 检查有效期、用途、目标名称等
确认该证书适用于预期目标 B
    ↓
信任证书中的 B 公钥
```

真实部署可能包含中间 CA，需要验证证书链。证书身份通常通过 SAN 列出主机名/IP；不应把“同一可信 CA 签发”当成“必然是我要连接的那个目标”。证书链验证通常使用本地信任材料，并不要求每次迁移都在线联系 CA。

| A 使用的公钥 | 来源 | 主要作用 |
| --- | --- | --- |
| CA 公钥 | 预先信任的 CA 证书等信任链材料 | 验证证书签发关系 |
| B 公钥 | B 在握手中出示的端点证书 | 验证 B 对本次握手的签名 |

B 的私钥通常在连接前准备好，QEMU 按配置加载使用；不是从 A 获取，也不是永久不可更换，可按管理要求轮换。

### 39.7 为什么拿到可信证书还不够：私钥持有证明

证书是公开信息，冒充者可以复制 B 的证书。因此还必须证明当前对方持有对应私钥。

以 TLS 1.3 的证书认证为例，B 对本次握手相关内容生成 CertificateVerify 签名，A 使用 B 证书中的公钥验证：

```text
B：本次握手相关内容 + B 的私钥 → 签名 S → 发给 A
A：本次握手相关内容 + 签名 S + B 的公钥 → 验签有效/无效
```

握手相关内容包括本次交换的新鲜信息，不能直接用旧连接中的证明冒充新连接。这里是概念说明，实际签名输入包含协议规定的上下文及握手摘要等。

必须记住三个纠正：

1. B 签的是本次握手相关内容，不是重新为自己的证书签名；证书签发者已经签过证书。
2. A 使用的是 **B 的公钥**，与 **B 的私钥**配对，不是 A 自己的公私钥。
3. 验签结果是有效/无效，**不是用公钥“解密出真正的证书”**。证书原本就已经发给 A。

可以这样复述：

> 证书验证建立“预期身份 B 与这个公钥”的可信绑定；握手验签证明当前对方能使用对应私钥。两者结合完成证书身份认证。

双向认证时，目标端也验证源端的证书和私钥持有证明。认证通过与更细粒度的访问授权仍是不同层次。

### 39.8 证书密钥与流量密钥不是同一套

| 密钥类别 | 用途 |
| --- | --- |
| CA 的签名密钥 | 签发证书，建立信任关系 |
| 端点证书对应的公私钥 | 端点身份认证：签名和验签 |
| 临时密钥交换材料 | 握手中协商共享秘密 |
| 流量密钥 | 对 TLS 记录进行认证加密和验证解密 |

以 TLS 1.3 使用证书和临时密钥交换的常见握手为例：两端各自生成临时秘密，交换可公开的密钥协商信息，各自计算出相同的共享秘密，再结合握手信息派生流量密钥。临时秘密不直接传输。

证书签名认证把握手协商与身份关联起来，防止被冒充者替换。真实握手中密钥交换和认证相互配合，不能理解为“先完成全部认证，之后才开始任何加密”；TLS 1.3 中一部分握手消息本身就已加密。

```text
身份认证：B 私钥签名 → A 用 B 公钥验签
数据保护：A 用 A→B 流量密钥加密 → B 用对应密钥验证、解密
```

两个传输方向使用不同的流量密钥。内存数据不是由证书私钥逐页加密，也不是拿公开证书当密码。

这些例子基于 TLS 1.3，不表示实验环境必然已经协商到该版本；实际版本和算法取决于两端库、能力与配置。本轮未执行 TLS 握手抓包或配置验证。

### 39.9 TLS record 与认证标签

TLS 接收迁移字节流后，将数据组织成 record，分别保护，不需要等待整台虚拟机的内存都生成完毕。

概念结构：

```text
TLS 记录头 │ 加密后的内容及认证标签
```

TLS 1.3 使用 AEAD（带关联数据的认证加密），结合流量密钥、每条记录的 nonce、相关头部信息等生成和验证密文。nonce 的生成与该方向的记录序号等有关；实际字段布局与算法细节本轮不展开。

认证标签是密码学完整性凭据，不是证书数字签名、普通哈希或“放在整次迁移末尾的一份总校验”。接收端必须结合密钥与协议上下文验证，不能只比较收到的标签文字。

```text
从 TCP 累计一条 TLS 记录
    ↓
TLS 层执行验证、解密
    ├─ 成功：把明文字节交给迁移代码
    └─ 失败：不交付为有效明文，报错并终止连接
```

验证和解密由 TLS 层完成；不是 TLS 只验标签，再让 QEMU 的 RAM 解析代码解密密文。TLS 检测到异常并不自动修复原始数据，也不能仅凭验证失败确定一定存在恶意攻击。

### 39.10 record、内存页、section、TCP 包的边界不同

| 单位 | 所属层次 | 谁理解其含义 |
| --- | --- | --- |
| RAM 页记录 | QEMU 迁移格式 | RAM 保存/加载逻辑 |
| section | QEMU 状态流组织 | 外层迁移框架及对象加载逻辑 |
| TLS record | 安全传输 | TLS 库 |
| TCP 分段 | 网络传输 | TCP 协议栈 |

一页可跨多个 TLS record，一个 record 也可包含多个迁移记录或它们的片段；record 也不等于一个 TCP 包。TLS 不知道 RAMBlock、偏移、EOS 的业务含义，它只还原受保护的原始字节。QEMU 再按迁移规则读出足够的数据并恢复对应内存。

TLS 验证通过，不替代设备版本、字段和加载检查。CPU/机器类型等兼容检查还可能在数据接收前进行，不是所有检查都在“最后解密后”统一执行。

### 39.11 libvirt 怎样让 QEMU 使用 TLS

管理员提前在各自主机准备证书、私钥和信任材料，并配置位置。libvirt 通过本地 QMP 控制各自 QEMU，建立 TLS 凭据对象和应用迁移参数。

[源码：qemuMigrationParamsEnableTLS](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration_params.c#L1169) 的主要工作包括：

- 检查迁移 TLS 证书目录配置及 QEMU 支持能力。
- 根据本端客户端/服务端角色、验证设置等准备 TLS 对象属性。
- 通过 `qemuDomainAddTLSObjects()` 等辅助函数在 QEMU 中创建对象。
- 将 TLS 对象名称填入 `tls-creds` 迁移参数。
- 按需设置 `tls-hostname`，用于验证预期目标身份。
- 参数随后由应用迁移参数的逻辑通过 QMP 传给 QEMU。

`tlsAlias` 是对象名称，不是密码或流量密钥。若 libvirt 建好连接再将 fd 交给 QEMU，QEMU 不能仅凭 fd 得知期望验证的服务器名，需配置相应信息。

QEMU 创建 TLS 凭据对象时加载相关材料，不是每传一页都重新读取证书。若私钥有口令，还涉及 secret 对象等配置；本轮没有部署这些内容。

```text
管理员准备本机证书等材料
    ↓
两端 libvirt ──各自本地 QMP──→ 各自 QEMU 的 TLS 凭据/迁移参数
    ↓
源 QEMU（客户端）──TCP 上的 TLS 握手──目标 QEMU（服务端）
    ↓
两端 TLS 层验证身份、建立密钥并保护迁移数据
```

QMP 负责配置和控制，TLS 握手消息走两端 QEMU 的迁移连接。启用 TLS 不表示把内存数据交回 libvirt 转发。证书或握手失败，不能将这条连接当成已建立的安全迁移通道继续发送。

### 39.12 TLS 参考与本节复述

- [QEMU TLS 配置、证书命名及证书验证](https://www.qemu.org/docs/master/system/tls.html)
- [TLS 1.3 握手概览](https://www.rfc-editor.org/rfc/rfc8446.html#section-2)
- [CertificateVerify](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.3)
- [TLS 记录保护](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.2)

复述：QEMU 按自己的迁移格式生成字节；libvirt 通过 QMP 配置本地 QEMU 使用预先准备的证书材料。两端在 TCP 上完成 TLS 握手，用证书和签名验证身份，协商派生流量密钥。TLS 将字节组成 record 并认证加密，目标 TLS 验证、解密后向迁移代码提供明文，QEMU 再解析并恢复虚拟机状态。

## 40. 第四项：异常恢复与后续学习进度

### 40.1 异常与恢复：故障场景、结果不确定与恢复边界

本节继续限定在**virsh 协调两端、普通 pre-copy、原生数据传输**。不能直接套用到 post-copy、P2P 或所有磁盘复制阶段。

#### 40.1.1 先区分哪条连接断开

```text
控制连接：virsh ↔ 对应主机上的 libvirt，承载 RPC
数据连接：源 QEMU ↔ 目标 QEMU，承载迁移流，可启用 TLS
```

控制连接断开，不直接证明数据连接也已断开；控制请求没有得到回复，不证明远端没有执行。本地 libvirt 与 QEMU 的 QMP 也是另一条连接，不能把全部故障笼统称为“网络断了”。

#### 40.1.2 场景一：pre-copy 中途数据连接失败，目标尚未接管

```text
源虚拟机：仍保留运行状态，可能还在运行，也可能已到暂停阶段
目标实例：只接收了部分状态，尚未开始客户机执行
```

处理方向：识别迁移失败，取消迁移并清理未完成的目标接收实例；源端原来仍在运行时，尽量保持运行，已经暂停时在安全条件允许下尝试恢复。

纠正前面的口述：

- 不是让只收到半份数据的目标虚拟机恢复运行。
- 不是把目标收到的半份数据再迁回源端；普通预拷贝中源端仍保留自己的状态。
- 清理目标运行实例不等于无条件删除目标磁盘镜像；非共享存储的副本处理留到 NBD 专题。
- 不是所有阶段失败都能恢复；源状态是否可用、目标是否接管、资源与锁条件等需要判断。

参考：[QEMU 迁移设备开发说明中的源状态保留](https://www.qemu.org/docs/master/devel/migration/main.html#general-advice-for-device-developers)。

#### 40.1.3 场景二：Finish 已执行，但回复丢失

一个可能的时间线：

```text
virsh 向目标 libvirt 发送 Finish 请求
    ↓
目标完成接管，客户机开始运行
    ↓
目标发出 Finish 成功回复
    ↓ 控制连接故障，回复未到达
virsh 无法获得成功结果；源端仍暂停等待收尾
```

回复的接收者是 **virsh 进程中的 libvirt 库**，不是直接发给源端守护进程。正常情况下，再由客户端发 Confirm 通知源端。

但从客户端的观察看，失联可能发生在请求发送前、执行中、执行后或回包途中。客户端不能仅凭“没收到回复”确定目标已经运行，也不能确定目标没有运行，这就是**执行结果不确定**。

即使目标已经运行，Confirm 等源端收尾仍可能未完成，不能把这种情形说成“整个迁移已经全部结束”。

#### 40.1.4 为什么不能盲目恢复源端，也不是必须同时暂停两端

若目标已运行，源端再恢复会产生两个活跃实例：共享存储可能双写，非共享存储也可能重复对外服务、分别写入而导致数据分叉。

处理原则：

| 已知情况 | 应理解的方向 |
| --- | --- |
| 目标尚未接管，源状态和资源条件允许 | 可以按相应取消/恢复路径让源端继续服务 |
| 已确认目标接管并正常运行 | 让目标继续运行，源端停止执行并完成清理 |
| 目标执行结果不能确认 | 不能因没有成功回复就贸然恢复源端；需进一步核实并满足安全恢复条件 |

libvirt 文档说明，客户端协调模式中失联会尝试中止迁移并恢复源端；不能安全完成时可能保留一端或两端暂停。这是可能的结果，不是“所有失联都强制同时暂停两端”的通用算法。连接已断时，也未必能够控制另一端。

参考：[libvirt managed direct migration](https://libvirt.org/migration.html#managed-direct-migration)。

**复述模板：**先判断断的是哪条连接、故障发生在哪个时刻，再判断目标是否接管、源端是否还能安全恢复。没有收到成功回复，只说明结果未知，不等于目标没有执行。

#### 40.1.5 结果未知时，重发命令不等于查询

假设第一次 Finish 已成功执行，目标已运行、迁入作业已结束，但成功回复丢失。再发 Finish，可能因为已经没有迁入作业而报错。第二次报错不证明第一次失败。

源码 `qemuMigrationDstFinish()` 先检查 `qemuMigrationJobIsActive(vm, VIR_ASYNC_JOB_MIGRATION_IN)`；正常收尾会调用 `qemuMigrationJobFinish()`。这些阶段接口不能被默认当作“重复调用总能返回原结果”的接口。

- 重发 Finish：要求对方再次执行操作。
- 查询状态：了解对应 UUID 的虚拟机、迁移作业目前处于什么状态。
- 查询失败：仍然无法获得状态，不能据此断定对方已经停止。

需要结合两端运行状态、作业状态、日志和资源所有权核实结果；某一次查询只是观察，不自动保证后续状态不会改变。

参考：[Finish 作业检查与收尾](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L7087)。

#### 40.1.6 运行状态与资源锁是不同问题

`paused` 表示客户机执行状态，不证明它仍有权写共享磁盘。若目标已接管，盲目恢复源端可能产生冲突。

在 `qemuProcessStartCPUs()` 中，先调用 `virDomainLockProcessResume()`，失败就返回；之后才调用 `qemuMonitorStartCPUs()`。在正确配置、所有参与者遵守同一套有效排他锁的前提下，锁可阻止冲突的资源使用。

| 机制 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 运行状态查询 | 查询时实例的执行状态 | 不能单独证明有权恢复或数据一致 |
| 资源锁 | 对受保护资源的互斥使用约束 | 不证明迁移已完成或客户机应用健康 |
| 取得锁失败 | 本次未能取得锁 | 也可能是锁服务或存储异常，不能直接证明目标运行 |

libvirt 有 `lockd`、`sanlock` 等插件，也有不执行锁操作的 `nop`；不能看到调用锁接口就认定实验已配置保护。非共享存储中，两端各锁住自己的磁盘副本也不能防止重复服务、数据分叉。

参考：[锁管理器](https://libvirt.org/kbase/locking.html)、[恢复 CPU 的源码](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_process.c#L3447)。

#### 40.1.7 隔离（fencing）与恢复不是同一步

管理连接不可达时，目标 QEMU 仍可能访问磁盘并服务用户。fencing 的作用是通过可靠手段阻止一端继续操作相关资源，例如独立电源管理关闭主机，或存储侧撤销访问权。断开 SSH 不能代替这些措施；存储隔离也不等于停止全部网络服务。

隔离并不会自动使旧源端状态变得可恢复：

```text
源端暂停在 T1
目标接管并运行到 T2，期间修改了内存和磁盘
即使此后目标被隔离，源端内存仍停留在 T1
```

共享存储可能已有 T2 的新磁盘内容，非共享存储的源副本可能已经落后。仍须选择一致、可用的状态恢复，不能直接 resume 旧源端。这是故障恢复设计，不表示 libvirt 在每次迁移失败时自动关闭目标主机。

> 查询用来了解状态；隔离用来阻止竞争；恢复还要选择正确的数据与运行状态。

参考：[ClusterLabs fencing](https://clusterlabs.org/projects/pacemaker/doc/3.0/Pacemaker_Explained/html/fencing.html)。

#### 40.1.8 post-copy：两端可能共同持有完整最新状态

post-copy 已切换且尚未传完时，客户机在目标执行。目标缺页时向源请求，源也在后台继续发送剩余页。

```text
页 P：已经到目标，并被目标修改，最新内容在目标。
页 Q：尚未到目标，仍需源端提供。
```

源端即使保留 P 的旧副本，也不具备目标后续的内存修改和最新 CPU 状态；目标又可能缺 Q。因此不能照搬普通 pre-copy 切换前的回退思路。

若只是连接故障、两端 QEMU 及所需状态仍保留，并满足版本/配置条件，可修复或重建通道，执行恢复握手、同步页接收情况，再继续原来的 post-copy。这是继续迁移，不是回退源端。

`POSTCOPY_PAUSED` 是迁移状态，不必等同于所有客户机 CPU 已停止执行：目标可能继续使用已收到的页，访问缺失页的线程会等待。任一端所需状态丢失，可能使运行中的虚拟机无法恢复；此时不能机械地关闭源 QEMU，它可能仍保留必需页。

参考：[QEMU post-copy recovery](https://www.qemu.org/docs/master/devel/migration/postcopy.html#postcopy-recovery)。

| 易混淆说法 | 准确理解 |
| --- | --- |
| XDR 就是 gRPC | XDR 是此处 libvirt RPC 使用的编码；不是 gRPC |
| RPC serial 用来给分片排序 | serial 关联请求/回复；流式接收按消息长度累计 |

| 迁移按整个 RAMBlock 一次传完 | 当前普通页路径按页组织；块身份用于定位 |
| 传源端内存指针让目标直接使用 | 传块身份和块内偏移，目标定位自己的内存 |
| PAGE/ZERO 按内容重要性分级 | 它们描述记录的编码与恢复方式 |
| ZERO 表示未使用的内存 | 表示页内容全零；使用历史无关 |
| EOS 表示一个 RAMBlock 完成 | EOS 表示本段 RAM 记录结束 |
| footer 对比整段长度并做哈希 | 只检查固定标记和 section ID，帮助检测错位 |
| EOF 表示最后一个内存页结束 | EOF 是主要迁移状态流的结束标记 |
| completed 必然表示客户机运行 | 迁入可 completed 而客户机保持 paused |
| Broadcast 是网络广播 | 此处是 libvirt 进程内部唤醒通知 |
| 机器类型版本就是 QEMU 软件版本 | 新 QEMU 可能支持旧机器类型；两者不能混同 |
| CPU 配置迁移就是寄存器复制 | 配置决定能力，寄存器等属于运行状态 |
| SSH 登录成功就加密了迁移数据 | 只保护经过 SSH 的通道；原生 QEMU 数据路径另行考虑 |
| QEMU 迁移数据先通过 XDR 编码 | XDR 属于 libvirt RPC；QEMU 迁移流使用自身二进制格式 |
| B 把公钥临时塞进 CA 证书 | B 的公钥在签发时已写入自己的端点证书，不能任意更改 |
| B 用私钥给自己的证书再次签名 | TLS 1.3 CertificateVerify 签本次握手相关内容 |
| A 用自己的公钥解出 B 的证书 | A 用 B 的公钥验签，结果是有效/无效；不是解出证书 |
| 证书私钥直接加密每页内存 | 证书密钥用于身份认证，流量密钥用于数据保护 |
| TLS 验标签后把密文交给迁移代码解密 | TLS 完成验证、解密后才交出有效明文 |
| TLS record 就是一页或一个 TCP 包 | 三者属于不同层次，边界不必一致 |
| QMP 承载两端 QEMU 的 TLS 握手 | QMP 配置本机 QEMU；握手走两端迁移 TCP 连接 |
| pre-copy 半途失败就恢复目标端 | 目标尚未接管时清理未完成实例，源端保持运行或安全恢复 |
| 把目标半份内存迁回去才能恢复源端 | 普通 pre-copy 源端仍保留状态，无需这样回传 |
| Finish 没回复就证明目标没运行 | 请求可能已执行但回复丢失，结果不确定 |
| 控制失联必须让两端都暂停 | 取决于实际状态和可控性；不能盲目恢复源端，也未必能控制目标 |
| 非共享磁盘就没有双活风险 | 仍可能重复服务与磁盘数据分叉 |

截至 2026-11-03：异常恢复补充见第 40 节；NBD 学习已展开并整理在第 42 节，新增纠错集中在第 42.18 节。

## 42. 非共享存储与 NBD：从连接到磁盘内容恢复

本节整理截至 **2026-11-03** 的讨论。主要场景为 libvirt 协调 QEMU、普通 pre-copy、原生迁移通道及 mirror + NBD 磁盘复制。图中的文件路径、导出名称、端口和大小都是教学示例。

### 42.1 分工与两条数据通道

| 组成 | 职责 |
| --- | --- |
| libvirt | 通过 QMP 配置、启动和检查两端 QEMU 的迁移及磁盘作业 |
| 源 QEMU 的 mirror | 组织磁盘内容复制、跟踪变化、维护作业状态 |
| 源 QEMU 的 NBD 客户端 | 向目标导出发送磁盘操作请求并接收回复 |
| 目标 QEMU 的内置 NBD 服务端 | 提供磁盘导出，通过目标块后端执行操作 |
| TCP socket / TLS | 承载字节流；启用 TLS 时保护通信 |

```text
源磁盘 → 源 QEMU mirror → NBD 客户端
                            │ NBD 请求 / TCP（可加 TLS）
                            ▼
目标磁盘 ← 目标 QEMU 块后端 ← 内置 NBD 服务端
```

目标端提供可写磁盘入口，源端向它写入。这里不要求另起一个独立的 NBD 服务进程，也不要求使用 Linux `/dev/nbdX` 来完成 QEMU 的客户端访问。

```text
内存、CPU、设备状态：QEMU 迁移格式 → 迁移连接
磁盘内容：          NBD 操作     → NBD 连接
```

磁盘内容不是放进 RAM PAGE 记录中传输。NBD 提供块访问协议，本身不会自动发现源盘变化并完成镜像同步。

参考：[QEMU mirror + NBD](https://www.qemu.org/docs/master/interop/live-block-operations.html#qmp-invocation-for-live-storage-migration-with-drive-mirror-nbd)。

### 42.2 端口、连接与导出：分别定位什么

NBD 的标准端口是 10809，但迁移不必使用它。libvirt 的 `qemuMigrationDstStartNBDServer()` 可以使用指定端口，也可以从迁移端口池申请端口，再通过 QMP 启动目标 QEMU 的 NBD 服务。

- `--disks-port` 指定目标磁盘传输监听端口。
- `--disks-uri` 可以指定磁盘通道的地址/端口或 UNIX socket，与 `--disks-port` 互斥。
- 客户端连接的目标端口必须对应服务端实际监听的端口。
- SSH 控制端口、内存迁移端口和 NBD 磁盘端口不能混为一谈。

| 信息 | 定位对象 |
| --- | --- |
| IP、端口 | NBD 服务 |
| export name（导出名称） | 服务提供的某个逻辑磁盘入口 |
| offset、length | 该磁盘中的数据区域 |

一个监听端口可以接受多条 TCP 连接。在当前常见多盘路径中，每块盘分别连接并选择自己的导出：

```text
连接 1 → B:50001 → disk1 导出 → 目标盘 A
连接 2 → B:50001 → disk2 导出 → 目标盘 B
```

不必为每次 WRITE 重连，也不必先复制完 A 再开始 B。进入传输阶段后，一条 NBD 连接关联到选定导出，不能在后续 WRITE 中随意换盘。本节以每盘一条连接说明，不把它当作 NBD 所有实现的唯一连接数量限制。

参考：[virsh migrate 参数](https://libvirt.org/manpages/virsh.html#migrate)、[目标 NBD 服务启动源码](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L635)。

### 42.3 握手与导出选择

以 fixed newstyle 协商为例：

```text
建立 TCP
  → 交换 NBD 协议标识与握手标志
  → 按配置进行 TLS 升级及其他协商
  → 客户端用 NBD_OPT_GO 指定 export name
  → 服务端返回容量、能力等信息及成功确认
  → 进入读写传输阶段
```

`NBD_OPT_GO` 成功后进入传输阶段。`NBD_OPT_INFO` 用于了解导出信息而不立即进入传输；兼容旧服务时还可能涉及 `NBD_OPT_EXPORT_NAME`。名称不是文件路径，映射关系由服务端配置。

参考：[NBD 协议与协商选项](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md)。

### 42.4 WRITE 请求、回复与请求标识

一条普通写请求的概念结构：

| 字段 | 示例 |
| --- | --- |
| 协议标记、命令标志 | 用于解析及表达附加要求 |
| type | NBD_CMD_WRITE |
| cookie | 42，用于关联本次请求和回复 |
| offset | 8192 字节 |
| length | 4096 字节 |
| data | 要写入的 4096 字节 |

进入读写阶段后，不必在每次 WRITE 中重新传导出名称。服务端对当前连接关联的导出执行操作，回复携带同一 cookie；简单回复的 error=0 表示成功，写回复不需要回传原数据。

一条连接可有多个在途请求，回复不必按请求顺序返回，因此要按 cookie 匹配。**这个 NBD cookie 只是请求标识，不是五阶段之间交换的 libvirt migration cookie。**

NBD 消息有自己的二进制格式，不使用 libvirt RPC 的 XDR；TCP 分段边界也不等于一次磁盘操作边界。

参考：[NBD 请求格式](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md#request-message)、[回复与传输语义](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md#transmission)。

### 42.5 写成功、FLUSH 与 FUA

普通 WRITE 成功不一定意味着数据已到非易失存储，目标存储栈可能还有缓存。

| 操作 | 语义 |
| --- | --- |
| 普通 WRITE | 完成本次写操作，允许在持久化前回复 |
| NBD_CMD_FLUSH | 对规则所覆盖的此前写入完成持久化后，才能成功回复 |
| WRITE + NBD_CMD_FLAG_FUA | 本次写入持久化后，才能成功回复 |

教学上的明确顺序：先等待一批 WRITE 成功回复，再发 FLUSH 并等待成功。不能把 FLUSH 当成自动覆盖所有尚在途中的写入。服务端必须已声明相应能力，客户端才能使用 FLUSH/FUA。

FLUSH 不重新传输原数据；FUA 也不是另一份磁盘副本。实现与底层存储需要正确遵守持久化语义。持久化完成不等于镜像同步作业结束，因为客户机还可能继续产生新写入。

参考：[NBD 写入顺序、FLUSH 与 FUA](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md#ordering-of-messages-and-writes)。

### 42.6 mirror 怎样跟踪复制期间的新写入

在 background 模式中，mirror 用脏位图记录需要同步的区域。位图是“待办状态”，不保存这一区域的新数据副本，也不表示数据损坏。

```text
源区域 B = 旧内容 → 已复制到目标
客户机把源 B 改为新内容
    → B 再次被标记为需要同步
    → 后台读取源 B，并向目标写入新内容
```

`bdrv_mirror_top_do_write()` 的后台路径会调用 `bdrv_set_dirty_bitmap()`。实际代码还协调在途 I/O 和范围冲突；不能把它实现成“复制完一律清标记”，否则会漏掉复制期间的新写入。

| copy-mode | 新写入的处理 |
| --- | --- |
| background | 跟踪变化，后台继续同步 |
| write-blocking | 写源端时同步执行目标写入，同时仍进行后台复制 |

write-blocking 不表示两块磁盘同一瞬间落盘，也不自动等于 FUA。`--copy-storage-synchronous-writes` 与同步处理源、目标写入有关。

达到 READY 后作业仍然存在，继续处理变化；READY 也不意味着自动切换到了 write-blocking 模式。`actively-synced` 与一般的 READY 概念需要区分。

参考：[mirror 写入路径](https://github.com/qemu/qemu/blob/master/block/mirror.c)、[MirrorCopyMode 定义](https://github.com/qemu/qemu/blob/master/qapi/block-core.json#L1468)。

### 42.7 磁盘 READY 怎样与内存迁移配合

当前阅读路径的主要顺序：

```text
启动各磁盘 mirror
  → 等待本次需复制的磁盘全部 READY
  → 启动内存等状态迁移
  → mirror 继续同步客户机的新磁盘写入
  → 最终切换时源客户机 CPU 暂停
  → 处理剩余磁盘同步、在途 I/O 和作业结果
  → 完成剩余状态传输及目标接管
```

`qemuMigrationSrcNBDStorageCopy()` 等待磁盘就绪，之后执行 `qemuMigrationSrcStart()`。最终等待 STOP 事件处理后，调用 `qemuMigrationSrcNBDCopyCancel(vm, false, ...)` 收尾磁盘作业。

这里的 **Cancel 不等于整次迁移失败或删除副本**：对已 READY 的 mirror，可以正常结束持续同步、保留目标结果。`false` 表示不是以整次迁移失败的方式强制中止。

若 QEMU 等待在 pre-switchover，libvirt 在块作业收尾后调用 `qemuMigrationSrcContinue()`，继续设备状态序列化等迁移工作。这里继续的是迁移流程，不是恢复源客户机 CPU 执行。

CPU 暂停本身不证明已提交的磁盘 I/O 全部完成；源端磁盘和内存必须在最终切换中协调，而不能只看一次 READY 就让目标运行。

参考：[磁盘初始复制](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L1289)、[最终等待与收尾](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L5205)、[取消单个作业的语义](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L941)。

### 42.8 磁盘、分区、qcow2 文件与 mirror 的关系

NBD 不根据内容判断“系统数据还是业务数据”来分盘。虚拟机配置先决定有哪些磁盘，复制任务再绑定对应源盘与目标导出。

| 对象 | 含义 |
| --- | --- |
| 虚拟磁盘 | 客户机可访问的块设备，是当前每盘复制任务的对象 |
| 磁盘内的分区 | 一块磁盘内部划分的区域，不因此自动变成另一块虚拟磁盘 |
| qcow2 文件 | 承载虚拟磁盘的一种后端格式 |
| 基础镜像 + 变化层 | 多个文件也可以共同承载同一块虚拟磁盘 |
| mirror 作业 | 绑定源块节点与目标块节点，管理复制和变化跟踪 |
| NBD 导出 | 目标块后端向远端提供的访问入口 |

简单配置可以“一盘一 qcow2”，但这不是通用定义，也不是“一文件必有一个 mirror”；磁盘还可以由 raw 文件、块设备等承载。

```text
任务 A：源盘 A → 目标盘 A 的导出
任务 B：源盘 B → 目标盘 B 的导出
```

客户机写盘 B 的偏移 8192，任务 B 处理对应变化；内容即使与盘 A 相同，也不会归给任务 A。

源码遍历 `vm->def->disks`，对需迁移磁盘调用 `qemuMigrationSrcNBDStorageCopyOne()`，建立磁盘作业记录，并通过 QMP 创建 mirror。

参考：[逐盘启动](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L1366)、[单盘复制作业](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L1222)。

### 42.9 多盘就绪检查

各盘有独立进度；libvirt 统一检查本次参与迁移的磁盘：

- 任一作业 FAILED：报告错误。
- 还有作业未 READY：继续等待。
- 全部 READY：通过这一步检查。

先 READY 的作业仍维护同步，不必等另一盘开始才工作。全部 READY 也不是将所有盘永久冻结的快照，仍需最终暂停与 I/O 收尾。

源码：`qemuMigrationSrcNBDStorageCopyReady()` 中通过 `notReady++` 统计未就绪作业。

参考：[多盘检查](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L806)。

### 42.10 复制的是逻辑内容，不是照搬 qcow2 文件布局

qcow2 除客户机数据外，还有格式头、L1/L2 映射、引用计数等元数据。逻辑磁盘偏移和镜像文件偏移不是同一个概念。

```text
源：逻辑偏移 8192 → 源 qcow2 映射 → 文件位置 X，内容 ABC
目标：逻辑偏移 8192 → 目标 qcow2 映射 → 文件位置 Y，内容 ABC
```

X 和 Y 可以不同，但客户机从相同逻辑位置读取到的内容需要一致。目标自行维护格式映射，不要求把源 qcow2 的内部表、布局、快照结构一并照搬。

这里的逻辑内容也包括客户机分区表、文件系统元数据和文件数据。QEMU 通常按块处理，无需逐个识别客户机文件名。此结论限定当前导出逻辑块后端的迁移路径；NBD 协议本身只定义导出字节空间的访问。

参考：[qcow2 cluster mapping](https://www.qemu.org/docs/master/interop/qcow2.html#cluster-mapping)、[NBD introduction](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md#introduction)。

### 42.11 一段磁盘数据怎样经过内存、NBD 到达目标

普通数据复制示例，先忽略零区域等优化：

1. mirror 选出逻辑 `offset=8192`、`length=4096` 的待同步区域。
2. 源 QEMU 的块层按 qcow2 映射或 backing chain 读取内容，放入本进程内存缓冲区。
3. mirror 向配置好的 NBD 目标后端写相同逻辑偏移。
4. NBD 客户端编码 WRITE 请求头及数据，经过 TLS（若启用）和 TCP 发送。
5. 目标解密、解析 NBD 请求，通过自己的块层完成相同逻辑位置的写入。
6. 目标回复，源端据此处理作业进度；后续修改仍可能需要再次同步。

`mirror_read_complete()` 的普通路径通过 `blk_co_pwritev(s->target, op->offset, op->qiov.size, &op->qiov, 0)` 将读取缓冲区交给目标后端。

**读取到内存，并不代表正在迁移客户机 RAM 页。** 这里只是借用源 QEMU 的缓冲区暂存磁盘数据。

| 粒度 | 作用 |
| --- | --- |
| 磁盘逻辑扇区/字节范围 | 表达磁盘地址和操作长度 |
| qcow2 cluster | 镜像内部的分配与映射单位 |
| mirror 跟踪粒度 | 记录哪些区域需要同步 |
| 一次 I/O / NBD 请求长度 | 本次实际读写的字节数 |
| 内存缓冲区、TLS record、TCP 分段 | 分别服务于暂存、安全封装和网络传输 |

这些单位无需一一对应。若逻辑扇区为 512 字节，一次 4096 字节读操作覆盖连续 8 个扇区；4 KiB 只是例子，不是固定协议大小，实际还要遵守对齐与请求大小限制。

参考：[mirror 普通复制路径](https://github.com/qemu/qemu/blob/master/block/mirror.c#L256)。

### 42.12 基础镜像链、全量与变化层复制

用“原稿 + 修改记录”理解：

| 区域 | base 基础层 | changes 当前层 | 客户机实际读到 |
| --- | --- | --- | --- |
| 1 | AAA | 未覆盖 | AAA |
| 2 | BBB | XXX | XXX |
| 3 | CCC | 未覆盖 | CCC |

- 全量同步：让目标获得组合后的 AAA、XXX、CCC；不要求复制相同的文件层级。
- 顶层/浅复制：主要复制当前层的 XXX；目标必须已具有正确基础内容，并正确关联目标当前层。
- 目标基础层若区域 1 是错误的 ZZZ，即使 XXX 的 NBD 写入成功，最终得到的也是错误结果 ZZZ、XXX、CCC。

源端若是多层链，目标需具有整个未复制底层所呈现的内容，不只是一个同名文件。相同文件名不能证明相同基础内容。

`--copy-storage-all` 表达全量复制；`--copy-storage-inc` 依赖相同基础内容来做增量复制，不是自动比较任意两份镜像找差异，也不是一般增量备份的脏位图机制。

还有两个不同时间范围：

```text
迁移前：相对基础层，区域 2 已从 BBB 改为 XXX → 初始复制 XXX
迁移中：客户机又把 XXX 改为 YYY → mirror 持续同步 YYY
```

> 镜像链与复制模式决定初始复制范围；运行中的 mirror 跟踪复制期间的新变化。

参考：[QEMU 浅复制示例](https://www.qemu.org/docs/master/interop/live-block-operations.html#qmp-invocation-for-live-storage-migration-with-drive-mirror-nbd)、[virsh 全量/增量选项](https://libvirt.org/manpages/virsh.html#migrate)。

### 42.13 NBD 使用 TLS：STARTTLS 与实际加密分开

```text
已有 TCP 连接
  → NBD 初始 fixed newstyle 握手
  → NBD_OPT_STARTTLS
  ← NBD_REP_ACK
  → 同一连接上的 TLS 握手：身份验证、协商密钥
  → 在 TLS 内继续导出选择和磁盘操作
```

STARTTLS 是请求升级，不是加密算法，也不要求建立第二条 TCP 连接。源 QEMU 在 `nbd_receive_starttls()` 中：

1. `nbd_request_simple_option(..., NBD_OPT_STARTTLS, ...)` 处理升级请求/回复。
2. `qio_channel_tls_new_client(ioc, ...)` 用 TLS 通道包装原 I/O 通道。
3. `qio_channel_tls_handshake(...)` 执行握手。

```text
源 QEMU 内部：mirror → NBD 请求字节 → TLS 库 → socket
目标 QEMU 内部：socket → TLS 验证/解密 → NBD 解析 → 磁盘后端
```

TLS 通道通过 `qcrypto_tls_session_write()`、`qcrypto_tls_session_read()` 等接口工作。NBD 的请求头、偏移、长度、数据及回复在升级后都受到 TLS 保护。不是另外起一个进程替 QEMU 加密。

内存和磁盘是独立通道，即使复用证书材料，也需各自建立 TLS 会话。不能看到内存已加密就推断 NBD 已加密。STARTTLS 同意后握手失败，应终止该会话，不能在同一会话退回明文继续。

参考：[NBD TLS 规则](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md#tls-support)、[QEMU NBD TLS 升级](https://github.com/qemu/qemu/blob/master/nbd/client.c#L617)、[TLS 通道读写](https://github.com/qemu/qemu/blob/master/io/channel-tls.c#L505)。

### 42.14 磁盘复制失败与连接中断

先限定源端仍运行、目标尚未接管：

| 故障 | 可得结论 |
| --- | --- |
| 目标返回写错误 | 本次未成功完成；不保证已经修改的部分自动回滚 |
| 没收到回复而连接中断 | 写入可能尚未执行、部分执行或已完成但回包丢失，不能当作成功确认 |

```text
NBD 错误/连接故障
  → 源 QEMU NBD 客户端
  → mirror 作业状态/错误处理
  → libvirt 通过 QMP 事件或查询得知
```

暂停、等待恢复还是判失败取决于错误与配置，不是所有错误都同样处理。libvirt 检查到镜像作业 FAILED 时报告错误，不能将它当成 READY。即使内存通道正常，也不能让磁盘未确认同步完成的目标接管。

如果源磁盘与实例正常，目标未接管时的方向是保留源服务，并按作业策略处理或中止迁移；清理目标接收实例不等于无条件删除目标镜像。

连接恢复不等于镜像已经一致。是否可继续，取决于作业、变化跟踪、在途请求结果和源盘后续修改等状态；不能按“已经复制 80%”直接从某个百分比续传，也不能把 NBD cookie 当成跨连接的自动去重记录。

参考：[libvirt mirror 错误检查](https://github.com/libvirt/libvirt/blob/master/src/qemu/qemu_migration.c#L806)、[NBD 请求结果](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md#request-types)。

### 42.15 实验准备：逻辑容量与实际空间

假设源镜像 `virtual size=40 GiB`，`disk size=8 GiB`：

- virtual size 是客户机看到的磁盘容量。
- disk size 是镜像在宿主机文件系统上的实际占用，不等于客户机文件系统已用空间。
- 实际占用只有 8 GiB，不代表数据都位于逻辑前 8 GiB；逻辑偏移 35 GiB 处也可能有数据。
- 目标按对应 40 GiB 逻辑容量准备，不能因源占用 8 GiB 就准备一块 8 GiB 虚拟磁盘。

目标虚拟容量足够，也要检查宿主机实际剩余空间。稀疏镜像创建成功不保证复制过程中不会空间不足；分配方式、元数据和后续写入也会影响空间需求。

libvirt 文档说明目标镜像可由用户预建，符合存储池条件时也可自动创建；`--copy-storage-inc` 要求预先创建目标镜像。是否适用需要核对实际版本、存储后端和配置。

参考：[qemu-img info](https://www.qemu.org/docs/master/tools/qemu-img.html#info)、[非共享磁盘迁移准备](https://libvirt.org/migration.html#migration-of-vms-using-non-shared-images-for-disks)。

### 42.16 实验准备：路径、磁盘设备标识与导出名称

源文件可在 `/data/vm.qcow2`，目标文件可在 `/ssd/vm.qcow2`。虚拟设备保持兼容对应，后端路径可以按主机调整。

```xml
<!-- 源端磁盘片段 -->
<disk type='file' device='disk'>
  <driver name='qemu' type='qcow2'/>
  <source file='/data/vm.qcow2'/>
  <target dev='vda' bus='virtio'/>
</disk>
```

目标对应片段可以把 source 路径改为 `/ssd/vm.qcow2`，但不能随意改变设备地址、控制器等客户机可见配置。

- XML 的 `source` 表示此磁盘的数据后端，不是在指“迁移源主机”。
- XML 的 `target dev` 表示虚拟设备的逻辑标识/排序提示，不是目标文件名，也不保证客户机中最终名称必然相同。
- NBD export name 由服务端关联到块后端，不必等于文件路径或 `vda`。
- `--xml` 提供完整的目标端 XML，支持这种宿主机路径调整；不是仅提交上述片段。持久化目标配置还需要留意 `--persistent-xml`。

```text
源 /data/vm.qcow2
  → mirror
  → NBD 连接选中 disk1（示例导出名）
  → 目标 QEMU 已配置的块后端
  → /ssd/vm.qcow2
```

改路径只是选择存储位置，不会自动完成复制。镜像准备、容量、路径访问权限和安全标签仍需在实验中验证；尚未对实际主机做这些操作。

参考：[磁盘 XML](https://libvirt.org/formatdomain.html#hard-drives-floppy-disks-cdroms)、[virsh 目标 XML 参数](https://libvirt.org/manpages/virsh.html#migrate)。

### 42.17 空白区域、零数据与未分配空间

“空白”必须区分：

| 情况 | 读取含义与处理原则 |
| --- | --- |
| 独立 qcow2 中未分配、无 backing 数据的区域 | 读取为零，目标也必须读为零 |
| 当前层未分配，但 backing 有数据 | 按 backing 读取，不能当作零 |
| 已分配且内容全零 | 可在确认零内容、能力与配置允许时优化 |
| 客户机文件系统认为空闲 | 可能残留旧字节，不能仅据此视为零 |

对确认全零的逻辑范围：

1. 已可靠确认目标对应区域本来就是零，可省略不必要写入。
2. 支持 NBD `WRITE_ZEROES` 时，可以只发偏移和长度，不携带大量零字节，让目标保证读取为零。
3. 无法使用对应优化时，可回退普通零数据写入。

```text
源区域读出全零，目标原来是 ABC
    → 什么也不做会留下 ABC，内容不一致
    → 必须让目标变成零，或先有可靠的目标已为零依据
```

目标可用稀疏分配、零标记等实现零语义，不要求实际分配同等大小的零数据。镜像 cluster 对齐、块状态和配置会影响是否采用优化，不能说所有零块必然走同一条路径。

**TRIM/discard 不等于 WRITE_ZEROES。** 单独 NBD TRIM 不保证之后读取为零；WRITE_ZEROES 即使内部借助空间回收，也必须满足读取为零的要求。

对于变化层未覆盖但基础层有 ABC 的区域：全量复制需保证 ABC 被还原；只复制变化层则依赖目标正确的基础内容，不能盲目置零。

libvirt 的零检测和“目标已为零”选项也需要满足真实前提；不能为了省传输而把含旧数据的目标声明成全零。

参考：[qcow2 未分配区域读取规则](https://www.qemu.org/docs/master/interop/qcow2.html#cluster-mapping)、[NBD WRITE_ZEROES / TRIM](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md#request-types)、[mirror 块状态选择](https://github.com/qemu/qemu/blob/master/block/mirror.c#L600)。

### 42.18 本轮纠错与学习停点

| 容易混淆 | 准确理解 |
| --- | --- |
| NBD 按数据内容分成系统盘、数据盘 | 磁盘先由虚拟机配置确定；NBD 访问选定导出 |
| 一盘一定一个 qcow2 文件 | 可以一文件，也可以多文件链或其他后端 |
| 两层 qcow2 就需要两个 mirror | 同一虚拟盘的镜像链仍可以是一个复制对象 |
| 一个监听端口只能有一条连接 | 一个端口可服务多条连接和多个导出 |
| 每写一块数据都要重连 | 复用已选中导出的连接发送多个请求 |
| 每块数据固定为 4 KiB | 4 KiB 是示例，长度遵守实现及协议限制 |
| 磁盘读入内存就是 RAM 页迁移 | 只是 QEMU 缓冲区暂存磁盘数据 |
| NBD offset 是 qcow2 文件偏移 | 此路径是导出的逻辑磁盘偏移 |
| NBD 自己保证两端不断同步 | mirror 跟踪与组织同步，NBD 执行远端操作 |
| READY 后就不用同步了 | 后续写入仍要处理，最终需协调收尾 |
| Cancel 一定表示失败 | 已 READY mirror 的正常结束也使用 cancel 语义 |
| WRITE 成功等于持久化完成 | 还要区分 FLUSH/FUA 等持久化语义 |
| NBD cookie 就是迁移 cookie | 前者关联请求/回复，后者交换迁移协商信息 |
| STARTTLS 是加密函数 | 它协商升级，QEMU 内 TLS 库实际握手和加密 |
| 复制变化层就是只复制迁移后修改 | 当前层也包含迁移前相对基础层积累的内容 |
| 空白或未分配区域一律跳过 | 需检查逻辑读取语义、backing 和目标内容 |
| 空闲块必然为零 | 客户机空闲空间可能仍有旧数据 |
| 源镜像占 8 GiB，目标容量 8 GiB 就够 | 应区分虚拟容量与实际占用 |

**记录结束位置：空白区域与零数据处理。** 这份更新记录了已讨论的协议和源码概念；尚未执行真实迁移、抓包、磁盘内容比较或故障恢复实验。后续应基于实际两端版本、磁盘 XML、存储池和网络/TLS 配置组织实验，而不是直接套用示意参数。
