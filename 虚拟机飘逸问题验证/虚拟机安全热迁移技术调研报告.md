# 虚拟机安全热迁移技术调研报告

---

**报告主题**：虚拟机安全漂移（热迁移）技术研究——数据传输安全、数据完整性与状态一致性分析

**实验环境**：KVM/QEMU + libvirt 虚拟化平台，两台物理宿主机（A、B），非共享存储部署

**完成日期**：2026 年 10 月

---

## 摘要

本调研围绕虚拟机安全漂移（热迁移）技术开展，通过在两台非共享存储宿主机（A、B）间对测试虚拟机 test2 实施在线热迁移，并结合迁移前基准建立、迁移过程观测、迁移后结果比对的全流程验证方法，系统分析了热迁移过程中**数据传输安全、数据完整性、状态一致性**三个核心维度的保证机制。调研过程中先后定位并解决了宿主机名解析异常、CPU 特性不兼容、SSH 非默认端口、反向免密缺失等 8 类实际问题，最终实现非共享存储在线热迁移完全成功，并以 Guest 内持续计数任务（counter.log）与测试文件 SHA-256 校验取得一致性的直接证据。在此基础上，本报告进一步给出迁移安全机制深度分析、国密算法（SM2/SM3/SM4）适配方案以及工程最佳实践建议。

---

## 1. 研究背景与目标

### 1.1 热迁移技术及其安全需求

虚拟机热迁移（Live Migration）指在不停止虚拟机运行的前提下，将其从一台物理主机迁移至另一台物理主机的过程，对用户与应用透明，广泛用于数据中心负载均衡、故障恢复与维护调度。

热迁移的独特安全需求在于：迁移通道承载的是虚拟机的**全部内存页、全部磁盘数据与运行状态**，属高价值敏感数据。若不加保护，同网段窃听者抓包即可还原虚拟机机密内容；若状态同步不当，迁移切换点即产生数据损坏或业务中断。因此本次调研聚焦三个维度：

| 维度 | 核心问题 | 风险 |
|---|---|---|
| 数据传输安全 | 迁移流量如何防窃听、防篡改、防劫持 | 内存/磁盘全量数据明文外泄 |
| 数据完整性 | 磁盘与文件数据在复制过程中是否零损坏 | 业务数据丢失或损坏 |
| 状态一致性 | CPU/内存/设备/时间状态在切换点是否精确连续 | 恢复失败、业务中断、状态撕裂 |

### 1.2 迁移的本质难题

热迁移本质上是把一个**持续演化的状态机**（vCPU 寄存器 + 内存 + 设备状态 + 磁盘）搬迁到另一台主机，且搬迁期间状态仍在不停变化。核心矛盾为：**复制速度赶不上状态变化速度怎么办？复制过程中两侧状态不一致怎么办？**

QEMU/KVM 的解法是一套分层收敛协议：**预拷贝（pre-copy）→ 脏页追踪 → 迭代收敛 → stop-and-copy 原子切换**，将"复制一台运行中的机器"这一动态问题转化为"复制一个冻结快照"的静态问题，以毫秒级停机为代价实现端到端一致。

## 2. 实验环境与前置检查

### 2.1 环境概况

- 虚拟化栈：libvirt/QEMU/KVM，两台宿主机 libvirt、QEMU 版本一致；
- 网络：两台宿主机同二层网段，均接入 Open vSwitch 网桥 br-ovs；
- 存储：**非共享存储**——A 的虚拟磁盘存放于 LVM/XFS，B 的磁盘位于根文件系统，决定迁移必须采用 `--copy-storage-all`（磁盘随迁移通道复制）；
- 迁移对象：虚拟机 test2（virtio 磁盘 qcow2，virtio 网卡接入 br-ovs）。

### 2.2 前置检查结论

| 检查项 | 方法 | 结论 |
|---|---|---|
| 管理链路 | 宿主机间 `qemu+ssh://` 远程 libvirt 访问 | 链路正常 |
| 软件栈版本 | libvirt/QEMU 版本比对 | 一致，无版本兼容性问题 |
| 网络配置 | 目标端 OVS 网桥检查 | br-ovs 正常启用，与源端匹配 |
| 存储布局 | 两端文件系统/挂载检查 | 不共享存储，确定非共享迁移模式 |
| 设备清单 | `virsh domblklist` | vda 系统盘 + sda 光驱（挂载 ISO），光驱需在迁移前弹出 |
| CPU 兼容性 | `virsh cpu-compare` | **不兼容**：目标端缺少 monitor、hle、rtm 特性（详见 3.2 问题 3） |

## 3. 迁移实践与问题解决

### 3.1 实施过程

1. 迁移前处理不可迁移设备：在虚拟机保持运行状态下弹出虚拟光驱 ISO，并以 `--persistent` 同步持久化配置；
2. 修改 CPU 配置为两端共同支持的固定 CPU Model（Haswell-noTSX-IBRS，`fallback='forbid'`）；
3. 执行迁移命令完成 A→B 在线迁移：

```bash
virsh migrate --live --persistent --copy-storage-all --verbose test2 \
  'qemu+ssh://root@<目标IP>/system?port=55555'
```

4. 迁移成功后目标端验证：虚拟机状态 running、磁盘已复制至目标存储目录、网络接口正常接入 br-ovs；目标端 vCPU 时间持续增长（`virsh domstats --vcpu`）、磁盘 I/O 指标持续变化（`virsh domblkstat`），证明 Guest 实际运行而非仅状态显示。

### 3.2 遇到的问题及解决方法

首次迁移及后续往返验证中共定位解决 8 类问题：

| # | 问题 | 失败环节 | 解决方法 |
|---|---|---|---|
| 1 | 虚拟光驱 ISO 阻碍迁移 | 迁移前检查 | 运行中弹出光驱 + `--persistent` 持久化 |
| 2 | 宿主机名解析异常，NBD 磁盘复制通道连接失败 | 数据通道建立 | 修正 hosts 名称解析；修正后数据传输达 100% |
| 3 | CPU 特性不兼容，数据传至 100% 后目标端状态恢复失败 | 状态恢复 | host-passthrough 改为固定 CPU Model + `fallback='forbid'` |
| 4 | SSH 非默认端口，`qemu+ssh://` 连接 22 端口被拒 | 管理链路 | URI 显式指定 `?port=55555` |
| 5 | 首次 SSH 连接指纹确认阻塞迁移命令 | 管理链路认证 | 迁移前手工 ssh 完成指纹确认 |
| 6 | 反向迁移免密未配置，认证阶段连接被断开 | 管理链路认证 | `ssh-keygen` + `ssh-copy-id` 配置单向密钥（双向迁移需双向配置） |
| 7 | Guest 不响应 ACPI 优雅关机信号 | 迁移前/后操作 | 记录为环境缺陷，操作统一采用 `virsh destroy`（两侧方式一致，对比仍公平） |
| 8 | 迁移后管理平台仍显示"关机"、原 Web VNC 会话失效 | 迁移后观测 | 属管理平台未同步归属变化；运行状态以目标端 virsh/vCPU/磁盘 I/O 直接证据为准 |

**问题 3 的机理性分析**（本次最有价值的失败案例）：虚拟机原采用 host-passthrough CPU 模式，将源宿主机物理 CPU 全部特性（含 hle、rtm 等）透传给 Guest。迁移切换阶段传输的 CPU/KVM 状态是源端特性的二进制序列，目标端硬件不具备其中部分特性，恢复时校验失败——即**迁移数据完整到达 100%，但状态"翻译不过去"**，一致性破坏发生在兼容性层而非传输层。该案例与修复后的成功迁移构成正反对照实验，证明：**状态一致的前提是两端对状态语义的解释一致**。

## 4. 完整性与一致性验证实验

### 4.1 验证方法设计

采用"迁移前基准 → 迁移中观测 → 迁移后比对"的全流程验证：

- **一致性基准**：迁移前在 Guest 内启动持续计数任务，每秒记录序号与时间戳写入 counter.log，任务全程保持运行；
- **完整性基准**：迁移前在 Guest 内创建测试文件并计算 SHA-256，校验值存于 before_sha256.txt；
- **迁移过程观测**：记录迁移命令执行、迁移进度、两端状态切换（源端 shut off、目标端 running 并自启恢复）。

### 4.2 验证结果

**状态一致性 ✅**
对比迁移前后 counter.log：计数任务在迁移过程中持续运行，**序号连续编号，未出现重置、跳变或回退**，迁移后终端状态与迁移前完全一致——Guest 工作负载在切换点上保持连续。
辅助证据：迁移前后 **IP 地址与网卡 MAC 地址保持一致**，网络层以上状态连续，仅物理出口发生切换。

**数据完整性 ✅**
迁移后重新计算测试文件 SHA-256 与基准比对：**校验值完全一致，未检测到内容修改或损坏**。该验证为端到端校验，不依赖中间机制声明，直接证明迁移后数据等于迁移前数据，为完整性证据链中最强一环。

### 4.3 迁移过程行为分析

- **内存**：QEMU 将虚拟机内存逐步预拷贝至目标端，源端继续运行产生的脏页持续补传，最终短暂停顿完成剩余状态同步后目标端恢复执行——迁移期间计数任务（内存中运行）未受影响；
- **磁盘**：非共享存储下磁盘随迁移通道复制，迁移期间 Guest 的持续写入（counter.log）全部完整保留至目标端磁盘。

## 5. 技术机制深度分析

### 5.1 状态一致性的保证机制

**（1）预拷贝 + 脏页追踪**
第一轮全量传输期间 VM 照常运行，用户无感；KVM 借助 EPT/NPT 硬件特性将 Guest 写入的内存页标记为脏页（`KVM_GET_DIRTY_LOG`），后续轮次仅重传脏页，数据量逐轮指数递减，剩余量低于阈值后进入切换。若脏页产生速率持续超过网络带宽，auto-converge（vCPU 节流）与超时回退机制保证收敛或安全失败。

**（2）stop-and-copy 原子切换——一致性的根本保证**
运行中机器的寄存器与全部内存无法在同一时刻原子读取，故迁移协议在切换阶段将 vCPU 全部暂停，把动态问题转化为静态问题：**冻结的快照可以被精确复制**。暂停期间一次性原子传输最后一批脏页、vCPU 寄存器、KVM 状态及非迭代设备状态，目标端加载后恢复执行。

**（3）单一执行源（防脑裂）与失败回退**
切换后仅目标端继续运行，源端退出，防止两侧状态分叉。且目标端正式执行前源端状态不销毁——迁移失败时源端回退继续运行，不存在中间状态，迁移整体具备**事务性**（本次首次迁移失败后源端虚拟机正常继续运行即为直接验证）。

**（4）设备状态的一致性**
虚拟机看到的"硬件"是 QEMU 进程内软件模拟的设备模型，其运行状态（队列游标、挂起中断、设备定时器进度）位于虚拟机之外、宿主机 QEMU 进程内，需在停机后序列化一次性传输。设备状态与 vCPU 执行耦合，只有 vCPU 冻结时才可精确快照——这是"RAM 可迭代、设备状态不可迭代"的根源。序列化格式依赖两端 QEMU 内部结构布局，版本不一致即解析错乱，故迁移要求两端 QEMU 版本与虚拟机定义一致。

**（5）Guest 感知时间的一致性**
停顿期间 vCPU 冻结，Guest 主观时间未流逝而物理时间已前进，造成 TSC（CPU 周期计数）与 RTC（壁挂时钟）读数矛盾。QEMU 在目标端恢复前将停顿时长折算为 TSC 偏移量预补，使 Guest 计时"假装"停顿未发生，两钟重新对齐；普通应用完全无感，时序敏感应用仍可能感知。counter.log 时间戳间隔即为此层的直接观测手段：间隔保持任务固有周期说明补偿生效，间隔拉大则为停顿泄漏的定量证据。

### 5.2 数据完整性的保证机制（非共享存储）

非共享存储下磁盘经迁移通道复制，机制为 **NBD 全量复制 + 写镜像**：

1. 源端 QEMU 内嵌 NBD 服务端，目标端连入建立磁盘复制通道；
2. `--copy-storage-all` 将 qcow2 逐块全量复制至目标端新磁盘文件；
3. **写镜像同步（关键）**：全量复制期间 Guest 仍在写盘，QEMU 对每次写 I/O 同时落源盘与目标盘——目标盘上被覆盖区域始终保持最新，与"复制后未再写"的区域无缝衔接，任何位置均为最新数据；
4. 切换阶段与内存同步完成后，目标盘与源盘到达同一状态点，目标端接管。

完整性的三重保障：

| 层级 | 机制 | 本次验证证据 |
|---|---|---|
| 传输层 | SSH 通道逐块校验，损坏自动重传 | qemu+ssh 加密通道 |
| 复制层 | 写镜像保证迁移期间新写入零丢失 | counter.log 迁移期间写入完整保留 |
| 端到端 | 迁移后独立重算校验值比对 | **SHA-256 前后完全一致** |

### 5.3 数据传输安全的保证机制

**（1）攻击面**
迁移流量包含全部内存页（登录会话、密钥、进程内存明文凭据）、全量磁盘数据（文件系统、数据库）与设备状态，为高价值窃听与篡改目标。

**（2）风险基线**
QEMU 原生迁移通道（`qemu+tcp://`）**明文、无加密、无认证**，同网段抓包即可还原内存内容，且迁移端口无认证存在劫持风险——不配置加密即明文传输。

**（3）本实验方案：qemu+ssh 加密隧道**
libvirt 将迁移数据流自动封装于 SSH 隧道，架构为：

```
源端 QEMU ─本地回环→ 源端 ssh 客户端 ══SSH 加密隧道══→ 目标端 sshd ─本地回环→ 目标端 QEMU
```

QEMU 仅监听本地回环（127.0.0.1），迁移端口不在网络暴露；加密由独立 ssh 进程实施，QEMU 完全无感知。该分层设计带来两个关键优势：**加密组件可替换（QEMU 零改动）**、**攻击面最小化（网络上不存在可扫描的迁移服务）**。

**（4）三重防线**

| 防线 | 机制 | 防护目标 |
|---|---|---|
| 机密性 | SSH 隧道加密，迁移流量全密文 | 链路窃听 |
| 完整性 | AEAD 认证加密（逐块校验码），篡改即中断 | 传输篡改、注入、重放 |
| 认证性 | 主机指纹验证（防中间人）+ 密钥认证（防未授权迁移） | 身份伪造、未授权操作 |
| 端到端裁决 | 迁移后 SHA-256 独立校验 | 最终防线，不一致即暴露 |

**（5）责任边界**
加密不由 QEMU 内置，而由**通道选型与服务器侧配置**决定：URI 方案名（ssh/tls/tcp）即加密策略，算法、端口、密钥均配置于宿主机。QEMU 始终仅对回环收发明文，密文仅存在于网络路径——此为下述国密适配可行的技术基础。

### 5.4 对外状态一致性：网络

迁移不改变 Guest 自身网络配置（IP/MAC 属于 Guest），A、B 同接 br-ovs 时虚拟网卡从源端 OVS 切至目标端 OVS，MAC 不变；切换后依靠 gratuitous ARP 通告与交换机自学习刷新转发表，产生数百毫秒 ARP 收敛延迟。本次验证 IP/MAC 前后一致：网络层以上状态连续，仅物理出口切换。

### 5.5 安全边界与遗留风险

- **源端数据残留**：`--copy-storage-all` 为复制而非搬移，迁移成功后源宿主机仍保留虚拟机完整磁盘副本。传输与目标端的安全不等于全链路闭环，源端副本的清理/销毁策略（安全擦除、留存管控）应纳入迁移安全规范；
- **信任边界**：迁移即向目标宿主机交付全部内存与磁盘数据，传输加密无法防范"目标端自身不可信"的情形——迁移目的地的选择本质是信任决策，需配套目标准入与审计；
- **post-copy 模式的权衡**：后拷贝模式可将停机压至数十毫秒且不受脏页率影响，但目标端中途故障即导致虚拟机死亡（不可回退），以可用性换取切换速度，关键业务应维持 pre-copy。

### 5.6 国密算法适配方案

QEMU/libvirt 原生迁移协议（tcp/ssh/tls）均不支持国密套件。现有方案与国密套件的映射关系：

| 安全功能 | 现有方案（qemu+ssh） | 国密对应 |
|---|---|---|
| 数据加密 | AES-CTR/GCM、ChaCha20 | SM4（分组加密） |
| 完整性校验 | HMAC-SHA2 / Poly1305 | SM3（杂凑） |
| 身份认证/密钥交换 | ED25519/RSA | SM2（椭圆曲线签名/密钥交换） |

适配路线（按落地难度递增）：

1. **网络层国密隧道封装（推荐）**：宿主机间建立国密 IPsec 隧道（SM4-ESP 加密、SM2 IKE 认证、SM3 完整性校验），QEMU 迁移命令零改动，加密对迁移完全透明。技术依据即 5.3（5）的分层结论——QEMU 仅对回环收发明文，网络路径上的国密隧道即可保护全部迁移流量。验证方式：建立隧道后重跑迁移，行为不变、业务照常，链路抓包确认为 SM4 密文；
2. **传输层国密改造**：以基于 Tongsuo/GmSSL 等国产密码库的国密改造版 SSH（或在迁移端口外建 国密 SSL 代理隧道）替换标准 sshd，满足"应用层运行国密"的更强要求，需自建软件栈与 SM2 证书体系，建议作为下一阶段课题。

**结论**：热迁移国密适配的可行路径为网络层隧道封装，对迁移透明；QEMU 原生协议不支持国密这一边界本身即为本次调研的重要结论之一。

---

## 6. 结论与最佳实践

### 6.1 调研结论

1. **数据完整性**：非共享存储热迁移依靠 NBD 全量复制 + 写镜像机制保证迁移期间磁盘数据零丢失；端到端 SHA-256 校验验证通过，未检测到任何数据修改或损坏；
2. **状态一致性**：预拷贝 + 脏页追踪 + stop-and-copy 原子切换保证切换点 CPU/内存/设备状态精确一致；Guest 内计数任务序号连续、IP/MAC 保持为直接证据，停机时间在毫秒级，业务无感；
3. **数据传输安全**：QEMU 原生协议仅提供明文通道，加密由通道选型决定；qemu+ssh 方案实现机密性、完整性、认证性三重保障，且加密层可替换——国密场景建议采用网络层国密 IPsec 隧道（SM2/SM3/SM4）透明封装；
4. **安全闭环提示**：迁移安全还需覆盖源端磁盘副本的清理策略与目标宿主机信任边界管理，二者是常被忽视的最后一环。

### 6.2 工程最佳实践

1. 跨宿主机热迁移**禁用 host-passthrough**，CPU 模型须为两端共同支持的固定型号并设 `fallback='forbid'`；`virsh cpu-compare` 应为迁移前强制预检项；
2. 迁移管理链路要求**发起方到目标方 SSH 密钥免密可达**；非默认 SSH 端口须在 URI 显式指定（`?port=`）；双向迁移需双向配置免密；
3. 迁移前以 `virsh domblklist` 清点设备，弹出光驱等不可迁移设备并以 `--persistent` 持久化；
4. 迁移前完成**版本一致性、名称解析、网络桥接、存储布局**四项环境预检；
5. 验证迁移成功与否应以目标端直接证据（virsh 状态、vCPU 时间增长、磁盘 I/O 变化）为准，**管理会话连续性与运行状态连续性分开验证**；
6. 建议 Guest 内预置计数/时间戳日志任务作为业务连续性标准验证手段，并留存迁移命令日志用于审计；
7. 生产环境建议迁移流量独立组网（专用迁移网络/VLAN），缩小窃听面并避免迁移大流量冲击业务网；
8. 制定迁移成功后源端磁盘副本的安全清理/留存策略，补全安全闭环。
