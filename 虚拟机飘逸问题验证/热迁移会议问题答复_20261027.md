## 1. CPU 配置一致性：迁移后起不来的根因与必须对齐的参数

### 1.1 问题定位

现象：迁移进度 100%，目标端状态恢复失败，源端 Guest 继续运行。

根因：迁移传输的是源端 CPU/KVM 状态的二进制序列（CPUID、MSR、XSAVE 等），目标端 CPU 缺少源端特性（本次为 `monitor`、`hle`、`rtm`），目标端 `KVM_SET_CPUID2` / `KVM_SET_MSRS` 或 QEMU 状态校验失败。**数据完整到达，但状态“翻译不过去”**。

结论：CPU 兼容性是迁移的**前置硬条件**，不是性能选项；必须纳入迁移前强制检查，不能依赖迁移失败后回滚。

### 1.2 必须保持一致的参数

| 层级 | 参数 / XML | 要求 | 检查方法 |
|---|---|---|---|
| CPU 模式 | `<cpu mode='custom'\|'host-model'\|'host-passthrough'>` | 生产禁用 `host-passthrough` | `virsh dumpxml` |
| CPU 模型 | `<model fallback='forbid'>Haswell-noTSX-IBRS</model>` | 两端一致，且目标支持 | `virsh cpu-compare`、`virsh domcapabilities` |
| CPU 特性 | `<feature name='hle' policy='disable'/>` 等 | 不可迁移特性显式 `disable`；禁止 `require` 目标没有的特性 | `virsh cpu-compare` |
| 拓扑 | `sockets/cores/threads/dies/clusters` | 完全一致 | XML diff |
| 机器类型 | `<os><type machine='pc-q35-7.2'>` | 一致，且目标 QEMU 存在该 machine type | `virsh domcapabilities --machine ...` |
| TSC | `invtsc`、`tsc-frequency`、`<timer name='tsc'>` | `invtsc` 默认阻止迁移；确需开启时固定频率并两端一致 | QEMU 启动日志、XML |
| Hyper-V / KVM | `<hyperv .../>`、`<kvm><hidden state='on'/>` | 一致（属于 CPUID 语义） | XML diff |
| NUMA / 大页 | `<numa>`、`<memoryBacking><hugepages>` | 大页尺寸一致，目标页数足够 | `virsh capabilities` |
| 固件 | loader / nvram、OVMF 版本 | 一致 | XML diff |
| 软件栈 | QEMU、libvirt 版本 | 一致或在兼容矩阵内 | `--version` |

### 1.3 推荐配置

```xml
<cpu mode='custom' match='exact' check='full'>
  <model fallback='forbid'>Haswell-noTSX-IBRS</model>
  <feature policy='disable' name='hle'/>
  <feature policy='disable' name='rtm'/>
  <feature policy='disable' name='invtsc'/>
  <topology sockets='1' dies='1' clusters='1' cores='4' threads='1'/>
</cpu>
```

- `fallback='forbid'`：目标不支持时直接失败，不静默降级；
- `check='full'`：启动和迁移时严格校验；
- 显式 `disable` 不可迁移特性，避免“源端有、目标端无”。

### 1.4 迁移前检查命令

```bash
# 1. 两端 CPU 能力对比（导出源端 CPU XML 后在目标端比较）
virsh dumpxml test2 | virsh cpu-baseline -   # 或手工提取 <cpu> 段
virsh cpu-compare --xml cpu.xml

# 2. 目标端 machine type / 域能力
virsh domcapabilities --machine pc-q35-7.2 --virttype kvm

# 3. XML 逐项 diff（CPU、拓扑、machine、设备）
virsh dumpxml test2 > a.xml
ssh -p 55555 root@B virsh dumpxml test2 > b.xml
diff -u a.xml b.xml

# 4. 迁移前 ABI 预检
virsh migrate --live --persistent --copy-storage-all --verbose --dry-run test2 ...
```

> libvirt 在 Begin/Perform 阶段会做 ABI 稳定性检查（CPU、拓扑、machine、设备型号），不通过会提前失败，不会等到 `loadvm`。把这项检查前移到变更流程，比迁移失败后再回滚更可控。

## 2. 拷贝内容与拷贝时间细化

### 2.1 拷贝内容

| 类别 | 具体内容 | 通道 | 说明 |
|---|---|---|---|
| 内存 | Guest RAM 已分配页、脏页 | migration stream | 预拷贝多轮迭代 |
| CPU 状态 | 通用寄存器、MSR、FPU/XSAVE、TSC | migration stream | stop-and-copy 一次传输 |
| 设备状态 | virtio 队列、中断、定时器、PCI 配置 | migration stream（VMState） | 只传状态，不传设备数据 |
| 迁移元数据 | domain XML、migration cookie、capabilities | libvirt RPC（SSH） | 数据量 KB 级 |
| 磁盘 | 全量磁盘数据 | NBD | `--copy-storage-all` |
| NVRAM / TPM | 固件变量、TPM 状态 | libvirt 单独处理 | 需实测确认是否随迁移复制 |

不拷贝：源端磁盘文件本身（目标端预创建）、宿主机页缓存、Guest 网络连接状态（依赖 ARP 收敛）。

### 2.2 时间模型

```
T_total   ≈ max(T_ram, T_disk) + T_downtime
T_ram     ≈ (M_alloc × N_iter) / BW + T_tail
T_disk    ≈ D_used / BW_disk
T_downtime≈ (Dirty_remaining + State_size) / BW
```

- 内存与磁盘并行复制，总时间取较大者；
- `downtime-limit` 默认 300 ms，超过则迁移失败或转 post-copy；
- 大磁盘场景瓶颈通常在磁盘复制，而不是内存。

### 2.3 实测记录模板（待填）

| 指标 | 值 | 采集方式 |
|---|---|---|
| Guest RAM | GiB | `virsh dominfo` |
| 磁盘已用 | GiB | `qemu-img info` |
| 迁移总耗时 | s | `virsh domjobinfo --completed` |
| 停机时间 | ms | 同上 |
| 平均内存带宽 | MiB/s | 同上 |
| 磁盘复制耗时 | s | `virsh blockjob test2 vda --info` |
| 脏页率 | MiB/s | `virsh domstats --dirtyrate test2` |
| 网络发送量 | GiB | `/proc/<qemu-pid>/net/dev` |

```bash
virsh domjobinfo test2 --completed
virsh blockjob test2 vda --info
virsh domstats --dirtyrate test2
```

### 2.4 结论表述建议

报告中不要只写“进度 100%”，应写成：

> 本次迁移拷贝内容为 8 GiB 内存 + 40 GiB 磁盘；磁盘复制与内存预拷贝并行，磁盘耗时 X s、内存收敛耗时 Y s，总耗时 Z s，停机 W ms；瓶颈在磁盘 NBD 复制，网络平均带宽约 B MiB/s。

## 3. 数据传输方式对比与 SSH 传输验证

### 3.1 三种方式对比

| 维度 | `qemu+ssh`（native） | `qemu+ssh --tunnelled` | `--tls` |
|---|---|---|---|
| 加密对象 | 仅 libvirt 控制 RPC | RPC + 迁移流 | 迁移流 + NBD（新版 libvirt） |
| 数据路径 | QEMU → QEMU 直连 | QEMU → libvirtd → SSH → libvirtd → QEMU | QEMU → QEMU 直连 |
| 认证 | SSH 主机密钥 + 用户密钥 | 同左 | x509 双向证书 + 主机名 |
| 性能 | 最好 | 最差（两次用户态拷贝） | 好（AES-NI） |
| 非共享存储 | 支持 | **不支持** | 支持 |
| 适用 | 只保护管理面 | 共享存储、带宽充足 | 本地盘、生产推荐 |

### 3.2 SSH 传输验证方案

**实验 1：证明 native 不加密**

```bash
# 迁移中，源端
ss -tnp | grep qemu                 # 期望：到 B:49152 / 49153 的 ESTAB
tcpdump -i br-ovs -X 'tcp port 49152' -c 5   # 期望：51 45 4d 55（QEMU 魔数）

# 目标端临时封禁迁移端口
iptables -I INPUT -p tcp --dport 49152:49215 -j REJECT
# 预期：SSH 控制仍通，迁移失败
```

**实验 2：证明 tunnelled 走 SSH**

前置：共享存储，去掉 `--copy-storage-all`。

```bash
virsh migrate --live --persistent --tunnelled --verbose \
  test2 'qemu+ssh://root@B/system?port=55555'
```

验证：

```bash
ss -ltnp | grep 4915                # 期望：无监听
tcpdump -i br-ovs -X 'tcp port 55555' -c 5   # 期望：SSH-2.0，且流量大
```

**实验 3：TLS 对比**

```bash
virsh migrate --live --persistent --copy-storage-all --verbose \
  --tls --tls-destination=nodeB.example.com \
  test2 'qemu+ssh://root@B/system?port=55555'
```

验证：

```bash
tcpdump -i br-ovs -X 'tcp port 49152' -c 5   # 期望：16 03 01
tcpdump -i br-ovs -X 'tcp port 49153' -c 5   # 期望：NBDMAGIC 后 16 03 01
```

### 3.3 对比指标表（待填）

| 指标 | native | tunnelled | TLS |
|---|---|---|---|
| 总耗时（s） | | | |
| 停机时间（ms） | | | |
| 平均带宽（MiB/s） | | | |
| 源端 CPU 占用（%） | | | |
| 目标端 CPU 占用（%） | | | |
| 网络发送字节 | | | |
| 数据是否加密 | 否 | 是（SSH） | 是（TLS） |

预期结论：`tunnelled` 明显慢于 TLS；TLS 接近线速；native 最快但数据面明文。

> 注意：`--tunnelled` 与 `--copy-storage-all` 互斥，libvirt 直接报错：
> `migration of non-shared storage is not supported with tunnelled migration and this QEMU`

## 4. 首次连接指纹确认能否默认确认

### 4.1 结论

可以做到“首次自动接受、之后严格校验”，但不能等同于“关闭校验”。

### 4.2 方案对比

| 方案 | 做法 | 安全性 | 适用 |
|---|---|---|---|
| `accept-new` | `StrictHostKeyChecking accept-new` | 首次 TOFU，之后变更拒绝 | 实验、自动化 |
| 预置 known_hosts | `ssh-keyscan` + 人工核对指纹 | 高 | 生产 |
| SSH CA | `@cert-authority` 签发主机证书 | 最高 | 规模化 |
| `no` + `/dev/null` | 关闭校验 | 无（可被 MITM） | 禁止 |

### 4.3 配置方式

`/root/.ssh/config`：

```
Host nodeB
  Port 55555
  StrictHostKeyChecking accept-new
  UserKnownHostsFile /root/.ssh/known_hosts
```

预置指纹（生产推荐）：

```bash
ssh-keyscan -p 55555 -t ed25519 nodeB >> /root/.ssh/known_hosts
ssh-keygen -lf /root/.ssh/known_hosts     # 与 CMDB/控制台核对
```

### 4.4 说明

- libvirt 的 ssh 传输调用系统 `ssh`，会读取 `~/.ssh/config`；
- 生产环境不建议 `StrictHostKeyChecking=no`，它等于放弃中间人防护；
- 主机密钥变更时应告警，而不是自动覆盖；
- 报告中应把“指纹确认阻塞”重新定义为“信任引导（trust bootstrap）问题”，并给出预置/CA 两种解法。

## 5. 热迁移的适用场景

### 5.1 适用

| 场景 | 说明 |
|---|---|
| 计划内维护 | 硬件、固件、内核、虚拟化软件升级，业务不中断 |
| 负载均衡 / 调度 | DRS、资源池动态调整 |
| 故障预警 | 结合硬件告警做预测性迁移 |
| 节能整合 | 低峰合并到少数主机 |
| 机房搬迁 | 配合存储与网络迁移 |
| 版本升级 | 同大版本、兼容矩阵内 |

### 5.2 不适用或需谨慎

| 场景 | 原因 |
|---|---|
| GPU / SR-IOV 直通 | 设备状态无法完整迁移，除非厂商提供迁移支持 |
| 机密计算（SEV/TDX） | 内存加密状态不可迁移 |
| 极高脏页率 | 无法收敛，停机超限 |
| 跨 CPU 架构 | 指令集不兼容 |
| 跨大版本 QEMU | 设备状态序列化格式不兼容 |
| 实时性极强业务 | 停机与 TSC 补偿仍有影响 |
| 无共享存储 + 大磁盘 | 复制时间长、带宽压力大 |
| 跨站点 | 延迟/带宽限制，通常用存储复制 + 冷迁移 |

### 5.3 模式选择

- 常规业务：pre-copy；
- 脏页率高、停机敏感：post-copy（以可用性换风险）；
- 大磁盘、非共享存储：copy-storage + 足够带宽/维护窗口；
- 站点级灾备：不要用热迁移替代，见第 6 条。

## 6. 其他迁移/灾备机制对比

| 机制 | RPO | RTO | 业务停机 | 适用场景 | 备注 |
|---|---|---|---|---|---|
| 热迁移 pre-copy | 0 | 秒级 | ms ~ s | 计划维护、调度 | 需共享或复制存储 |
| 热迁移 post-copy | 0 | 秒级 | ms | 脏页率高 | 目标故障可能丢 VM |
| 冷迁移 | 0 | 分钟 | 分钟 | 非关键业务 | 简单可靠 |
| save / restore | 0 | 分钟 | 分钟 | 维护、快照 | 单机 |
| 快照 | 时点 | 分钟 | 短 | 回滚 | 非持续保护 |
| 备份（全/增） | 小时级 | 小时 | 无 | 数据保护 | 需恢复演练 |
| 存储复制（同步） | 0 | 分钟 | 无 | 同城双活 | 距离受限 |
| 存储复制（异步） | 秒 ~ 分 | 分钟 ~ 小时 | 无 | 异地灾备 | 依赖带宽 |
| HA 集群 | 0 | 分钟 | 重启 | 主机故障 | 不是迁移 |
| FT | 0 | 0 | 无 | 核心业务 | 成本高，KVM 原生无 |
| COLO | ~ms | 秒 | 无 | 连续保护 | 复杂，落地少 |
| CDP | ~0 | 分钟 | 无 | 核心数据 | 成本高 |

**结论**：热迁移解决“计划内不中断”，不解决“站点级灾难”。灾备需要“复制 + 备份 + 演练”的组合，不能用热迁移替代。

## 7. 实现逻辑分析

### 7.1 libvirt 调用链

```
virsh migrate
 └─ virDomainMigrate3
     ├─ Begin3    → qemuDomainMigrateBegin3    → 校验 + XML + cookie
     ├─ Prepare3  → qemuDomainMigratePrepare3  → 建盘 + 启动 QEMU(-incoming defer)
     │                                          → nbd-server-start
     ├─ Perform3  → qemuDomainMigratePerform3  → migrate-set-parameters
     │                                          → blockdev-mirror（磁盘）
     │                                          → migrate tcp:B:49152
     ├─ Finish3   → qemuDomainMigrateFinish3   → 确认目标运行
     └─ Confirm3  → qemuDomainMigrateConfirm3  → 销毁源端
```

### 7.2 QEMU 迁移状态机

```
setup → active → pre-switchover → device → completed
                  │
                  ├─ 失败 → failed / cancelled
                  └─ post-copy → postcopy-active → postcopy-paused → postcopy-recover
```

- `ram_save_iterate`：按脏页位图迭代发送；
- `qemu_savevm_state_complete_precopy`：暂停 vCPU 后发送设备状态；
- `migration_completion`：切换点；
- `qemu_loadvm_state`：目标端加载并校验。

### 7.3 关键机制

- **脏页追踪**：KVM `KVM_GET_DIRTY_LOG` 或 dirty ring；
- **收敛控制**：`downtime-limit`、`max-bandwidth`、`auto-converge`；
- **磁盘**：`blockdev-mirror sync=full` + `write-blocking`，切换前 `block-job-complete`；
- **失败回滚**：pre-copy 失败源端 resume；post-copy 失败目标端 paused，需 `migrate-recover`。

### 7.4 建议

报告中增加一张“控制面 / 数据面 / 磁盘面”的调用链图，把 libvirt RPC、QMP、migration stream、NBD 四条线分开画，便于说明安全边界。
