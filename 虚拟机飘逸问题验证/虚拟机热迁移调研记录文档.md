# 虚拟机热迁移（安全漂移）技术调研记录文档

> 任务：调研虚拟机安全漂移（热迁移）技术，分析漂移过程中如何保证**数据传输安全**、**数据完整性**以及**状态一致性**。
> 实验对象：虚拟机 test2，源宿主机 A → 目标宿主机 B（非共享存储场景）

---

## 1. 热迁移技术概述

### 1.1 定义
虚拟机热迁移（Live Migration）是指在不停止虚拟机运行的情况下，将其从一台物理主机迁移到另一台物理主机的过程。该过程对用户和应用透明，几乎不造成服务中断，广泛应用于数据中心管理、负载均衡和故障恢复。

### 1.2 涉及的三大安全维度（本次调研核心）
| 维度 | 机制 | 风险点 |
|---|---|---|
| 数据传输安全 | qemu+ssh 隧道 / TLS 证书 / 明文 tcp: | 明文迁移流中内存页可被抓包还原，泄露敏感数据 |
| 数据完整性 | NBD / --copy-storage-all 全量复制 + 迭代预拷贝 | 复制过程中数据损坏或丢失 |
| 状态一致性 | 预拷贝迭代收敛 + 停机切换（downtime） | CPU/设备状态恢复失败、业务中断过长 |

## 2. 实验环境与前置检查（已完成 ✅）

### 2.1 磁盘状况检查
- 检查 test2 磁盘状况：test2 下有两块设备 —— **vda**（真正的虚拟硬盘/系统盘）与 **sda**（虚拟光驱中的安装 ISO）。
- 迁移前处理：在虚拟机继续运行的情况下弹出虚拟光驱中的 ISO，并以 `--persistent` 更新持久化配置。

### 2.2 存储共享性检查
- 虚拟机 A 的 `/opt/vm-disks` 存放在 LVM/XFS 文件系统上；
- 虚拟机 B 无独立挂载，磁盘属于 B 的根文件系统；
- **结论：A、B 不共享存储 ⇒ 本次为非共享存储热迁移，需使用 `--copy-storage-all`。**

### 2.3 迁移管理链路验证（A → B）
- 目的：验证宿主机 A 能访问目标宿主机 B，并能通过 libvirt 远程管理 B 上的 KVM 虚拟机。
- 操作：在宿主机 A 上通过 ssh 连接宿主机 B，并以 `qemu+ssh://` 测试访问 B 的 libvirt。
- 结果：A 可通过 qemu+ssh 获取 B 上的虚拟机列表，**迁移管理链路正常**。

### 2.4 迁移兼容性检查
- libvirt、QEMU 版本一致，软件栈层面无版本兼容性问题。
- 目标宿主机 B 正常启用 Open vSwitch 网桥 br-ovs，与源虚拟机网络桥接配置匹配，网络具备迁移条件。
- **CPU 兼容性检查**：提取 A 的 CPU 能力信息并在 B 上用 `virsh cpu-compare` 验证，结果显示 **CPU 不兼容** —— B 缺少 monitor、hle、rtm 特性；虚拟机当前采用 host-passthrough CPU 模式，需进一步处理 CPU 模型兼容性。

## 3. 迁移实践与问题分析（已完成 ✅）

### 3.1 首次迁移尝试（失败 ❌）

- **现象一**：宿主机名称解析异常导致 NBD 磁盘复制通道连接失败；
- **现象二**：修正名称解析后，迁移数据可传输至 100%，说明网络及非共享存储复制链路已打通；但最终在目标端恢复虚拟机 CPU/KVM 状态时失败；
- **原因分析**：结合前期 CPU 兼容性检查，判断主因为虚拟机采用 host-passthrough CPU 模式，而两台宿主机 CPU 特性不完全兼容；
- **后续计划**：采用双方共同支持的固定 CPU Model 后重新进行热迁移验证。

### 3.2 迁移过程中遇到的问题及解决方法汇总

首次迁移及其后的往返迁移验证过程中，先后遇到以下问题，均定位并解决：

**问题 1：虚拟光驱（ISO）阻碍迁移**
- **现象**：test2 挂载两块设备——vda（虚拟硬盘/系统盘）和 sda（虚拟光驱中的安装 ISO）。目标端无法直接迁移光驱介质。
- **解决**：在虚拟机保持运行的状态下，仅弹出虚拟光驱中的 ISO（`virsh change-media test2 sda --eject`），并以 `--persistent` 同步更新持久化配置，使重启后配置也不回退。
- **经验**：迁移前用 `virsh domblklist` 检查设备清单，不可迁移设备（光驱、直通设备）需提前处理。

**问题 2：宿主机名称解析异常，NBD 磁盘复制通道连接失败**
- **现象**：首次发起非共享存储迁移时，目标端无法连接源端的 NBD 磁盘复制服务，迁移在起始阶段即失败。
- **原因**：迁移数据通道建立时需要按源端宿主机**主机名**发起连接，而环境中的名称解析（hosts/DNS）未正确配置源端主机名与 IP 的对应关系，解析失败导致通道无法建立。
- **解决**：修正服务器间主机名解析（配置 hosts 记录）。修正后迁移数据可传输至 100%，证明网络与磁盘复制链路已打通。
- **经验**：非共享存储迁移依赖主机名解析，迁移前应在两端执行主机名解析验证（`ping <对端主机名>`）。

**问题 3：CPU 特性不兼容，迁移至 100% 后目标端恢复失败**
- **现象**：数据全部传完（进度 100%），但最终在目标端恢复虚拟机 CPU/KVM 状态时报错，迁移整体失败，源端虚拟机回退继续运行。
- **原因**：虚拟机采用 **host-passthrough** CPU 模式（直接透传源宿主机物理 CPU 全部特性），而 `virsh cpu-compare` 预检已提示目标宿主机缺少 monitor、hle、rtm 特性。迁移切换阶段传输的 CPU 状态是源端特性的二进制序列，目标端硬件不具备这些特性，恢复时校验失败——**数据完整到达，但状态"翻译不过去"**，一致性破坏在兼容性层而非传输层。
- **解决**：修改 test2 的 CPU 配置为双方共同支持的固定 CPU Model（Haswell-noTSX-IBRS，`fallback='forbid'`，附带要求 vmx 特性），将 CPU 状态约束在两端硬件能力交集之内。
- **经验**：跨宿主机热迁移禁用 host-passthrough；`virsh cpu-compare` 应作为迁移前强制预检项；`fallback='forbid'` 保证遇不兼容环境显式报错而非静默降级。

**问题 4：管理链路 SSH 端口非默认，`qemu+ssh://` 连接被拒绝**
- **现象**：反向迁移（B→A）时执行 `virsh migrate ... qemu+ssh://10.19.207.34/system`，报错 `ssh: connect to host 10.19.207.34 port 22: Connection refused`。
- **原因**：环境 SSH 均使用非默认端口（55555），libvirt 默认去连 22 端口，被拒绝。
- **解决**：在迁移 URI 中显式指定端口与用户，采用已验证成功的格式：`qemu+ssh://root@10.19.207.34/system?port=55555`。
- **经验**：非默认 SSH 端口必须在 URI 中显式声明，端口参数写法为 `?port=` 查询参数。

**问题 5：首次 SSH 连接指纹确认卡住迁移**
- **现象**：修正端口后迁移命令输出 `The authenticity of host ... can't be established. ED25519 key fingerprint ... Are you sure you want to continue connecting (yes/no)?`，进程停住。
- **原因**：libvirt 底层调用 ssh 时无法进行交互式确认/密码输入，首次连接的主机指纹确认（以及密码认证）会阻塞迁移。
- **解决**：先以手工 `ssh -p 55555 root@<目标IP>` 完成首次指纹确认（回答 yes），再单独解决密钥认证（见问题 6），之后迁移不再受阻。
- **经验**：迁移前先用手工 ssh 打通一次链路，把所有交互步骤消化掉。



### 3.3 第二次迁移（成功 ✅）
- 迁移命令参数：`--live --persistent --copy-storage-all`（成功命令示例：`virsh migrate --live --persistent --copy-storage-all --verbose test2 'qemu+ssh://root@<目标IP>/system?port=55555'`）
- 迁移前调整：采用双方共同支持的固定 CPU Model。
- **结果**：虚拟机非共享存储在线热迁移验证成功——
  - 目标宿主机上虚拟机状态为 **running**；
  - 虚拟磁盘已成功复制至目标存储目录；
  - 网络接口正常连接至 br-ovs。
- **结论：目标宿主机已成功接管虚拟机，热迁移完成。**

## 5. 完整性与一致性的技术机制深度分析

### 5.1 一致性模型：迁移的本质问题

热迁移本质上是把一个**正在演化的状态机**（vCPU 寄存器 + 内存 + 设备状态 + 磁盘）从 A 搬到 B，且搬迁期间状态还在不停变化。核心矛盾：**复制的速度赶不上状态变化的速度怎么办？复制到一半虚拟机还在跑，两边状态不一致怎么办？**

QEMU/KVM 的答案是一套分层收敛协议：**预拷贝（pre-copy）→ 脏页追踪 → 迭代收敛 → stop-and-copy 原子切换**。

### 5.2 状态一致性的保证机制（内存 / CPU / 设备）

**（1）预拷贝 + 脏页追踪（iteration phase）**
- 第一轮全量：VM 在 A 上正常运行，QEMU 把全部内存页顺序传到 B，用户业务全程无感——这就是"热"的来源；
- 脏页位图：KVM 利用 EPT/NPT 硬件特性（内存页被 guest 写入时硬件自动置 dirty 位）追踪每轮传输中又被修改的页，通过 `KVM_GET_DIRTY_LOG` 获取；
- 迭代收敛：第二轮只传脏页，第三轮只传上轮脏页中又变脏的……每轮数据量指数递减，剩余脏页量小于阈值时进入切换阶段；
- 收敛保护：若脏页产生速度持续超过网络带宽，QEMU 提供 auto-converge（强制节流 vCPU 降低脏页速率）与 `--timeout` 机制，保证收敛可达成或超时回退。

**（2）stop-and-copy 原子切换（switch phase）——一致性的根本保证点**
- A 上的 vCPU 全部暂停，VM 状态冻结成静态快照；
- 传输最后一批脏页 + vCPU 寄存器状态 + KVM 内核状态 + 非迭代设备状态（RAM 是可迭代设备可分多轮传；设备状态不可迭代，必须在停机后一次性原子传输）；
- B 端 QEMU 加载全部状态，恢复执行。

为什么必须停机：无法在同一时刻原子地读取运行中机器的寄存器和全部内存。stop-and-copy 把动态问题转化为静态问题——**冻结的快照是可以精确复制的**，这是一致性的数学基础。

**（3）单一执行源（防脑裂）**
切换后只有 B 继续运行，A 端 QEMU 退出，避免两边从同一状态分叉。同时 QEMU 保证 B 正式开始执行前源端状态不销毁——迁移失败（如本次首次迁移的 CPU 状态恢复失败）时源端可回退继续运行，不会两头落空。

**（4）状态可序列化的前提：CPU 兼容性**
切换阶段传输的 CPU/KVM 状态是源端 CPU 特性的二进制序列。本次首次迁移失败的机理正是如此：host-passthrough 将 A 的 CPU 特性（含 hle/rtm 等）透传给 guest，B 收到的状态描述包含其硬件不具备的特性，恢复时校验失败——**数据完整传到了 100%，但状态"翻译不过去"**，一致性破坏在兼容性层而非传输层。改用双方共同支持的固定 CPU Model（Haswell-noTSX-IBRS，`fallback='forbid'`）后，状态被限制在两端能力交集内，恢复成功。结论：**一致的前提是两端对状态语义的解释一致**。

**（5）扩展：设备状态的一致性——"看不见的硬件"也要搬家**

虚拟机看到的"硬件"（网卡、磁盘控制器、定时器等）并非物理设备，而是 **QEMU 进程内软件模拟的设备模型**。由此，迁移涉及的状态分为三个地盘：

| 内容 | 位置 | 迁移方式 |
|---|---|---|
| Guest 应用、内核、驱动程序及其在内存中的数据 | Guest 内存 | 内存预拷贝 + 脏页追踪（可迭代、可边跑边传） |
| **模拟设备自身的运行状态**（设备队列游标、挂起未送达的中断、设备内部定时器进度等） | **宿主机 QEMU 进程内**（虚拟机外面） | 停机后序列化为设备状态流，一次性原子传输（不可迭代） |
| 宿主机真实硬件 | 宿主机 | 不迁移，目标端使用本机硬件 |

设备状态不可迭代的原因：设备状态与 vCPU 执行耦合（guest 继续运行就会改变设备状态——发新包、触发新中断），**只有 vCPU 冻结时设备状态才静止、才可被精确快照**。这解释了"RAM 可迭代、设备状态必须在 stop-and-copy 一次传完"的分类依据。

序列化格式依赖两端 QEMU 的内部数据结构布局：若两端 QEMU 版本不同，同一设备状态流会被按不同结构体布局解析，导致状态错乱——QEMU 在迁移流头部携带版本与配置标识，不匹配时目标端拒绝迁移。这就是迁移前要求"libvirt/QEMU 版本一致"以及"两端虚拟机定义（设备型号）一致"的底层原因。

**（6）扩展：Guest 感知时间的一致性——迁移停顿的"时间黑洞"**

stop-and-copy 期间 vCPU 冻结数百毫秒，但 **guest 对停顿无直接感知**（恢复后从冻结点继续执行，主观上时间未流逝），而物理时间已真实流逝。由此产生 guest 内部两类时钟的矛盾：

| 时钟源 | guest 的理解 | 停顿后的偏差 |
|---|---|---|
| vCPU 时间戳计数器（TSC/指令级时钟） | 数 CPU 走了多少周期 | vCPU 停止 → 计数少走 → 计算出的时间**落后** |
| 虚拟 RTC/壁挂时钟 | 直接读"现在几点" | 真实时间已前进 → 读数**超前** |

用一个类比说明：如同一局游戏中途被打晕 1 小时——主观上只过了一瞬（CPU 心跳停了），墙上的挂钟却真实走了 1 小时，"秒表"（TSC）与"挂钟"（RTC）之间出现了 1 小时的矛盾。Guest 内核定期以两钟互相校验，迁移停顿会造成数百毫秒的不一致差值，可能引发 `clocksource unstable` 告警，并影响日志时间戳、定时任务触发时机、TCP 重传超时判定乃至依赖时间戳的认证协议。

QEMU 的补救机制（"骗它骗到底"）：源端冻结 vCPU 时记录精确停顿时长并随状态传输，目标端恢复 vCPU 前将该时长**折算为 TSC 偏移量补进计数器**，使 guest 读到的 CPU 周期数"假装"停顿从未发生，两钟重新对齐；同时重新校准 pv 时钟（kvm-clock）。

```
停顿 500ms 示例：
  停顿前：TSC = 10,000,000,000（对应 10.000s）  挂钟 = 12:00:10.000
  恢复前：500ms × CPU频率 = 1,500,000,000 个周期 → 预补入 TSC
  恢复后：TSC = 11,500,000,000（对应 10.500s）  挂钟 = 12:00:10.500
  → guest 两钟读数重新一致，停顿被"抹平"
```

但补偿并不完美——它能骗过**时钟读数**，骗不过**真实世界**：停顿期间外部到达的 TCP 包真实迟到、本应触发的定时任务真实延迟、外部请求真实变慢。因此：普通应用经补偿后完全无感；时序敏感应用（精密计时、加密握手、高频测量）仍可能感知异常。

**本次实验的对应验证**：counter.log 中序号连续（1001→1002 不重置不跳号）验证 vCPU/内存状态恢复正确；对比迁移切换点前后相邻两条记录的**时间戳间隔**，则可直接观测时钟补偿效果——间隔保持约 1 秒（任务固有的 sleep 周期）说明补偿生效、guest 对停顿无感知；间隔拉大（如 1.5 秒）则是停顿泄漏进 guest 挂钟读数的定量证据。序号与时间戳双重连续，构成状态一致性与时钟一致性两个层面的证据。

### 5.3 数据完整性的保证机制（磁盘，非共享存储）

本环境 A、B 不共享存储，磁盘通过迁移通道复制，机制为 **NBD 全量复制 + 写镜像（write mirroring）**：

1. 迁移启动后，QEMU 在源端内嵌 NBD 服务端，目标端连入（首次迁移失败即因名称解析异常导致该通道未建立）；
2. `--copy-storage-all` 将 qcow2 逐块读出、传输至目标端新磁盘文件（全量复制）；
3. **关键：写镜像同步**——全量复制期间 guest 仍在写盘，每个写 I/O 同时落到源盘与目标盘，保证复制完成后被覆盖区域仍为最新（源码分析确认其实现为 QEMU blockdev-mirror 镜像语义，见 5.9）；
4. 切换阶段与内存同步完成后，目标盘与源盘达到同一状态点，目标端接管后从目标盘继续读写。

完整性的三重保障与本次验证的对应：

| 层级 | 机制 | 实验证据 |
|---|---|---|
| 传输层 | TCP/SSH 通道校验和/加密，损坏自动重传 | qemu+ssh 加密通道 |
| 复制层 | 写镜像保证迁移期间新写入不丢失 | counter.log 连续 |
| 端到端 | 迁移后独立重算校验值对比 | **SHA-256 前后完全一致 ✅**（不依赖中间机制，直接证明迁移后数据 == 迁移前数据，证据链最强） |

### 5.4 对外状态一致性：网络

迁移不改变 VM 自身的网络配置（IP/MAC 属于 guest），但需保证外部可达性连续：

- **同二层网段（本环境）**：A、B 均接 br-ovs，VM 的 vnet 口从 A 的 OVS 切换到 B 的 OVS，MAC 不变；
- 切换后外部交换机 CAM 表仍指向旧端口，依靠 gratuitous ARP 主动通告 + 交换机自学习刷新，产生数百毫秒的 ARP 收敛延迟；
- 本次验证 IP/MAC 迁移前后不变：**网络层以上状态连续，仅物理出口发生切换**。

### 5.5 证据链总结

| 机制 | 保证什么 | 实验证据 |
|---|---|---|
| 预拷贝 + 脏页追踪 | 停机前业务不中断 | 迁移期间 counter 持续增长 |
| stop-and-copy | 切换点状态精确一致 | 切换后计数**继续编号**（不清零/不跳变/不回退） |
| 单一执行源 | 不脑裂 | A shut off + B running，终端状态与迁移前一致 |
| CPU 状态可恢复 | 状态语义两端一致 | host-passthrough 失败 → 固定 Model 成功（正反对照） |
| NBD 全量 + 写镜像 | 磁盘零丢失 | SHA-256 前后一致 |
| 网络状态保留 | 用户可达性 | IP/MAC 不变，业务可继续访问 |

### 5.7 数据传输安全的保证机制

**（1）攻击面分析：迁移流量里有什么**

迁移通道传输的不是零碎文件，而是虚拟机的全部核心数据：

| 数据类型 | 内容 | 泄露后果 |
|---|---|---|
| 全部内存页 | 整个 RAM 逐页传输——登录会话、加密密钥、数据库缓存、进程内存中的明文凭据 | 全部机密暴露 |
| 磁盘全量数据 | `--copy-storage-all` 场景下整个 qcow2 逐块传输——文件系统、数据库、配置文件 | 相当于整块硬盘外泄 |
| CPU/设备状态 | 寄存器、设备配置序列 | 状态可被还原分析 |

两类核心威胁：**窃听**（同网段抓包即可还原内存/磁盘内容）与**篡改/劫持**（中间人篡改传输块、伪装迁移目标）。

**（2）原生通道的风险基线**

QEMU 原生迁移数据通道（`qemu+tcp://`）为**明文、无加密、无认证**：迁移流量走随机高位端口（49152~49215），同网段任何主机抓包跟踪该 TCP 流即可直接辨认内存页中的明文内容；且目标端迁移端口无认证，存在被抢先连接劫持的风险。**即"不配置加密 = 明文裸奔"。**

**（3）本实验方案：qemu+ssh 加密隧道**

本实验采用 `qemu+ssh://` URI，libvirt 自动将迁移数据流封装于 SSH 加密隧道：

```
A 的 QEMU ─本地回环→ A 的 ssh 客户端 ══SSH 加密隧道══→ B 的 sshd ─本地回环→ B 的 QEMU
```

- **QEMU 仅监听本地回环（127.0.0.1）**，迁移端口不在物理网络暴露；
- **加密**：隧道内全部内存页/磁盘块为 SSH 密文，抓包仅见 SSH 协议帧；
- **认证（双向）**：主机指纹验证（迁移时确认的 ED25519 fingerprint，防中间人伪装）+ 密钥认证（免密配置保证仅持有合法私钥的宿主机可发起迁移，防未授权迁移）；
- **完整性**：SSH 使用 AEAD 认证加密（如 AES-GCM），每个数据块自带校验码，传输中任何篡改都会导致校验失败、连接中断。

**（3）控制面与数据面的区分（重要认知修正）**

`qemu+ssh://` URI 首先表示 **libvirt 通过 SSH 与目标端 libvirt 建立安全的远程管理连接（控制面）**，不能仅凭该 URI 断言全部迁移数据均经 SSH 加密：

```
控制面：virsh/libvirt-A ══SSH══▶ libvirt-B
         （发起迁移、创建目标QEMU、设置参数、查询状态）

数据面（安全状况需分别确认）：
QEMU-A ── QEMU migration stream ──▶ QEMU-B   ← RAM/CPU/设备状态
QEMU-A ── NBD/block 存储流 ────────▶ 目标盘    ← 非共享存储磁盘数据
```

即：**控制面安全 ≠ 数据面安全**。数据面若需经 SSH 保护，须依赖 libvirt 的 tunnelled migration 或迁移参数显式指定；本实验迁移命令中未显式使用 tunnelled/TLS 参数，因此迁移 stream 与 NBD 存储流的实际加密状态**不能从命令行反推，须以连接观测为准**（见（3-1）验证方法）。此前的记录曾将 qemu+ssh:// 直接等同于"全部迁移数据经 SSH 加密"，属认知偏差，特此修正。

**（3-1）数据面加密状态的实验验证方法**

```bash
# 迁移进行时观察连接分布：
ss -tnp          # 识别 QEMU/libvirt/SSH 相关连接

# 抓包判断 SSH 端口之外是否存在 QEMU 直连流量：
tcpdump -i any host <对端IP> -nn
```

判据：若 SSH 连接之外存在 QEMU 到目标端的独立 TCP 连接，则数据面未走 SSH 隧道；若全部连接封装于 SSH 进程内，则为 tunnelled migration。同时需检查 libvirt/QEMU 系统配置，因安全机制可能由配置强制启用。

**（3-2）QEMU 原生数据面安全机制：TLS**

QEMU 原生迁移数据流的标准安全保护是 **TLS（`--tls` / qemu+tls://）**。注意：**TLS 是安全协议，不是单一加密算法**——TLS 层负责身份认证、密钥协商、机密性、完整性，具体密码算法由协议及底层密码库（GnuTLS）决定（如 ECDHE 密钥交换 + AES-GCM 认证加密）。TLS 位于 QEMU 迁移数据处理之后：QEMU 先完成数据选择/编码/可选压缩形成 migration stream，TLS 只看到字节流，不需要理解 RAM/脏页/设备状态的区别。

数据面的完整安全布局（非共享存储须双通道覆盖）：

```
Migration stream ──▶ TLS 加密 ──▶ 网络
NBD/storage stream ──▶ 需单独保护（NBD TLS 或隧道）──▶ 网络
```

**（3-3）QEMU 与安全通道的协作机制**

无论 SSH 隧道还是 TLS，架构本质一致：**QEMU 迁移协议自身只产生明文 stream，安全保护由外层通道组件实施**。QEMU 原生 transport 包括 tcp、tls、exec、fd、unix 等，其中 exec 是"把 migration stream 经管道交给任意外部程序"的开放接口——外部程序可以是 SSH、国密代理等，这是国密原型验证（见 5.8）的天然入口；且 exec 保护 migration stream 不等于自动保护 NBD 存储流，磁盘路径仍需单独处理。

压缩与加密的顺序恒为**压缩 → 加密**（若启用）：加密后的数据接近高熵，再压缩无收益。本实验命令未使用 `--compressed`，故未启用通用迁移压缩；但 dirty-page 追踪、zero-page 特殊编码等属于迁移优化机制，与通用压缩是不同概念，即使未开压缩也可能存在。

**（4）机密性/完整性/认证性的防线（按通道分别适用）**

| 层 | 机制 | 防什么 | 适用范围 |
|---|---|---|---|
| 控制面 | libvirt SSH 管理连接加密 + 主机指纹/密钥认证 | 管理指令窃听、未授权迁移发起 | qemu+ssh:// 已确认覆盖 |
| 数据面-迁移流 | TLS（认证/密钥协商/AEAD 加密）或 tunnelled SSH | 内存/状态数据窃听、篡改、重放 | 须显式启用并经连接观测确认 |
| 数据面-存储流 | NBD TLS 或隧道封装 | 磁盘数据窃听、篡改 | 需单独配置 |
| 端到端 | 迁移后 SHA-256 独立校验（本实验已验证一致） | 最终裁决：数据不一致即被发现 | 独立于通道，任何方案均适用 |

**（5）责任边界结论**

安全不由 QEMU 迁移协议内置，而由**通道选型与配置**决定；且控制面与数据面须分别评估、分别加固。QEMU 产出的永远是明文 migration stream，安全保护发生在通道层——这一分层是国密适配（5.8）可行的技术基础。

### 5.8 国密算法适配方案

**（0）修正后的适配基础**

结合控制面/数据面区分（5.7（3）），国密改造的正确切入点是**安全协议层**而非 QEMU 迁移算法本身：保留 QEMU 成熟的 pre-copy、脏页追踪、zero-page、压缩等机制不改动，将国密能力（SM2/SM3/SM4）注入通道层。QEMU 原生 `exec` transport（migration stream 经管道交给任意外部程序）是第一阶段原型的天然入口——国密代理程序置于 QEMU 与网络之间即可验证可行性；但 exec 保护 migration stream 不自动覆盖 NBD 存储流，非共享存储场景须双通道分别保护，且建议两通道使用独立会话密钥、由统一身份认证体系管理。

完整协议设计不能简化为"直接用 SM4 加密"，还须覆盖：双向身份认证、会话密钥建立、认证加密（完整性）、重放防护、密钥生命周期、迁移/存储通道密钥隔离、异常中止与恢复、证书管理。

**（1）现状与算法映射**

QEMU/libvirt 原生迁移协议（tcp、ssh、tls）均不支持国密套件。本实验现用方案与国密套件存在逐项对应关系：

| 安全功能 | 现有方案（qemu+ssh） | 国密对应 |
|---|---|---|
| 数据加密 | AES-CTR/GCM、ChaCha20 | **SM4**（分组加密） |
| 完整性校验 | HMAC-SHA2 / Poly1305 | **SM3**（杂凑） |
| 身份认证/密钥交换 | ED25519/RSA | **SM2**（椭圆曲线签名/密钥交换） |

**（2）适配路线（按落地难度）**

- **路线 1（推荐）：网络层国密隧道封装**。在宿主机 A、B 之间建立国密 IPsec 隧道（国密安全网关或支持国密的软件 VPN，采用 SM4-ESP 加密、SM2 IKE 认证、SM3 完整性校验）。QEMU 迁移命令零改动，加密对迁移过程完全透明。技术依据即 5.7（5）的分层结论：QEMU 只对回环收发明文，网络路径上的国密隧道即可保护全部迁移流量。
- **路线 2：传输层国密改造**。将 OpenSSH 替换为基于 Tongsuo（铜锁）/GmSSL 等国产密码库的国密改造版（SM4 加密套件 + SM2 认证），或在 QEMU 迁移端口外以国密 SSL 代理建立隧道。可满足"应用层跑国密"的更强要求，但需自建软件栈与 SM2 证书体系。
- **路线 3：验证建议**。在 A、B 间建立国密隧道后重跑迁移：迁移行为不变、业务照常，链路抓包验证为 SM4 密文，即完成"国密加密下的热迁移验证"。

**（3）结论**

热迁移国密适配的可行结论是：**QEMU 原生协议不支持国密套件，国密加密应通过网络层隧道（路线 1）实现，对迁移过程透明；这一边界本身即为本调研的重要结论之一。** 若要求应用层国密，需改造 SSH/TLS 软件栈（路线 2），工作量显著增大，建议作为下一阶段课题。

### 5.9 源码视角：三大保证机制在 libvirt 源码中的落点

> 基于 libvirt/libvirt（master 分支）源码分析（2026-10）。调用链：`virsh cmdMigrate`（tools/virsh-domain.c:11854）→ `virDomainMigrate3/ToURI3`（src/libvirt-domain.c）→ remote RPC（remote_daemon_dispatch.c，Begin3/Prepare3/Perform3/Finish3/Confirm3）→ QEMU driver（src/qemu/qemu_migration.c）→ QMP 命令（qemu_monitor_json.c）。

**（1）一致性 = libvirt v3 事务协议 + QEMU 收敛算法**

- **事务性回滚**：源端在 Perform 完成后**不停止 VM**——真正停源端的是收到目标端 Finish 成功后的 `qemuMigrationSrcConfirm`（qemu_migration.c:4273）；一旦目标端失败，Confirm 走失败分支恢复源端运行。即迁移为两阶段提交：**失败即整体回滚，不存在"半迁移"状态**——首次迁移（CPU 恢复失败）后源端 test2 仍正常运行的代码级原因。
- **防脑裂**：只有目标端 `qemuMigrationDstFinish`（7087）确认接管成功，源端才停机退出，执行顺序由协议消息序列强制保证单一执行源。
- **原子切换**：stop-and-copy 由 QEMU 内部收敛判定触发，libvirt 侧 `qemuMigrationSrcWaitForCompletion`（2252）轮询 `query-migrate` 至 switchover；新版 pre-switchover 暂停点由 `qemuMigrationSrcContinue`（4629）发 `migrate-continue` 放行——**切换时机本身也是两端协调的**。
- **状态语义关卡**：数据传至 100% 只代表传输层完成，最终裁决在目标端 QEMU 加载 KVM/设备状态那一刻——host-passthrough 失败案例即此关卡（`DstFinish` 报错 → Confirm 回滚）。

**（2）完整性 = blockdev-mirror 语义 + 传输校验 + 端到端验证**

- **磁盘复制引擎为 blockdev-mirror**（源码分析的重要修正）：libvirt 不逐块拷盘，而是目标端 `qemuMigrationDstStartNBDServer`（635）起 NBD 接收端，源端 `qemuMigrationSrcNBDStorageCopyBlockdev`（1162）下发 QMP `blockdev-mirror` 将源盘镜像至目标盘。"写镜像"的真正实现在 QEMU block 层的 mirror job：**镜像期间新写 I/O 自动双落盘，pivot 时点两盘字节级一致**——一致性是 mirror 语义的算法性质，而非事后补救。
- **传输层**：migration stream 与 NBD 流均经 TCP/隧道传输，逐包校验重传；SSH/TLS 下为 AEAD，篡改即断连。
- **端到端裁决**：迁移后独立重算 SHA-256 对比（本实验已验证一致），不依赖任何中间机制声明——机制层是"声明"，端到端校验才是"独立验证"。

**（3）安全性 = 完全外置于通道层（源码结构性证明）**

- QEMU 迁移序列化代码只产出**明文字节流**，任何路径中均无加密逻辑；加密只出现在 QEMU 进程之外（GnuTLS/ssh/隧道）。transport 选择位于 `qemuMigrationSrcStart`（4814）组装的 QMP URI 与参数下发（`qemu_migration_params.c`），四种路径：tcp（明文）、tls（GnuTLS）、tunnelled（`SrcPerformTunnel` 5494，随控制面连接走 SSH）、exec/fd（交外部程序）。
- **控制面/数据面是两个独立选择点**（源码分界佐证 5.7（3）的修正）：控制面加密由 URI 方案名（qemu+ssh）决定，数据面加密由 Perform 阶段 transport/参数决定，二者无必然绑定。
- **国密入口的源码依据**：exec transport 将明文流经管道交给任意外部程序，国密代理（SM4/SM3/SM2）可在零改动 QEMU/libvirt 迁移逻辑的前提下插入数据路径——此为源码中明确存在的扩展接口，支撑 5.8 的适配路线。

**（4）三维度汇总对照**

| 维度 | 保证点 | 源码证据 | 实验证据 |
|---|---|---|---|
| 一致性 | v3 事务 + 失败回滚 | `SrcConfirm`(4273) 失败即恢复源端 | 首迁失败后源端继续运行 |
| | 原子切换 | `SrcWaitForCompletion`(2252) 等 switchover | counter.log 序号连续 |
| | 防脑裂 | Finish 成功后才停源端 | A shut off + B running |
| | 状态语义可恢复 | 目标端加载 KVM 状态校验 | host-passthrough 失败 → 固定 Model 成功 |
| 完整性 | 磁盘镜像语义 | `blockdev-mirror` 写自动双落盘 | 迁移期间 counter.log 写入完整保留 |
| | 传输校验 | transport 层 AEAD/校验和 | — |
| | 端到端裁决 | 机制外独立验证 | SHA-256 前后一致 ✅ |
| 安全性 | 加密在通道层 | QEMU 序列化代码无加密逻辑 | — |
| | 控制面/数据面独立 | dispatch 层与 Perform 层两个选择点 | 讨论汇总修正结论 |
| | 认证 | SSH 指纹/密钥认证（问题 5 实证） | 迁移前须打通认证 |
| | 国密入口 | exec transport 管道接口 | 支撑 5.8 国密路线 |

**结论**：源码揭示三个维度是同一分层架构的三个侧面——libvirt 事务协议保证"过程不出错"（一致性的**事务性**），QEMU 收敛与镜像算法保证"数据语义正确"（一致性与完整性的**算法性**），安全性完全外置于通道层（既是风险——不配置即明文，也是机遇——国密可透明替换）。

### 5.10 本节总结

热迁移通过"**运行中预拷贝、脏页持续追踪收敛、最终短暂停机原子同步全部剩余状态、目标端接管后源端退出**"的协议，把"复制一台正在运行的机器"这一动态问题转化为"复制一个冻结快照"的静态问题，从而在毫秒级停机（downtime）的代价下，保证了 CPU、内存、设备、磁盘、网络五类状态的端到端一致与完整。本次实验通过 counter.log 连续性、SHA-256 校验一致、IP/MAC 保持三个直接证据完整验证了该机制。

## 6. 总结与最佳实践

- **状态一致性**：预拷贝 + 脏页追踪 + stop-and-copy 原子切换保证切换点状态精确一致；counter.log 连续编号为直接证据。源码分析（5.9）确认 libvirt v3 协议为两阶段提交事务，失败整体回滚（首次迁移失败后源端继续运行即为其代码级体现）。
- **数据完整性**：非共享存储下 `--copy-storage-all` 依靠 NBD 全量复制 + blockdev-mirror 写镜像（QEMU block 层镜像语义，写 I/O 自动双落盘）保证迁移期间磁盘零丢失；端到端 SHA-256 对比验证通过。
- **传输安全**：迁移须区分控制面与数据面——`qemu+ssh://` 确保的是 libvirt 管理连接（控制面）的 SSH 加密；数据面（migration stream + NBD 存储流）的安全须单独配置（原生 TLS / tunnelled migration / NBD TLS）并以连接观测验证。端到端 SHA-256 校验为独立于通道的最终裁决。国密适配建议优先在安全协议层（TLS 层国密改造或网络层国密隧道）实施，保留 QEMU 成熟迁移机制不改动。
- **最佳实践建议**：
  1. CPU 模型必须使用两端共同支持的固定 CPU Model（禁用 host-passthrough），并设 `fallback='forbid'` 使不兼容时显式报错；
  2. 迁移管理链路要求源宿主机到目标宿主机 SSH 密钥免密可达，SSH 非默认端口需在 URI 中显式指定（`qemu+ssh://host/system?port=xxx`）；
  3. 迁移前弹出虚拟光驱等不可迁移设备，并以 `--persistent` 更新持久化配置；
  4. 迁移前完成 libvirt/QEMU 版本、网络桥接、存储布局（是否共享存储决定迁移参数）三项兼容性检查；
  5. 建议迁移前在 Guest 内预置计数/时间戳日志任务，作为业务连续性的标准验证手段。
