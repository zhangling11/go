## 术语表

| 术语 | 含义 |
|---|---|
| **CPU 特性位（feature flag）** | CPU 支持的一项具体能力的标志，如 `aes`、`avx2`、`sha_ni` |
| **特性清单** | 一个 CPU 所拥有的全部特性位的集合 |
| **CPUID** | x86 指令，Guest 用它查询自身能力。**返回的是 KVM 递过去的那份答案，不是物理 CPU 的真实情况** |
| **domain XML** | libvirt 描述一台虚拟机的配置文件，CPU 配置即在其中 |
| **domcapabilities** | libvirt 输出的"本节点能创建出哪些 CPU"的能力清单 |
| **ABI 兼容** | 迁移过程中 Guest 所见的硬件接口保持一致。热迁移的根本前提 |
| **A 值** | 源端 Guest 实际可见的特性集（本文自定义术语，见 §5.2） |
| **B 值** | 目标节点能够提供的特性集（本文自定义术语，见 §5.2） |
| **四项全同** | libvirt 对 host-passthrough 安全迁移的前提：hardware + QEMU 版本 + 微码版本 + 配置 |
| **machine type** | QEMU 模拟虚拟主板的"图纸"，规定芯片组、插槽、设备地址、中断路由、ACPI 表。名称带版本号（如 `pc-q35-7.2`），每个版本冻结后永久保留 |
| **ACPI 表** | 虚拟主板的"设备清单"，Guest 开机时逐字节解析，据此建立自己的设备地址表 |
| **伪同构** | 型号字符串相同，但微码或 QEMU 版本不同。**本文自定义术语，是 host-passthrough 最危险的失效场景** |

# 第一章　机制基础：CPU 模式到底控制什么

## 1.1 一句话定位

三种 CPU 模式**只控制一件事**：

> **Guest 执行 `CPUID` 指令时，KVM 递给它哪些「CPU 特性位」。**

减去这件事，"CPU 模式"与 vCPU 数量、内存大小、磁盘配置**没有任何关系**——那些是另外的配置项。**这是最常见的误解来源：把 CPU 模式当成资源模板。**

三者的真正区别只有两点：

1. **谁决定这份特性清单**
2. **这份清单有没有被写下来**

## 1.2 什么是「清单」

### 1.2.1 清单的样子

在任意 KVM 宿主机上执行：

```bash
cat /proc/cpuinfo | grep -m1 flags
```

输出（Intel 机器为例）：

```
flags : fpu vme de pse tsc msr pae mce cx8 apic sep mtrr pge mca cmov
        pat pse36 clflush mmx fxsr sse sse2 ss ht syscall nx pdpe1gb
        rdtscp lm constant_tsc arch_perfmon nopl xtopology tsc_reliable
        nonstop_tsc cpuid tsc_known_freq pni pclmulqdq ssse3 fma cx16
        pcid sse4_1 sse4_2 x2apic movbe popcnt tsc_deadline_timer aes
        xsave avx f16c rdrand hypervisor lahf_lm abm 3dnowprefetch
        invpcid_single ssbd ibrs ibpb stibp fsgsbase tsc_adjust bmi1
        avx2 smep bmi2 erms invpcid rtm avx512f avx512dq rdseed adx
        smap avx512ifma clflushopt clwb avx512cd sha_ni avx512bw
        avx512vl xsaveopt xsavec xgetbv1 xsaves ...
```

**这一串 `aes`、`avx2`、`sha_ni`、`avx512f`、`adx`……就是「清单」。**

每一项称为一个 **CPU 特性位**，代表一种能力。

### 1.2.2 对密码业务直接相关的特性

| 特性位 | 作用 |
|---|---|
| `sm3` / `sm4`（名称视 CPU 与内核版本而定） | 国密算法硬件加速 |
| `aes` | AES-NI 硬件加解密 |
| `sha_ni` | SHA-1/SHA-256 硬件摘要 |
| `adx` / `bmi2` | RSA、ECC 大数模幂加速 |
| `avx2` / `avx512f` | 批量运算向量化 |
| `rdrand` / `rdseed` | 硬件熵源 |

> ⚠️ 特性名的**确切拼写**（`sm3` vs `sm3-avx`、`sha_ni` vs `sha-ni`）随 CPU、内核与 QEMU 版本变化，引用前须按目标环境核对。详见 §5.7。

### 1.2.3 Guest 的清单从哪来

Guest 里的程序（含 OpenSSL、GmSSL、厂商密码库）判断"我有没有某个能力"时，执行的是 `CPUID` 指令。

**它返回的不是物理 CPU 的真实答案，而是 KVM 递给它的那份答案。** 在 Guest 眼里，KVM 扮演出一个"假的 CPU"。KVM 可以：

- 原样全部转给 Guest（host-passthrough）
- 转的同时抄一份书面记录（host-model）
- 只给一份自己指定的（custom）

**删掉哪几项、抄不抄记录，就是三种模式的全部区别。**

## 1.3 这个机制为什么影响密码运算性能

以 OpenSSL 的典型写法为例：

```c
if (cpuid_has("sha_ni")) {
    use_hardware_sha();     // 硬件指令，快
} else {
    use_software_sha();     // 软件查表/位运算，慢
}
```

**它查询的是"Guest 被告知的清单"，不是物理 CPU 的实际能力。**

所以：同一台物理机，Guest 里密码库快还是慢，**完全取决于 KVM 递过去的那份清单**。

> ⚠️ 具体是哪个密码库、有没有编译期写死路径、有无运行时分派，决定了这条判断实际怎么走。**需查 VSM 镜像内的实际实现**，本次未核实。

# 第二章　三种 CPU 模式

## 2.1 host-passthrough：「不给清单，你自己看」

### 2.1.1 官方定义

> ✅ "With this mode, **the CPU visible to the guest should be exactly the same as the host CPU** even in the aspects that libvirt does not understand."
> —— `libvirt.org/formatdomain.html`

**关键短语**：`even in the aspects that libvirt does not understand`（连 libvirt 自己都不认识的方面也照给）。

**但必须注意**：这里的"照给"是**运行时行为**——KVM 开机时按宿主的 CPU 现装一份递给 Guest。**迁移时并不打包这份东西一起走。** host-passthrough 的 domain XML 里，CPU 段只有一行标记：

```xml
<cpu mode='host-passthrough' check='none' migratable='on'/>
```

**没有任何一行 `<feature>`。** 所以源端 Guest 到底拥有哪些特性，在迁移链路上是**不可见**的——这是理解第三章所有现象的起点。

### 2.1.2 迁移风险（官方原文）

> ✅ "Migration of a guest using host-passthrough is **dangerous** if the source and destination hosts are **not identical in both hardware, QEMU version, microcode version and configuration**."

> ✅ "If such a migration is attempted then the guest **may hang or crash** upon resuming execution on the destination host."

> ✅ "even with `migratable='on'` migration will be dangerous unless both hosts are identical as described above."

### 2.1.3 必须纠正的误解

**host-passthrough 不是「禁止热迁移」，是「不保证热迁移的结果」。**

- 措辞是 **dangerous**（危险），不是 **forbidden**（禁止）
- libvirt **不会拒绝**这个请求
- 它会放行，然后在目标端恢复执行时挂住或崩溃

### 2.1.4 「identical」的准确含义——四项全同

官方条件是**四项同时相同**，不是"CPU 型号相同"：

| 条件 | 为什么不能只看型号 |
|---|---|
| **hardware** | 型号相同但步进（stepping）不同，暴露的特性可能不同 |
| **QEMU version** | 同一台机器升级 QEMU 8.0 → 8.1，机型默认行为可能变 |
| **microcode version** | **最容易忽略的一条**。同型号 CPU 若两台节点的 BIOS/微码批次不同，特性集可能不一致 |
| **configuration** | libvirt 配置、CPU 相关参数 |

> **实际含义**：host-passthrough 的真实前提是「**两台节点是同一时间、同一镜像、同一批次装出来的**」。
>
> 这不是"同型号"，是"同一个模子里刻出来的"。**只比对 CPU 型号字符串是不够的**——微码版本不同但型号字符串完全一致，是最容易踩的坑（见 §7.1「伪同构」）。

## 2.2 host-model：「自动给你写一份清单」

### 2.2.1 官方定义

> ✅ "The host-model mode is essentially a shortcut to **copying host-model CPU definition from domain capabilities XML into domain XML**."

libvirt 开机时做的事：读宿主机 CPU 能力，**挑一个最接近的命名模型**（如 `Skylake-Client-IBRS`），把模型名 + 完整特性列表写进 domain XML。

### 2.2.2 清单在 XML 里的形态

```bash
virsh dumpxml vsm-caiwu-01 | grep -A 40 '<cpu'
```

```xml
<cpu mode='host-model' check='partial'>
  <model fallback='allow'>Skylake-Client-IBRS</model>
  <feature policy='require' name='aes'/>
  <feature policy='require' name='avx2'/>
  <feature policy='require' name='sha_ni'/>
  <feature policy='require' name='pcid'/>
  <feature policy='require' name='invpcid'/>
  ... （几十行）
</cpu>
```

**这几十行 `<feature>` 就是那份清单的书面版**——它是 §1.2.1 中 `/proc/cpuinfo` 那串内容的子集，被逐条抄进了 XML。

### 2.2.3 迁移行为（官方原文）

> ✅ "During migration, **complete CPU model definition is transferred** to the destination host so the migrated guest will see **exactly the same CPU model** for the running instance of the guest."

libvirt 拿着一份完整定义到目标端问："你能不能提供这些？"

- 能 → 迁，且运行中的 Guest 看到完全相同的 CPU
- 不能 → **当场失败，迁移根本不开始**

### 2.2.4 它的代价（官方原文）

> ✅ "shutting down and restarting the guest **may present different hardware** to the guest according to the capabilities of the new host."

**原因**：清单是**每次开机重新算的**。换到新宿主机再开机，能力不同，算出来的清单就不同。

所以 host-model 只保证「**这次运行期间不变**」，不保证「永久不变」。

### 2.2.5 它和 host-passthrough 给的东西几乎一样

host-model 挑的是"最接近宿主的命名模型"，所以递给 Guest 的特性**几乎等于** host-passthrough。区别只有一个，但这个区别决定一切：

> **host-model 有收据，host-passthrough 没有。**

| | 递给 Guest 的特性 | 有没有留存记录 | 迁移时能否提前检查 |
|---|---|---|---|
| host-passthrough | 几乎全部 | ❌ 无 | ❌ 不能 |
| host-model | **几乎全部**（一样） | ✅ 在 XML 里 | ✅ 能 |

**推论：host-model 与 host-passthrough 在性能上没有区别**（给的清单几乎相同），差别在可检查性。

## 2.3 custom：「你自己写清单」

### 2.3.1 官方定义

> ✅ "In this mode, the cpu element describes **the CPU that should be presented to the guest**. This is the default when no mode attribute is specified."

> ✅ "This mode makes it so that a persistent guest will see **the same hardware no matter what host** the guest is booted on."

### 2.3.2 清单在 XML 里的形态

```xml
<cpu mode='custom' check='partial'>
  <model fallback='forbid'>Haswell-noTSX</model>
  <feature policy='disable' name='avx512f'/>
  <feature policy='disable' name='avx512bw'/>
</cpu>
```

含义：**不管宿主机有多强，Guest 只能看到 Haswell 这一代的特性，AVX-512 一律不给。**

`Haswell-noTSX` 这个模型名本身就代表一份**固定的、早就写好的**清单。

### 2.3.3 特性裁剪是单向且不可逆的

Guest 判断自己有什么，靠 `CPUID` 返回值。custom 模式做的事是：**把 Guest 能看到的特性位裁掉一部分。**

这个裁剪是**单向的**：

- Guest 看到"我没有 SM4 指令" → 走软件实现 → **它永远不会知道宿主其实有**
- 没有任何机制能让 Guest 事后发现"其实有，只是没告诉我"

所以这不是"降频"那种可恢复的损失，是**从开机那一刻就定死的算力档位**。

### 2.3.4 基线定了就不能改，除非关机

官方（vSphere）说明：**CPU 特性集是在开机时确定的。** ✅

- custom 基线一旦生效，Guest 看到的算力档位就固定到下次关机
- 想"迁过去先降级跑，之后发现不对再调回来" → **做不到**，必须关机重配再开机
- 而关机对密码业务就是一次中断

**这意味着 custom 基线的选择是一次性的、有代价的决策，不能当临时开关用。**

## 2.4 三者对照总表

| 维度 | host-passthrough | host-model | custom |
|---|---|---|---|
| **Guest 看到什么** | 宿主原样（全部） | 几乎宿主原样 | 你指定的基线 |
| **谁决定清单** | 宿主机 | libvirt 自动挑最接近的命名模型 | 你自己写 |
| **清单是否留存** | ❌ **无** | ✅ 在 domain XML 里 | ✅ 在 domain XML 里 |
| **迁移时传什么** | **不传** | 完整 CPU 定义 | 你写的那份 |
| **能否跨代际迁** | ❌ 不能 | ⚠️ 能迁到"能力够"的机器（**不等于能跨代际**） | ✅ 能（基线够老即可） |
| **失败发生在什么时候** | **迁移跑到 100% 后才崩** | **迁移开始前就报错** | **迁移一定成功** |
| **性能** | 满血（基准） | **满血**（几乎相同） | 按基线打折 |
| **重启后特性会变吗** | 会（跟着新宿主走） | 会（重新算清单） | **不会**（写死的） |
| **能否改配置不关机** | 需关机 | 需关机 | 需关机 |
| **官方对迁移的措辞** | dangerous | transferred | same hardware no matter what host |

## 2.5 一个便于传达的比方

假设要给客人（Guest）上一桌菜（CPU 指令）：

| 模式 | 做法 | 客人吃到什么 | 换一家餐厅（迁移）会怎样 |
|---|---|---|---|
| **host-passthrough** | 后厨有什么上什么，**不写菜单** | 和这家后厨完全一致 | 换一家后厨不一样的 → **端上来的可能对不上，客人噎住** |
| **host-model** | 后厨有什么上什么，**但当场写下一张菜单** | 和这家后厨几乎一致 | 换餐厅时**拿着菜单问**"这些你们能不能做" → 不能就当场取消 |
| **custom** | **你提前写好一张固定菜单** | 只有菜单上那些，别的一概没有 | 任何餐厅都能做这张菜单 → **一定能上桌，但客人吃不到别的** |

**核心记忆点**：host-passthrough 和 host-model **客人吃到的几乎一样**，差别只在**有没有菜单**；custom 客人吃到的**明显少**，但就因为它少，**哪儿都能做**。

# 第三章　关键现象：为什么 host-passthrough 会在进度 100% 失败

> 本章解释本平台最痛的现象：迁移一路跑到进度 100%，才在目标端状态恢复阶段失败。

## 3.1 三个常见误解

| 常见说法 | 错在哪 | 准确说法 |
|---|---|---|
| "host-passthrough 会先把宿主机所有 CPU 特性**传过去**" | **什么都没传** | 迁移时 XML 里的 CPU 段只有 `<cpu mode='host-passthrough'/>` 这一行标记，不携带任何特性信息 |
| "因为 libvirt **读不懂**那些特性" | 不是读不懂 | 是**根本没有可读的内容**——那行标记的含义只是"按我宿主机自己的来" |
| "到了目标端**对比**传过来的特性和本机特性，不一致就失败" | **没有"对比"这个动作** | 没有比对环节。是目标端先按自己的 CPU 装好 vCPU，再把源端的 vCPU 状态灌进去，灌不进去就崩 |

> **问题不是"传了什么但理解不了"，而是"什么也没传，所以没人知道该装成什么样"。**

## 3.2 实际发生的链条

```
源端 Guest 跑在「≈ 源宿主 CPU」上
      │
      │  迁移开始：只搬 ① domain XML  ② 内存 + 寄存器 + MSR 状态
      │             XML 里的 CPU 段 = 一行标记，不含任何特性
      ▼
目标端 QEMU 启动，看到 mode='host-passthrough'
      │
      │  → 按「目标宿主机自己的 CPU」装配 vCPU
      │  → 它不知道源端那边是什么 CPU，也没人告诉它
      ▼
状态恢复阶段：把源端 vCPU 的寄存器和 MSR 灌进去
      │
      │  这些状态里带着源宿主才有的东西
      ▼
KVM_SET_CPUID2 / KVM_SET_MSRS 拒绝 → guest 挂住或崩溃
```

`KVM_SET_CPUID2` 是**整个迁移过程中第一次真正用到那些特性**的时刻——即 `Perform` 阶段末尾的状态恢复。在此之前，`Prepare` / `Begin` 阶段都不会触发这个问题，所以进度条已经跑到 100%。

## 3.3 对照：host-model 为什么能提前失败

```
host-model 的 XML 里有完整清单：
  <model>Skylake-Client-IBRS</model>
  <feature policy='require' name='aes'/>
  <feature policy='require' name='sha_ni'/>
  ... 几十行
      ▼
目标端在 Prepare 阶段就能逐条问自己「这些我能不能提供」
      ▼
提供不了 → 当场拒绝，QEMU 根本不启动
```

**两者的本质区别是「有没有一份可以拿去问的书面清单」，不是"libvirt 懂不懂"**：

| | 有没有清单 | 能不能提前问 | 失败时机 |
|---|---|---|---|
| **host-model** | ✅ 有（几十行 `<feature>`） | ✅ 能问 | **迁移开始前** |
| **host-passthrough** | ❌ 无（只有一行标记） | ❌ 没得问 | **跑到 100% 后的状态恢复** |

> **核实边界**：上表中"host-passthrough 非同构迁移危险、Guest 可能挂住或崩溃"是 libvirt 原文（✅ §2.1.2）；但"**具体失败在哪一阶段、为何如此**"是本文根据官方定义做的 **⚠️ 推论**，未抓到 libvirt 明确表述。须由 §9 的 E-01 实验验证：跨代际迁一次，记录停在哪一站、stderr 报什么。

# 第四章　Q1 三个子问题的正式答复

## 4.1 host-passthrough 是"只允许迁到相同型号"，还是"不允许迁移"？

**都不是。**

> **host-passthrough 把可迁移范围锁定为「四项全同的同构集群」，但它不阻止你尝试迁到别处——只是不保证结果。**

- 不是"禁止"，是**危险**
- 不是"同型号"，是**硬件 + QEMU 版本 + 微码版本 + 配置四项全同**

## 4.2 其他两种模式都能允许不同 CPU 的热迁移吗？

| 模式 | 能否迁到不同 CPU 的机器 |
|---|---|
| **host-model** | ⚠️ **能，但条件是目标机能提供源端那份完整清单**。所以它换来的主要是"**失败可控**"——迁不了会在 Prepare 阶段当场报错，而不是跑到 100% 才挂。**它并不把"不能迁"变成"能迁"** |
| **custom** | ✅ **唯一能真正做到跨代际互迁的方案**（"same hardware no matter what host"）。前提是基线选得足够老、足够普遍 |

**关键差别**：custom 的可迁移范围由**你选的基线**决定，是可控的；host-model 由**目标端的实际能力**决定，是碰运气的。

> **这是三者比较里最容易说错的一条**：常有人把 host-model 理解成"能跨代际"，那是把"失败更可控"误当成了"能力更强"。真正的分界线是——host-model 的能力上限由**目标端 CPU**决定，custom 的由**你选的基线**决定。

## 4.3 性能上有没有差异？

**机制清楚，具体数值必须实测。**（官方不给任何倍数；vSphere 明确说明文档不讨论 CPU 兼容的性能代价 ✅）

| 模式 | 性能 | 机制 |
|---|---|---|
| **host-passthrough** | **零损失（基准）** | Guest 直接用宿主全部指令 |
| **host-model** | **接近零损失** | 运行中 Guest 看到的是源端完整 CPU 定义，特性一个不少 |
| **custom（旧代际基线）** | **可能数倍下降** | 基线越老，暴露的新指令越少 |

## 4.4 一个容易被忽略的不对称：只有 custom 会「静默降级」

| 模式 | 迁移到不匹配的目标 | 结果 |
|---|---|---|
| host-passthrough | 危险 | **失败**（跑到 100% 后挂/崩）→ 你能看到 |
| host-model | 迁移前检查 | **失败** → 你能看到 |
| custom（低基线） | **成功** | **一切正常，只是慢** → **你看不到** |

**custom 的降级是唯一一种"迁移完全成功但业务变慢"的情况。** 没有报错、没有日志、没有告警。唯一的迹象是密码运算 TPS 掉了一截，而运维很可能去查网络、查负载、查业务代码——**查不到这里**。

> 这就是为什么界面文案必须写出来：
> **"目标端不支持 SM4 加速指令，迁移后密码运算性能预计下降 X%"**
>
> 这句话的本质是**把一个静默的损失，提前变成显式的告知**。不在预检里说出来，就永远没人知道。

# 第五章　兼容性检查规格：比什么、和谁比、怎么判

> 本章是本文档的核心实施部分，回答预检 B 组（PC-L2-B1~B4）到底怎么做。
> **三句话概括**：先比架构；再确定比的两端是「Guest 见的」和「目标端能给的」；最后按特性类型分级判定。

## 5.0 检查的输入输出

| 项 | 内容 |
|---|---|
| **输入** | 源 VSM 的标识 + 目标节点标识 |
| **输出** | 一份**差异项清单**，每项含：特性名、源端有无、目标端有无、特性类型、判定结果（阻断/警告）、责任方 |
| **不输出** | 单纯的"兼容/不兼容"布尔值——无法解释原因，也无法生成界面文案 |

## 5.1 第零步：架构先行

在讨论具体特性之前，先排除一个更底层的问题：

> **如果集群里同时存在 x86 节点和 ARM 节点（鲲鹏），两边能比的不再是特性，而是根本不能迁。**

| | x86 | ARM64 |
|---|---|---|
| 密码扩展 | AES-NI、SHA-NI、GFNI、SM3/SM4 扩展 | ARMv8 Crypto Extensions（AES、SHA1/2，ARMv8.2 起含 SM3/SM4） |
| 指令编码 | 完全不同 | 完全不同 |
| **能否互为迁移目标** | **❌ 不能，任何配置都不行** | |

**所以预检的第一步是比对 `<os><type arch=>`。架构不一致直接阻断，后面的特性比对根本不用做。**

> ⚠️ 海光、兆芯虽然是 x86 兼容，但**国密扩展的实现路径与 Intel 不同**（走的不是 Intel 的 CPUID 位定义），所以"都是 x86"也不代表特性清单可以直接互相比较。**本次未核实具体差异，须按实际机型验证**。

## 5.2 第一步：确定比较的两端（A 值与 B 值）

**核心结论：**

> **比的是「Guest 实际看到的特性清单」（A 值）和「目标节点能够提供的特性清单」（B 值），判的是 A ⊆ B 是否成立。**
>
> **不是"节点 A 的 CPU vs 节点 B 的 CPU"——那是 host-passthrough 模式下的退路，不是通用做法。**

### 5.2.1 A 值与 B 值的定义

| | **A：Guest 实际看到的清单** | **B：目标端能提供的清单** |
|---|---|---|
| **含义** | 源端这台 VSM 的 vCPU 对 Guest 呈现的特性集 | 目标节点上的 QEMU/KVM 实际能创建出哪些 CPU |
| **从哪读** | 源端 **VSM 的 domain XML**（运行态） | 目标节点的 **`virsh domcapabilities`** |
| **特性** | 跟着 VSM 走，随 VSM 的 CPU mode 而不同 | 跟着节点走，同一节点对同一机器类型的 B 值相同 |

### 5.2.2 B 值为什么不能用 `/proc/cpuinfo`

**这是最容易搞错的一点。**

| 来源 | 含义 |
|---|---|
| `/proc/cpuinfo` | 宿主机**物理上**有什么 |
| `virsh domcapabilities` | QEMU **实际能建出来**什么 |

两者可能不一致：QEMU 版本旧，可能无法暴露宿主机的新特性；某些特性也可能被 libvirt 配置屏蔽。

**判"能不能迁"必须用后者。** `/proc/cpuinfo` 只在 §7.1 的集群同构性核查里用（那里比的是物理机是否同构）。

### 5.2.3 A 值在 host-passthrough 下不存在

| 源端 mode | A 值在哪 | 比什么 | 算法 |
|---|---|---|---|
| **host-passthrough** | ❌ **不存在**——XML 里只有一行标记，没有任何 `<feature>` | **源节点 CPU 能力 vs 目标节点 CPU 能力** | **比"相同"**（四项全同），不能只比"子集" |
| **host-model** | ✅ 在 live XML 里（几十行 `<feature>`） | **VSM 的 CPU 定义 vs 目标节点能力** | **比"子集"** A ⊆ B |
| **custom** | ✅ 在 XML 里（你写的基线） | **VSM 的基线模型 vs 目标节点是否支持** | **比"子集 + 模型名是否存在"** |

**为什么 host-passthrough 必须比"相同"而不能比"子集"**：它没有清单，无法判 A ⊆ B，只能退一步用"两端节点完全一样"作为**充分条件**。这正是 libvirt 原文给出的退路（§2.1.4 四项全同）。

## 5.3 第二步：B1 分派——按 cpu mode 决定比较算法

**PC-L2-B1 读 `<cpu mode>` 本身不产生"能不能迁"的结论，它是后续判定的分派开关。**

**如果不读 mode 直接比对，只有两种做法，且两种都是错的**：

| 错误做法 | 后果 |
|---|---|
| 一律按"型号相同"判 | 对 custom 模式**误伤**（本来能迁的被拦） |
| 一律按"特征集子集"判 | 对 host-passthrough **放水**（漏掉微码/QEMU 版本差异） |

### 5.3.1 三个读取陷阱

**① 必须读 VSM 的当前实际位置，不能读库里的 `host_id`**

A 值必须在 **VSM 当前实际所在的节点**上读。如果数据库记录的源节点与实际位置不一致（发生过漂移或记录陈旧），读出来的 A 值就是错的。

> **实现上**：先查 VSM 的运行位置，用该位置去查 XML，然后才比对。**不能直接用 `vsm.host_id` 字段。**

**② host-model 必须读 live XML，不能读 `--inactive`**

`virsh dumpxml --inactive` 读到的是**未展开**的 `<cpu mode='host-model'/>`，依然没有清单；只有运行态的 `virsh dumpxml` 里才有展开后的模型名与 `<feature>` 列表。

> ⚠️ 此条为对 libvirt 行为的通用理解，**本次未录入原文**。实现前建议用一台 host-model 的 VM 对比 `virsh dumpxml` 与 `virsh dumpxml --inactive` 的输出来确认。

**③ B 值要带 machine type 读**

`domcapabilities` 的输出随 machine type 变化（对应 PC-L2-B3/B4）。读 B 值时须同时传 `--machine`，与 VSM 当前的 machine type 一致。

## 5.4 第三步：特性全量比对

### 5.4.1 为什么读取阶段不能筛

**不要预先写一份"重要特性白名单"然后只比这几条。** 原因有三：

1. **你不知道目标端缺哪一个**——可能缺的是完全没预料到的一项
2. **特性之间有依赖**——`avx512f` 缺失会让 `avx512bw`、`vaes`、`gfni` 全部失效，但 A ⊆ B 的集合判断本身会自然处理
3. **漏掉一项的代价是不对称的**——多比一项只是多一次集合运算，少比一项可能漏掉真正的阻断原因

**正确做法：让 `virsh cpu-compare` / `domcapabilities` 交出全量集，只在判定阶段做筛选。**

### 5.4.2 三层职责分离

| 层 | 做什么 | 筛不筛 |
|---|---|---|
| **① 读取** | 取 A 值和 B 值的完整特性集 | **全量取，一项不筛** |
| **② 判定** | 逐项按类型定阻断/警告 | 按 §5.5 规则分级 |
| **③ 展示** | 界面排序与文案 | 按业务影响加权（§5.6） |

**如果不把这三层分开，就会变成一大坨 if-else，既无法解释"为什么这项拦那项不拦"，也无法复用。**

### 5.4.3 输出形态：差异列表，不是布尔值

```
目标端缺少：hle, rtm, avx512vbmi
两端一致：aes, avx2, sha_ni, adx ...
```

## 5.5 第四步：分级判定

| 差异类型 | 判定 | 依据 |
|---|---|---|
| **用户级（user-level）特性**不匹配 | **阻断**，不管 VSM 有没有在用 | vSphere EVC 官方 ✅ |
| **内核级（kernel-level）特性**不匹配 | **仅当 VSM 的 CPU 定义里 `policy='require'` 了它才阻断** | 同上 ✅ |
| 目标端**多出**特性 | **不阻断**（Guest 看不到多余项） | — |
| 差异项无法归类 | **阻断**（"无法判定必须判阻断"，见预检规格 §4.1） | — |

**实现路径**：`virsh cpu-compare` 拿到差异列表 → 逐项查类型 → 结合 VSM 的 `<feature policy='require/disable'>` 配置定级。

## 5.6 第五步：展示加权（密码特性表）

**这一层不改变"能不能迁"的结论，只改变界面怎么排、话怎么说。**

| 特性（QEMU/libvirt 名） | 干什么 | 缺了对密码业务 | 级别建议 |
|---|---|---|---|
| `sm3` / `sm4` | 国密算法硬件指令 | 国密运算回落软件实现，**数量级下降** | 用户级 → 阻断 |
| `aes` / `vaes` | AES-NI / 向量 AES | 批量加解密回落软件实现 | 用户级 → 阻断 |
| `pclmulqdq` / `vpclmulqdq` | 无进位乘法（GCM 核心） | AES-GCM 无法硬件加速 | 用户级 → 阻断 |
| `sha_ni` | SHA-1/SHA-256 硬件摘要 | 摘要运算回落软件实现 | 用户级 → 阻断 |
| `gfni` | Galois 域运算 | **SM4 位切片实现的关键**，AES 也受益 | 用户级 → 阻断 |
| `adx` / `bmi2` | 大数运算加速 | RSA/ECC 模幂变慢 | 用户级 → 阻断 |
| `avx2` / `avx512f` / `avx512vl` | 向量化 | 批量对称运算无法并行，与上面几项叠加 | 用户级 → 阻断 |
| `rdrand` / `rdseed` | 硬件熵源 | 退到 `/dev/urandom`（可用，但语义变了） | ⚠️ 打扰动性判断 |
| `pcid` / `invpcid` | TLB 跨地址空间复用 | 上下文切换开销上升 | 内核级 → 按需 |
| `x2apic` / `tsc-deadline` | 中断与定时器路径 | 中断延迟变差 | 内核级 → 按需 |

> ⚠️ 上表"级别建议"是**本文按 vSphere 分级规则做的映射，非官方逐项定性**。特性名的确切拼写也需按实际 QEMU 版本核对（见 §5.7）。

## 5.7 三个实现陷阱

### 5.7.1 特性名有三套说法

同一个特性，在三个地方有三种写法：

| 场景 | 名称写法 | 例子 |
|---|---|---|
| `/proc/cpuinfo` 的 flags | 下划线 | `sha_ni`、`tsc_deadline_timer`、`invpcid_single` |
| QEMU `-cpu` 参数 / `domcapabilities` | 连字符 | `sha-ni`、`tsc-deadline`、`invpcid` |
| libvirt `<feature name=>` | 基本同 QEMU | `sha-ni` |

> ⚠️ 具体映射规则随版本变化，**本次未核实完整映射表**。

**如果自己写一个 `split()` 然后按字符串比对，会把所有带下划线或连字符的项全部判成"不一致"，然后报告一片红。**

**这正是"不要手工写清单"的第二个理由**：让 libvirt 自己的比对函数去做，它内部有名称映射表。

### 5.7.2 源端读错节点

见 §5.3.1 陷阱①。**这是最容易导致"预检通过但迁移仍然失败"的实现 bug。**

### 5.7.3 把"检查失败"当成"检查通过"

`virsh cpu-compare` 执行出错、输出为空、返回码非零——**一律判阻断**，绝不能吞掉错误当通过。

> 用户看到一片绿、迁移却失败，从此不再相信预检。这是这类预检最常见的实现 bug。

## 5.8 责任方归属

**差异项一律归到"目标节点"**——差异项天然可以回答"这是哪一端缺的东西"。

| 差异类型 | 责任方 | 处理建议 |
|---|---|---|
| 目标节点缺特性 | 目标节点 | 换节点，或升级 CPU |
| 目标节点缺 machine type | 目标节点 | 升级 QEMU |
| 两端 QEMU/微码不一致（host-passthrough） | **两端都要看** | 统一版本 |
| 源 VSM 的 CPU 定义本身异常 | **源 VSM** | 查导入流程 |

## 5.9 最小实现清单

如果只是为了生成界面上的"1 项阻断"，最后大概率会落在这几项上。**但这份清单用于"排序"，不用于"判定"**：

```
架构先行            ：os.type.arch 一致？
密码核心（阻断级）  ：sm4, sm3, aes, sha-ni, gfni, pclmulqdq
向量（阻断级）      ：avx2, avx512f, avx512vl, vaes
公钥（阻断级）      ：adx, bmi2
熵源（警告级）      ：rdrand, rdseed
内核类（按需）      ：pcid, invpcid, x2apic, tsc-deadline
```

## 5.10 host-passthrough 下的特殊处理

host-passthrough 没有 A 值，因此：

| 用途 | 是否适用 |
|---|---|
| **迁移前判定** | ❌ 不适用——只能退回"四项全同"判定（§7.1） |
| **失败后诊断** | ✅ **适用**——用合成 A 值（§7.3 路线一）生成差异列表，作为**事后诊断信息**贴到结果卡 |

> 这是 host-passthrough 场景下这套比对流程唯一的价值点，但价值很高：它能把"迁移失败"变成"**迁移失败，目标端缺少 sm4、gfni、avx512f**"。

## 5.11 machine type 检查（B3 / B4）

> 与 CPU 特性检查是**两套独立的失效原因**：CPU 管「Guest 能不能做某件事」，machine type 管「设备长在哪个位置」。两者不可互相替代。

### 5.11.1 machine type 是什么

虚拟机没有真实主板，Guest 以为的那些硬件（芯片组、PCI 插槽、中断控制器、定时器、ACPI 表）**全是 QEMU 用软件模拟出来的**。

**machine type 就是 QEMU「造假电脑」用的图纸**——上面规定了用什么芯片组、有几个插槽、每个设备放哪、地址怎么分、中断怎么走、ACPI 表长什么样。

在 domain XML 中的位置：

```xml
<os>
  <type arch='x86_64' machine='pc-q35-7.2'>hvm</type>
</os>
```

名称拆解：

| 片段 | 含义 |
|---|---|
| `pc` | PC 兼容机这一类图纸 |
| `q35` | 用 Q35 芯片组（另一种是老的 `i440fx`） |
| `7.2` | **QEMU 7.2 那一版时的图纸** |

**不同图纸不是"参数不同"，是两台结构不同的机器**（插槽数、PCIe 支持、南桥型号全都不同）。

### 5.11.2 为什么图纸名后面要带版本号

QEMU 每版都在改自己模拟的硬件（加设备、挪默认地址、改 ACPI 表）。如果直接改，**所有现存虚拟机下次重启都会出问题**。

因此 QEMU 的做法是：

> **每发布一版，就把当时的图纸冻结、起个带版本号的名字、永久保留，绝不修改。**

所以 `pc-q35-7.2` 在 QEMU 升级到 8.1、9.0 之后依然存在且一字不改。**这正是 QEMU 能承诺"同版本 + 同 machine type 必须可迁移"的机制来源**（✅ §8.1 PC-L2-B3）。

### 5.11.3 为什么迁移必须两端一致

**关键在于 Guest 会把布局抄进自己的内存，而且之后不再重扫。**

```
开机时：   Guest 读 ACPI 表、扫 PCI 总线
        → 把「网卡在插槽 3、地址 0x...、中断 16 号」全部记进内存
        → 之后再也不问，直接用记下来的地址

迁移时：   整块内存搬运 → 这份「设备地址表」跟着一起搬走

目标端：   Guest 醒过来，继续按记忆去「插槽 3」找网卡
```

**它不是每次访问设备都问一遍，它记的是「门牌号」而不是「住户」。** 目标端布局不同，Guest 就会按旧地址访问错误的位置。

> ⚠️ 「Guest 缓存设备布局、运行期不重新枚举」是通用操作系统知识，**本次未抓 QEMU/内核官方原文**。此为机制解释，引用前建议核实。

### 5.11.4 不一致的后果

| 布局要素不一致 | Guest 的行为 | 后果 |
|---|---|---|
| **设备地址 / PCI 插槽** | 按旧地址访问，那里可能是别的设备 | **数据写到错误位置**（最危险） |
| **ACPI 表** | 设备树与实际不符 | 设备"消失"、电源管理异常 |
| **中断路由** | 中断发给错误的设备 | 丢中断、设备超时 |
| **定时器** | 时间源地址变化 | **时间跳变**、定时任务紊乱 |
| **芯片组（i440fx ↔ q35）** | 根本是两套机器 | 大概率直接起不来 |

> **最坏的情况不是"起不来"，是"起来了，但按旧地址读写到别处"。** 不报错、无告警，可能几个月后才暴露——**对密码业务而言，这意味着数据写入了错误位置，而不只是迁移失败。**

### 5.11.5 它不会报错的原因

整条链路上**没有任何一环在检查布局一致性**：

| 环节 | 检查什么 | 查布局吗 |
|---|---|---|
| QEMU 迁移 | 内存是否传完 | ❌ |
| libvirt | domain XML 是否传完 | ❌（若 CPU/机型段只有别名） |
| Guest 操作系统 | **什么都不查，它以为自己还在原机器上** | ❌ |
| 业务程序 | 系统 API 返回成功 | ❌ |

**Guest 永远不知道「我换了台机器」——这正是虚拟化的设计目标。而无感的另一面，就是出了问题它也不会说。**

### 5.11.6 B3 / B4 各查什么

| 编号 | 查什么 | 通俗说法 | 抓的情况 |
|---|---|---|---|
| **PC-L2-B3** | 源端 `<type machine=>` == 目标端将要使用的 | 两边图纸是不是**同一张** | 两端都能创建，但**创建出来不一致** |
| **PC-L2-B4** | 目标端 QEMU **存在**该 machine type | 目标端档案里有没有这张图纸 | 目标端 QEMU 太老，**根本没有这个机型** |

**两条缺一不可**：

- **只做 B3** → 名字对上，但目标端没这张图纸 → 执行阶段才失败
- **只做 B4** → 图纸有了，但源端要的是另一张 → 布局不一致

**推荐顺序**：先 B3（纯字符串比对，零成本），再 B4（需查询目标节点）。

### 5.11.7 最隐蔽的陷阱：`machine='pc'` / `machine='q35'` 这类别名

XML 里有时不写具体版本，而写别名。**别名的含义是「本机 QEMU 最新那一版」**：

```
源节点 QEMU 7.2   →  machine='q35' 解析成  pc-q35-7.2
目标节点 QEMU 8.1 →  machine='q35' 解析成  pc-q35-8.1
                                ↑ 字符串一致，实际图纸不同
```

**字符串比对通过，实际布局不一致**——这是"预检通过但迁移照样出事"的经典原因。

> ⚠️ **未核实**：libvirt 是在何时把别名解析为具体版本的（写入时固化，还是启动时解析），本次未查到确切机制。
>
> **若保留别名，B3 的正确实现必须先解析再比对**，不能直接比字符串。实现前须用实机验证。

### 5.11.8 平台必须查证的一件事

**平台创建 VSM 时有没有显式指定 machine type？**

```bash
virsh dumpxml <vsm-name> | grep -E '<os>|machine='
```

| 输出 | 判断 | 风险 |
|---|---|---|
| `machine='pc-q35-7.2'`（**具体版本**） | 图纸已写死 | ✅ 安全；但仍需确认各节点 QEMU 均 ≥ 7.2 |
| `machine='q35'` / `machine='pc'`（**别名**） | 随本机 QEMU 版本自动变化 | ⚠️ **节点 QEMU 版本不同就出错，且字符串检查查不出** |
| **完全没有 `machine=` 属性** | 完全依赖宿主机默认值 | ⚠️ **最危险**，图纸随 QEMU 版本漂移，无人记录 |

> **这和 §7.1「伪同构」是同一类问题**：型号、配置看着都一样，但 QEMU 版本悄悄不同，machine type 就悄悄不同。此项即 RQ-1-04 判定为"未核"的原因。

### 5.11.9 附带收益与边界

machine type 名称**内嵌了 QEMU 版本号**，所以：

> **「两端 machine type 名称相同」≈「两端 QEMU 版本足以共同支持这个机型」**

B3/B4 用几乎零成本的方式获得了 PC-L2-C1（QEMU 版本 n↔n+1）的**大部分**收益。

> **但这是必要不充分条件。** 两台 QEMU 9.0 与 9.5 都能提供 `pc-q35-7.2`，B3 通过，但其余设备状态的兼容性仍需 C1 单独判定。**不能因 B3 通过而免除 C1。**

# 第六章　性能损失分析

## 6.1 三类损失要分开算

custom 基线降低时，Guest 丢的东西不是一回事，混在一起谈会算错账：

| 类型 | 表现 | 能否接受 |
|---|---|---|
| **性能损失** | 软件回落到慢实现，功能正常但变慢 | 可量化，有时可接受 |
| **功能损失** | 软件检测不到必需指令，拒绝启动或运算异常 | 直接不可用 |
| **静默性**（性质，非损失） | 前两类都可能**不报错** | 最危险 |

## 6.2 具体丢什么（按对密码业务的影响排序）

| 特性 | 丢了的后果 | 类型 |
|---|---|---|
| **SM3 / SM4 指令扩展** | 国密运算从硬件指令回落到软件实现，**数量级差异** | 性能 |
| **AES-NI / VAES** | AES 批量加解密回落软件实现，数量级差异 | 性能 |
| **SHA-NI** | SHA-1/256 摘要回落软件实现 | 性能 |
| **ADX / BMI2** | RSA、ECC 的大数模幂回落，公钥运算明显变慢 | 性能 |
| **AVX2 / AVX-512** | 批量对称运算、部分哈希无法向量化，进一步叠加 | 性能 |
| **RDRAND / RDSEED** | 硬件熵源不可用，退到 `/dev/urandom`（可用但语义变了） | 性能/语义 |
| **PCID / INVPCID** | TLB 不跨地址空间复用，上下文切换开销上升 | 性能 |
| **TSC-deadline / x2APIC** | 定时器与中断路径退化 | 性能 |

> ⚠️ 上表中"数量级差异""明显变慢"为**通用认知，非本次核实的官方数据**。具体倍数必须以 §9 的 E-01 实测为准。

## 6.3 为什么可能是"数倍"而不是"慢 10%"

因为这不是同一个算法跑慢了一点，而是**换了算法实现**：

```
有硬件指令：一条指令完成一轮 SM4 变换
无硬件指令：查表 + 移位 + 异或，每轮几十条指令
```

而且往往**叠加第二层损失**：软件实现通常也难以向量化，于是连"多路并行"这个补偿手段也没有。两层叠加，就不是百分比了。

## 6.4 还要再乘一层：VSM 里用的是哪个密码库

| 密码库类型 | 缺指令时的行为 |
|---|---|
| OpenSSL 1.1.1+（支持 SM4） | 有运行时分派，会**静默选慢路径** |
| GmSSL / 厂商 SDK | 行为可能不同，某些版本**直接报错退出**（变成功能损失） |

> ⚠️ 这一条无法外部核实，**需查 VSM 镜像内实际使用的密码库与版本**。

## 6.5 静默降级的不对称性

见 §4.4。**custom 是唯一"迁移完全成功但业务静默变慢"的模式**——这条不对称性是"界面必须显式告知性能预估"这一设计的根本理由。

# 第七章　本平台现状与选型

## 7.1 前置判断：我们的集群是同构的吗

**这一节必须放在所有模式讨论之前。** 因为"该不该改 CPU 模式"完全取决于这个答案——如果集群本来就是同构的，现有配置已经是最优解，改任何模式都只是多一次关机加一分性能损失。

### 7.1.1 核查命令

每台节点都跑，把输出并排比对：

```bash
# ① CPU 型号与步进
lscpu | grep -E 'Model name|Stepping'

# ② 微码版本（最容易被忽略的一项）
grep -m1 microcode /proc/cpuinfo

# ③ QEMU 版本
qemu-system-x86_64 --version | head -1

# ④ libvirt 版本
virsh --version
```

### 7.1.2 判定表

| 输出情况 | 同构性 | 现有 host-passthrough | 该做什么 |
|---|---|---|---|
| **全部一致** | ✅ 同构 | **安全，且是最优解** | **什么都不用改。** 把这几项做进 B1 预检，保证将来扩节点时不会悄悄破坏它 |
| **型号一致，微码或 QEMU 不一致** | ⚠️ **伪同构**（最危险） | **已经是一个隐患** | 先统一微码 / QEMU 版本。此类不一致**从型号字符串上完全看不出来**，但足以让迁移在 100% 崩溃 |
| **型号不一致** | ❌ 异构 | **必炸** | 三选一：统一硬件，或改 host-model（受限），或改 custom（有性能代价）——见 §7.4 |

> **「伪同构」是这一节真正要发现的东西。** 采购时说"都买同一型号"，不等于同构：只要中间有一台打过 BIOS/微码补丁、或 QEMU 被单独升级过，四项全同就已经破了。**这是本平台最可能踩的坑，而且它不会在任何界面上表现出来。**

### 7.1.3 一条推论

**如果核查结果是"全部一致"，那么"选 host-passthrough 还是 host-model"这个问题本身就不成立**——同构集群里两个都能用，而 host-passthrough 不需要任何改造，性能还最优。

**改造模式只在核查结果是"伪同构"或"异构"时才有必要。**

## 7.2 平台现状

平台默认 `host-passthrough`：

- `arch.go:23` —— 默认 CPU 模式即 host-passthrough ✅
- `import_guest.go:394` —— 导入时写 `<cpu mode='host-passthrough' check='none' migratable='on'/>` ✅

**所以所有现存 VSM 都是 host-passthrough。**

| 维度 | 现状 |
|---|---|
| 密码运算性能 | **最优**（无牺牲） |
| 可迁移范围 | **仅限四项全同的节点** |
| 预检里能否比对 | ❌ **没有比对对象**——host-passthrough 没有 A 值 |

> 注意这一条只影响**检查怎么实现**，不影响**集群该不该改模式**。可以用 §7.3 路线一在检查层面绕过它，不必为了"能预检"而改 CPU 模式。

## 7.3 三条现实的路线（仅在判定为伪同构 / 异构时需要选）

| 路线 | 做法 | 优点 | 缺点 | 停机 |
|---|---|---|---|---|
| **一：人工补出 A 值** | 用 `virsh cpu-compare` 合成宿主机 CPU 定义，两端互比 | 不改动任何 VSM | 是**模拟**——真正的清单并不存在，只能近似 | **零** |
| **二：改为 host-model** | 现存 VSM 改 CPU 模式 | 清单现成，检查更可靠；性能几乎不损失（§2.2.5） | **换来的只是"失败可控"，不是"能跨代际"** | 每台一次 |
| **三：改为 custom（低基线）** | 指定一个足够老的基线 | **唯一能真正做到跨代际互迁** | 密码运算**确定性性能损失**；基线一旦确定运行中不可改 | 每台一次 |

> **核实边界**：路线二曾被单独推荐为"更划算的选择"——**那个结论只在集群已经异构时才成立**。集群同构时，路线二纯属多余改造。此建议为笔者的工程判断，非官方结论。

## 7.4 选型规则

| 选择 | 前提 | 可迁移范围 | 密码性能 | 失败模式 | 改造代价 |
|---|---|---|---|---|---|
| **host-passthrough（现状）** | 四项全同 | 仅四项全同的节点 | **最优** | **跑到 100% 才崩** | 无 |
| **host-model** | 目标机能提供源端清单 | 目标端能力够即可（**不能跨代际**） | **满血** | 迁移**开始前**报错 | 一次关机 |
| **custom（高基线）** | 无 | 同代际 | 略有损失 | 迁移前报错 | 一次关机 |
| **custom（低基线）** | 无 | **跨代际** | **数量级损失** | 永不失败（但会静默变慢） | 一次关机，且不可逆 |

**归纳成一句可判定的规则**：

> - **集群同构** → host-passthrough，**不改**
> - **集群异构但不跨代际** → host-model，性能满血，失败可控
> - **集群必须跨代际互迁** → **只有 custom**，代价是确定性的性能损失

**两个反向结论**：

1. **集群本来就同构时，改 custom 是纯粹的损失**——牺牲密码性能去换一个用不到的可迁移性。
2. **异构且必须互迁时，宁可要"确定的、可量化的"损失**（custom 基线设多老、损失基本可预期），也比 host-passthrough 的"跑到 100% 随机崩溃"可控得多。

# 第八章　实施规格：预检 B 组

> 本章是《热迁移预检项规格_2026-11-06.md》§2 B 组的细化补充，两者配套使用。

## 8.1 B 组条目定义

| 编号 | 检查项 | 级别 | 依据 | 当前状态 |
|---|---|---|---|---|
| **PC-L2-B0** | **架构一致**：`<os><type arch=>` 两端相同 | 阻断 | §5.1 | ❌ **缺失** |
| **PC-L2-B1** | 读源端 `<cpu mode>`，作为后续判定的分派开关 | 分派（本身不判定） | §5.3；平台默认 host-passthrough（`arch.go:23`）✅ | ❌ **缺失** |
| **PC-L2-B2** | CPU 特性逐项比对，按特性类型分级判定 | 分级（见 §8.3） | §5.4 / §5.5；分级规则对标 vSphere ✅ | ❌ **缺失** |
| **PC-L2-B3** | machine type 一致（`<os><type machine=...>`） | 阻断 | QEMU 原文："migration is only supposed to work if you use the same machine type in both source and destination" ✅ | ❌ **缺失** |
| **PC-L2-B4** | 目标端存在该 machine type | 阻断 | `virsh domcapabilities --machine` 两端比对 | ❌ **缺失** |

## 8.2 节点数据采集要求（B 组的真正起点）

平台目前大概率只采集了 CPU 型号字符串。要落地 B 组，节点注册信息必须先补三个字段：

| 字段 | 采集方式 | 用途 |
|---|---|---|
| **CPU 型号 + 步进** | `lscpu` 的 `Model name` / `Stepping` | 粗筛 |
| **微码版本** | `/proc/cpuinfo` 的 `microcode` 字段 | **host-passthrough 四项全同判定的关键** |
| **QEMU 版本** | `qemu-system-x86_64 --version` | 对应 PC-L2-C1 |

> **这一步和 §7.1 的集群同构性核查是同一件事**：核查命令就是采集这些字段，判定表就是把这些字段两两比对。**先做一次人工核查并记录；再把字段做成节点注册的必填项，把判定做成预检的 B1 项。** 人工核查是一次性的，注册字段是长期的——后者保证新节点接入时不会悄悄引入异构。

## 8.3 分级判定规则

| 特性类型 | 不匹配时 | 来源 |
|---|---|---|
| **用户级（user-level）特性** | **只要两端不匹配就阻断**，不管 VM 实际有没有在用 | vSphere 官方 EVC 文档 ✅ |
| **内核级（kernel-level）特性** | **仅当 VM 实际暴露了目标机缺少的特性时才阻断** | 同上 ✅ |
| 无法归类 | **阻断** | 预检规格 §4.1 |

## 8.4 界面呈现要求

1. **差异项必须带责任方 + 【去处理】跳转**（见 §5.8）
2. **"无法判定"要明说**：不显示绿勾，显示灰问号 + "无法判定，已按阻断处理"
3. **密码相关特性优先排序**（§5.6），并给出业务影响措辞，而不只是特性名
4. **host-passthrough 下失败后**：把合成的差异列表作为诊断信息呈现（§5.10）

# 第九章　实验验证计划 E-01

## 9.1 一个必须先说清的坑

⚠️ **host-passthrough 迁异构会直接失败，所以测不到"迁移后的性能"。**

RQ-4-07 真正能测的是「**custom 基线的降级代价**」，不是「host-passthrough 的性能」。写实验方案时必须写明白，否则测完发现没数据。

| 场景 | 能测什么 |
|---|---|
| host-passthrough 迁异构 | 只能测**失败现象**（在哪一步挂、报什么错），测不到性能 |
| **先改 custom 基线 → 再迁** | 这才是 **RQ-4-07 的实质**：性能差异倍数 |
| host-model 迁异构 | 若能成功，测「零损失」是否成立 |

## 9.2 采集命令

```bash
# Guest 内，同一台 VSM，分别在不同 CPU 基线开机后跑
openssl speed -evp sm4-cbc
openssl speed -evp sm3
openssl speed -evp aes-128-gcm
openssl speed -evp sha256
openssl speed rsa2048      # 测 ADX/BMI2 这条路径
```

## 9.3 代理指标 vs 业务实测

⚠️ **`openssl speed` 只是代理指标**。真正的答案是 VSM 自己的业务压测——因为实际用的密码库、有没有运行时分派，决定了这个损失到底会不会发生。

如果密码库是编译期写死走硬件指令的，缺指令时它可能直接起不来，那测 openssl 就没意义了。

## 9.4 实验前置条件

见 §8.2 的三个字段。**没有这些数据，实验连分组都做不了**（不知道该挑哪几台机器作为"同构"和"异构"对照）。

## 9.5 需一并验证的推论

| 待验证项 | 出处 | 验证方式 |
|---|---|---|
| host-passthrough 失败的具体阶段（是否在状态恢复时 `KVM_SET_CPUID2` 失败） | §3.3 | 跨代际迁一次，记录阶段与 stderr |
| host-model 迁 batched 的成功边界 | §4.2 | 反向迁移（新→旧）测试 |
| 微码不同但型号相同是否真的会失败 | §7.1「伪同构」 | 找两台同型号不同微码的节点互迁 |

# 第十章　结论摘要

## 10.1 机制层

1. 三种 CPU 模式只控制 **CPUID 递给 Guest 的特性位清单**，与 vCPU/内存/磁盘配置无关。
2. 三者区别只有两点：**谁决定清单**、**清单有没有被写下来**。
3. host-passthrough **没有清单**；host-model 与 custom 有清单，写在 domain XML 里。
4. host-passthrough 的"照给"是**运行时行为**，迁移时不打包清单一起走。

## 10.2 行为层

5. host-passthrough 不是"禁止迁移"，是"**不保证结果**"。前提是**四项全同**（硬件 + QEMU + 微码 + 配置），不是"同型号"。
6. 只有 custom 会**静默降级**——迁移成功但业务变慢，无任何告警。
7. host-model **不能跨代际**，它换来的是"失败可控"（Prepare 阶段报错），不是"能力更强"。

## 10.3 检查层

8. 比对的是 **A 值（Guest 见的）⊆ B 值（目标端能给的）**，不是节点与节点直接比。
9. **架构先行**：x86 vs ARM 不一致直接阻断，不进特性层。
10. **读取不筛、判定分级、展示加权**——三层职责必须分离。
11. **B 值必须用 `domcapabilities`，不能用 `/proc/cpuinfo`**。
12. **host-passthrough 没有 A 值**，只能退化为"四项全同"判定；比对流程仅用于失败后诊断。
13. 特性名有下划线/连字符两套写法，**手工字符串比对必错**。
14. **machine type 与 CPU 特性是两套独立的失效原因**：前者管"设备在哪"，后者管"能不能做"。
15. **machine type 错误最危险的形态是"迁移成功但读写错位"**，不报错、无告警，可能长期潜伏。
16. **`machine='q35'` 这类别名会让字符串比对假通过**，B3 可能须先解析别名再比对。

## 10.4 平台层

17. 平台默认 host-passthrough，**所有现存 VSM 均无清单**。
18. 选型前必须先做 §7.1 的**集群同构性核查**；同构则**不必改**。
19. 真正需要警惕的是「**伪同构**」——型号相同但微码/QEMU 不同，界面上完全看不出来。
20. **平台 XML 是否显式写死 machine type 尚未查证**，这决定现存 VSM 是否已处于风险中。

## 10.5 首要待办

| 顺序 | 事项 | 理由 |
|---|---|---|
| 1 | **集群同构性核查**（§7.1 四条命令） | 决定后续所有选型讨论是否有意义 |
| 2 | **查平台 XML 是否写死 machine type**（§5.11.8 一条命令） | 成本最低，但可能直接发现现存 VSM 已在风险中 |
| 3 | 节点注册补三个字段（§8.2） | B 组落地的真正前提 |
| 4 | `virsh cpu-compare` 试跑，确认输出格式 | 决定 B2 能否按设计实现 |
| 5 | E-01 实验 | 唯一的确定性数据来源 |

# 附录 B　核查命令速查卡

> 可直接发给运维同事执行。所有命令只读，不修改任何配置。

## B.1 集群同构性核查（每台节点执行）

```bash
#!/bin/bash
# 输出本节点的 CPU 同构性指纹，逐台比对
echo "=== $(hostname) ==="
echo "[型号]   $(lscpu | grep 'Model name' | cut -d: -f2 | xargs)"
echo "[步进]   $(lscpu | grep 'Stepping'   | cut -d: -f2 | xargs)"
echo "[微码]   $(grep -m1 microcode /proc/cpuinfo | awk '{print $3}')"
echo "[QEMU]   $(qemu-system-x86_64 --version | head -1)"
echo "[libvirt] $(virsh --version)"
```

**比对方法**：所有节点的五条输出**逐行完全相同**才算同构。任何一行不同都要记录在案。

## B.2 单台 VSM 的 A 值读取

```bash
# ① 先确认真实运行位置（不能用数据库里的 host_id）
virsh list --all | grep <vsm-name>

# ② 读运行态 XML 的 CPU 段（host-model 必须用 live，不能加 --inactive）
virsh dumpxml <vsm-name> | sed -n '/<cpu/,/<\/cpu>/p'
```

## B.3 目标节点的 B 值读取

```bash
# ① 目标节点的 CPU 能力（这是"能建出来什么"，不是 /proc/cpuinfo）
virsh domcapabilities | sed -n '/<cpu>/,/<\/cpu>/p'

# ② 该 machine type 是否支持
virsh domcapabilities --machine <machine-type> | head -40

# ③ 该 machine type 是否存在（列表）
virsh domcapabilities --machine <machine-type>
```

## B.3a machine type 核查（B3/B4）

```bash
# ① 平台生成的 XML 到底写的是什么（具体版本 / 别名 / 完全没写）
virsh dumpxml <vsm-name> | grep -E '<os>|machine='

# ② 目标端是否有这张图纸
virsh domcapabilities | grep -o 'machine="[^"]*"' | sort -u | grep <machine-type>

# ③ 别名解析成什么（参数写法待核实，见附录 A 第 4 项）
virsh domcapabilities --machine q35 | head -20
```

## B.4 迁移失败后的诊断

```bash
# 合成源节点的 CPU 定义，带到目标节点比对
virsh capabilities | sed -n '/<cpu>/,/<\/cpu>/p' > /tmp/src-host-cpu.xml

# 在目标节点上执行（参数写法待核实，见附录 A 第 2 项）
virsh cpu-compare /tmp/src-host-cpu.xml
```

## B.5 密码性能基线采集（Guest 内）

for alg in sm4-cbc sm3 aes-128-gcm sha256; do
  echo "=== $alg ==="
  openssl speed -evp $alg 2>/dev/null | tail -2
done
