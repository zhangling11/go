## 0. 一句话概括

Hyper-V 的热迁移 = **一套"先比对兼容性、再执行搬移"的两步式流程**，外层套了两层壳（有无故障转移集群），搬迁 cmdlet 统一为 `Move-VM`。

对我们的最大参考价值是它的**接口设计**：

1. **`Compare-VM` 与 `Move-VM` 是两个独立命令**——先出一份兼容性报告，报告里逐条列出不兼容项，修完再执行。这正好是我们"预检 → 提交"两步式设计的业界同款。
2. **处理器兼容性是一个"每 VM 可开"的开关**，不是集群基线，也不是宿主机配置——这是 CPU 兼容性问题的第三种解法。
3. **兼容性报告本身是对象**，可以持有、可以修改、可以重新比对，甚至可以直接喂给 `Move-VM` 执行。

## 1. 两种部署形态

这一节的区分是全文的前提，先讲透。

### 1.0 底层事实

Hyper-V 是 Windows Server 上的虚拟化功能：一台物理机（**主机 / Host**）上跑若干虚拟机。热迁移 = 把一台**正在运行**的虚拟机从 A 机搬到 B 机，业务几乎不停。

搬的时候要回答两个问题：**谁来指挥？搬一半出事了谁来收摊？** 答案取决于有没有"集群管家"。

### 1.1 形态一：带故障转移集群（Failover Clustering）

**先有集群，才有迁移。**

把 2 台及以上 Windows Server 加进一个**集群（Cluster）**，由 **WSFC**（Windows Server Failover Clustering）服务统一管理。加入后这几台机器对外像一个整体。

> **比方**：几台机器住进同一个小区，请了**物业公司**（集群服务）。物业手里有账本，记着每台机器上跑着什么。要从 3 号楼搬到 5 号楼，是**跟物业说**，物业派人搬、改账、通知各方。更要紧的是：3 号楼塌了，**物业会自动**把里面的虚拟机在别的楼重新启动——这就是高可用（HA）。

特征：

- 迁移与故障自动接管是**同一个管家提供的两项服务**；
- 通常配**共享存储**（磁盘放在 SAN/网络存储，两台机都能访问），迁移**只搬内存不搬磁盘**，所以快；
- 出问题由管家统一善后。

### 1.2 形态二：不带集群（standalone / 独立主机）

**只有两台普通的、互不相识的 Windows Server。**

> **比方**：自己找朋友搬家，搬完就完事。但如果你家着火了，**没有任何人来管你的家具**——因为压根没有物业。

特征：

- 迁移是**纯手工动作**，无自动接管；
- 没有共享存储，必须**内存 + 磁盘一起搬**（即 shared-nothing，共享无）；
- A 机中途宕了、或发起迁移的管理机崩了，**没有人自动清理残局**。

### 1.3 对比

| 维度 | 带故障转移集群 | 不带集群（standalone） |
|---|---|---|
| 有没有"管家" | 有（WSFC） | 没有 |
| 谁执行迁移 | 集群服务调度 | 直接对某台机下命令 |
| 迁移搬什么 | 主要搬内存（磁盘在共享存储不动） | **内存 + 磁盘一起搬** |
| 主机意外宕机 | **虚拟机自动在别的机器重启**（HA） | 虚拟机就是死了，没人管 |
| 前置条件 | 共享存储、域环境、集群配置、仲裁盘等一整套 | 两台同域机器，开个开关即可 |
| 配置复杂度 | 高 | 低 |
| 典型场景 | 生产环境、要求高可用 | 单机维护、小规模、测试 |

### 1.4 版本沿革（为什么文档先讲集群）

在 Windows 世界里，**热迁移早年是"集群"的附属功能**——先搭集群才谈得上迁移。后来才放宽。

- ✅ 带集群形态：官方称 live migration "when paired with Windows Failover Clustering, allows the creation of highly available and fault tolerant systems"
- ✅ 不带集群形态：**Windows Server 2016 起支持**。原文："In Windows Server 2016, there are fewer restrictions on live migration deployment. It now works without Failover Clustering."

文档的叙述顺序是历史惯性：先讲传统集群形态，再讲新的独立形态。

### 1.5 对照我们：我们是"缺失的管家"

我们的场景是裸 KVM + 自研平台，没有 WSFC、没有 vCenter、没有 Proxmox 集群服务——**按分类属于形态二，且是最裸的那种**。

但看我们平台自己做了哪些事：

| 平台已实现的能力 | 在"形态一"里由谁提供 |
|---|---|
| 迁移前兼容性预检 | 管家（集群服务） |
| 迁移中进度跟踪、取消 | 管家 |
| 失败/取消后清理目标端残留磁盘 | 管家 |
| 完成后五项结果验证 | 管家 |

**这些恰恰是集群管家免费提供的东西。** 因为我们没有管家，每一件都得平台自己写。这也解释了大纲 §3.5 里为什么清理逻辑做得比很多开源项目细致——不是我们格外勤快，是没人替我们兜底，不做就会出事。

**反过来，有一件我们永远做不到管家那样**：主机真的宕机时自动把 VSM 接管过来。**那是 HA 的活，不是迁移的活。** 这条应明确写进范围外说明，避免"做了热迁移就等于有了高可用"的误解。

## 2. 前提条件（standalone 路径）

### 2.1 权限与角色

| 条件 | 要求 | 核实 |
|---|---|---|
| 权限 | 源、目标两台机器上的 **Hyper-V Administrators** 或 **Administrators** 组成员 | ✅ |
| 配约束委派时 | 额外要 **Domain Admins**（域管理员） | ✅ |
| 角色 | **两端都装了 Hyper-V 角色** | ✅ |

**为什么权限要"两端"**：迁移不是单向推送。源机要"交出"虚拟机（关闭、释放资源），目标机要"接收"（注册、加载状态、启动）。两个动作都要管理员权限，只在一端有权限做不成。

**为什么"角色"这条容易踩坑**：管理工具（Hyper-V Manager）和 Hyper-V 角色是两个独立功能。目标机只装了管理工具、没装角色时，能连上、能看见、**一迁就失败**。

> **对照我们**：平台用 `qemu+ssh://root@...` 连过去，等于两端都是 root，权限这关天然不存在——但这意味着**我们的权限边界比 Hyper-V 粗得多**。Hyper-V 至少有个"Hyper-V 管理员"中间层（能管虚拟机但不能管域），我们是全 root。这条不是功能缺失，是**权限粒度问题**，值得在安全章记一笔。

### 2.2 域关系：同一 AD 域，或互相信任的域 ← 最容易被忽略

| 条件 | 要求 | 核实 |
|---|---|---|
| 域关系 | **两端在同一 AD 域，或互相信任的域** | ✅ |
| 管理工具 | 至少 WS2016 或 Win10，或在源/目标机上直接运行 | ✅ |

**为什么是硬门槛**：Hyper-V 的认证不是"我知道你的密码"，而是"域控制器能证明你是你说的那个人"。跨域/工作组环境下没有可信第三方（域控）来证明，Kerberos 就签发不出票据。

> **对照我们**：我们走 SSH，认证基础是"主机密钥 + 用户密钥"，不需要中心化域控——这是我们比 Windows 方案轻的地方。**但代价是信任要靠人工建立**（首次连接确认主机指纹）。
>
> 会议答复 §4 讨论的"首次指纹确认能不能默认接受"，本质上就是在补 Windows 用 AD 域控解决的同一个问题。**两边都在解"信任从哪来"**，只是 Windows 有机构背书，我们只能靠 TOFU 或 CA。这个视角可以直接写进 §3.3 安全章。

### 2.3 版本门槛：注意是"两个版本"同时受限

| 限制 | 内容 | 核实 |
|---|---|---|
| 宿主机版本 | Windows Server 2012 R2 及以上都能互相迁 | ✅ |
| **虚拟机版本** | **必须 ≥ 5**（WS2016 ↔ WS2012 R2 互迁的场景） | ✅ |

**"虚拟机版本"是什么**：Hyper-V 给每台虚拟机打一个版本号，代表它支持哪些虚拟硬件特性（新的虚拟网卡型号、新的配置项等）。**版本号只增不减——一旦升级就降不回去。**

所以一台"版本 5"的虚拟机能在 2012 R2 和 2016 之间自由迁移，因为两边都认得版本 5 的配置。但虚拟机升到版本 8（只有 2016 支持）后，迁回 2012 R2 就不行——**旧系统读不懂新配置**。

> **这条对我们价值最大，是 Q2 问题的现成范本。**
>
> 微软的解法不是"靠兼容矩阵碰运气"，而是**给每台虚拟机一个显式的、单调递增的版本号，迁移时先比版本号**。可以照抄：
>
> 1. 给每台 VSM 打一个"兼容性版本"（创建时按当时的集群基线确定）；
> 2. 迁移前预检只做一件事——比对这个版本号在不在目标节点的支持范围内；
> 3. 想升版本必须先关机（因为改配置）——与 RQ-1-14"冷迁移要求关机"同理。
>
> 这比"比 QEMU 版本字符串"靠谱得多：QEMU 版本号是自由的（各发行版打各自的补丁），而这个版本号是我们自己说了算的。

### 2.4 认证方式（两选一，各有各的难受）

这是 Hyper-V 迁移里最反直觉的一块。**两种认证方式，微软没给"都好"的答案，而是让你在两种麻烦里选一种。**

#### 2.4.1 CredSSP（默认）

**做法**：发起迁移的账号凭证被"转发"到源机，源机拿它去连目标机。

| | 内容 | 核实 |
|---|---|---|
| 优点 | 不需要配域委派，开箱能用 | ✅ |
| 缺点 | **必须先登录到源机**，才能发起从源机往外迁的操作 | ✅ |

官方举了一个很具体的例子：

> 你登录 TestServer01，把虚拟机迁到了 TestServer02。现在想迁回来——**你得先登录 TestServer02**。不登录直接迁会报错：
>
> `Virtual machine migration operation failed at migration Source. Failed to establish a connection with host XXX: No credentials are available in the security package 0x8009030E.`

**为什么这么别扭**：CredSSP 的设计是"凭证只能在当前登录会话里转发"。人登在 A 机上，凭证就在 A 机；要操作 B 机，凭证不在 B 机上。所以**"从哪台机发起"和"登录在哪台机"必须一致**。

> **对照我们**：这解释了为什么**自动化迁移在 Windows 上必须用 Kerberos**——不能自动化就没有定时迁移、批量迁移。我们平台是服务端统一发起（后端进程直接调 virsh），天然没有这个问题，**这是架构上的优势**。

#### 2.4.2 Kerberos + 约束委派

**做法**：在 AD 里给源机配一条"授权记录"，明确写"A 机有权代表用户去访问 B 机的哪些服务"。

| | 内容 | 核实 |
|---|---|---|
| 优点 | 不需登录源机，可自动化；凭证不落地，更安全 | ✅ |
| 缺点 | 配置复杂，要域管理员动手；**且要逐对配置**——A→B、B→A 是两个方向，得配两遍 | ✅ |

集群大了，配置量是 N×(N-1)。官方说明配委派时在"可委派的服务"里要选两项：

| 服务 | 什么时候勾 |
|---|---|
| **Microsoft Virtual System Migration Service** | 迁虚拟机本身（必选） |
| **cifs** | 要把存储一起迁，或只迁存储时 |

> **对照我们**：这套复杂度正是"Windows 迁移在中小环境里少用"的原因。我们不需要 AD，**但 SSH known_hosts 管理有同构的问题**——每对节点之间都要有信任关系，节点数增长时维护成本同样是 N²。这条在 §3.3 讨论"信任引导"时应提一句。

#### 2.4.3 一个真实的"升级把迁移搞坏"的坑（务必记下）

官方明确写明：

> 从 **Windows Server 2025** 起，所有加入域的服务器**默认开启 Credential Guard**。开启后 **CredSSP 方式的实时迁移直接不可用**，必须改用 Kerberos 约束委派。

**重要性在于**：坏掉的不是迁移协议、不是虚拟机，而是**迁移所用的认证机制**。升级前一切正常，升级后立刻报 0x8009030E。

> **这正是我们 Q2 最该警惕的场景。**
>
> Q2 实验若只比"QEMU 8.0 vs 8.1 能不能迁"，会漏掉一整类问题。版本矩阵必须**分两层查**：
>
> 1. **迁移协议层**：QEMU 版本、machine type（大纲 RQ-1-05 已有）
> 2. **迁移的承载链路层**：SSH 版本、加密算法策略、主机密钥体系、libvirt RPC 版本
>
> 第 2 层在我们这里的典型表现：OpenSSH 升级后默认禁用某些算法（如 ssh-rsa），导致 `qemu+ssh` 突然连不上——**报错指向"认证失败"，极易被误判成"密码错了"**。
>
> 建议：作为独立实验项挂进 E-02，或在运维规范章写成"升级前检查清单"。

### 2.5 性能选项（三选一，默认压缩）

| 选项 | 做法 | 什么时候用 | 核实 |
|---|---|---|---|
| **TCP/IP** | 内存原样复制，不压缩 | 带宽充裕、CPU 紧张 | ✅ |
| **Compression**（**默认**） | 先在源机压缩内存，再传 | 网络是瓶颈的通用场景，省带宽 | ✅ |
| **SMB** | 走 SMB 3.0；网卡支持 RDMA 时自动用 **SMB Direct**；配好 SMB Multichannel 时自动多连接并发 | 有 SMB 基础设施时 | ✅ |

**为什么默认是压缩**：迁移传的是虚拟机内存，而内存里**大量是零页和重复数据**（刚启动的虚拟机尤其明显），压缩率通常很高。省带宽的收益一般大于压缩消耗的 CPU。

**SMB 那个选项不是"换传输协议"**，而是换成了"走文件共享那条路"——好处是能复用 SMB 已有能力：RDMA（绕过 CPU 直接内存对内存，极快）、Multichannel（多条网线并行）。

> **对我们：这是一个真实的空缺。**
>
> 我们平台用 `virsh migrate`，**没有任何压缩选项**。QEMU 其实有压缩能力（`migrate-set-parameters` 里的 `compress-level`、`compress-threads` 等），但 `execute.go` 里没有设置。这意味着：
>
> - 本地盘 + 非共享存储场景下，磁盘复制往往是瓶颈（见 RQ-1-09 时间模型 `T ≈ max(T_ram, T_disk)`）；
> - 大段空白/零数据（密码机镜像通常如此）压缩后能省下可观带宽和时间；
> - 但**没有任何数据说压缩值不值**——CPU 压缩开销与带宽节省的平衡点必须实测。
>
> **建议**：作为低成本功能改进项（加个"启用压缩"开关），但必须先测。挂进 E-03/E-04 作对照组：同镜像、同网络，开/关压缩各跑一次，比较总耗时与源端 CPU 占用。

### 2.6 并发数

✅ 默认**同时进行 2 个实时迁移**，可在 Hyper-V 设置中改。

**为什么要有这个限制**：一个迁移就能打满一条网线。两个同时跑，第二个速度腰斩；十个同时跑，全部超时失败。所以**"并发数"本质上是带宽预算的表达方式**。

> **对照我们**：现在是单任务队列（`taskqueue`），天然并发为 1，不会出现这个问题。但反过来——**如果将来要做批量迁移（已列范围外），第一件要设计的就是这个限制，而不是先做并发。**

### 2.7 网络：官方明示迁移流量不加密

这一节是全文对安全章影响最大的一节，单独展开。

#### 2.7.1 先说清楚：一次迁移会用到**几条**网络通路

很多人把"迁移网络"当成一条线，实际是**多条，且安全属性各不相同**。Hyper-V 的迁移至少涉及：

| 通路 | 走什么 | 作用 |
|---|---|---|
| **控制/管理通路** | WMI/CIM 调用、迁移指令、配置协商 | 指挥"迁哪台、往哪迁" |
| **认证通路** | Kerberos 票据 或 CredSSP 凭证转发 | 证明"我有权发起" |
| **内存迁移数据通路** | 虚拟机内存全量字节 | 真正搬数据 |
| **磁盘数据通路**（`-IncludeStorage` 时） | 虚拟硬盘文件内容 | 连带搬盘 |
| **SMB 通路**（选了 SMB 性能选项时） | 内存数据走 SMB 3.0 | 借 SMB 的 RDMA/多通道 |

**关键点：加密与否要逐条看，不能笼统说"迁移加密了没有"。**

#### 2.7.2 数据通路上跑的到底是什么

| 内容 | 敏感程度 | 说明 |
|---|---|---|
| **虚拟机内存全量数据** | **极高** | 数据库缓存、会话状态、**密钥材料、密码运算中间态** |
| **CPU 状态、MSR、寄存器** | 高 | 能还原出部分运算过程 |
| **设备状态、virtio 队列** | 中 | 队列里有正在传输的业务数据 |
| **磁盘内容**（非共享存储时） | **极高** | 整个系统盘，含配置文件、密钥文件 |

> **对我们平台尤其直接**：VSM 的内存里有密码运算中间态和密钥材料。内存被完整抓走，等于把**密码机的运行态**送出去——这比抓一次业务流量严重得多，因为它是可复用的状态快照。

#### 2.7.3 官方结论与它的解法

✅ 官方原文意思：**live migration traffic isn't encrypted when sent over the network**。

✅ 官方给出的对策**不是加密，而是隔离**：安全最佳实践是把迁移流量隔离到**可信的私有网络**（物理隔离的独立网线，或独立 VLAN 等）。

用一句话概括微软的思路：

> **不在数据上加锁，改在"路上设卡"**——这条路只有我的两台服务器走，别人根本进不来，那就不用锁。

> **比方**：搬家搬钢琴，**没装箱子**（不加密），但**走的是自家后院的小路**（隔离网络），外面的人看不见。如果后院小路和公共马路是通的，钢琴就真的裸露在街上了。

#### 2.7.4 为什么微软选择不加密（这个取舍值得理解）

不是说微软做不到加密，而是**权衡后不默认做**：

| 因素 | 加密的代价 |
|---|---|
| **CPU 开销** | 迁移是持续数分钟的大流量传输，加解密要吃 CPU |
| **吞吐** | 迁移本来就受网络带宽限制，加密会进一步压低有效带宽 |
| **部署复杂度** | 要管证书、要发证、要轮换，中小企业吃不消 |
| **收益可替代** | 如果网络本来就物理隔离，加密几乎没有额外收益 |

**这个取舍逻辑本身对我们有参考价值**：我们做整改方案时，不能只写"必须上 TLS"，还要回答"上 TLS 之后迁移慢多少"。这正好是 §2.5 压缩选项要实测的同一类问题，可以合并进 E-03 的实验设计。

#### 2.7.5 最重要的一点：认证 ≠ 加密

Hyper-V 的身份认证做得非常完整：

- AD 域控做身份背书
- Kerberos 票据 + 约束委派限定权限
- 甚至凭证都不落地（Kerberos 路线）

**但它完全没有解决"路上有没有人偷看"这个问题。**

| 控制项 | 解决什么 | Hyper-V |
|---|---|---|
| **身份鉴别** | "你是不是你说的那个人"（防冒充） | ✅ 做得完整 |
| **传输机密性** | "路上有没有人偷看"（防窃听） | ❌ 明文 |

**这是两个独立的控制项，做了前者不等于做了后者。**

> **对大纲的直接指导**：§3.3 安全章必须把这两条分开写，不能合并成一个"迁移安全"：
> - **RQ-3-04（身份鉴别）**
> - **RQ-3-01（传输机密性）**
>
> 分开写的好处是：即使身份鉴别做得好，机密性那条依然可以如实判"不符合"——这正是我们平台的实际情况。

#### 2.7.6 对照我们平台：三条通路的加密状态

我们平台的结构（依据 `execute.go:122,128`）：

| 通路 | 我们用什么 | 加密状态 |
|---|---|---|
| **控制面** | `qemu+ssh://root@host` — libvirt RPC 走 SSH | ✅ **加密** |
| **内存迁移数据面** | `--migrateuri tcp://host` — QEMU 直连 | ❌ **明文** |
| **磁盘数据面** | `--disks-uri tcp://host` — NBD 直连 | ❌ **明文** |

**和微软对比的结论**：

| | 身份认证 | 控制面加密 | 数据面加密 | 网络隔离要求 |
|---|---|---|---|---|
| Hyper-V | ✅ 完整 | ✅ | ❌ 明文 | ✅ **官方明确要求** |
| 我们平台 | ⚠️ SSH 密钥 | ✅ SSH | ❌ 明文 | ❓ **未见文档化要求** |

**所以我们如果没做网络隔离，就比微软更差**——因为微软虽然也明文，但它至少把"必须隔离"写成了明文要求；我们连这个要求都还没写进部署规范。

#### 2.7.7 立即能做的过渡措施（不需要任何改造）

在 TLS 改造完成之前，有一个**成本极低、当天可做**的缓解措施：

**核查迁移端口是否真的只在管理网/专用网里，没有暴露在业务网。**

具体要查的：

1. **端口范围**：QEMU 迁移流的端口。⚠️ 段值需实测确认（OpenStack 官方文档写的是 **49152–49215**，可作参考，但那是 OpenStack 的部署约定，不等于 libvirt 强制规定）；
2. **监听地址**：`--migrateuri tcp://host` 里的 host 解析到什么地址？是管理网 IP 还是 0.0.0.0（监听所有网卡）？**这一条最容易被忽略**——如果 QEMU 监听在 0.0.0.0，那业务网也能连上；
3. **防火墙规则**：节点间是否只对管理网段放通该端口，业务网段是否拒绝。

核查命令：
```bash
# 迁移中，源端看实际连接落到哪个网卡/IP
ss -tnp | grep qemu
# 看监听地址（是否 0.0.0.0）
ss -ltnp | grep qemu
# 防火墙规则核查
iptables -L INPUT -n -v | grep -E '4915|4916'
```

> **为什么这条值得单独列出来**：TLS 改造需要排期、需要证书体系，可能几个月。而"确认端口没暴露在业务网"是**一小时能查完的事**。在密码业务场景下，这段窗口期里不能什么都不做。
>
> 这也符合安全整改的常规做法：**先做低成本缓解，再做根治方案**，两件事并行不冲突。

#### 2.7.8 本节结论

1. **"迁移加密"不是一个开关，要按通路逐条判断**——控制面加密不等于数据面加密，我们正是这种情况；
2. **认证完整不代表数据安全**——Hyper-V 是最好的反例；
3. **官方明示不加密是本行业常态，但不是我们的免责理由**——密码业务的合规要求高于通用虚拟化；
4. **过渡措施优先级高于根治方案**——先确认端口没暴露，再排 TLS 改造；
5. **整改方案必须带性能数据**——"上 TLS 慢多少"必须实测，否则评审会问穿（并入 E-03 实验设计）。

⚠️ **待核实**：Hyper-V 迁移的具体端口号与监听行为，本次未抓到官方明确说明。若要在报告中引用，需自行到 `learn.microsoft.com` 的 live migration 网络章节核对。

## 3. 执行迁移：两种操作入口

### 3.1 图形界面（Move Wizard）

✅ 步骤：
1. Hyper-V Manager → 左侧选主机 → 中间"虚拟机"面板 → **右键虚拟机 → 选择 Move** → 打开 **Move Wizard**
2. 向导页依次选择：**迁移类型**（只移 VM / 移 VM 及存储）、**目标服务器**、**选项**
3. 最后 **Summary 页确认 → Finish**

> **对照我们的界面设计**：微软的向导是**线性分页**（一页一决策），我们的是**单弹窗多区块 + 两个按钮**（推荐 + 预检）。两种范式各有道理：
> - 向导式适合"步骤固定、每步只有一个决策"的场景；
> - 单弹窗式适合"信息要互相对照"的场景（选节点后看存储池余量、看预检结果、回头改节点）。
>
> 我们的场景需要反复对照（换节点 → 池变 → 预检失效 → 重来），**单弹窗是对的**，不该改成向导。这个判断可以写进设计说明，回应"为什么不学 Hyper-V 做向导"。

### 3.2 命令行（Move-VM）

✅ 官方示例（移 VM 且移存储，全部文件落到 `D:\LMTest`）：
```powershell
Move-VM LMTest TestServer02 -IncludeStorage -DestinationStoragePath D:\LMTest
```

✅ 常用参数（已核实定义），按"我们能对应上"的顺序：

| 参数 | 作用 | 我们的对应 |
|---|---|---|
| `-DestinationHost` | 目标主机 | 界面 c3 目标节点 / `--migrateuri` |
| `-IncludeStorage` | **VM 与存储一起移**（等价于非共享存储整盘复制） | 我们恒开（`--copy-storage-inc`） |
| `-DestinationStoragePath` | 所有 VM 数据统一落到一个目录 | 界面 c6 目标存储池（粗粒度单池） |
| `-VirtualMachinePath` / `-SnapshotFilePath` / `-SmartPagingFilePath` | 配置文件 / 检查点 / 智能分页文件**分别**指定路径 | **我们没有**（粒度更粗） |
| `-Vhds` | 哈希表数组，逐个磁盘指定 `SourceFilePath` → `DestinationFilePath` | **我们没有**（按池自动落位） |
| `-RetainVhdCopiesOnSource` | 迁完后**在源端保留**父 VHD | **我们没有这个概念** |
| `-RemoveSourceUnmanagedVhds` | 迁完后**删除**源端父 VHD（差分盘场景） | **我们没有这个概念** |
| `-ResourcePoolName` | 目标端处理器资源池 | 无对应 |
| `-AsJob` | 后台作业方式运行 | 我们的任务队列 |
| `-Passthru` | 成功返回 VM 对象；**因不兼容而失败时返回 CompatibilityReport 对象** | 无对应 |

#### 差距一：存储路径的粒度

Hyper-V 支持三档：

1. **全部一个目录**（`-DestinationStoragePath`）
2. **分类指定**（配置一处、快照一处、分页文件一处）
3. **逐盘指定**（`-Vhds`，每个虚拟硬盘单独定路径）

我们只有一档：**选一个池，所有文件按规则落进去**。

**密码平台可能需要的场景**：密码机镜像里可能有"系统盘"和"密钥/日志盘"，业务上希望分开放（敏感数据盘放加密盘或独立盘）。我们目前做不到。

⚠️ **但这是远期改进项，且必须先确认业务上是否真有这个需求**——不要凭想象加功能（对应需求确认表的"范围外"原则）。

#### 差距二：源端副本的处置（更要紧）

`-RetainVhdCopiesOnSource` 和 `-RemoveSourceUnmanagedVhds` 是**两个显式参数**，意思是"迁移完成后，源端那份磁盘文件留不留，由你明确决定"。

**这不是一个可选功能，而是把一件危险的事显式化了。** 微软的做法说明："源端留不留数据"是需要管理员明确决定的，不能由系统悄悄决定。

**我们完全没有这个概念。** 需要问清楚的问题：

1. 迁移成功之后，源节点上的磁盘文件到底删了没有？
2. 如果删了，是 `execute.go` 哪一行删的？
3. 如果是 `virsh migrate` 自动删的，怎么证明它删干净了（而不是留了个空文件/目录）？

> 这直接对应大纲安全章 **RQ-3-06：迁移完成后源端磁盘副本须按数据销毁要求处置（复制不等于搬移）**。
>
> 在密码业务场景下，"源端是不是还留着一份完整的 VSM 磁盘镜像"是个**必须能回答的问题**——留着就是密钥材料的第二份拷贝，属于数据残留。**这是全篇对我们最要紧的一条。**
>
> 建议：列为 §3.3 安全章必查项，判定方式用 E-05 顺带验证——迁移成功后到源节点 `ls` 磁盘目录，看文件是否真的没了。

#### 附：一个隐形的"执行前一步"

严格说这不算"执行迁移"，但微软流程里**它排在前面**：

```powershell
$report = Compare-VM -Name TestVM -DestinationHost TestDestinationHost
```

先出兼容性报告，逐条看 `$report.Incompatibilities`，修完了再 `Move-VM`。详见 §4。

## 4. 兼容性预检：Compare-VM（最值得抄的一块）

### 4.1 它是什么

✅ 官方定义："Compares a virtual machine and a virtual machine host for compatibility, returning a **compatibility report**."

✅ 用途原文："useful when trying to import or migrate a virtual machine that is **incompatible** with the target server."

### 4.2 典型用法（官方示例）

```powershell
# 1. 先比对，拿到报告对象
$report = Compare-VM -Path 'D:\vm1\...\53EAE599-....XML'

# 2. 逐条看不兼容项
$report.Incompatibilities | Format-Table -AutoSize
# Message                                    MessageId  Source
# -------                                    ---------  ------
# Could not find Ethernet switch 'Production'.   33012  ...VMNetworkAdapter

# 3. 就地修复（示例：把它报告的 Source 对象拿来断开网卡）
$report.Incompatibilities[0].Source | Disconnect-VMNetworkAdapter

# 4. 拿修好的报告重新比对
Compare-VM -CompatibilityReport $report

# 5. 报告干净后，直接用它执行
Move-VM -CompatibilityReport $report
```

### 4.3 为什么这块对我们价值最高

**报告的每一条不兼容项都自带"责任对象"（Source），可以直接对该对象施加修复动作。**

对比我们现有的预检设计：预检报告输出的是**一行行文字**（"目标节点不存在同名交换机 sw-caiwu"），用户看完还得自己回到别处去建交换机。Hyper-V 的做法是报告项 → 对象 → 动作 三者打通。

⚠️ 注意：这要求"不兼容项"能被建模成对象，Hyper-V 因为所有资源都在同一个系统里（网卡、交换机、路径都是 Hyper-V 自己的对象）才能做到。我们的交换机、安全组、存储池在别的模块里，做"一键修复"成本高得多。**所以可借鉴的不是"一键修复"，而是这条原则**：

> **预检的每一条不通过项，都应该能让用户从报告里直接跳转到修复它的那个界面的正确位置。**

这个降级版我们做得到（跳转 + 预置筛选），成本低，体验提升明显。建议写进界面设计 B3 预检报告区的改进项：红色阻断项后加一个【去处理】链接。

### 4.4 与 CPU 兼容性直接相关的官方报错

✅ 触发条件（官方原文大意）：**虚拟机未开启处理器兼容性，且存在一个或多个快照**，两端处理器版本不同时，迁移失败，报：

> "The virtual machine cannot be moved to the destination computer. **The hardware on the destination computer is not compatible with the hardware requirements of this virtual machine.**"

✅ 修复方式：关机 → Hyper-V Manager → 设置 → **Processors → Compatibility** → 勾选 **"Migrate to a computer with a different processor version"**，或：
```powershell
Set-VMProcessor TestVM -CompatibilityForMigrationEnabled $true
```

> **这是 CPU 兼容性问题的第三种解法，值得单独记一笔**：
>
> | 解法 | 做法 | 代价 | 谁在用 |
> |---|---|---|---|
> | 提升基线 | 集群统一 custom CPU 模型 / EVC 基线 | 全集群都损失新特性 | vSphere EVC、libvirt custom |
> | 要求同型号 | host-passthrough + 只迁同型号 | 集群异构即失效 | **我们平台现状** |
> | **逐 VM 降级** | 对这个 VM 开"兼容模式"，牺牲它的新特性换可迁移 | 该 VM 性能损失 | **Hyper-V** |
>
> 我们目前只有第二种（而且连"同型号"这个条件都没在预检里校验）。**第三种是成本最低的补充**——不必改造整个集群，只要给"需要跨型号迁移的那几个 VSM"打上标记，迁移前自动降 CPU 特性。但这需要 QEMU/libvirt 层的对应能力（`<cpu mode='custom' check='partial'>` + 特性裁剪），且必须在 VM 关机时才能改，落地成本要实验验证（可挂到 E-01）。

## 6. 该抄的三件事 / 不抄的两件事

### 该抄

1. **预检报告项 → 可跳转修复**（§4.3 的降级版）。给每条红色阻断项配【去处理】链接，跳到对应模块并预置筛选。成本低，直接改善"预检说不行但用户不知道去哪改"的困境。
2. **逐 VM 的 CPU 兼容模式**（§4.4 第三种解法）。不必改造全集群基线，只对需要跨型号迁移的 VSM 打标记。**这是解决我们"默认 host-passthrough + 异构集群"死结成本最低的一条路**，值得排在 E-01 实验里验证。
3. **源端副本处置显式化**（§3.2 的 `RetainVhdCopiesOnSource`）。对应安全章 RQ-3-06，我们目前完全没有这个概念——迁移完源端磁盘副本怎么处置，代码里没有选项，文档里没有说明。

### 不抄

1. **线性向导式的迁移界面**（§3.1）。我们的场景需要反复对照（换节点→池变→预检失效），单弹窗多区块更合适。这条要在设计说明里写清楚，否则评审会问"为什么不学 Hyper-V"。
2. **AD 域 + 约束委派那套认证体系**（§2.4）。我们是 Linux/SSH 环境，强行引入 AD 委派是给自己找麻烦；但要知道它的存在——我们"SSH 主机密钥首次确认"的困境，在 Windows 世界对应的是"约束委派配置"，**两边都是"信任引导"问题**。

把前文散落的建议收成一张表，按"距离可执行还有多远"排序。

| 项 | 我们现状 | 建议动作 | 优先级 | 依赖 |
|---|---|---|---|---|
| **源端副本处置**（§3.2 差距二） | 无定义 | ① 代码确认迁移后源盘是否删除、在哪删；② 列为 §3.3 安全章必查项；③ E-05 顺带 `ls` 验证 | **P0** | 无（现在就能查代码） |
| **认证链路随版本断裂**（§2.4.3） | 未考虑 | Q2 版本矩阵增加"承载链路层"检查（SSH 版本/算法策略/主机密钥/libvirt RPC）；运维章写"升级前检查清单" | **P0** | 无（可先出检查清单） |
| **迁移端口网络暴露核查**（§2.7.7） | 未见文档化要求 | ① 查 `ss -ltnp` 是否监听 0.0.0.0；② 查防火墙是否只对管理网段放通；③ 结论写进部署规范 | **P0** | 无（一小时能查完） |
| **迁移加密整改（TLS）**（§2.7） | 数据面明文 | 按 Nova 记录的方案上原生 TLS；**同时实测"上 TLS 后慢多少"** | **P1** | 证书体系；性能数据并入 E-03 |
| **VSM 兼容性版本标记**（§2.3） | 无 | 借鉴 Hyper-V 的"虚拟机版本号"，给 VSM 打显式递增版本，迁移预检只比版本号 | P1 | 需先定集群基线 |
| **预检阻断项可跳转修复**（§4.3） | 报告只有文字 | B3 预检报告每条红色阻断项后加【去处理】链接 | P1 | 界面设计文档更新 |
| **逐 VM CPU 兼容模式**（§4.4） | 无 | E-01 实验中验证 QEMU 层实现成本 | P1 | 实验环境 E-01 |
| **迁移压缩**（§2.5） | 无开关 | E-03/E-04 加对照组实测收益，再决定是否加开关 | P2 | 实验环境 |
| **存储路径分档**（§3.2 差距一） | 仅单池 | 先确认业务是否真需"系统盘/密钥盘分开"，再决定 | P3 | 业务确认 |
| **HA / 宕机自动接管**（§1.5） | 无 | **明确写进范围外**，避免"做了热迁移就有高可用"的误解 | — | 无 |

**三个 P0 都是"不需要实验环境、现在就能查"的类型**：

- **源端副本残留**（安全上最要紧，密码业务不能留第二份密钥拷贝）
- **认证链路断裂风险**（可先出检查清单，不必等 Q2）
- **端口网络暴露**（一小时能查完，TLS 改造前的过渡缓解）

建议下一步顺序：**先查端口暴露和源端副本这两件当天的活**，再排 TLS 改造的工期。
