**关键认知**：libvirt 只下命令、QEMU 干活。数据通道建立后，libvirt 一次字节都不碰，只做"介绍人 + 监督者 + 事务裁决者"。

## 2. 控制通道 vs 数据通道：连接时序

### 2.1 控制通道建立

```
宿主机 A                                    宿主机 B
virsh（本地 unix socket）→ libvirtd-A
   libvirtd-A 解析 URI: scheme=ssh, port=55555
   fork: ssh -p 55555 root@10.19.207.10 nc -U /var/run/libvirt/libvirt-sock
        ═══ SSH 加密隧道 ═══▶ sshd-B → nc → libvirtd-B
```

- virsh 只跟本机 libvirtd 说话（本地 socket，不走网络）；
- SSH 是 libvirtd 自己 fork 的子进程，本质是"加密网线"；
- 隧道上跑 libvirt 自有 RPC 协议（XDR 序列化），六阶段所有协调消息都走它；
- **实验对应**：问题 4（端口 55555）、问题 5（指纹确认）、问题 6（B→A 免密缺失）全部卡在这一步。

### 2.2 数据通道拉起

1. Begin（源端本地）：生成迁移 XML + cookie₁；
2. Prepare（经控制通道）：目标端起 **-incoming 空壳 QEMU** + NBD 接收端，回传数据通道地址 + cookie₂；
3. Perform：源端经**本地 QMP** 对 QEMU-A 下发 `migrate tcp://<B>:<port>`——**数据通道是 QEMU-A 直连 QEMU-B，libvirt 完全不在数据路径上**。

### 2.3 三个推论

1. **控制面 ≠ 数据面**：`qemu+ssh://` 只保证 libvirtd 间 SSH 加密；QEMU 直连走什么由 Perform 下发的 URI/参数决定；
2. **tunnelled 模式是唯一例外**（`--tunnelled`）：数据流复用 SSH 控制连接。判据：`ss -tnp` 看 QEMU 间是否有独立 TCP 连接（native）或 QEMU 只连本机 libvirtd（tunnelled）；
3. **"介绍人"模型**：libvirt 负责 (a) 两端各铺 QEMU、(b) 递接收地址、(c) 监督回滚，数据一字节不碰。

## 3. 五阶段逐段解析

> 全部行号对准本地 qemu_migration.c。

### 3.0 总入口与模式判定

```
qemuMigrationSrcPerform (:6526)
 ├─ p2p     → SrcPerformJob (:6311)      ← virsh --p2p / qemu+ssh 走这里
 └─ direct  → SrcPerformPhase (:6448)
```

### 3.1 阶段 ① Begin —— 源端打包"迁移档案"（本地）

```
SrcPerformPeer2Peer3 (:5744)        ← v3 协议总编排
  └─ SrcBeginPhase (:2793)
       ├─ SrcIsAllowed (:1538)      ← 合法性：直通设备、锁
       ├─ SrcIsSafe (:1851)         ← 存储安全：可写共享盘、镜像状态
       ├─ BeginPhaseValidateDiskTargetList (:2768)
       └─ BeginXML (:2712)           ← 生成迁移 XML + cookie₁
```

**产物**：迁移 XML（VIR_DOMAIN_XML_MIGRATABLE 格式）+ cookie 第一段。Perform 入口处会再复查一遍安全检查（:6360-6364，双重保险）。

### 3.2 阶段 ② Prepare —— 目标端铺"空壳接收端"（经控制通道）

源端把 XML+cookie₁ 发给目标端（:5893-5925 `dconn->driver->domainMigratePrepare3Params`；tunnelled 走 PrepareTunnel3Params），目标端执行：

```
DstPrepareAny (:3773)               ← Prepare 总入口
 ├─ DstPrepareResume (:3674)        ← 恢复中断迁移分支
 └─ DstPrepareFresh (:3500)
      └─ DstPrepareActive (:3313)
           ├─ DstPrepareStorage (:444)
           │    └─ DstPrecreateDisk (:306)      ← 按需预创建目标盘
           ├─ DstPrepare (:3168)                 ← 组装 -incoming 参数
           ├─ DstPrepareDiskSeclabels (:580)     ← 磁盘 SELinux 标签
           ├─ DstPrepareAnyBlockDirtyBitmaps (:3248)
           ├─ DstStartNBDServer (:635)           ← 非共享存储：起 NBD 接收
           └─ DstRun (:2478)                     ← 启动空壳 QEMU（-incoming 监听）
```

**关键点**：空壳 QEMU 不执行任何 guest 代码，纯监听等数据（:2520 注释明确写着 Wait 在 Finish 阶段调用）。完成后回传 **uri_out（数据通道地址）+ cookie₂**（:5939 `uri = uri_out`）。

### 3.3 阶段 ③ Perform —— 数据面真正开动

```
SrcPerformNative (:5391)             ← native（tcp/tls 直连）
SrcPerformTunnel (:5494)             ← tunnelled（复用控制连接）
  └─ 共同汇入 SrcRun (:4965)          ← 数据迁移执行体
       ├─ CookieParse (:5047)
       ├─ SrcGraphicsRelocate (:5056) ← VNC/SPICE 会话重定向
       ├─ ParamsCheck (:5063)
       ├─ 磁盘（非共享存储，:5131）:
       │    SrcNBDStorageCopy (:1289)
       │      ├─ ...Blockdev (:1162) → QMP blockdev-mirror（写自动双落盘）
       │      └─ ...Ready (:806)     ← 轮询所有盘 mirror 就绪
       ├─ SrcStart (:4814)            ← 下发 QMP "migrate"（数据通道建立）
       │    └─ SrcConnect (:4569)
       ├─ SrcWaitForCompletion (:2252) ← 轮询 query-migrate 等收敛
       │    （pre-switchover 暂停点 → SrcContinue (:4629) 放行，:5228）
       └─ 完成后: SrcNBDCopyCancel (:992) ← 取消 mirror 即 pivot
```

**源码注释（:5954-5957）**：

> "Perform the migration. The driver isn't supposed to return until the migration is complete. **The src VM should remain running, but in paused state until the destination can confirm migration completion.**"

即：Perform 返回时源 VM 只是暂停、没有销毁，一切等 Confirm。

**QEMU 内部并行发生的事**（libvirt 只监控）：内存 pre-copy 迭代收敛（脏页逐轮重传）、磁盘 blockdev-mirror 全量+写双落盘，两流并行；stop-and-copy 由 QEMU 收敛判定触发，最终脏页 + vCPU 寄存器 + KVM/设备状态一次性原子传输。

### 3.4 阶段 ④ Finish —— 目标端加载、校验、恢复

```
DstFinish (:7087)
 ├─ DstFinishOffline (:6810)         ← 离线迁移分支
 └─ DstFinishActive (:6978)
      ├─ DstWaitForCompletion (:2297) ← 等目标 QEMU 数据收齐
      └─ DstFinishFresh (:6849)
           ├─ DstVPAssociatePortProfiles (:6617) ← 关联网卡端口
           ├─ DstOPDRelocate (:2411)
           ├─ DstStopNBDServer (:758)
           └─ DstPersist (:6669)      ← --persistent 写持久配置
      └─ DstComplete (:6747)          ← 发 RESUME，目标 VM 跑起来
```

目标端真正"活过来"的动作在 DstComplete，但只有源端随后 Confirm 成功才被最终承认。**host-passthrough 失败案例死在这里**：状态加载校验失败 → DstErrorReport (:7539) → 失败码传给源端。

### 3.5 阶段 ⑤ Confirm —— 源端"生死判决"

```
SrcConfirmPhase (:4169)
 ├─ CookieParse（只取 STATS 字段，:4214）
 ├─ 用目标端 timeDelta 修正统计（:4226-4234）
 ├─ retcode == 0（成功）:
 │    SrcComplete (:4122)      ← 杀源 VM，发 SHUTOFF_MIGRATED
 └─ retcode != 0（失败，:4244-4258）:
      ├─ SrcNBDCopyCancel      ← 取消残留磁盘镜像
      └─ SrcRestoreDomainState (:253) ← ★ 源 VM 恢复运行（事务回滚）
```

**源码注释（:4239-4241）**：

> "Did the migration go as planned? **If yes, kill off the domain object. If something failed, resume CPUs**"

## 4. p2p vs direct 模式差异

| 对比项 | p2p（点对点） | direct（直接） |
|---|---|---|
| 主动协调者 | **源端 libvirtd-A**（经 SSH 代理协调 B） | **客户端 virsh**（分别连两端 libvirtd） |
| 源码入口 | `SrcPerformPeer2Peer3 (:5744)` | `SrcPerformPhase (:6448)` |
| virsh 连接 | 只连本机 libvirtd-A | 同时连 A、B 两个 libvirtd |
| 控制线 | virsh→A、A⇄B | virsh→A、virsh→B（两条） |
| 本环境 | ✅ `virsh migrate 'qemu+ssh://…'` 实际即此模式 | — |

**共同点**：无论哪种模式，数据面都是 QEMU-A 直连 QEMU-B，libvirt 不在数据路径上。模式差异只影响控制面的连线归属。

# 第二篇 关键机制

## 5. Cookie 机制：阶段间的"随行行李"

**问题背景**：v3 六阶段是独立 RPC 调用，分处两个进程两台机器，无共享内存——RPC 参数装不下的协调状态需要带外传递。Cookie 就是一段随阶段间消息传递的结构化数据（`qemu_migration_cookie.c`，字段以 `QEMU_MIGRATION_COOKIE_*` 标志区分）。

| 字段 | 内容 | 保证什么 | 实验对应 |
|---|---|---|---|
| LOCKSTATE | 分布式锁状态 | 锁正确交接，防双端同时持锁写盘 | 有状态锁管理器时**强制启用** |
| NBD | 磁盘迁移端口/export/盘列表 | 磁盘通道状态两端一致 | --copy-storage-all 协调 |
| GRAPHICS | VNC/SPICE 会话信息 | 图形会话重定位 | 迁移后 VNC 失效需重连（问题 8） |
| PERSISTENT | 持久化域定义 | 目标端配置延续 | --persistent 生效 |
| NETWORK | 带宽参数 | 带宽约束跨端一致 | — |
| STATS | 迁移统计 | 两端统计一致可审计 | domjobinfo 数据 |
| CAPS | 源端能力清单 | 目标端据此适配 | 跨版本容错 |
| BLOCK_DIRTY_BITMAPS | 块脏位图（磁盘增量，与内存脏页两回事） | 备份链不断 | — |
| CPU 热插拔状态 | vCPU 拓扑 | 恢复后热插拔正确 | — |

**保证的三类性质**：

1. **事务完整性**——各阶段看到同一份协调状态，六阶段才能作为原子事务执行+回滚；
2. **对外状态连续性**——图形会话、持久配置、锁一并交接；
3. **可审计**——STATS 两端一致。

**与安全的分工**：现代版本的防劫持由通道层认证（SSH 指纹/密钥、TLS 证书）承担，cookie 角色收敛为状态传递——**安全靠通道认证，协调靠 cookie**。

## 6. 稀疏数据处理：20G 磁盘只用 10G 怎么迁

### 6.1 三个"大小"要分清

| 概念 | 值 | 说明 |
|---|---|---|
| 虚拟容量 | 20G | Guest 看到的磁盘大小 |
| 实际占用 | ~10G | qcow2 稀疏文件实占（allocation bitmap 记录有效 cluster） |
| Guest 已写入 | ≤10G | 文件系统层面有效内容 |

### 6.2 处理方式

- **磁盘**：blockdev-mirror 遍历 qcow2 的 allocation map，**只对已分配 cluster 发起读 I/O**——未分配区域不产生读取和传输。传输量 ∝ 实际使用量而非虚拟容量；目标端同样按需分配，不会膨胀成 20G 实占。
  注意：Guest 里删掉的文件仍算已分配（qcow2 层不知道文件系统空闲），迁移量 ≈ 历史写入总量。
- **内存**：zero-page detection——全零页只发特殊标记不逐字节传，目标端本地补零；这是内建优化，不需要 `--compressed`。

### 6.3 实验意义

迁移耗时按 ~10G 量级估算；可选验证 = 迁移前后 `qemu-img info` 对比 virtual size（20G）与 actual size（~10G），目标盘 actual size 接近源盘即"只迁移已分配块"的直接证据。

## 7. 三大保证的源码落点

> 与主文档 5.9 节呼应。

| 维度 | 保证点 | 源码证据 | 实验证据 |
|---|---|---|---|
| **一致性** | v3 事务+失败回滚 | `SrcConfirm(:4273)` 失败即 `SrcRestoreDomainState(:253)` | 首迁失败后源端继续运行 |
| | 原子切换 | `SrcWaitForCompletion(:2252)` 等 switchover | counter.log 序号连续 |
| | 防脑裂 | Finish 成功后才停源端 | A shut off + B running |
| | 状态语义可恢复 | 目标端加载 KVM 状态校验 | host-passthrough 失败 → 固定 Model 成功 |
| **完整性** | 磁盘镜像语义 | `blockdev-mirror` 写自动双落盘 | 迁移期间 counter.log 写入完整保留 |
| | 传输校验 | transport 层 AEAD/校验和 | — |
| | 端到端裁决 | 机制外独立验证 | SHA-256 前后一致 ✅ |
| **安全性** | 加密在通道层 | QEMU 序列化代码无加密逻辑（全文搜索不到） | — |
| | 控制面/数据面独立 | dispatch 层与 Perform 层两个选择点 | 讨论汇总修正结论 |
| | 认证 | SSH 指纹/密钥（问题 5 实证） | 迁移前须打通认证 |
| | 国密入口 | exec transport 管道接口 | 支撑国密路线 |

**一句话总结**：三个维度是同一分层架构的三个侧面——libvirt 事务协议保证"过程不出错"（**事务性**），QEMU 收敛与镜像算法保证"数据语义正确"（**算法性**），安全性完全外置于通道层（既是风险——不配置即明文，也是机遇——国密可透明替换）。

# 第三篇 场景与产业

## 8. 适用场景分析

> 对应会议议题 5。

### 8.1 判断框架：三个核心问题

热迁移的代价：源端 CPU/内存开销（<10%）、迁移网络带宽（≈实际数据量）、停机时间（数十毫秒~秒级）。换来的是**业务不中断 + 过程透明**。判断场景是否适用，问三件事：

1. 业务能否容忍几十~几百毫秒停顿 + 迁移期间 5%~10% 性能抖动？
2. VM 状态能否序列化？（直通设备、特殊时钟依赖会卡住）
3. 收益（调度自由、避免停机维护）是否大于代价？

### 8.2 典型适用场景 ✅

| 场景 | 说明 | 机制/实验支撑 |
|---|---|---|
| **计划内硬件维护** | 换内存、内核补丁、固件升级——VM 提前迁走，宿主机随便折腾，维护从"业务停机 N 小时"变"毫秒级切换" | 本环境使用方式：test2 迁走后 A 进入维护态 |
| **资源调度/负载均衡** | 热点主机过载时分散 VM；低峰合并 VM 空出整机省电（整合填谷） | `migrate-setspeed`/`--downtime` 支撑批量编排 |
| **节能/ECO 调度** | VM 集中后整机下电，数据中心 PUE 优化 | 大厂"柔性休眠"实践 |
| **灰度升级/软件栈换代** | QEMU/libvirt/内核大版本升级，VM 逐台迁到新集群 | 要求两端 QEMU 兼容、CPU Model 取交集（呼应问题 3） |
| **故障预防（预测性迁移）** | 内存 CE 错误增多、磁盘 SMART 预警时抢先迁移 | **依赖共享存储**（否则全量复制赶不上故障发展） |

### 8.3 有条件适用 ⚠️

| 场景 | 条件与权衡 |
|---|---|
| **非共享存储大盘迁移** | 磁盘实际占用百 GB~TB 时 blockdev-mirror 以小时计且占满网络。适合一次性搬迁，不适合频繁调度（本环境 ~10G 小盘可行；生产大盘调度靠共享存储只迁内存+状态，分钟级） |
| **高脏页率负载** | 内存大且写密集（内存数据库）时脏页率可能持续超过带宽永不收敛；auto-converge 节流伤性能，`--timeout-action` 兜底要么收敛要么安全放弃 |
| **时序敏感业务** | "时间黑洞"：TSC 补偿骗得过时钟读数骗不过真实世界（外部包迟到、定时任务延迟数百 ms）；普通 Web/DB 无感，高频交易/精密计时须放停机窗口 |
| **含直通设备的 VM** | GPU 直通（VFIO）、SR-IOV 网卡状态不可序列化，`SrcIsAllowed(:1538)` 直接拒绝；只能停机迁移，或设备虚拟化（virtio-gpu/mdev） |
| **跨 CPU 兼容边界** | Intel↔AMD、跨代际迁移 host-passthrough 必挂（已实证）；固定 Model 取交集可解但损失部分性能特性 |

### 8.4 不适用 ❌

| 场景 | 原因 | 替代方案 |
|---|---|---|
| **故障瞬间切换（硬宕机恢复）** | pre-copy 需要源端活着持续供数，主机已死无从迁移 | **HA**：共享存储+心跳，目标端重新拉起（分钟级 RTO，内存态丢失） |
| **异地容灾** | 广域 RTT 使脏页重传效率崩塌 | 存储层异步复制 + 容灾端热备 |
| **RPO=0 极致要求** | 热迁移本身有失败回退可能 | 存储双活/同步复制兜底 |
| **无状态可重建服务** | 重启成本本来就秒级，收益趋零 | 容器调度重启、CRIU |
| **强安全隔离场景** | 迁移=向目标宿主机交付全部内存+磁盘（信任边界） | 目的地准入审计、源端副本安全擦除 |

## 9. 与其他迁移灾备机制的对比

> 对应会议议题 6。9.1 立分类坐标系，9.2 逐项机制详解，9.3 完整对比表，9.4 核心结论。

### 9.1 分类坐标系：所有机制在解决同一个问题

所有"迁移/灾备"机制本质都在回答：**计算状态（CPU/内存）与数据状态（磁盘）从哪来、放到哪、什么时刻同步**。按此可画成二维分类：

```
                 状态同步时机
                 事前(持续)        事中(一次性)      事后(恢复时)
计算状态 ────►  FT容错/COLO      热迁移/冷迁移     HA/重启拉起
(CPU/内存)     (双机同步执行)    (源活着时搬运)    (不保留,重新引导)
                 │                │                │
数据状态 ────►  存储复制/双活     随迁移复制/共享   备份恢复
(磁盘)         (DRBD/存储镜像)    存储不搬运        (快照/CDP)
```

记住这张图，所有机制都是四个象限的组合：

- 热迁移 = 计算事中搬 + 数据不搬（共享存储）或事中搬（copy-storage）；
- HA = 计算事后重建 + 数据事前同步（共享存储/复制）；
- 备份 = 数据事后 + 计算不保留。

### 9.2 逐项机制详解

**（1）冷迁移（Shut down & Migrate）**
- 原理：正常关机 → 拷贝磁盘镜像 → 目标端导入启动。无状态同步难题（状态为零）；
- RPO=0（关机后无新写入）；RTO = 停机时长（分钟~小时）；
- 优点：无兼容性风险（不存在运行态恢复问题）、可跨任何 CPU/版本/直通设备——**一切热迁移失败的兜底方案**；
- KVM 生态：`virsh migrate --offline`（只搬定义），或手工 qemu-img 拷贝。

**（2）热迁移（本调研主题，作对比基准）**
- pre-copy：RPO=0，RTO≈停机窗口（毫秒~秒），要求源端活着；
- post-copy：RTO<100ms 但不可回退（源死后 VM 即亡）。

**（3）HA 高可用（High Availability）**
- 原理：共享存储放磁盘 + 心跳检测宿主机失联 + 仲裁防脑裂 + 目标节点重新拉起 VM；
- 关键点：**内存态不保留**——VM 重新走一遍引导，TCP 连接断、进程重新起（与热迁移的本质区别）；
- RPO=0（磁盘在共享存储上没动）；RTO 1~5 分钟（检测超时 + 仲裁 + 引导）；
- KVM 生态：oVirt/RHV HA、pacemaker+libvirt、OpenStack masakari（虚机疏散 evacuate）；
- 与热迁移配合：生产标配"热迁移做计划内 + HA 做计划外"。

**（4）FT 容错 / 主备双活（Fault Tolerance / COLO）**
- 原理：主备两台机器**同步执行**同一个 VM——主机的所有输入（网络包、磁盘写、时钟）同步复制到备机，备机执行相同指令流。主机死时备机无缝接管，**零停机、内存态完整保留**；
- KVM 现状：QEMU 内置 **COLO**（COarse-grained LOck-step，`migration/colo.c`），基于热迁移协议扩展——先正常热迁移建底，之后持续同步差异；Xen 有 Remus；
- 代价：网络时延直接加在每条指令路径上、单 vCPU 场景较成熟、带宽要求高；
- 与热迁移的关系：**COLO 的建立阶段就是一次热迁移**——"迁移协议作为灾备基座"的例证。

**（5）存储复制（DRBD / Ceph RBD mirroring / 商业存储双活）**
- 原理：只保数据面——块设备级同步/异步镜像到异地，计算层出问题靠其他机制拉起；
- 同步复制：RPO=0 但写时延受距离限制（同城内）；异步复制：RPO=秒~分钟，可跨广域；
- KVM 生态：DRBD（内核级，最常见）、Ceph rbd-mirror、LINSTOR；
- 定位：灾备三要素里专管"数据不丢"，与热迁移/HA（管"计算恢复"）组合使用。

**（6）快照/备份（Snapshot / Backup）**
- 原理：某时刻状态的只读副本。qcow2 内部快照（qemu-img snapshot）、外部快照（blockcommit/blockpull 链）、全量+增量备份；
- 新一代能力：基于迁移位图的**增量备份**——QEMU dirty bitmap 做 CBT（changed block tracking）只备变化的块。源码分析中的 `BLOCK_DIRTY_BITMAPS` cookie 字段即为此服务；
- RPO = 备份间隔（小时~天）；RTO = 分钟~小时；
- 定位：防误删/勒索/逻辑错误——热迁移和 HA 都防不了"数据本身错了"的场景，这是备份不可替代的原因。

**（7）CDP 持续数据保护**
- 原理：备份的极致化——持续记录每个写 I/O 日志，可恢复到**任意时间点**（秒级 RPO）；
- 代价：写放大、日志存储大；商业方案为主（Veeam CDP、阿里云连续备份）。

**（8）CRIU 检查点恢复（进程/容器级）**
- 原理：把运行中进程树（不冻结整台 VM，而是容器内的进程组）的全部状态 dump 到磁盘镜像，异地 restore；
- 定位：热迁移的"轻量亲戚"——不停 VM 只停进程组，容器场景的准热迁移；也是 Firecracker 快照的底层思想。

### 9.3 完整对比表

| 机制 | RPO | RTO | 内存态 | 源端要求 | 网络要求 | 成本 | KVM 生态 |
|---|---|---|---|---|---|---|---|
| **热迁移 pre-copy** | 0 | 毫秒~秒 | **保留** | 活着 | 高（≈实际数据量） | 低 | virsh 原生 |
| 热迁移 post-copy | — | <100ms | 保留 | 起步需活 | 中（拉式） | 低 | QEMU 原生 |
| **冷迁移** | 0 | 分钟~小时 | 不保留 | 可关机 | 低 | 最低 | virsh 原生 |
| **HA** | 0（共享存储） | 1~5 分钟 | **不保留** | **死了才触发** | 心跳即可 | 中 | pacemaker/oVirt |
| **FT/COLO** | 0 | **≈0（无感）** | **保留** | 双机在线 | **持续、时延敏感** | 高 | QEMU COLO |
| **存储复制** | 0（同步）/秒级（异步） | 取决上层 | — | — | 持续 | 中 | DRBD/Ceph |
| **快照/备份** | 小时~天 | 分钟~小时 | 不保留 | — | 低峰即可 | 低 | qemu-img/dirty bitmap |
| CDP | 秒级 | 分钟 | 不保留 | — | 持续 | 高 | 商业为主 |
| **CRIU** | 0 | 秒级 | 保留（进程级） | 活着 | 中 | 低 | Podman 原生 |

### 9.4 三条核心结论

1. **机制之间是组合而非竞争**：生产容灾架构是分层拼装——"数据面靠存储复制/备份兜底，计划内计算搬运用热迁移，计划外靠 HA，极致要求上 FT/COLO"。每个机制只在它那层最优。

2. **内存态是否保留是分水岭**：热迁移/FT/CRIU（保留，用户无感）vs HA/备份/冷迁移（不保留，进程重启连接断）。这条线决定了各机制的适用场景边界。

3. **热迁移协议是"基座技术"**：COLO 建立在热迁移之上、增量备份的 dirty bitmap 与迁移脏页追踪同源、postcopy 与 FT 的拉式同步思想相通——**本次调研深入的热迁移机制，是其他多个灾备机制的公共底座**。这一点把整个调研的价值再拔高一层。

## 10. 市场产品实践：热迁移的产业佐证

### 10.1 公有云：热迁移是基础设施的"隐形日常"

| 厂商 | 产品/能力 | 实际用途 |
|---|---|---|
| **AWS** | EC2 Live Migration | 宿主机安全补丁/固件/Nitro 卡升级时迁走用户实例**不重启**（仅 1~2 秒网络抖动），官方 SLA 不算停机 |
| **Google Cloud** | Live Migration（"透明维护"卖点） | 每年公开维护数千宿主机而不触发用户告警 |
| **Microsoft Azure** | Memory Preserving Maintenance | 大型维护活动（约 90%）用热迁移完成，仅少量需重启走通知流程 |
| **阿里云** | ECS 热迁移 | CPU 微码漏洞修复（幽灵/Meltdown 补丁）时热迁用户 ECS 避免重启 |
| **腾讯云** | CVM 热迁移 | 宿主机下线、碎片整理、机型换代 |

- **共同点**：迁移由**平台方为维护自己的硬件**发起，用户无感，规模是每天数以万计次；
- **洞察**：云厂商卖的不是"迁移功能"，而是**"维护对用户不可见"的 SLA 承诺**——热迁移把硬件维护从"客户事件"变成"内部操作"。

### 10.2 虚拟化/私有云平台：管理员调度工具

| 产品 | 能力 | 典型场景 |
|---|---|---|
| **VMware vSphere** | **vMotion**（行业标杆，KVM 热迁移设计参照之一）+ Storage vMotion | **DRS 全自动调度**：ESXi 过载时自动把 VM vMotion 到空闲主机；维护模式一键排空整台主机 |
| **Proxmox VE** | 内置 KVM 热迁移 + 存储迁移 | 中小企业自建云标配 |
| **OpenStack** | nova live-migration | 计算节点"掏空再升级"标准流程 |
| **华为 FusionCompute 等国产平台** | 热迁移 + 维护模式 | 信创服务器分批换代业务不中断 |

**vMotion 两个可借鉴形态**（支撑产品化路线，会议议题 8）：

1. **Storage vMotion**：VM 不动磁盘搬家（KVM 对应 `virsh blockcopy`）——存储扩容/换阵列利器；
2. **DRS 自动调度**：迁移发起方从人变成调度算法——热迁移成熟的标志是被编排进调度系统。

### 10.3 容器/新形态平台：迁移思想的延伸

| 产品 | 做法 |
|---|---|
| **KubeVirt** | 直接复用 KVM 热迁移（`virtctl migrate`），云原生平台上 VM Pod 在 K8s 节点间漂移——KVM 热迁移嵌入 K8s 生态的主流路径 |
| **CRIU + Podman/Docker** | 容器检查点/恢复（同族技术）：冻结成磁盘镜像异地恢复，用于秒级扩容、Serverless 冷启动优化 |
| **AWS Firecracker MicroVM** | Lambda/Fargate 快照启动：迁移式状态序列化用于 ms 级冷启动——"迁移到一个还没出生的目标端" |

### 10.4 从市场产品反推的补充场景

1. **安全补丁"无感修复"**（AWS/阿里云）：CPU 漏洞微码修复必须重启宿主机，整机重启前热迁走所有 VM——**安全合规驱动**的迁移，与"安全热迁移"调研主题直接呼应：迁移通道不加密，这个高频场景就是泄密通道；
2. **集群自动平衡**（DRS 模式）：热迁移从"操作"变成"策略执行单元"；
3. **整机排空/碎片整理**（腾讯云/维护模式）：宿主机长期运行碎片化，排空重启再填回恢复性能；
4. **存储与计算分离迁移**：磁盘和 VM 各自独立迁移，组合出"换存储不动 VM""换 VM 不动存储"两种模式；
5. **Serverless/弹性伸缩加速**（CRIU/Firecracker）：迁移思想的跨界应用。

# 第四篇 产品化设计（会议议题 8）

## 11. 热迁移产品化：迁移前 / 迁移中 / 迁移后功能设计

> 综合市面产品（vSphere、OpenStack、阿里云/腾讯云）热迁移模块的功能盘点，结合本实验踩坑经验，形成三阶段功能设计。

### 11.1 迁移前：预检与决策

| 功能 | 做法 | 对应实验教训 |
|---|---|---|
| **兼容性预检（L1 静态）** | 迁移前自动比对：CPU Model 兼容（cpu-compare）、QEMU/libvirt 版本、存储空间、网络拓扑、设备清单（光驱/直通设备）——纯只读，秒级完成 | 问题 1（光驱）、3（host-passthrough）、4~6（链路）——8 个问题中 6 个可被 L1 挡住 |
| **迁移演练（L2 shadow）** | 影子迁移：真实迁移到目标端但**不执行 Confirm 切换**，验证通过后丢弃——验证"能不能迁"而不承担切换风险 | libvirt `--print-xml` 是其雏形 |
| **目标宿主机推荐** | 调度器打分：资源余量、预估迁移时长、反亲和性、历史成功率；**预检结论纳入打分**（CPU 不兼容一票否决，而非迁过去才发现） | 问题 3 的教训：推荐必须先过预检 |
| **带宽/时长/收敛预估** | 按历史脏页率预估迁移时长与成功概率；脏页率 > 带宽的 VM 提前告警"可能不收敛" | 高脏页率场景（8.3 节） |

### 11.2 迁移中：可观测与控制

| 功能 | 做法 | 说明 |
|---|---|---|
| **实时进度** | domjobinfo 产品化：进度百分比、剩余数据量、**预计剩余时间**（按当前速率）、**收敛风险指示**（剩余脏页下降趋势变平 = 可能不收敛，提前告警） | 真正有用的进度条不止显示"传了多少"，还要预判"能不能收敛" |
| **动态限速** | 迁移中调 `migrate-setspeed`，业务高峰自动降速/夜间提速 | |
| **暂停/恢复/取消** | 任务级控制；v3 事务保证"取消"永远是安全操作（失败必回滚，无半迁移状态） | 事务性是产品敢提供"取消"按钮的底气 |
| **关键事件流** | 阶段事件推送（"进入 stop-and-copy""已完成切换"）+ 异常告警 | 对应六阶段 |
| **任务队列与并发控制** | 全局限速 + 并发上限，防止同时 50 个迁移把网络打爆 | 运维真实事故的常见来源 |

### 11.3 迁移后：验证与闭环

| 功能 | 做法 | 对应实验 |
|---|---|---|
| **迁移结果验证** | 自动对比迁移前后关键指标（IP/MAC、服务可达性、进程存活）；**健康探针内置化**——迁移前自动在 guest 内起探针（counter.log 思想）、迁移后自动收数比对，输出"业务连续性验证报告" | counter.log/SHA-256 验证方法论的直接产品化，市面上基本没有，**差异化亮点** |
| **失败自动归因诊断** | 错误码 → 原因 → 修复建议知识库 | 本实验 8 个问题的排错过程即知识库冷启动语料——别人从头积累，我们已有 |
| **源端清理** | 迁移成功后源磁盘的安全擦除选项 | 呼应主文档 5.5 信任边界 |
| **审计日志** | 谁、何时、迁了什么、走哪条通道、结果——满足合规 | |
| **断点恢复** | 基于 libvirt DstPrepareResume（:3674），网络闪断后可从断点继续 | 长距离迁移刚需 |

### 11.4 迁移目的推荐：面向用户的场景化选项

> 产品化思路：不让用户填"目标服务器 IP"，而是让用户选**迁移意图**，由平台按意图推荐目的地。

| 用户选项 | 迁移意图 | 平台推荐策略 |
|---|---|---|
| **服务器升级** | 为腾空某台宿主机做维护/换代 | 推荐**同集群资源最充裕**的候选机；可联动"维护模式一键排空"（该宿主机上所有 VM 逐台迁走） |
| **资源集中** | 省电/降本，低峰期整合 | 推荐**已承载 VM 最多且余量足够**的机器（合并填谷），夜间窗口批量执行 |
| **负载均衡** | 某宿主机过载，分散热点 | 推荐**负载最低**且满足反亲和约束的候选机；DRS 式可自动触发 |
| **集群稳定度** | 预防性迁移（硬件亚健康、故障预警） | 推荐**硬件健康度最高**的候选机；联动故障预测信号（内存 CE、SMART） |

**设计要点**：

1. **意图 → 策略 → 推荐三段式**：用户只选意图，打分策略封装在平台内，结果仍须通过 11.1 的预检一票否决——推荐与预检是串联关系，不是并联；
2. **四种意图可组合**（如"负载均衡 + 集群稳定度"），优先级由用户声明或平台默认（稳定度 > 负载 > 升级 > 集中）；
3. **推荐要透明**：给出"为什么推荐这台"（打分明细）——运维需要可解释性，黑盒推荐在故障复盘时会被质疑；
4. **迁移窗口联动**：资源集中/批量场景自动挂到低峰窗口（11.2 的动态限速配合）。

### 11.5 批量与策略层（单台之上的产品化）

- **维护模式一键排空**：选定宿主机，平台自动把所有 VM 逐台迁到推荐主机（vSphere/阿里云均有）；
- **调度策略集成**：DRS 式阈值触发自动迁移、节能整合策略；
- **批量编排**：并行度控制、依赖顺序（先迁依赖服务）；
- **灰度窗口**：只允许在配置的时间窗口内自动迁移；
- **安全策略层**：迁移通道强制加密开关（禁明文 tcp 的租户级策略）、证书管理、迁移网络隔离、目标机准入白名单——**国密通道支持是市面产品均未提供的差异化特性**（exec transport + 国密代理路线）。

### 11.6 产品化工作分解（MVP → 完整版）

| 阶段 | 内容 | 落地依据 |
|---|---|---|
| **MVP（一期）** | L1 静态预检、简单目标推荐（资源余量打分）、迁移任务封装（发起/取消/进度）、失败归因知识库 v1 | 全部基于本调研已有知识；8 个问题即知识库语料 |
| **二期** | 动态限速、批量编排与维护排空、审计日志、健康探针内置化、场景化意图推荐（11.4） | |
| **三期（差异化）** | 国密通道选项、shadow 演练（L2）、断点恢复、DRS 自动调度 | 国密为独有卖点 |

**一句话总结**：三个核心设想（预检/推荐/进度）均踩在市面产品的真实模块上；补足"失败归因""并发控制""安全策略"三个运维最痛点；差异化亮点是**健康探针内置化**（本实验验证方法论的产品化）与**国密通道**（调研成果的落地）。
