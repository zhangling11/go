## 0. 先说清楚 R1 的边界

R1 的原文只约束一件事：**提交迁移前必须通过预检，不通过不能提交**。它本身**不规定查什么**。

检查项来自三个来源，而这三处目前**互不一致**：

| 来源 | 内容 | 条目数 |
|---|---|---|
| **代码现状**（`preview.go`） | 源 VM 存在性 / 冷热模式与电源 / 同名冲突 / 目标存储 / 磁盘路径 | 5 项 |
| **界面设计**（§4 b3-b） | 兼容性 / 资源 / 磁盘容量 / 网络落位 / 路径冲突 / 带宽预估 | 6 类 |
| **官方文档要求**（本文汇总） | libvirt / QEMU / OpenStack / Hyper-V / vSphere 各自明确的硬前提 | 见正文 |

**结论：设计文档写六类，代码只覆盖其中一部分，而六类本身也不全。** 本文是把三处对齐后的完整清单。

### 0.1 为什么分三层，而不是一个平铺的长列表

全部塞进一个"预检"会让它变成"点一次等半分钟"的重操作，而用户每换一个目标节点就要重来一次。

vSphere 官方公开承认"两者都换时一次判不完"，所以它**分批判**——选主机时不校验数据存储，等选定数据存储时才确认。我们该学这个思路。

| 层 | 什么时候跑 | 性能要求 | 目的 |
|---|---|---|---|
| **L1 轻量硬过滤** | 每次点【系统推荐】 | 毫秒~百毫秒级 | 快速排除不可行节点，产出候选卡片 |
| **L2 深度预检** | 选定节点 + 存储池后，点【预检】 | 秒级可接受 | 判定"这台机器上的这块盘能不能安放、网络能不能落位" |
| **S 提交复核** | 点【提交迁移】时 | 毫秒级 | 保证预检结论与执行时刻的状态一致 |

## 1. L1 轻量硬过滤（推荐阶段执行）

这一层的结果就是**候选节点卡片**的来源；全部落空时展示「推荐失败面板」，逐节点列出淘汰原因。

| 编号 | 检查项 | 判定方式 | 依据 | 当前状态 |
|---|---|---|---|---|
| **PC-L1-01** | 目标节点在线、非维护态 | 节点状态查询 | — | 待核 |
| **PC-L1-02** | 目标节点 ≠ 源节点 | 标识比对 | — | 界面已限制（下拉置灰源节点） |
| **PC-L1-03** | CPU 型号 / 微架构兼容 | 节点注册信息中的 CPU 型号比对；细化判定见 PC-L2-06 | libvirt `formatdomain.html`：`migratable='on'` **不构成**跨主机安全迁移的依据，原文"即使 migratable='on'，除非两台主机完全相同，否则迁移仍是危险的" ✅ | ❌ **缺失** |
| **PC-L1-04** | 资源余量：目标节点剩余 vCPU/内存 ≥ VSM 规格 | 节点资源查询 | — | 待核 |
| **PC-L1-05** | 存储容量：目标池可用 ≥ 磁盘**已分配量** | `qemu-img info` 的 disk size（非 virtual size） | — | 待核（取值口径见 §2 E 组说明） |

| **PC-L1-07** | 磁盘路径无冲突 | 目标路径存在性检查 | — | 待核 |

> **这七项与界面设计 §3.3「推荐失败面板」的逐节点淘汰原因是同一套判定**。面板已设计好，此处确认的是后端能否一次跑完这七项。

## 2. L2 深度预检（选定节点 + 存储池后执行）

这是 R1 的主战场。按 A–H 分八组。

### A 组：对象与状态（缺一即无法开始）

| 编号 | 检查项 | 级别 | 依据 | 当前状态 |
|---|---|---|---|---|
| **PC-L2-A1** | 源 VSM 存在且可访问 | 阻断 | — | ✅ 已有（`preview.go`） |
| **PC-L2-A2** | 电源状态与迁移模式匹配：热迁移要求运行中；**冷迁移要求已关机** | 阻断 | libvirt 冷迁移语义 | ✅ 已有（`preview.go:99-100`，对应 RQ-1-14，判定符合） |
| **PC-L2-A3** | 目标节点无同名 VSM | 阻断 | — | ✅ 已有（`preview.go:105-108`，对应 RQ-5-12） |
| **PC-L2-A4** | **该 VSM 当前无其他进行中的任务**（迁移中 / 克隆中 / 快照中 / 重装中） | 阻断 | — | ❌ **缺失，建议补** |
| **PC-L2-A5** | 源节点上该 VSM 的 domain 状态正常（`paused` / `crashed` / `pmsuspended` 不可迁） | 阻断 | libvirt domain state 语义 ⚠️ 未抓到原文 | 待核 |

> **A4 是本组最该补的一条**：用户完全可能在任务队列里已有这条 VSM 的克隆任务，同时又发起迁移。两个任务抢同一份磁盘，后果比迁移失败严重（可能损坏磁盘）。
>
> 现有 `preview.go` 的阻断项清单里没有"该 VSM 有进行中任务"这一条。

### B 组：CPU 与机器类型（当前最大缺口）

| 编号 | 检查项 | 级别 | 依据 | 当前状态 |
|---|---|---|---|---|
| **PC-L2-B1** | 读源端 `<cpu mode>`，判定是否 `host-passthrough` | 若为 pt 且两端非同一型号 → 阻断 | 平台默认即 `host-passthrough`（`arch.go:23`）；导入时写 `<cpu mode='host-passthrough' check='none' migratable='on'/>`（`import_guest.go:394`） ✅ | ❌ **缺失** |
| **PC-L2-B2** | CPU 特性逐项比对，按特性类型分级判定 | 分级（见下） | `virsh cpu-compare`；分级规则对标 vSphere ✅ | ❌ **缺失** |
| **PC-L2-B3** | machine type 一致（`<os><type machine=...>`） | 阻断 | QEMU 官方原文："migration is only supposed to work if you use the same machine type in both source and destination" ✅ | ❌ **缺失**（对应 RQ-1-04，判"未核"） |
| **PC-L2-B4** | 目标端存在该 machine type | 阻断 | `virsh domcapabilities --machine` 两端比对 | ❌ **缺失** |

**B2 的分级规则（这是比"同型号才能迁"更细的判定逻辑）**：

| 特性类型 | 不匹配时 | 来源 |
|---|---|---|
| **用户级（user-level）特性** | **只要两端不匹配就阻断**，不管 VM 实际有没有在用 | vSphere 官方 EVC 文档 ✅ |
| **内核级（kernel-level）特性** | **仅当 VM 实际暴露了目标机缺少的特性时才阻断** | 同上 ✅ |

> 实现路径：用 `virsh cpu-compare` 拿到差异列表，再按 VM 的 `<feature policy='require/disable'>` 配置分级判定。

**为什么 B 组这么要紧**：本组缺失直接导致会议答复 §1.1 记录的现象——迁移一路跑到进度 100%，才在目标端状态恢复阶段因 `KVM_SET_CPUID2` / `KVM_SET_MSRS` 校验不过而失败。**本该在预检 3 秒内拦住的事，变成了一次完整的无效迁移。**

### C 组：版本兼容

| 编号 | 检查项 | 级别 | 依据 | 当前状态 |
|---|---|---|---|---|
| **PC-L2-C1** | QEMU 版本在 **n ↔ n+1** 范围内（同版本 + 同 machine type 则必须可迁） | 阻断 | QEMU 官方："This have to work, and if it doesn't work it is a bug"；仅承诺相邻版本兼容，经 `hw_compat_X.Y` 维护 ✅ | ❌ **缺失**（对应 RQ-1-05，判"不符合（流程性）"） |
| **PC-L2-C2** | libvirt 版本 | 警告 | 影响特性可用性（如 native TLS 需 4.4.0+，见 OpenStack 文档 ✅） | ❌ 缺失 |
| **PC-L2-C3** | **承载链路层兼容**：SSH 版本 / 加密算法策略 / 主机密钥体系 / libvirt RPC 版本 | 阻断 | Hyper-V 官方记录的先例：WS2025 默认启用 Credential Guard 后，**CredSSP 方式的实时迁移直接不可用** ✅ | ❌ **缺失** |

> **C3 为什么放进预检而不是只写在运维手册里**：
>
> 我们走 `qemu+ssh://root@host`（`execute.go:122`）。OpenSSH 升级后默认禁用某些算法（如 `ssh-rsa`）会导致连接失败，**报错指向"认证失败"，极易被误判成"密码错了"**。
>
> 这是"能不能迁"的一部分，不是运维注意事项。建议作为独立检查项，或在预检里并入 F 组的管理面可达性检查（PC-L2-F3）一并做。

### D 组：资源

| 编号 | 检查项 | 级别 | 依据 | 当前状态 |
|---|---|---|---|---|
| **PC-L2-D1** | 目标节点剩余 vCPU ≥ VSM 规格 | 阻断 | — | 待核 |
| **PC-L2-D2** | 目标节点剩余内存 ≥ VSM 规格 | 阻断 | — | 待核 |
| **PC-L2-D3** | 承接后目标节点 CPU / 内存占用不超安全线 | 警告 | 意图软排序中的"承接后整体负载"口径（R3） | ❌ 缺失 |

> D3 只做警告不做阻断：超安全线不等于不可迁，但要让用户知道迁移后目标节点会进入什么状态。

### E 组：存储

| 编号 | 检查项 | 级别 | 依据 | 当前状态 |
|---|---|---|---|---|
| **PC-L2-E1** | 目标存储池存在且属于该目标节点 | 阻断 | R8；存储池按节点加载（`/api/storage-pool/vm-targets` 需指定节点） | 待核 |
| **PC-L2-E2** | 目标池可用空间 ≥ 磁盘**已分配量** | 阻断 | `qemu-img info`（`helpers.go:157` 已在用） | 待核（取值口径见下） |
| **PC-L2-E3** | 目标磁盘路径无冲突 | 阻断 | — | ✅ 已有 |
| **PC-L2-E4** | 迁移后目标池剩余空间不低于安全水位 | 警告 | — | ❌ 缺失 |

> **E2 的取值口径是这里最容易错的地方**：
>
> `qemu-img info` 有两个尺寸字段——**virtual size（标称容量）** 与 **disk size（实际已分配量）**。两者可能差一个数量级（60 GiB 的盘可能只分配了 8 GiB）。
>
> - 拿 **virtual size** 做容量核算 → 过度保守，本来能迁的迁不了；
> - 拿 **disk size** 是对的，但**必须与 `--copy-storage-inc` 的实际传输量口径一致**。
>
> ⚠️ 而 `--copy-storage-inc` 的官方语义是"**源目标共享同一 base image 时只传差异层**"，与 `execute.go:209` 用 `qemu-img create` 新建空白盘的做法**存在语义矛盾**（详见大纲 RQ-1-10 与本章 §5 待核实项 1）。在 E-03 实验确认前，**容量核算与耗时预估一律按 `--copy-storage-all`（全盘复制）口径理解**。

### F 组：网络

| 编号 | 检查项 | 级别 | 依据 | 当前状态 |
|---|---|---|---|---|
| **PC-L2-F1** | 目标节点存在同名 + 同 CIDR 的 VPC 交换机 | 阻断 | R3a | 待核 |
| **PC-L2-F2** | 目标节点存在同名安全组 | 阻断 | R3a | ❌ 待核 |
| **PC-L2-F3** | **管理面可达**：`qemu+ssh://` 到目标节点连通 | 阻断 | `execute.go:122` 使用 `qemu+ssh://` | ❌ **缺失** |
| **PC-L2-F4** | **数据面端口可达**：源 → 目标的迁移流端口放通 | 阻断 | `--migrateuri tcp://`（`execute.go:128`），QEMU 直连 | ❌ **缺失** |
| **PC-L2-F5** | **`migrateuri` 中的 host 解析到管理网 IP，而非 `0.0.0.0` 或业务网** | 警告 | libvirt migration.html：迁移 URI 不含端口，"端口由 hypervisor 自选" ✅；**具体段值待实测**（RQ-1-07） | ❌ **缺失** |

> **F4 / F5 是当前设计里没有、但一定会咬人的两条。**
>
> 迁移流是明文 TCP 直连，不走 SSH 隧道。若端口不通，迁移要到**数据同步阶段**才失败——用户白等几分钟，而且失败原因会是一句 stderr 原文。
>
> F5 正是 Hyper-V 记录 §2.7.7 里那件"一小时能查完"的事，装进预检就变成每次迁移自动核查。

**F5 的实现方式**（可复用运维侧的核查命令）：
```bash
# 迁移中，源端看实际连接落到哪个网卡/IP
ss -tnp | grep qemu
# 看监听地址（是否 0.0.0.0）
ss -ltnp | grep qemu
```

| 编号 | 检查项 | 级别 | 依据 | 当前状态 |
|---|---|---|---|---|
| **PC-L2-G1** | 预估总耗时 `T ≈ max(T_ram, T_disk) + T_downtime` | 展示 | 会议答复 §2.2；RQ-1-09 | ❌ 缺失 |

## 3. S 层：提交前瞬时复核

这三项在点【提交迁移】的瞬间执行，**用毫秒级查询，不做深度校验**。

| 编号 | 检查项 | 级别 | 为什么必须有 | 当前状态 |
|---|---|---|---|---|
| **PC-S1** | **预检凭证校验**：预检返回的 hash 与提交时参数指纹一致 | 阻断 | 预检与提交是两个接口（`/migration/preview` 与 `/migration/migrate`），中间用户可改节点、改池、改限速。现在只能靠"别在这两个按钮之间改东西"这句口头约定 | ❌ **缺失** |
| **PC-S2** | **目标占用锁**：目标节点 + 存储池未被其他迁移占住 | 阻断 | 两个人可同时预检同一节点、都通过、都提交 | ❌ **缺失** |
| **PC-S3** | 目标节点仍在线 | 阻断 | 预检到提交之间可能刚好掉线 | ❌ 缺失 |

> **S1 / S2 属于 R1 的职责范围**，不该另立需求。它们解决的是同一个问题：**预检结论与执行时刻必须一致**。
>
> 实现成本极低：S1 是一个 hash 比对，S2 是一条数据库记录加一次查询。但收益极大——把"口头约定"变成了"系统保证"。
>
> 对照参考：Hyper-V 的做法是让 `Compare-VM` 产出一个**可持有、可修改、可回灌**的报告对象，并把报告直接喂给 `Move-VM -CompatibilityReport` 执行。我们不需要做到对象级，一个 hash 就能拿到核心收益。

## 4. 三级判定规则（比条目本身更重要）

| 级别 | 判定条件 | 界面表现 | 对提交的影响 |
|---|---|---|---|
| **阻断** | 明确不满足，**或无法判定** | 红叉 + 原因 + 【去处理】跳转 | 提交按钮锁死 |
| **警告** | 满足但接近边界；或结论不确定但可接受 | 黄叹号 + 建议动作 | 不锁死 |
| **通过** | 明确满足 | 绿勾 | — |
| **展示** | 与可行性无关，只是告知 | 灰字 | — |

### 4.1 「无法判定」必须判阻断

这是密码业务该有的默认值，也是最容易做反的一条：

- 查不到目标端主机密钥指纹 → **阻断**，不能说"应该没问题"
- 查不到目标端 machine type 列表 → **阻断**，不能说"大概支持"
- `virsh cpu-compare` 命令执行出错 → **阻断**，不能吞掉错误当通过

> **反例**：把"检查失败"当成"检查通过"，是这类预检最常见的实现 bug。用户看到一片绿，迁移却失败，从此不再相信预检。

### 4.2 阻断项必须能定位到责任对象

现在的预检报告输出的是**一行行文字**（如"目标节点不存在同名交换机 sw-caiwu"），用户看完还得自己回到别处去创建。

至少要做到：**每条阻断项标注"这是哪一端的什么问题"**——目标节点资源缺失 / 源 VM 配置问题 / 平台数据问题。这样用户才知道该去哪改。

（Hyper-V 能做到"报告项 → 责任对象 → 一键修复动作"三者打通，是因为它的所有资源都在同一个系统里。我们的交换机、安全组、存储池在别的模块，做一键修复成本高。但**标出责任归属**是低成本可做的。）

## 5. 三处必须先解决的矛盾 / 待核实项

### 5.1 待核实：`--copy-storage-inc` 的语义矛盾（影响 E2 与 G1）

`execute.go:128` 使用 `--copy-storage-inc`，但官方语义要求"源目标共享同一 base image"；而 `execute.go:209` 用 `qemu-img create` 新建空白盘。

**两处组合与官方语义相矛盾**——大概率是"新建空白盘 ⇒ 全部内容都算增量"侥幸成立，但**未经验证**。

**处置**：确认前，容量核算（E2）与耗时预估（G1）一律按 `--copy-storage-all`（全盘复制）口径理解。E-03 实验须包含"目标端预置同一 base image vs 空白盘"对照组。

### 5.2 待决策：「强制预检」与「跳过预检」自相矛盾

R1 叫**强制**预检，验收标准却写着：

> ③ 未预检时提交按钮不可用，**仅"跳过预检"开关可解锁**

**强制 + 可跳过 = 不强制。** 而且这个开关只需点一下：不需要权限、不需要理由、不留审计。在密码业务的迁移上，这等于把唯一一道拦截做成了装饰。

三个选项：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A 删掉跳过开关** | R1 名副其实 | 最干净，但真遇到"预检某项误报 + 业务紧急"时无出路 |
| **B 保留但加三道锁**（推荐） | 仅平台管理员可见 + 必须填写跳过原因 + 写入审计日志 | 参照 PVE `--force` 仅 root 可用的处理。让它**贵**，贵到只在真要命时才用 |
| **C 改名** | 不叫"强制预检"，叫"预检提示" | 改动最小，但等于承认这条需求没做到 |

> 推荐 **B**。理由：完全堵死会逼人在紧急时绕过系统去手敲 `virsh`，那比留着开关更糟——至少经过界面的操作会留痕。

### 5.3 待核实：后端是否已有"该 VSM 有进行中任务"的检查

`preview.go` 的阻断项清单里未见此项（PC-L2-A4）。需确认是"在别处已做"还是"确实没有"。

## 7. 界面呈现建议（配合 b3-b 明细列表）

### 7.1 分组展示，不摊平

预检报告按 A–H 分组折叠，默认展开**有问题的组**，通过的组收起。26 项平铺会让报告不可读。

```
预检结果  ⚠ 通过，存在 3 项警告、0 项阻断
├─ ▾ CPU 与机器类型        ✕ 1 项阻断
│     ✕ CPU 特性不兼容：目标节点缺少 monitor / hle / rtm
│       责任方：目标节点 node-02　【去处理】
├─ ▸ 对象与状态             ✓ 全部通过（5 项）
├─ ▸ 版本兼容               ✓ 全部通过（3 项）
├─ ▾ 网络                   ⚠ 1 项警告
│     ⚠ 迁移流 host 解析为 0.0.0.0，可能监听全部网卡
├─ ▾ 预估                   展示
│     磁盘复制 约 8 分 20 秒　内存同步 约 40 秒　合计 约 9 分钟
└─ ▸ 安全状态               展示
```

### 7.2 三条展示规范

1. **阻断项必须带责任方 + 【去处理】跳转**（§4.2）
2. **"无法判定"要明说**：不要显示绿勾，显示灰问号 + "无法判定，已按阻断处理"
3. **预检通过后显示凭证状态**：如"预检凭证已生成（有效期至 14:32）"，让 S1 的存在对用户可见——用户知道"预检完改东西要重检"，比在报错里才发现好
