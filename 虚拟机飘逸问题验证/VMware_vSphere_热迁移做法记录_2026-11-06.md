## 0. 一句话概括

vSphere 的迁移体系是四家里**最完整、最体系化**的，它的核心不是"怎么搬内存"，而是三件事：

1. **把"迁移"拆成三个正交维度**（换主机 / 换存储 / 两者都换），而不是一个功能
2. **把 CPU 兼容性问题从"逐 VM 打补丁"提升到"集群级统一基线"（EVC）**——这是我们对 CPU 困境最该看的答案
3. **迁移加密做成了产品级的三档策略**（Disabled / Opportunistic / Required），而不是一个开或不开的开关

---

## 1. 迁移的三个维度（最核心的框架）

vSphere 官方文档把迁移按"动了什么"分成三类，这是整个体系的骨架：

| 类型 | 动什么 | 冷迁移叫什么 | 热迁移叫什么 |
|---|---|---|---|
| **只换计算资源** | VM 跑到另一台主机，磁盘不动 | Cold Migration | **vMotion** |
| **只换存储** | VM 磁盘换到另一个数据存储，主机不变 | Cold Migration | **Storage vMotion** |
| **两者都换** | 主机 + 存储同时换 | Cold Migration | **vMotion（含存储）** |

✅ 官方对冷迁移的定义：移动**已关机或已挂起**的 VM 到新主机，可选连带搬配置文件和磁盘文件；冷迁移还可以"从一个虚拟交换机迁到另一个""从一个数据中心迁到另一个"，**支持手动或定时（scheduled）**。

✅ 官方对热迁移（vMotion）的定义：移动**已开机**的 VM 到新主机，可选连带搬磁盘或文件夹到不同数据存储；"**without any interruption in its availability**"（服务不中断）。

> **这个三维框架对我们很有用**：我们目前是"只换计算资源 + 强制连带换存储"（非共享存储，恒 `--copy-storage-inc`），相当于把三类压成了一类。这本身没错（我们的存储池是节点本地的），但**在文档里应该把这件事说清楚**——不是我们做不到换存储，是我们的存储模型里"换主机必然换存储"，两者不可分割。
>
> 这个说法比"我们只支持一种"更准确，也更能说明我们的架构约束。

### 1.1 其他迁移对象（vSphere 6.0+）

✅ 官方列出的跨对象迁移：

| 迁移到 | 说明 |
|---|---|
| **另一个虚拟交换机** | 标准↔标准、标准↔分布式、分布式↔分布式；网络配置和策略随适配器一起转移 |
| **另一个数据中心** | 冷或热；目标端需在分布式交换机上有专用端口组 |
| **另一个 vCenter Server** | 需 Enhanced Linked Mode；**Advanced Cross vCenter vMotion**（7.0 U1c+）无需 Linked Mode，可跨不同 SSO 域；7.0 U3+ 支持跨 vCenter 克隆 |

✅ 官方还明确划了一条边界：**克隆/复制 VM、或在同一数据中心内移动文件夹/资源池，不算迁移。**

> 这条边界值得记：vSphere 把"迁移"定义得很严格——**必须是换了宿主机或换了存储位置**。我们文档里用"迁移"这个词时也应当守住这个定义，别把"同一节点内换存储池"也叫迁移，否则概念会乱。

## 2. vMotion 到底搬了什么

⚠️ 官方概览页只说"moves a powered on VM to a new host"，**没有逐项列出搬哪些状态**。以下是通用理解，**本次未抓到原文，引用前需核实**：

| 搬 | 不搬 |
|---|---|
| 内存内容（含脏页迭代） | 磁盘内容（除非同时用 Storage vMotion） |
| CPU 状态、寄存器、MSR | 宿主机页缓存 |
| 设备状态、virtio/虚拟设备队列 | |
| 网络连接状态（借助端口组配置随迁） | |

> **注意**：这一节我标了 ⚠️。如果要写进正式报告，必须回原文核实——vSphere 文档在这块写得比较散，不像 libvirt 有集中的 "what is migrated" 章节。

## 3. EVC：本节是全篇最有价值的部分

### 3.1 EVC 是什么

✅ 官方定义：EVC（Enhanced vMotion Compatibility）确保集群内**所有主机向虚拟机呈现相同的 CPU 特性集，即使各主机的实际 CPU 不同**。目的就是避免因 CPU 不兼容导致的 vMotion 失败。

### 3.2 为什么需要它（官方给的理由）

✅ 关键论述：

- vMotion 会传输运行中（或已挂起）VM 的状态，**所以目标 CPU 必须提供 VM 之前一直在用的那些指令**；
- 主频、缓存大小、核心数量可以不同，**但 CPU 必须来自同一厂商类别（Intel 或 AMD）**；
- 一台 VM 的 CPU 特性集在**开机时**确定，取决于：宿主机 CPU 家族/型号、BIOS 设置、ESXi 版本、VM 的兼容性设置、Guest OS。

> **最后这条极重要**：**CPU 特性集是在开机时固定下来的。** 这解释了为什么我们平台的迁移失败发生在"进度 100% 之后的状态恢复阶段"——传输没问题，是目标机没有源机当年开机时呈现给 Guest 的那批特性（`monitor`、`hle`、`rtm`）。
>
> 这跟会议答复 §1.1 的现象完全吻合。**vSphere 官方文档给了这个现象一个体系化的解释，可以直接引用到调研报告里。**

### 3.3 基线怎么工作

✅ 核心机制：

- **EVC 在集群层面工作**，不是在每台 VM 上打补丁；
- EVC 模式（mode）定义一个**基线处理器特性集**——相当于把某个**（通常是更老的）处理器代际**的特性集，呈现给所有 VM；
- 于是**新指令即使物理硬件支持，也干脆不暴露**；
- 实际暴露了哪些特性，可以用 **CPUID 特性标志**查看。

✅ 官方明确否定另一种做法：

> 用**逐 VM 的自定义 CPU 兼容性掩码**（custom CPU compatibility masks）来处理，"**is not recommended**"（不推荐），应当用 EVC。

### 3.4 集群级约束

✅ 关键约束：

- 配了 EVC 模式的集群，**集群内每一台主机、以及之后新加入的每一台主机，都必须满足 EVC 要求**（即其 CPU 至少支持基线特性）；
- EVC 与 DRS、HA **完全兼容**；
- **可以对已有集群开启**，也可以**后续修改模式**。

### 3.5 无 EVC 时会发生什么（这条最有实操价值）

✅ 官方给出了极为精确的判定规则：

| 特性类型 | 不匹配时的后果 |
|---|---|
| **用户级（user-level）特性** | **只要两端不匹配就阻止迁移，不管 VM 实际有没有在用这些特性** |
| **内核级（kernel-level）特性** | **只有当 VM 实际暴露了目标机缺少的特性时才阻止迁移** |

✅ 官方举的实例：集群里混有不同代际的 AMD CPU（有的支持 3DNow!、有的不支持），需要 EVC 模式或 CPU 掩码来隐藏这些指令。

> **这两条规则可以直接迁移到我们的设计方案里**，而且是**比我们现在的思路更细的判定逻辑**：
>
> 我们现在的困境是"host-passthrough 模式下，只要 CPU 型号不同就不敢迁"。vSphere 的做法是**分级判定**：
> - 对"一定会暴露给 VM 的"特性 → 严格比对；
> - 对"可能不暴露的"特性 → 看 VM 实际配置。
>
> 这相当于给"能不能迁"提供了一个**可计算的判定规则**，而不是"同型号才能迁"这种粗放结论。我们做预检时完全可以照这个逻辑实现：用 `virsh cpu-compare` 拿到差异列表，再按"该特性是否 require / 是否 disable"分级判定。

### 3.6 EVC 模式与 VM 的关系

✅ 官方说明：

- EVC 模式对应处理器家族/代际，每种模式呈现该代际的特性集作为基线；
- **VM 的 EVC 模式决定它能在哪些主机上迁移和开机**；
- **VM 的 EVC 模式与集群配置的模式是独立的**（可以不一致）。

> 最后这条意味着 EVC 有**两层**：集群策略层（该集群的主机必须满足什么）和 VM 属性层（这台 VM 要求什么）。这比 Hyper-V 的"逐 VM 兼容开关"更完整，也比我们目前的"全局一种模式"灵活。

## 4. 迁移前兼容性检查

### 4.1 在哪里

✅ 在 **Migrate Virtual Machine 向导**中。选定目标主机或集群后，向导**底部有一个"兼容性面板"（Compatibility panel）**，显示该目标是否匹配 VM 配置。通过时显示 "**Compatibility checks succeeded**"。

> **这条对我们的界面设计直接有参考**：vSphere 把兼容性结果显示在**向导底部常驻**，用户每换一个目标就立刻看到结论。
>
> 我们现在的设计是"点【预检】→ 出 B3 报告区"。相比之下 vSphere 是**边选边判**。差别在于：
> - vSphere 的检查是**轻量的即时判定**（能否迁），适合频繁切换目标；
> - 我们的预检是**重量级的深度校验**（六类检查 + 容量核算），不适合每次切换都跑。
>
> **结论：不必照抄"边选边判"，但可以考虑在选节点时做一次轻量预判**——至少在候选卡上直接标红"不可迁移"，避免用户选了才发现要重来。这和我们 B2 候选卡的硬过滤是同一思路，方向已经对了。

### 4.2 检查什么

✅ 官方列出：

| 场景 | 检查范围 |
|---|---|
| 只换计算资源 | 源/目标主机、目标资源池、数据存储、网络 |
| 只换存储 | 同上，**去掉网络** |
| 两者都换 | 前期检查更少——比如选了目标主机时**不校验该主机的数据存储**，等选定数据存储时才确认；目标是集群时，按 **DRS 的主机推荐**来校验 |

✅ 另外两条硬性检查：

- **源和目标的宿主机都必须启用 vMotion**；
- **虚拟硬件兼容性**——例如使用 Enhanced VMXNET 网卡的 VM，不能迁到不支持它的 ESXi 主机。

> **"两者都换时前期检查更少"这条值得注意**：vSphere 承认这种场景没法一次判完，所以**分批检查**。这和我们"先选节点 → 再选池 → 再预检"的三段式是同一个问题的不同解法，我们的做法（明确分成三步，每步只判当前能判的）实际上**更清晰**。

### 4.3 检查结果怎么呈现

✅ 官方说明：

- 面板会同时显示**警告（warnings）和错误（errors）**；
- **警告不阻止迁移**——通常可以继续；
- **错误会阻止迁移**——如果没有无错的目标可选，点"下一步"只会重新显示错误，无法继续。

> **这和我们的阻断/警告分级完全一致**（b3-a 的绿/黄/红三态）。这条可以作为"我们的分级设计符合业界通行做法"的佐证写进报告。

## 5. 迁移加密：产品级三档策略

这是 vSphere 比 Hyper-V 明显更强的一块，也是我们安全章整改最好的参照。

### 5.1 保护什么

✅ 官方定义：加密 vMotion 保护"用 vSphere vMotion 传输的数据的**机密性、完整性和真实性**"，**对未加密 VM 和已加密 VM 都适用**，包括跨 vCenter 实例。

### 5.2 三档模式

✅ 对**未加密的 VM**，有三个模式：

| 模式 | 行为 |
|---|---|
| **Disabled** | 不加密 |
| **Opportunistic**（**默认**） | 源和目标宿主都支持加密时就加密（ESXi 6.5+） |
| **Required** | 只允许加密的 vMotion；任一端不支持就**迁移失败** |

### 5.3 与 VM 加密的关系

✅ 官方规则：

- **已加密的 VM 永远走加密 vMotion，无法关闭**；
- 加密磁盘**在任何情况下都加密传输**；未加密磁盘只有在"两端都启用了加密 vMotion"时才加密（**同一主机内的数据存储迁移仍不加密**）；
- 把一台 VM 加密时，会**记录当时的 vMotion 设置**；之后即使解密，该设置仍保持 Required，直到手动修改。

### 5.4 性能

⚠️ **官方该页明确说明不讨论加密 vMotion 的性能影响**。要引用"加密慢多少"必须自测。

> 这一点很重要：即便是 vSphere 这么成熟的产品，**官方文档也不给加密的性能代价数据**。所以我们做 TLS 整改时，"慢多少"必须自己测，不能指望找到现成数字。这条应写进 E-03 实验的必要性论证里。

## 6. 其他能力

| 能力 | 说明 | 核实 |
|---|---|---|
| **并发迁移限制** | vCenter 对**每台主机、每个网络、每个数据存储**的并发迁移和置备操作数都有上限 | ✅ |
| **vMotion 流量隔离** | 使用 **vMotion TCP/IP 栈**承载 vMotion 流量；冷迁移/克隆/快照使用置备（provisioning）栈 | ✅ |
| **DRS 联动** | 目标是集群时，向导按 DRS 主机推荐校验 | ✅ |
| **定时/计划迁移** | 冷迁移支持手动或**定时（scheduled）** | ✅ |
| **超大磁盘** | 带 >2 TB 磁盘的 VM 迁移，源和目标 ESXi 必须 6.0+ | ✅ |
| **DPU 主机间迁移** | vSphere 8.0 Distributed Services Engine 支持在带 DPU 的服务器间迁移 VM | ✅ |

> **并发限制的一个细节值得抄**：vSphere 的限制是**按主机、按网络、按数据存储三个维度分别算**，而不是一个全局数字。这比 Hyper-V 的"全局默认 2"精细得多——因为瓶颈可能在不同地方（网线满了 vs 存储 IOPS 满了）。
>
> 我们现在并发为 1，暂时用不上；但将来做批量迁移时，**这个三维度模型是现成的设计参照**。

## 7. 四家对比总表

| 维度 | vSphere | Hyper-V | Nova | 我们 |
|---|---|---|---|---|
| 迁移维度拆分 | **三维（主机/存储/两者）** | 两维（仅 VM / VM+存储） | 两维（默认/块迁移） | 压缩为一维 |
| CPU 兼容解法 | **集群级 EVC 基线 + VM 级 EVC 模式（两层）** | 逐 VM 兼容开关 | 调度器 filter | 无 |
| 兼容性检查时机 | **向导内边选边判（轻量）** | 独立的 `Compare-VM`（重量） | 调度器 filter | 手动点预检（重量） |
| 检查结果分级 | **警告/错误（警告不阻断）** | 不兼容项列表 | NoValidHost | 绿/黄/红三态 |
| 迁移加密 | **三档策略（默认 Opportunistic）** | ❌ 明文，靠网络隔离 | 原生 TLS（推荐）/ tunnelled | ❌ 明文 |
| 加密粒度 | 可按 VM/集群策略控制 | 无 | 全局配置 | 无 |
| 加密性能数据 | **官方不给** | 官方不给 | 官方不给 | — |
| 流量隔离 | 独立 vMotion TCP/IP 栈 | 建议隔离网络 | 建议独立网络 | 未文档化 |
| 并发限制 | **按主机/网络/存储三维度** | 全局默认 2 | 配置项 | 单任务 |
| HA 联动 | DRS + HA 完整 | 故障转移集群 | 无（需外部） | 无（范围外） |

## 8. 该抄的三件事 / 不抄的两件事

### 该抄

1. **迁移的"三维拆分"作为文档框架**（§1）。我们虽然压缩成了一维，但**在调研报告里应当用这个框架说明"为什么我们只有一种"**——是因为存储模型决定了主机与存储不可分，而不是功能缺失。这比含糊带过专业得多。

2. **EVC 的分级判定规则**（§3.5）。"用户级特性严格比对 / 内核级特性看 VM 实际配置"——这是把"同型号才能迁"的粗放结论，换成**可计算的判定规则**。我们预检完全可以按这个逻辑用 `virsh cpu-compare` 实现。

3. **加密的三档策略设计**（§5.2）。不是"开/关"，而是 **Disabled / Opportunistic / Required** 三档，且**默认 Opportunistic**（能加密就加密，不能就降级继续）。这个设计对我们的启示是：**TLS 整改可以分步走**——先做 Opportunistic（节点都支持就加密，不支持的降级并告警），不必一步到位强制 Required。这样改造风险和对现网的冲击都小得多。

### 不抄

1. **集群级 EVC 基线本身**（§3.3）。EVC 要求"集群内所有主机、以及后续新增主机都必须满足基线"，这需要集群管理器这个实体存在。我们**没有集群管理实体**，硬做 EVC 等于先造一个集群管理器——成本远超收益。我们该抄的是它的**判定规则**，不是它的**实现形态**。

2. **向导式的边选边判**（§4.1）。vSphere 的检查是轻量的即时判定，我们的预检是六类深度校验，性质不同。我们保持"手动预检 + 候选卡硬过滤"的组合更合适。**但可以在候选卡上直接标红不可迁移**，这是低成本改进。

| **EVC 集群基线** | 无 | **明确不做**，理由写进范围外（无集群管理实体） | — | 无 |
